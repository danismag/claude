## 1. Какую задачу решают инструменты

У кластера Kubernetes нет экрана, поэтому всё, что вы о нём узнаёте, приходит через программы. От выбора программы зависит скорость разбора проблемы, поэтому сначала посмотрим, какие инструменты есть в курсе и чем они различаются.

### Два пути к кластеру

**API-сервер** (API server, `kube-apiserver`) — единственная точка входа в кластер: через него проходят все запросы на чтение и изменение объектов (01-1). Большинство инструментов говорят с ним по HTTPS, и этот путь удобен, но работает, только пока жив control plane.

Второй путь — зайти на узел и спросить его служб напрямую. На узле работают **kubelet** (агент, который запускает контейнеры пода) и containerd (среда выполнения контейнеров, 00-1, 01-2). Они не зависят от API-сервера, поэтому при аварии control plane узловые инструменты остаются единственным источником правды.

### Инструменты курса

Таблица ниже сводит инструменты по пути, которым они ходят к кластеру. Карточка инструмента стоит в разделах 2–4, там, где инструмент впервые появляется в курсе; jq — вспомогательный и карточки не имеет.

| Инструмент | Путь | Для чего | Карточка |
|---|---|---|---|
| kubectl | API-сервер | основной клиент: читать, менять, отлаживать | §2 |
| kubectx, kubens | kubeconfig | быстро менять кластер и namespace | §3 |
| krew | GitHub, kubectl | устанавливать плагины kubectl | §3 |
| kind | Docker | создавать и удалять кластер стенда | §3 |
| k9s | API-сервер | терминальный интерфейс поверх kubectl | §4 |
| stern | API-сервер | хвост логов многих подов сразу | §4 |
| crictl | узел | контейнеры и логи на узле мимо API | §4 |
| jq | вывод других команд | выбирать поля из JSON | §1 |

### Фильтр JSON: jq

**jq** (JSON processor) — консольный фильтр: читает JSON со стандартного ввода и печатает выбранные поля. Вспомогательный инструмент не имеет отдельной карточки, но он нужен с 01-1: курс разбирает им ответы API и etcd, когда `-o jsonpath` не хватает. Установите его на хост: это один небольшой пакет, настройки он не меняет, откат — `sudo apt-get remove jq`.

```bash
sudo apt-get install -y jq        # Ubuntu
sudo pacman -S jq                 # Manjaro
jq --version
echo '{"a":1,"b":[2,3]}' | jq -c '.b'
```

Первая команда ставит jq в Ubuntu, вторая — в Manjaro. Третья печатает версию, а четвёртая берёт поле `b` и печатает его одной строкой (`-c` — компактный вывод).

Результат (версия зависит от дистрибутива):

```
jq-1.7.1
[2,3]
```

Разбор: строка `jq-1.7.1` подтверждает установку; курс использует только базовые возможности (`.поле`, `-c`, `-r`, `length`), которые есть во всех версиях 1.6 и новее. Строка `[2,3]` показывает, что jq разобрал JSON и выбрал массив.

### Инструменты, которые придут позже

Четыре инструмента получат карточки в тех частях, где они впервые нужны в лабораторных работах:

## 2. Как устроен kubectl

kubectl — тонкий клиент: он берёт адрес и ключи из файла, превращает вашу команду в HTTP-запрос и печатает ответ. Чтобы им управлять уверенно, нужно понимать, откуда он берёт кластер и какой запрос отправляет.

### kubeconfig и контекст

**kubeconfig** — YAML-файл с тремя списками: кластеры (адрес API-сервера и сертификат центра), пользователи (чем вы доказываете, кто вы) и контексты. **Контекст** (context) — именованная связка «кластер + пользователь + namespace по умолчанию», и kubectl работает с тем контекстом, который записан в поле `current-context`.

```
kubeconfig (~/.kube/config)
 ├─ clusters:  kind-lab ── адрес API-сервера + сертификат центра
 ├─ users:     kind-lab ── клиентский сертификат и ключ
 └─ contexts:  kind-lab ── (cluster=kind-lab, user=kind-lab, namespace=…)
current-context: kind-lab   ◄── отсюда kubectl берёт «где я»
```

Схема 2. Три списка kubeconfig и указатель на текущий контекст. Строка `namespace` в контексте необязательна.

Файл ищется по порядку: флаг `--kubeconfig`, переменная `KUBECONFIG`, затем `~/.kube/config`. В переменной можно перечислить несколько файлов через двоеточие, и kubectl склеит их: `KUBECONFIG=~/.kube/prod:~/.kube/stage`. Флаг `--context` выбирает контекст на одну команду, не меняя файл.

Контекст — главная защита от ошибки «удалил не в том кластере». Правило такое: контекст всегда виден в приглашении shell (например, через kube-ps1), а рабочий кластер лежит в отдельном kubeconfig и подключается явно.

### Из команды в запрос

**Discovery** (обнаружение) — запрос к API-серверу за списком доступных типов объектов и их путей. kubectl делает его, чтобы узнать, что слово `pods` живёт по адресу `/api/v1`, а `deployments` — по адресу `/apis/apps/v1`. Ответ он кэширует на диске в `~/.kube/cache`, поэтому повторные команды быстрее.

```
kubectl get pods -n orders
  │ 1. прочитать kubeconfig → адрес, сертификат
  │ 2. discovery: pods → группа core, версия v1 (кэш ~/.kube/cache)
  │ 3. GET https://<apiserver>/api/v1/namespaces/orders/pods
  │       заголовок Accept: …as=Table…
  ▼
API-сервер: аутентификация → авторизация (RBAC) → ответ в виде таблицы
  │ 4. kubectl печатает готовые колонки
  ▼
экран
```

Схема 3. Путь одной команды `get`. Колонки таблицы формирует сервер, а не kubectl.

Путь запроса строится по правилу `/apis/<группа>/<версия>/namespaces/<ns>/<ресурс>/<имя>`, а для старейших типов (под, Service, узел) группа пуста, и путь начинается с `/api/v1`. Этот же адрес вы будете вызывать через `curl` в 01-1.

### Свои настройки: kuberc и вывод KYAML

Личные настройки kubectl с версии 1.34 хранят отдельно от kubeconfig, в файле **kuberc** (kubectl preferences). Это YAML-файл `~/.kube/kuberc` с алиасами команд и значениями флагов по умолчанию, а адресов кластеров и ключей в нём нет. Другой путь задают переменной `KUBERC` или флагом `--kuberc`, а значение `KUBERC=off` временно отключает файл.

```
~/.kube/config  ── где и кто: кластеры, пользователи, контексты (его дописывают kind и облака)
~/.kube/kuberc  ── как: алиасы и флаги по умолчанию (только ваши привычки)
```

Схема 4. Два файла kubectl. Смотрите на правую часть: kubeconfig отвечает за доступ, kuberc — за поведение команд.

Пример ниже включает вопрос перед каждым удалением и добавляет команду `kubectl getn`.

```yaml
apiVersion: kubectl.config.k8s.io/v1beta1
kind: Preference
defaults:
- command: delete          # значения по умолчанию для kubectl delete
  options:
  - name: interactive      # спрашивать подтверждение перед удалением
    default: "true"
aliases:
- name: getn               # новая команда kubectl getn
  command: get
  options:
  - name: output
    default: name          # вывод только тип/имя
```

Разбор:

1. `defaults` — флаг `--interactive=true` для каждой `kubectl delete`; явный флаг в командной строке сильнее файла.
2. `aliases` — команда `kubectl getn` работает как `kubectl get -o name`; имя алиаса не может совпадать со встроенной командой.
3. `v1beta1` — kuberc в стадии beta с 1.34 и включён по умолчанию; выключить механизм целиком можно переменной `KUBECTL_KUBERC=false`.

С 1.35 в kuberc есть поле `credentialPluginPolicy`, которое ограничивает, какие программы-плагины аутентификации вправе запускать kubectl (06-1). В 1.36 настройки можно менять и командой `kubectl kuberc set`, не открывая файл.

**KYAML** — строгое подмножество YAML, в котором строковые значения стоят в кавычках, а вложенность задают скобки `{}` и `[]`, а не отступы. Такой вывод не ломается от сдвига отступа, и значение `NO` не превращается в `false`. kubectl печатает его по флагу `-o kyaml`. В 1.34 формат был alpha, с 1.35 он beta и включён по умолчанию, а в 1.37 стал stable. Начало вывода `kubectl get pod NAME -o kyaml` одинаково для любого пода:

```
---
{
  apiVersion: "v1",
  kind: "Pod",
  …
```

Что в выводе: строка `---` открывает документ, фигурная скобка — объект, ключи идут без кавычек, а строковые значения — в кавычках.

### Карточка инструмента: kubectl

**Назначение:** kubectl — командная строка для работы с API Kubernetes. Через неё читают объекты, применяют манифесты, смотрят логи, заходят в поды и пробрасывают порты. В курсе это главный инструмент: примерно каждая вторая команда — kubectl.

**Как работает:** kubectl загружает kubeconfig, отправляет запрос REST-клиентом и печатает ответ выбранным принтером, а расширяют его плагины — исполняемые файлы в `PATH`.

```
kubectl <команда>
  ├─ загрузка kubeconfig (флаг > $KUBECONFIG > ~/.kube/config)
  ├─ REST-клиент: HTTPS, сертификат или токен из kubeconfig
  ├─ кэш discovery: ~/.kube/cache
  ├─ принтер: table | yaml | json | jsonpath | custom-columns | name
  └─ плагины: файлы kubectl-<имя> в PATH (kubectl <имя> …)
```

Схема 5. Устройство kubectl: вся «магия» — в сервере, а kubectl только шлёт запросы и печатает ответы.

**Откуда берёт данные:** адрес и ключи kubectl берёт из kubeconfig, а список типов объектов — из discovery. Сами объекты приходят с API-сервера, который читает их из etcd (01-1), а локально kubectl хранит только кэш discovery.

**Основные команды:** блок сводит команды, которые понадобятся в лабораторных работах, а комментарий в конце строки говорит, что она делает.

```bash
kubectl config get-contexts                    # список контекстов; звёздочка — текущий
kubectl config use-context kind-lab            # переключить контекст
kubectl config set-context --current --namespace=orders   # namespace по умолчанию
kubectl auth whoami                            # кем кластер считает меня
kubectl auth can-i delete pods -n orders       # разрешено ли мне это действие
kubectl get pods -n orders -o wide             # список с узлом и IP пода
kubectl get pods -A --field-selector=status.phase!=Running   # отбор на стороне сервера
kubectl get pod NAME -o jsonpath='{.status.podIP}'           # одно поле объекта
kubectl get pod NAME -o kyaml                  # весь объект в строгом YAML (KYAML)
kubectl explain deployment.spec.strategy       # описание поля из схемы кластера
kubectl api-resources                          # типы объектов и их короткие имена
kubectl diff -f app.yaml                       # что изменит apply, без записи
kubectl apply -f app.yaml --dry-run=server     # проверка на сервере без записи
kubectl events -n orders --for pod/postgres-0  # события одного объекта
kubectl logs deploy/orders-api --tail=20       # лог одного пода из Deployment
kubectl exec -it pod/NAME -- sh                # shell в контейнере
kubectl debug -it pod/NAME --image=busybox:1.37 --target=api   # временный контейнер
kubectl port-forward svc/orders-api 9000:80    # локальный порт 9000 → под за Service
kubectl get deploy orders-api -v=8             # показать HTTP-запросы kubectl
```

В блоке три группы команд. Первые пять выбирают кластер и проверяют права, а следующие восемь читают объекты и пробуют запись. Последние шесть показывают события и логи, открывают доступ к поду и отладку. Подробно каждую группу разбирают разделы 3–5 и лабораторные работы.

**Команды для скриптов:** в скриптах опираются на стабильный вывод и коды возврата, а не на красивые таблицы.

- `-o name` — одно имя на строку, удобно для `xargs`.
- `-o jsonpath=…` и `-o json | jq` — точные поля.
- `--no-headers` — таблица без шапки.
- `kubectl wait --for=condition=Ready pod/X --timeout=60s` — ждать готовности с тайм-аутом.
- `kubectl diff` — код возврата 0 (разницы нет), 1 (есть разница), больше 1 (ошибка).
- `--context` и `--namespace` — явно в каждой команде, чтобы не зависеть от текущего контекста.
- `--request-timeout=10s` — не зависать на недоступном API-сервере.

**Частые ошибки:**

- Не тот контекст: команда сработала, но в другом кластере. Проверяйте `config current-context`.
- Не тот namespace: `No resources found in default namespace`. Нужен флаг `-n` или `-A`.
- `connection refused` на `127.0.0.1:<порт>`: узлы kind остановлены или kubeconfig устарел (00-1 §5).
- `Forbidden`: у вашего пользователя нет права на действие (06-1).
- Пустой результат `jsonpath`: опечатка в пути или одинарные кавычки не те; сверяйте с `-o json`.

**Установка:** в Ubuntu и Manjaro kubectl уже стоит после работы 1 из 00-1. Его версия должна отличаться от версии кластера не больше чем на одну минорную. Для удобства добавьте в `~/.bashrc` алиас и автодополнение.

```bash
alias k=kubectl
source <(kubectl completion bash)
complete -o default -F __start_kubectl k
```

Первая строка вводит короткое имя `k`, вторая подключает автодополнение команд и имён объектов, а третья переносит это автодополнение на алиас.

## 3. Как управлять: выбирать поля, менять безопасно, переключаться

Управление в kubectl — это три действия: достать нужное поле, безопасно проверить изменение и быстро сменить кластер или namespace. Для каждого есть свой приём и свой инструмент.

### Выборка полей: -o, jsonpath, custom-columns

Флаг `-o` (output) задаёт формат вывода, и формат выбирают по задаче:

- **wide** — таблица с лишними колонками: узел, IP, образ.
- **yaml** — весь объект, включая `status` и `managedFields`.
- **name** — только `тип/имя`, для конвейеров.
- **jsonpath** — одно-два поля или цикл `range`.
- **custom-columns** — своя таблица.
- **go-template** — условия и форматирование сложнее jsonpath;
- **kyaml** — весь объект в строгом YAML (§2).

**JSONPath** — язык путей, которым kubectl выбирает поля из объекта, например `{.metadata.name}`; для списка объектов путь начинают с `.items[*]`. Цикл `{range .items[*]}…{end}` обходит элементы, фильтр `?(@.поле=="значение")` отбирает нужные, а `{"\t"}` и `{"\n"}` вставляют табуляцию и перевод строки.

**custom-columns** — формат, в котором вы сами называете колонки: `ЗАГОЛОВОК:.путь`. Он удобен, когда нужна читаемая таблица из нескольких полей. Сортировку, арифметику и вложенные условия ни один из форматов не умеет: для них выводят JSON и передают в `jq`.

Часть отбора лучше отдать серверу: флаг `-l` (label selector) отбирает по меткам, а `--field-selector` — по полям вроде `status.phase` и `spec.nodeName`. Сервер отдаёт только нужные объекты, и через сеть идёт меньше данных.

### Безопасная запись: diff и dry-run

**Dry-run** (пробный запуск) — выполнение команды без сохранения результата; у kubectl два таких режима, и проверяют они разное, а `kubectl diff` добавляет к серверной проверке сравнение.

| Команда | Что проверяет | Пишет в etcd |
|---|---|---|
| `--dry-run=client` | только разбор манифеста на машине | нет |
| `--dry-run=server` | валидацию и admission на API-сервере | нет |
| `kubectl diff` | то же, затем сравнение с живым объектом | нет |

**Admission** — этап обработки запроса в API-сервере, на котором политики и вебхуки проверяют или меняют объект (01-1, 06-3). Режим `server` проходит его целиком, поэтому ловит ошибки схемы и политик, а режим `client` их пропускает.

```
apply --dry-run=client   манифест ──► разбор на вашей машине ──► печать
apply --dry-run=server   манифест ──► API-сервер: валидация → admission ──╳ запись пропущена
diff                     манифест ──► API-сервер (как server) ──► сравнение с живым ──► diff
```

Схема 6. Три пробных режима: до проверок API-сервера доходят только `server` и `diff`.

В CI для манифестов используют `--dry-run=server`, а если кластера под рукой нет — `kubeconform`, который проверяет схему локально. Перед боевым `apply` на живом кластере смотрят `kubectl diff`: он показывает, что изменится.

### Карточка инструмента: kubectx и kubens

**Назначение:** kubectx переключает контекст, а kubens — namespace по умолчанию. Обе команды короткие, имеют автодополнение и запоминают предыдущее значение. Это та же правка kubeconfig, что делают `config use-context` и `config set-context`, только быстрее.

**Как работает:** утилиты читают kubeconfig и меняют в нём одно из двух полей.

```
kubectx kind-lab   ─► kubeconfig: current-context = kind-lab
kubens orders      ─► kubeconfig: contexts[current].namespace = orders
kubectx -          ─► вернуться к предыдущему контексту (запоминается в файле состояния)
```

Схема 7. Что меняет каждая команда: правка записывается в файл kubeconfig и действует во всех терминалах.

**Откуда берёт данные:** список контекстов — из kubeconfig, а список namespace — с API-сервера, для чего нужно право на чтение namespace.

**Основные команды:**

```bash
kubectx                  # список контекстов, текущий подсвечен
kubectx kind-lab         # переключить контекст
kubectx -                # вернуться к предыдущему контексту
kubectx -c               # показать текущий контекст
kubens                   # список namespace
kubens orders            # сделать orders текущим namespace
kubens -                 # вернуться к предыдущему namespace
kubens -c                # показать текущий namespace
```

Первые четыре строки управляют контекстом, остальные — namespace, а знак `-` везде значит «предыдущее значение».

**Команды для скриптов:** в скриптах kubectx и kubens не используют, потому что они меняют общий файл kubeconfig и параллельные задачи мешают друг другу. Вместо них в каждую команду пишут `--context` и `--namespace`.

**Частые ошибки:**

- namespace сменился и в соседнем окне терминала: `kubens` правит общий файл, а не настройку окна;
- `kubectx -` перепутали с `kubectx -c` и вместо показа переключили контекст;
- список namespace пуст: не хватает права на чтение namespace.

**Установка:** в Ubuntu ставят бинарники `kubectx` и `kubens` из релиза проекта на GitHub с закреплённой версией 0.11.0. В Manjaro есть пакет `kubectx` в репозитории extra, и он ставит обе команды. Команды установки даны в работе 1, шаг 9.

### Карточка инструмента: krew

**Назначение:** krew — менеджер плагинов kubectl. **Плагин** (plugin) — программа `kubectl-<имя>` в `PATH`, которую kubectl запускает как `kubectl <имя>`. Через krew плагины из общего каталога ставят и обновляют одной командой.

**Как работает:** krew сам — плагин kubectl: он скачивает **индекс** (index) — список плагинов с адресами архивов и контрольными суммами — и раскладывает выбранные плагины в свой каталог.

```
kubectl krew install tree
   │ 1. обновить индекс (git-репозиторий krew-index на GitHub)
   │ 2. скачать архив плагина, сверить контрольную сумму
   ▼
~/.krew/store/tree/…   ◄── файлы плагина
~/.krew/bin/kubectl-tree  ◄── ссылка; каталог ~/.krew/bin должен быть в PATH
   ▼
kubectl tree deploy/orders-api
```

Схема 8. Установка плагина: плагин запускается от вашего пользователя и с вашим kubeconfig.

**Откуда берёт данные:** индекс и архивы krew берёт с GitHub. Плагин затем ходит в кластер с вашими правами, то есть это чужой код с доступом к вашему кластеру, поэтому ставьте только понятные вам плагины.

**Основные команды:**

```bash
kubectl krew update            # обновить индекс плагинов
kubectl krew search tree       # найти плагины по слову
kubectl krew info tree         # описание, версия, источник
kubectl krew install tree neat # установить плагины
kubectl krew list              # установленные плагины
kubectl krew upgrade           # обновить все плагины
kubectl krew uninstall tree    # удалить плагин
```

В курсе пригодятся два плагина: `kubectl tree` рисует дерево владельцев Deployment → ReplicaSet → Pod, а `kubectl neat` чистит YAML от служебных полей. Он убирает `status`, `managedFields` и другие поля, которые заполняет сервер.

**Команды для скриптов:** в скриптах плагины ставят из явного списка, а для воспроизводимости — командой `kubectl krew install --manifest=<файл>` с зафиксированным манифестом плагина.

**Частые ошибки:**

- `unknown command "krew"`: каталог `~/.krew/bin` не добавлен в `PATH`;
- ошибки сети при `update`: нет доступа к GitHub;
- два плагина с одним именем команды: kubectl запускает тот, что раньше в `PATH`.

**Установка:** в Ubuntu krew 0.5.0 ставит сам себя из архива релиза, а затем каталог `~/.krew/bin` добавляют в `PATH` через `~/.bashrc`. В Manjaro ставят пакет `krew` из репозитория и добавляют ту же строку `PATH`. Шаги даны в работе 1, шаг 10.

### Карточка инструмента: kind

**Назначение:** kind (Kubernetes IN Docker) создаёт кластер, где каждый узел — контейнер Docker, и стенд курса целиком построен на нём (00-1). Для обучения и проверки манифестов это самый быстрый способ получить настоящий кластер.

**Как работает:** kind запускает контейнеры из образа узла `kindest/node`, где уже есть systemd, kubelet и containerd. Затем на первом узле kubeadm создаёт control plane, а остальные узлы присоединяются к нему командой `kubeadm join`.

```
kind create cluster --name lab --config kind.yaml
   │
   ├─► docker run lab-control-plane  (kindest/node: systemd, kubelet, containerd)
   ├─► docker run lab-worker, lab-worker2, lab-worker3
   ├─► внутри control-plane: kubeadm init;  в worker: kubeadm join
   └─► дописать контекст kind-lab в ~/.kube/config
```

Схема 9. Создание кластера: в итоге появляются четыре контейнера Docker и новый контекст в kubeconfig.

**Откуда берёт данные:** kind читает файл конфигурации (на стенде `~/lab/k8s/kind.yaml`: число узлов, проброс портов, настройки containerd) и спрашивает Docker. Отдельно состояние кластера kind не хранит, потому что всё лежит в контейнерах.

**Основные команды:**

```bash
kind get clusters                       # имена кластеров kind на этой машине
kind get nodes --name lab               # контейнеры-узлы кластера lab
kind export kubeconfig --name lab       # вернуть контекст kind-lab в kubeconfig
kind export logs ./kind-logs --name lab # собрать логи всех узлов в каталог
kind delete cluster --name lab          # удалить кластер (на стенде — через lab-down.sh)
```

На стенде кластер поднимает и гасит `lab/lab-up.sh` и `lab/lab-down.sh` (00-1): они заодно управляют реестром образов. Прямой `kind delete cluster` реестр не затронет, но оставит его без кластера.

**Команды для скриптов:** `kind get clusters` печатает по имени на строку и подходит для проверки `grep -qx lab`, а повторный `kind export kubeconfig` безопасен. В CI используют `kind create cluster --wait 120s`: команда ждёт готовности control plane до 120 секунд.

**Частые ошибки:**

- `too many open files` в логах kubelet: мало `fs.inotify.max_user_instances` (00-1 §5, работа 1).
- `port is already allocated`: порт хоста занят другим контейнером (00-1 §5).
- `permission denied` на сокете Docker: пользователь не входит в группу `docker`.
- После перезагрузки машины `kubectl` отвечает `connection refused`: узлы-контейнеры остановлены, их запускает `lab-up.sh`.

**Установка:** в Ubuntu kind ставят статическим бинарником версии 0.32.0 с сайта проекта, а в Manjaro — командой `sudo pacman -S kind`. Команды уже даны в 00-1 (работа 1, шаг 3).

## 4. Как увидеть состояние

Состояние кластера видно на трёх уровнях: описание типов, HTTP-запросы клиента и состояние контейнеров на узле, и для каждого уровня есть свой инструмент.

### Типы объектов: explain и api-resources

Команда `kubectl explain` показывает описание любого поля объекта. Схему она берёт из OpenAPI вашего кластера, включая пользовательские типы (CRD, 09-1), поэтому ответ точнее документации другой версии. Поле задают путём через точку, например `deployment.spec.strategy`, а флаг `--recursive` печатает всё дерево полей.

Команда `kubectl api-resources` перечисляет все типы объектов кластера: короткие имена, группу API, признак «живёт в namespace». Фильтр `--api-group=…` ограничивает вывод одной группой, а `kubectl api-versions` показывает все группы и версии. На стенде есть типы Gateway API: `gateways` (короткое имя `gtw`), `httproutes`, `grpcroutes` и `backendtlspolicies` — все в группе `gateway.networking.k8s.io/v1`.

### Что делает kubectl на самом деле: флаг -v

**Уровень подробности** (verbosity) задают флагом `-v` от 0 до 9. На уровне 6 kubectl печатает URL и коды ответов, а на уровне 7 — ещё и заголовки запроса. На уровне 8 добавляются тела запросов и ответов, обрезанные по длине, а на уровне 9 тела печатаются целиком. Флаг нужен, чтобы понять три вещи: какой путь API использует команда, что вернул сервер и сколько это заняло.

```
-v=6   метод, URL, код ответа, время
-v=7   + заголовки запроса
-v=8   + тела запросов и ответов (обрезаны)
-v=9   + тела целиком
```

Схема 10. Уровни `-v`: для разбора обычно хватает уровней 6 и 8.

С помощью `-v` отлаживают «kubectl висит» (медленный API-сервер, зависший плагин аутентификации), ответ 403 от RBAC и строят запросы `curl` к API (01-1). Практика — работа 1, шаг 6.

### Карточка инструмента: k9s

**Назначение:** k9s — терминальный интерфейс (**TUI**, text user interface) для кластера. Он показывает списки объектов в реальном времени и позволяет смотреть логи, заходить в поды и удалять объекты клавишами.

**Как работает:** k9s ходит в API-сервер тем же путём, что и kubectl, и открывает **watch** — подписку на изменения объектов (01-1). Поэтому таблица на экране обновляется без команды `get`.

```
k9s ─► kubeconfig (контекст) ─► API-сервер: list + watch по выбранному типу
  │
  └─► экран: таблица ◄── события watch;  клавиши ─► logs, exec, describe, delete
```

Схема 11. k9s поддерживает открытое соединение и перерисовывает таблицу при каждом событии.

**Откуда берёт данные:** с API-сервера, под текущим контекстом и с вашими правами. Права k9s не расширяет, поэтому действие, на которое у вас нет права, вернёт ошибку.

**Основные команды:** первая строка запускает k9s, а остальные — клавиши и команды внутри него.

```
k9s --readonly -n orders   # запуск без права менять и удалять; namespace orders
:pods  :deploy  :ns        # перейти к списку нужного типа
/текст                     # фильтр по подстроке; Esc сбрасывает
d                          # describe выбранного объекта
l                          # логи выбранного пода
s                          # shell в контейнере
0                          # показать все namespace
?                          # справка по клавишам
:q                         # выйти (также Ctrl-C)
```

Флаг `--readonly` отключает изменяющие действия (удаление, редактирование, shell), поэтому чужой кластер открывайте именно так.

**Команды для скриптов:** их нет, потому что k9s — интерфейс для людей. В скриптах и runbook'ах пишут команды kubectl, которые можно скопировать и повторить.

**Частые ошибки:**

- `Ctrl-D` на строке удалил объект после одного подтверждения: на чужом кластере запускайте k9s с `--readonly`;
- работа не в том кластере: текущий контекст показан в шапке экрана;
- k9s не запускается без терминала, например в CI и в `docker exec` без `-t`.

**Установка:** в Ubuntu ставят пакет `.deb` из релиза проекта на GitHub, а в Manjaro — пакет из репозитория extra командой `sudo pacman -S k9s` (0.51.0). Шаги даны в работе 3, шаг 9.

### Карточка инструмента: stern

**Назначение:** stern показывает логи многих подов в одном потоке, и каждая строка помечена именем пода и контейнера своим цветом. Новые поды, например после выкатки, он подхватывает сам.

**Как работает:** stern выбирает поды по имени (регулярное выражение) или по метке, открывает поток логов каждого и смешивает их по времени.

```
stern -n orders orders-api
   │ 1. найти поды, имя которых подходит под orders-api
   │ 2. открыть поток логов для каждого контейнера (API: pods/log)
   │ 3. следить за новыми подами и подключаться к ним
   ▼
[orders-api-aaa api] строка …      [orders-api-bbb api] строка …
```

Схема 12. stern объединяет потоки логов, которые `kubectl logs` показывает по одному.

**Откуда берёт данные:** с API-сервера из **подресурса** (subresource — отдельного адреса внутри объекта) `pods/log`, так же, как `kubectl logs`, поэтому и права нужны те же.

**Основные команды:**

```bash
stern -n orders orders-api            # хвост логов подов, чьё имя содержит orders-api
stern -n orders -l app=orders-api     # то же, но по метке
stern -n orders orders-api --tail 5   # начать с пяти последних строк каждого пода
stern -n orders orders-api -c api     # только контейнер api
stern -n orders orders-api --since 10m   # логи за последние 10 минут
stern -A 'orders|postgres' --no-follow   # поды из всех namespace, без слежения
```

Все команды, кроме последней, следят за новыми строками, пока вы не нажмёте Ctrl-C.

**Команды для скриптов:** для обработки логов используют `-o raw` (только текст) или `-o json`, а слежение отключают флагом `--no-follow`. Для разовой выборки одного пода хватает `kubectl logs`.

**Частые ошибки:**

- слишком широкий шаблон имени: поток забит чужими логами;
- забыт флаг `-n`: stern ищет только в текущем namespace;
- контейнер ещё не создан: поток пуст, причину ищут в `kubectl describe`.

**Установка:** в Ubuntu бинарник из архива релиза кладут в `/usr/local/bin`, а в Manjaro ставят пакет из extra командой `sudo pacman -S stern` (1.34.0). stern ставится и как плагин krew, а шаги установки даны в работе 3, шаг 8.

### Карточка инструмента: crictl

**Назначение:** crictl — командная строка для среды выполнения контейнеров на узле. Это аналог «docker ps» для узлов с containerd: он показывает то, что реально запущено, в обход API-сервера.

**Как работает:** crictl говорит с containerd через сокет по протоколу **CRI** (Container Runtime Interface) — стандартному интерфейсу, которым kubelet управляет контейнерами (01-2). Через тот же сокет работает и kubelet.

```
crictl ps ──► unix-сокет /run/containerd/containerd.sock ──► containerd ──► контейнеры
                 ▲
kubelet ─────────┘   (тот же интерфейс CRI; поэтому crictl видит то же, что видит kubelet)
```

Схема 13. crictl и kubelet — два клиента одного сокета, поэтому crictl отвечает, даже если kubelet и API-сервер лежат.

**Откуда берёт данные:** из containerd через сокет, адрес которого берётся из файла `/etc/crictl.yaml` или флага `--runtime-endpoint`. Для доступа к сокету обычно нужны права root.

**Основные команды:** блок показывает команды для узла, а на стенде их вызывают через `docker exec lab-worker`.

```bash
crictl ps                      # запущенные контейнеры
crictl ps -a                   # и остановленные, с числом попыток (ATTEMPT)
crictl ps --name postgres      # фильтр по имени контейнера
crictl pods --name postgres-0  # песочницы (pause) подов
crictl logs ID                 # лог контейнера по идентификатору
crictl logs --tail=20 -f ID    # последние 20 строк и слежение
crictl inspect ID              # подробности контейнера в JSON: pid, mounts, cgroup
crictl exec -it ID sh          # команда внутри контейнера
crictl images                  # образы на узле
crictl stats                   # использование CPU и памяти
```

Идентификатор берут из колонки `CONTAINER` вывода `crictl ps`: crictl принимает и короткий идентификатор из таблицы (13 знаков), и любое его уникальное начало.

**Команды для скриптов:** флаг `-q` печатает только идентификаторы, а `-o json` — полный JSON. Типичная связка — подставить вывод `crictl ps -q --name postgres` в `crictl logs`.

**Частые ошибки:**

- `permission denied` на сокете: нужны права root (`sudo crictl …`).
- `connect: no such file or directory` для сокета: crictl не нашёл runtime, задайте `--runtime-endpoint`.
- Искали контейнер командой `docker ps` на узле с containerd: Docker там нет, контейнеров он не покажет.
- `crictl rm` и `crictl rmp` на живом узле: kubelet увидит пропажу и пересоздаст контейнер, но на проде так делать нельзя.

**Установка:** на хосте стенда crictl не нужен, потому что на узлах kind он уже есть. На обычном узле Ubuntu ставят пакет `cri-tools` из репозитория `pkgs.k8s.io`, того же, что и для kubectl. В Manjaro программа идёт в пакете `crictl` из репозитория extra.

## 5. Что ломается и как найти причину

Когда приложение не работает, поиск идёт в четыре шага: прочитать логи, зайти внутрь, добавить инструмент, которого нет в контейнере, и проверить сеть. Если API-сервер недоступен, всё то же делают на узле.

### Логи и exec

Команда `kubectl logs` читает лог контейнера, который kubelet хранит на узле. Форма `kubectl logs deploy/orders-api` берёт один под Deployment и печатает его имя, а форма `kubectl logs -l app=orders-api --prefix` читает все поды по метке. С меткой kubectl по умолчанию печатает по 10 последних строк каждого пода, а флаг `--prefix` добавляет в начало строки имя пода и контейнера.

Большинство задач решают три флага: `--previous` печатает лог предыдущего запуска контейнера, `--since=10m` ограничивает период, а `-f` следит за новыми строками. Если контейнер ещё не создан (`ImagePullBackOff`, `CreateContainerConfigError`), логов нет, и причину ищут в `kubectl describe` (02-1 §5).

Команда `kubectl exec -it pod/X -- sh` запускает программу внутри контейнера, но только если эта программа есть в образе. Минимальные образы (distroless) не содержат даже `sh`, а в образе orders-api на базе `python:3.12-slim` нет `ps` и `curl`. В таких случаях нужен отладочный контейнер.

### Под без shell: kubectl debug

**Ephemeral-контейнер** (ephemeral container) — временный контейнер с нужными инструментами, который добавляют в уже работающий под. Он сразу делит с подом сеть, а с флагом `--target` — и пространство PID выбранного контейнера, то есть видит его процессы. Тома пода `kubectl debug` в него не подключает, поэтому файлы цели читают через `/proc/<pid>/root`.

```
Pod orders-api-…
 ├─ контейнер api (python, без ps и curl)
 │      ▲
 │      │  общие: пространство PID (с --target) и сеть пода
 │      ▼
 └─ ephemeral-контейнер dbg (busybox): ps, wget, ls /proc/1/root
```

Схема 14. Отладочный контейнер добавляется к работающему поду, а файловую систему цели видно через `/proc/1/root`.

Команда ниже создаёт контейнер `dbg` с образом busybox, привязывает его к контейнеру `api` и открывает shell. **Профиль** (profile) задаёт права отладочного контейнера: `general` добавляет право трассировки процессов `SYS_PTRACE`, и в kubectl 1.36 это профиль по умолчанию.

```bash
P=$(kubectl -n orders get pod -l app=orders-api -o jsonpath='{.items[0].metadata.name}')
kubectl -n orders debug -it $P --image=busybox:1.37 --target=api --profile=general -c dbg -- sh
```

Разбор:

1. `P` — имя первого пода orders-api.
2. `--target=api` — контейнер, чьи процессы увидит отладочный контейнер.
3. `-c dbg` — имя нового контейнера.

Внутри работают `ps`, `wget -qO- http://127.0.0.1:8000/version` и `ls /proc/1/root/srv/app`, а практику даёт работа 3, шаг 4.

Ephemeral-контейнер нельзя удалить или изменить: он остаётся в `spec.ephemeralContainers` до пересоздания пода. Для пода Deployment это не страшно, а одиночный под придётся пересоздать, чтобы убрать контейнер. Портов, проб и ресурсов у такого контейнера не бывает (02-1 §3).

Свойства, которых нет в профилях, задают флагом `--custom`: он принимает частичную спецификацию контейнера в YAML или JSON (stable с 1.32). Так добавляют, например, переменные окружения или capability `NET_ADMIN`, но имя, образ и команду этим флагом не меняют.

### Копия пода и отладка узла

К контейнеру, который падает сразу после старта, не подключиться, поэтому режим `--copy-to` создаёт копию пода с другой командой запуска. Оригинал остаётся нетронутым, а профиль `general` убирает у копии метки, пробы и init-контейнеры, чтобы Service не слал в неё трафик. Пример: `kubectl debug NAME --copy-to=NAME-dbg --container=app -- sleep 3600`.

Команда `kubectl debug node/lab-worker -it --image=busybox:1.37 --profile=sysadmin` создаёт под на самом узле. Любой профиль отладки узла даёт поду общие с узлом процессы и сеть и монтирует корень узла в `/host`, а `sysadmin` добавляет привилегированный режим. Внутри такого пода `chroot /host crictl ps` показывает контейнеры узла, поэтому он заменяет `ssh`, когда доступа к машине нет. Сам под отладки не удаляется, и его убирают вручную.

Права такого пода равны правам root на узле. Применяйте режим только на узлах, где вам это разрешено, и удаляйте под сразу после работы (06-3).

### port-forward

Команда `kubectl port-forward svc/orders-api 9000:80` открывает на вашей машине порт 9000 и пересылает соединения на порт 80 Service. По умолчанию порт слушает только `localhost` (`127.0.0.1` и `::1`), а туннель идёт через API-сервер и kubelet. В 1.35 стал stable переход `exec`, `attach` и `port-forward` с протокола SPDY на WebSocket, поэтому прокси между kubectl и API-сервером должен пропускать WebSocket.

При пробросе к Service kubectl выбирает один под в момент запуска и дальше работает только с ним, то есть балансировки нет. Поэтому для проверки распределения трафика port-forward не подходит (03-2), но годится, чтобы быстро открыть сервис без Gateway или Ingress.

### Узел при недоступном API-сервере

Если API-сервер лежит, `kubectl` бесполезен, и тогда заходят на узел (по `ssh`, на стенде — `docker exec`) и действуют в таком порядке.

1. `crictl ps -a` — какие контейнеры запущены и сколько у них попыток запуска.
2. `crictl logs ID` — лог упавшего контейнера.
3. `journalctl -u kubelet` и `journalctl -u containerd` — логи служб узла.
4. Файлы в `/var/log/pods` — те же логи подов, но прямо с диска.
5. `/etc/kubernetes/manifests` на узле control plane — манифесты **static pod** (статических подов): kubelet запускает их сам, без API-сервера (01-2).

**Журнал** (journal) — хранилище логов systemd, его читают командой `journalctl`; флаг `-u служба` оставляет записи одной службы. Логи подов лежат в каталоге вида `/var/log/pods/<namespace>_<под>_<uid>/<контейнер>/<N>.log`, где `N` — номер попытки запуска. Формат строки: время, поток (`stdout` или `stderr`), метка полной или частичной строки и текст.

Пока API-сервер жив, журнал службы узла можно прочитать и без входа на узел. Запрос `kubectl get --raw "/api/v1/nodes/lab-worker/proxy/logs/?query=kubelet"` (node log query, stable с 1.36) отдаёт журнал kubelet через API-сервер. Он работает, только если в конфигурации kubelet включены поля `enableSystemLogHandler` и `enableSystemLogQuery`, а у вас есть право на подресурс `nodes/proxy` (11-1).

## 6. Пределы и значения по умолчанию

В этой части нет настроек, которые меняют работу кластера, но есть числа, на которые опираются разборы.

### Версии и совместимость

- kubectl может отличаться от версии API-сервера не больше чем на одну минорную версию (для кластера 1.36 подходят 1.35–1.37). Правила совместимости разобраны в 10-3.
- На стенде: Kubernetes 1.36.1, kind 0.32.0, containerd 2.3.1.
- Версии инструментов из репозиториев Manjaro (extra): k9s 0.51.0, stern 1.34.0, kubectx 0.11.0, krew 0.5.0; для Ubuntu курс закрепляет те же версии релизов GitHub.
- kuberc — beta с 1.34, KYAML — beta с 1.35 и stable в 1.37; профиль `kubectl debug` по умолчанию в 1.36 — `general`.

### Таймауты и кэш

- `--request-timeout` по умолчанию равен 0: kubectl ждёт ответа без ограничения. В скриптах задавайте значение явно.
- Кэш discovery лежит в `~/.kube/cache`. Если после установки CRD новый тип не виден, удалите каталог кэша.
- События (events) API-сервер хранит 1 час (`--event-ttl`), поэтому смотреть их надо сразу (11-1).
- `kubectl logs -l` по умолчанию печатает 10 последних строк каждого пода; `port-forward` по умолчанию слушает только `localhost`.

### Логи на узле

- kubelet ротирует логи контейнеров: до 5 файлов на контейнер, каждый не больше 10 МиБ (поля `containerLogMaxFiles` и `containerLogMaxSize`).
- После удаления пода его каталог в `/var/log/pods` тоже удаляется. Долгая история логов требует системы сбора.

### Отладочные контейнеры

- Ephemeral-контейнер нельзя удалить: он живёт до пересоздания пода.
- Порты, пробы и ресурсы для него задать нельзя.
- Под отладки узла (`debug node`) остаётся после выхода и ждёт ручного удаления.

#### Шаг 8. Посмотреть разницу и проверить apply

Команды готовят копию манифеста стенда с тремя репликами, показывают разницу с живым объектом и проверяют применение на сервере.


| Часть команды | Значение |
|---|---|
| `cp …` | работать с копией, файл стенда не трогать |

| `kubectl diff -f` | показать разницу между файлом и живым объектом |
| `echo "diff exit=$?"` | вывести код возврата `diff` |
| `apply --dry-run=server` | проверить применение на сервере без записи |

Результат `diff` (сокращён):

```
...
```

Разбор:

1. Строки `-` и `+` — что изменится: поле `replicas` с 2 на 3 и счётчик `generation`, который сервер увеличит сам.
2. `diff exit=1` — разница есть; при отсутствии разницы код был бы 0.
3. `configured (server dry run)` — Deployment изменится, `unchanged` — остальное совпадает с живым состоянием.
4. Проверьте `kubectl -n orders get deploy orders-api`: реплик по-прежнему две, запись не выполнялась.

**Вопросы для самопроверки.**

1. Чем `kubectl apply --dry-run=server` отличается от `--dry-run=client`?
2. Почему jsonpath-шаблон для списка подов начинается с `.items[*]`?
3. Где в выводе `-v=8` видны группа и версия API, и что значит `as=Table`?
4. Почему в скриптах не используют `kubens`?
5. Как временно отключить kuberc, если kubectl ведёт себя непривычно?

<details>
<summary>Ответы</summary>

1. Режим `server` отправляет запрос на API-сервер, где проходят валидация и admission, но не записывает объект. Режим `client` только разбирает манифест локально и пропускает ошибки схемы и политик.
2. `get pods` возвращает объект-список, а сами поды лежат в его поле `items`. Для одного объекта (`get pod X`) путь начинается сразу с поля.
3. В адресе запроса: он строится как `/apis/<группа>/<версия>/namespaces/<ns>/<ресурс>/<имя>`. `as=Table` значит, что kubectl просит сервер вернуть данные уже в виде таблицы.
4. Он правит общий файл kubeconfig, поэтому параллельные задачи влияют друг на друга. В скриптах `--namespace` и `--context` пишут явно в каждую команду.
5. Задать `KUBERC=off` на время команды или сессии. Переменная `KUBECTL_KUBERC=false` выключает сам механизм kuberc.

</details>

### Лабораторная работа 2. На узле: crictl, journalctl, логи подов

### Лабораторная работа 3. Внутрь пода: logs, exec, debug, port-forward

**Риски.** Работа добавляет временные объекты в кластер и ставит программы на хост.

- **Что меняется.** В кластере: в один под orders-api добавляется ephemeral-контейнер (шаг 4); в `lab-00-2` создаются поды `crash`, `crash-dbg` и под отладки узла `node-debugger-…` (шаги 2, 5, 6). На хосте: открывается порт `127.0.0.1:9000` (шаг 7), в `/usr/local/bin` ставятся `stern` и `k9s` (шаги 8–9).
- **Надолго ли.** До уборки. Ephemeral-контейнер удалить нельзя: он исчезнет вместе с подом при `rollout restart`.
- **Безопасность.** Под отладки узла на шаге 6 получает `hostPID`, `hostNetwork` и корень узла в `/host`, а профиль `sysadmin` добавляет привилегированный режим. На стенде узел — контейнер Docker, на настоящем кластере это права root на узле. Порт 9000 слушает только `localhost`. Бинарники скачайте с GitHub и сверьте контрольную сумму (`checksums.txt` у stern, `checksums.sha256` у k9s).
- **Влияние на систему.** Перезапуск подов orders-api в уборке на несколько секунд уменьшает число готовых реплик, сквозной запрос из 00-1 работает на оставшейся. Данные PostgreSQL не затрагиваются.
- **Откат.** Блок «Уборка» в конце работы.

**Цель.** Прочитать лог упавшего контейнера, зайти в под без shell и на узел через `kubectl debug`, пробросить порт и посмотреть логи через stern и k9s.

**Что понадобится.** Стенд 00-1 с подами orders-api, namespace `lab-00-2`, образ `busybox:1.37`, интернет для шагов 8 и 9.

**Схема опыта.**

```
шаг 1–2  logs, logs --previous          падающий под crash
шаг 3–4  exec, debug --target           под orders-api (ephemeral dbg)
шаг 5    debug --copy-to                копия crash-dbg
шаг 6    debug node                     под node-debugger на узле
шаг 7    port-forward                   localhost:9000 → svc/orders-api
шаг 8–9  stern, k9s                     логи и интерфейс
```

Схема 17. Шаги идут от безопасных к рискованным, а объекты кластера создают или меняют шаги 2, 4, 5 и 6.

#### Шаг 1. Прочитать лог работающего приложения

Эту работу вы выполняете сами, результаты в ней — ожидаемые. Команды читают логи Deployment и всех его подов.

```bash
kubectl -n orders logs deploy/orders-api --tail=3
kubectl -n orders logs -l app=orders-api --prefix --tail=2
```

| Часть команды | Значение |
|---|---|
| `logs deploy/orders-api` | взять один под Deployment |
| `--tail=3` | последние три строки |
| `-l app=orders-api` | все поды с этой меткой |
| `--prefix` | перед строкой имя пода и контейнера |

Ожидаемый результат: строки журнала HTTP-запросов в формате из кода приложения (00-1, работа 3, шаг 1). Строка содержит адрес клиента и запрос, например `<IP> "GET /ready HTTP/1.1" 200 -`: это проба готовности, которую kubelet посылает каждые 2 секунды. Вторая команда добавляет к строкам префикс вида `[pod/orders-api-…/api]`.

Разбор:

1. Первая команда выбирает один под, поэтому видны запросы только к нему.
2. Строки `/ready` идут от kubelet: период пробы 2 с задан в манифесте стенда.
3. С `--prefix` видно, какой под ответил на запрос. Так находят «больную» реплику.

#### Шаг 2. Прочитать лог упавшего контейнера

Эту работу вы выполняете сами, результаты в ней — ожидаемые. Команды создают под, который пишет строку и падает, а затем читают лог его предыдущего запуска.

```bash
kubectl run crash --image=busybox:1.37 -- sh -c 'echo "run failed: no config"; exit 1'
sleep 40
kubectl get pod crash
kubectl logs crash --previous
```

| Часть команды | Значение |
|---|---|
| `kubectl run crash` | одиночный под с именем `crash` |
| `sh -c '…; exit 1'` | напечатать строку и выйти с ошибкой |
| `sleep 40` | подождать несколько перезапусков |
| `logs --previous` | лог предыдущего экземпляра контейнера |

Ожидаемый результат `get pod`: статус `CrashLoopBackOff` и число перезапусков больше нуля. Ожидаемый результат `logs --previous`:

```
run failed: no config
```

Разбор:

1. `CrashLoopBackOff` — контейнер падает, kubelet ждёт перед следующей попыткой (02-1 §2).
2. Лог текущего экземпляра может быть пуст: контейнер только что перезапущен или ещё не запущен.
3. Флаг `--previous` читает лог завершившегося запуска, и причина падения видна.

#### Шаг 3. Увидеть пределы exec

Команда проверяет, есть ли в контейнере orders-api привычные инструменты отладки `ps`, `curl` и `ss`.

```bash
P=$(kubectl -n orders get pod -l app=orders-api -o jsonpath='{.items[0].metadata.name}')
kubectl -n orders exec $P -- which ps curl ss; echo "exit=$?"
```

| Часть команды | Значение |
|---|---|
| `P=$(…)` | имя первого пода orders-api |
| `exec $P -- which …` | выполнить `which` в контейнере |
| `echo "exit=$?"` | показать код возврата |

Результат:

```
exit=1
```

Перед этой строкой kubectl может напечатать сообщение `command terminated with exit code 1`.

Разбор:

1. Код 1 значит, что хотя бы одной программы нет: в образе `python:3.12-slim` нет ни одной из трёх.
2. Установить их в работающий контейнер нельзя без перестройки образа.
3. Решение — ephemeral-контейнер на следующем шаге.

#### Шаг 4. Войти в под через ephemeral-контейнер

Команда добавляет в под orders-api контейнер `dbg` с busybox и открывает shell, и этот контейнер видит процессы контейнера `api`.

```bash
kubectl -n orders debug -it $P --image=busybox:1.37 --target=api --profile=general -c dbg -- sh
```

| Часть команды | Значение |
|---|---|
| `debug -it $P` | отладка пода с интерактивным терминалом |
| `--image=busybox:1.37` | образ с нужными инструментами |
| `--target=api` | общее пространство PID с контейнером `api` |
| `--profile=general` | права для отладки, в том числе `SYS_PTRACE` |
| `-c dbg` | имя нового контейнера |

Внутри открывшегося shell выполните три команды: список процессов, запрос к приложению и просмотр его файлов.

```bash
ps
wget -qO- http://127.0.0.1:8000/version
ls /proc/1/root/srv/app
```

| Часть команды | Значение |
|---|---|
| `ps` | процессы, видимые в общем PID-пространстве |
| `wget -qO- http://127.0.0.1:8000/version` | запрос к приложению по `localhost`, сеть общая |
| `ls /proc/1/root/srv/app` | файловая система контейнера `api` через `/proc` |

Результат:

```
PID   USER     TIME  COMMAND
    1 10001     0:00 python -m app.main
  148 root      0:00 sleep 600
…
{"version": "2.0", "pod": "orders-api-6d54d4c46b-fvq75"}
__init__.py
main.py
```

Строка `sleep 600` — процесс отладочного контейнера, запущенного с другой командой; у вас на её месте будет `sh` с другим PID.

Разбор:

1. PID 1 принадлежит процессу приложения `python -m app.main` от пользователя 10001. Это контейнер `api`, а не отладочный.
2. Приложение отвечает на `127.0.0.1:8000`: сеть пода общая.
3. Путь `/proc/1/root/srv/app` ведёт в файловую систему контейнера `api`: видны `__init__.py` и `main.py`.
4. Выход из shell не удаляет контейнер `dbg`: проверьте `kubectl -n orders get pod $P -o jsonpath='{.spec.ephemeralContainers[*].name}'`.

#### Шаг 5. Разобрать упавший под на копии

Эту работу вы выполняете сами, результаты в ней — ожидаемые. Команды создают копию пода `crash`, у которой команда запуска заменена на `sleep`, и проверяют, что копия жива.

```bash
kubectl debug crash --copy-to=crash-dbg --container=crash -- sleep 3600
sleep 5
kubectl get pod crash crash-dbg
kubectl exec crash-dbg -- ls /
```

| Часть команды | Значение |
|---|---|
| `debug crash --copy-to=crash-dbg` | создать копию пода под новым именем |
| `--container=crash` | у какого контейнера заменить команду |
| `-- sleep 3600` | новая команда: ждать час |
| `exec crash-dbg -- ls /` | выполнить команду в живом контейнере копии |

Ожидаемый результат `get pod`: `crash` в статусе `CrashLoopBackOff`, `crash-dbg` в статусе `Running`, `1/1`. Команда `ls /` печатает корень файловой системы busybox.

Разбор:

1. Оригинал не затронут, он продолжает падать и сохраняет историю.
2. Копия живёт достаточно долго, чтобы зайти в неё через `exec` и руками запустить исходную команду.
3. Так отлаживают контейнеры, которые падают быстрее, чем вы успеваете подключиться.
4. Профиль `general` убрал у копии метки и пробы, поэтому Service и контроллеры её не подхватят.

#### Шаг 6. Зайти на узел через debug node

Команда создаёт в namespace `lab-00-2` под на узле `lab-worker` и выполняет в нём `crictl ps` через корень узла.

```bash
kubectl -n lab-00-2 debug node/lab-worker -it --image=busybox:1.37 \
  --profile=sysadmin -- chroot /host crictl ps
kubectl get pods -A | grep node-debugger
```

| Часть команды | Значение |
|---|---|
| `debug node/lab-worker` | запустить под отладки на этом узле |
| `--profile=sysadmin` | привилегированный режим поверх общих с узлом PID и сети |
| `chroot /host` | сделать корнем файловую систему узла |
| `crictl ps` | список контейнеров узла |
| `grep node-debugger` | найти под отладки и его namespace |

Результат: kubectl создаёт под `node-debugger-lab-worker-…`, и `crictl ps` в нём показывает контейнеры узла `lab-worker`, как в работе 2. Вторая команда показывает под отладки и его namespace, а в спецификации пода стоят `hostPID: true` и `hostNetwork: true`.

Разбор:

1. Под запущен на узле и видит его процессы и сеть (`hostPID`, `hostNetwork`).
2. Через `/host` доступна вся файловая система узла: это замена `ssh`, когда доступа к машине нет.
3. Под не удаляется после выхода. Он остаётся в состоянии `Completed` или `Running`, пока вы его не удалите.

#### Шаг 7. Пробросить порт и проверить балансировку

#### Шаг 8. Хвост логов многих подов через stern

Эту работу вы выполняете сами, результаты в ней — ожидаемые. Шаг ставит stern на хост (Риски выше) и читает им логи двух подов сразу.

В Manjaro stern ставят командой `sudo pacman -S stern`. Затем запустите команду ниже, посмотрите вывод несколько секунд и остановите её клавишами Ctrl-C.


| Часть команды | Значение |
|---|---|
| `stern -n orders orders-api` | логи всех подов, чьё имя содержит `orders-api` |
| `--tail 3` | начать с трёх последних строк каждого пода |

Ожидаемый результат: строки обоих подов вперемешку, каждая с префиксом из имени пода и контейнера.

Разбор:

1. Обе реплики видны в одном потоке: проще заметить, что одна из них ведёт себя иначе.

#### Шаг 9. Посмотреть кластер в k9s

Эту работу вы выполняете сами, результаты в ней — ожидаемые. Шаг ставит k9s на хост (Риски выше) и запускает его в режиме чтения.

В Ubuntu k9s ставят пакетом `.deb` из релиза проекта через `apt-get`.


В Manjaro k9s ставят командой `sudo pacman -S k9s`, а запускают одинаково в обоих дистрибутивах.

```bash
k9s --readonly -n orders
```

| Часть команды | Значение |
|---|---|
| `--readonly` | запретить изменяющие действия |
| `-n orders` | открыть namespace `orders` |

Внутри k9s введите `:pods`, выберите под стрелками и откройте его логи клавишей `l`, а описание — клавишей `d`. Выйдите командой `:q` или клавишами Ctrl-C.

Ожидаемый результат: таблица подов `orders-api-…` и `postgres-0` со статусом `Running`; она обновляется без нажатий клавиш.

Разбор:

2. Клавиша `l` открывает тот же лог, что `kubectl logs`, `d` — тот же вывод, что `kubectl describe`.
3. Из-за `--readonly` клавиши удаления и shell не работают. Это сознательное ограничение.

**Итог.**

| Что узнали | Где видно |
|---|---|
| `--previous` читает лог упавшего запуска | шаг 2 |
| В минимальном образе нет инструментов | шаг 3, код 1 |

| `debug node` даёт доступ к узлу без `ssh` | шаг 6 |
| port-forward к Service не балансирует | шаг 7, один и тот же под |
| stern и k9s собирают то же, что kubectl, удобнее | шаги 8 и 9 |

**Уборка.** Останавливаем проброс по pid-файлу, удаляем временные поды и под отладки, пересоздаём поды orders-api без ephemeral-контейнера, возвращаем namespace по умолчанию и удаляем namespace работ.

```bash
kill $(cat ~/lab/k8s/00-2/pf.pid)
kubectl delete pod crash crash-dbg --now
kubectl get pods -A | grep node-debugger
kubectl -n orders rollout restart deploy/orders-api
kubectl -n orders rollout status deploy/orders-api
kubectl config set-context --current --namespace=default
kubectl delete ns lab-00-2
rm -rf ~/lab/k8s/00-2
```

Третья строка выводит под отладки, если он остался вне `lab-00-2`, и тогда его удаляют командой `kubectl -n <namespace> delete pod <имя>`. Удаление namespace `lab-00-2` убирает и под отладки, если он лежал в нём. `rollout restart` только добавляет в шаблон Deployment аннотацию с временем перезапуска, поэтому `kubectl apply` манифестов стенда не нужен.

Установленные stern и k9s можно оставить. Чтобы убрать их, в Ubuntu выполните `sudo rm /usr/local/bin/stern` и `sudo apt-get remove k9s`, а в Manjaro — `sudo pacman -Rns stern k9s`.

**Вопросы для самопроверки.**

1. Чем `kubectl logs --previous` отличается от обычного `kubectl logs`?
2. Что нужно указать, чтобы ephemeral-контейнер видел процессы целевого контейнера?
3. Можно ли удалить ephemeral-контейнер из пода, и как избавиться от него?
4. Почему port-forward к Service нельзя использовать для проверки балансировки?
5. Чем опасен под, созданный командой `debug node` с профилем `sysadmin`?

<details>
<summary>Ответы</summary>

1. Обычная команда читает лог текущего экземпляра контейнера, `--previous` — лог предыдущего, завершившегося запуска. После падения именно там причина.
2. Флаг `--target=<имя контейнера>`: он включает общее пространство PID с целью. Сеть пода общая и без него, а тома `kubectl debug` в отладочный контейнер не подключает.
3. Нельзя: он остаётся в `spec.ephemeralContainers` до пересоздания пода. Для пода Deployment помогает `rollout restart`.
4. kubectl выбирает один под при запуске и шлёт в него весь трафик. kube-proxy и распределение по подам он не использует.
5. Под получает права root на узле: привилегированный режим, общие с узлом процессы и сеть, корень узла в `/host`. Создавайте его только там, где это разрешено, и удаляйте сразу после работы.

</details>
