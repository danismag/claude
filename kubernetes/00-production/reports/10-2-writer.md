## Сомнительные места
- Все три работы без реального вывода, начинаются фразой «Эту работу вы выполняете сами…». Вывод везде ожидаемый, числа заменены на «…»/N.
- Подтверждено документацией (WebFetch etcd v3.6 maintenance/recovery/FAQ, k8s configure-upgrade-etcd, блог etcd 3.6): quota 2 ГиБ/8 ГиБ, NOSPACE и последовательность compact-defrag-disarm, пороги fsync 10 мс и commit 25 мс, нечётное число членов, максимум 7, snapshot-count 10000, удаление snapshot status/restore из etcdctl, флаги --bump-revision/--mark-compacted, --skip-hash-check, downgrade validate/enable, upgrade через 3.5.20+, /livez /readyz, пять членов для production.
- Не подтверждено: наличие etcdutl (и его в PATH) в образе registry.k8s.io/etcd:3.6.x-0 и на стенде; запуск `etcdutl` как command одноразового пода работы 2 держится на этом. Если etcdutl нет, шаги 2 и 4 работы 2 не сработают.
- heartbeat 100 мс и election timeout 1000 мс — умолчания etcd по памяти (FAQ чисел не даёт).
- Фоновая запись backend «раз в ~100 мс» (схема 3) — по памяти.
- Формулировка «компакция API-сервера удаляет историю старше предыдущей отметки (5 мин)» — по памяти о реализации.
- «etcd по умолчанию отвечает на чтение через кворум (linearizable)» и вывод «без кворума свежие чтения не проходят» — по памяти.
- kubeadm: флаг `--snapshot-count=10000` в манифесте etcd (шаг 3 работы 1); порт метрик 2381 `--listen-metrics-urls=http://127.0.0.1:2381`; `curl` есть в образе узла kind; в манифесте etcd строка `    - etcd` (4 пробела) и `path: /var/lib/etcd` тома etcd-data — на них держатся sed-команды работ 2 и 3.
- Отсутствие в манифесте kubeadm `--auto-compaction-*` — по памяти.
- `kind create cluster --kubeconfig <файл>`; имя контейнера `lab-10-2-control-plane`, под `etcd-lab-10-2-control-plane`; пул ресурсов (~1 ГиБ RAM, ~1 ГБ диска) — оценка.
- Структура JSON `endpoint status -w json` (`.[0].Status.header.revision`, `.dbSize`, `.dbSizeInUse`) и столбцы таблицы (`IN USE`, `PERCENTAGE NOT IN USE`) в 3.6; вывод `compacted revision N`, `Finished defragmenting etcd member[…]`, `alarm disarm` печатает снятую тревогу.
- Текст ошибки `etcdserver: mvcc: database space exceeded` в ответе kubectl, число итераций 60–70 (400 КБ × ~70 ≈ 32 МиБ) — расчёт, не замер; перезапуски scheduler/controller-manager при NOSPACE — предположение (написано «могли»).
- Метка `apiserver_storage_objects` с `resource` — по памяти.
- Работа 2: restore-под в namespace `lab-10-2-after` (исчезает после восстановления), hostPath `/var/lib` узла kind; после восстановления scheduler/controller-manager не останавливались, только apiserver и etcd. Имена каталогов `snap`/`wal` в `member` — по структуре etcd.
- Размер etcd на пустом kind и «DB SIZE единицы мегабайт» — оценка.
- Версия etcd 3.6.8 для kubeadm 1.36 и 3.7.0 для 1.37 — из research-k8s-changes (не сверено с constants.go); версия внутри kind-образа 1.36.1 не проверена. Бета EtcdRangeStream упомянута как «через флаг» в 1.37 (в исследовании: beta on 1.37).
