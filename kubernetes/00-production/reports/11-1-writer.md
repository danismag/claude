## Сомнительные места
Все четыре работы начинаются фразой «Эту работу вы выполняете сами…», потому что реального вывода по теме почти нет.
- Реальный вывод из старой версии: только две строки `kubectl top nodes` (lab-control-plane 95m/646Mi, lab-worker 15m/134Mi, прогон 2026-10-14, лаба 2 шаг 1), значения `containerLogMaxSize 10Mi`, `containerLogMaxFiles 5` (configz, лаба 4 шаг 4), формат симлинка в /var/log/containers и форма `REASON/COUNT` событий (Scheduled 1, Pulled 4, Created 4, Started 4, BackOff 3 — из OOM-пода старой 05-1, перенесена как пример формы для пода crash). Остальной вывод — ожидаемый.
- Лаба 1: точный текст сообщений Failed/BackOff для образа busybox:1.37-nope, формат «4s (x2 over 18s)» в колонке LAST SEEN у `kubectl events`, `No events found` после TTL; вывод `grep -c event-ttl` = 0 (флаг в kind не задан — предположение); поля count/firstTimestamp/lastTimestamp/source в jq (старая форма core/v1, а kubelet пишет через старый recorder — по памяти).
- События: утверждение, что core/v1 и events.k8s.io/v1 отдают одни и те же объекты с конвертацией полей — по памяти; константы 25/1 per 300 с/10 за 600 с (events_cache.go) и finishTime 6 мин, refreshTime 30 мин (events/event_broadcaster.go) сверены по master, а не по release-1.36; применимость spam-фильтра/агрегатора к kubelet и к scheduler (разные recorder) описана упрощённо.
- `eventRecordQPS` 50 / `eventBurst` 100 — по types.go release-1.36; исследование говорит, что «0 = без лимита» новое в 1.37, а в types.go 1.36 это уже написано — в тексте оставлено «значение 0 снимает ограничение» без привязки к версии.
- Node log query: types.go 1.36 даёт `enableSystemLogHandler` default true, `enableSystemLogQuery` default false; страница system-logs называет handler по умолчанию false и в заметке 1.36 «достаточно handler». Противоречие описано в тексте (§6, лаба 4 шаг 4), результат запроса в лабе оставлен «либо строки, либо ошибка». Параметры query/pattern/sinceTime/untilTime/tailLines — по странице system-logs.
- Права node log query: «при прямом обращении хватает `nodes/log`» — по исследованию (fine-grained authz), не проверено; про рекомендацию ограничить nodes/logs в 1.37 (стартовые логи kubelet содержат конфиг) в тексте нет — добавить при ревью, если нужно.
- Ротация (лаба 4): имена ротированных файлов `0.log.<дата-время>` и сжатие старых в `.gz`, размеры 2–10 МиБ, общий размер `du` — по памяти о log manager kubelet; скорость генератора (около 1 МиБ в секунду, `yes | head -c`, `tr '\000'`, `fold` не используется) не измерена; 16 КиБ как размер деления строки (метка P) — по памяти о containerd; утверждение, что `kubectl logs` читает только текущий файл, — по памяти; удаление каталога логов после удаления пода «до минуты» — оценка.
- metrics-server: 15 с — по README (флаг `--metric-resolution` в README не назван, взят из плана 05-4); ресурсы 100m/200MiB и +1m/2MiB на узел — README; «хранит последнюю пару замеров» — по памяти; формат ответа Metrics API (`window` ~15 с, `usage.cpu` в `n`, память в `Ki`) — по памяти; сообщение `metrics not available yet` и «30–60 секунд» — по памяти; `metrics.k8s.io` v1 GA в 1.37 — по исследованию.
- Метрики: имена `kubelet_running_pods`, `kubelet_pleg_relist_duration_seconds`, `workqueue_depth`, `apiserver_flowcontrol_rejected_requests_total`, `apiserver_request_duration_seconds`, `prober_probe_total` (метки) — по памяти; `node_cpu_usage_seconds_total`, `container_cpu_usage_seconds_total` с меткой времени в мс на /metrics/resource — по памяти. Числа в выводе шагов 4–5 (1043, 812, 402, 214, 9) — иллюстрация формы, не измерения. Проверка `grep -c '^apiserver_'` даёт число строк, а не метрик.
- Порты 10259/10257, bind 127.0.0.1 в kubeadm/kind, код 403 (или 401) без токена, открытые /healthz /livez — по памяти (в странице system-metrics порты не названы); `curl` в узле kind есть (по 10-2).
- kube-state-metrics: v2.20.0 и соответствие Kubernetes 1.36 — README main (матрица); состав ClusterRole, образ, securityContext, kustomization (namespace kube-system) — raw v2.20.0; удобство `namePrefix` с ClusterRoleBinding (обновление roleRef и subjects) и удалённый ресурс `//examples/standard?ref=v2.20.0` в kustomize из `kubectl kustomize` (нужен git) — по памяти и не проверено; имя Service `lab-11-1-kube-state-metrics` и порт `http-metrics` для прокси сервиса — по манифестам (порт в Service не читал, имя взято из контейнера: **проверить**, у Service в examples/standard порты названы `http-metrics` и `telemetry`); флаги `--resources` и `--metric-labels-allowlist` — по памяти; названия метрик kube_job_status_failed, kube_node_status_condition — по памяти.
- Лаба 3 шаг 3: вывод строк `kube_pod_status_phase` (оба пода `Running`, в том числе `crash` — возможна фаза Running при CrashLoopBackOff, но в начале падения возможна и другая); порядок меток в строках не проверен, регулярные выражения не зависят от него.
- Цепочка прав лабы 2: `kubectl create clusterrole … --non-resource-url=/metrics`, `kubectl create token --duration=10m`, `docker exec -e` — ожидаемое поведение.
- Устаревшая оговорка: «версия Metrics API v1 — GA в 1.37» одной фразой, как в 05-4.
