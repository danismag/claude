## 1. Какую задачу решает control plane

Control plane отвечает на вопрос, как держать сотни контейнеров в нужном виде, когда машины и процессы падают. Он хранит описание «как должно быть» и сам устраняет расхождения. Сначала разберём идею, а компоненты — в §2.

### Желаемое и фактическое состояние

**Control plane** (плоскость управления) — компоненты, которые принимают описания объектов, хранят их и принимают решения. **Data plane** (плоскость данных) — то, что работает по этим решениям: контейнеры, сеть, правила пересылки. **Узел** (node) — машина кластера, на которой запускаются контейнеры. На стенде узлы — это контейнеры Docker `lab-worker`, `lab-worker2` и `lab-worker3` (00-1).

Вы не отдаёте команду «запусти три копии», а записываете в объект желаемое состояние, поле `spec`. Компоненты записывают в поле `status` то, что есть на самом деле. Так устроен **Deployment** — объект с описанием приложения и числом копий, `replicas: 3` (02-2). Копии — это **поды** (Pod): один или несколько контейнеров на одном узле (02-1).

### Цикл согласования

**Контроллер** (controller) — программа, которая следит за объектами одного вида и приводит факт к желаемому. Она работает в бесконечном цикле, который называют **reconcile loop** (цикл согласования).

```
   ┌────────────────────────────────────────────────────────────┐
   ▼                                                            │
наблюдать ──► сравнить spec со status ──► действовать ──► записать status
 (watch)       «нужно 3, есть 2»          создать один под    «есть 3»
```

Схема 2. Один оборот цикла. Если расхождение осталось, цикл идёт снова.

Пример: **ReplicaSet** — объект, который держит заданное число одинаковых подов; Deployment создаёт его сам (02-2). Контроллер ReplicaSet видит «нужно три, есть два» и создаёт один под, а если вы удалили под, цикл снова видит разницу.

### Что из этого следует

Модель «желаемое против фактического» объясняет три ситуации, которые встречаются каждый день.

- **Удалил под, он вернулся.** Подом владеет контроллер, поэтому удалять надо владельца или менять `replicas`.
- **Поправил руками, через минуту откатилось.** Объектом управляет кто-то ещё: оператор, Argo CD (08-1) или Helm при следующем обновлении.
- **Status устарел.** Status пишет контроллер, и если контроллер стоит, status показывает прошлое состояние (§5, лабораторная работа 3).

## 2. Как устроен control plane

Компоненты control plane общаются не друг с другом, а через один сервер. Разберём роли компонентов, путь запроса, хранилище, подписку на изменения и выбор лидера.

### Компоненты и static pod

В control plane и на узлах работают шесть компонентов.

- **kube-apiserver** — единственная точка входа в API. Проверяет запросы, читает и пишет etcd, рассылает события подписчикам.
- **etcd** — хранилище всего состояния кластера. Это key-value база с репликацией (§2, «Хранение в etcd»).
- **kube-scheduler** — для каждого пода без узла выбирает узел и записывает выбор в объект.
- **kube-controller-manager** — один процесс, в котором работают около 40 контроллеров: Deployment, ReplicaSet, Node, Job, EndpointSlice и другие.
- **kubelet** — служба systemd на каждом узле. Запускает назначенные узлу поды и отправляет их status.
- **kube-proxy** — на каждом узле программирует правила для Service (03-2).

Первые четыре на стенде работают на узле `lab-control-plane` как static pod. **Static pod** (статический под) — под, который kubelet создаёт сам по файлу в каталоге `/etc/kubernetes/manifests`, без API-сервер. Так решена задача «курица и яйцо»: API-сервер запускается не через API-сервер. Kind собирает кластер через kubeadm, и тот кладёт в этот каталог четыре манифеста.

```
узел lab-control-plane
/etc/kubernetes/manifests/
   etcd.yaml   kube-apiserver.yaml   kube-controller-manager.yaml   kube-scheduler.yaml
        │
        └──► kubelet следит за каталогом ──► containerd запускает контейнеры
                     │
                     └──► создаёт в API mirror pod (копия только для чтения)
```

Схема 3. Файл в каталоге — единственный источник правды для static pod. **Mirror pod** (зеркальный под) — запись в API, по которой видно static pod. Править её нельзя, и она может отставать от реальности.

### Путь запроса через API-сервер

Каждый запрос проходит одну и ту же цепочку проверок, и объект попадает в etcd только после всех шагов.

```
kubectl ──HTTPS──► kube-apiserver
                    1. аутентификация: кто вы                              → 401
                    2. авторизация: можно ли вам это действие              → 403
                    3. mutating admission: правки объекта, значения по умолчанию
                    4. проверка схемы: типы и обязательные поля            → 422
                    5. validating admission: квоты, PodSecurity, запреты   → 403
                    6. запись в etcd
```

Схема 4. Шесть шагов внутри API-сервер; справа указан код ответа при отказе.

Разберём шаги по порядку.

1. **Аутентификация** (authentication) — API-сервер узнаёт, кто пришёл: по сертификату x509, токену ServiceAccount или OIDC; не узнал — ответ 401.
2. **Авторизация** (authorization) — проверка, что этому пользователю разрешено действие. На стенде включены режимы Node и RBAC (06-1), а отказ даёт ответ 403.
3. **Mutating admission** (изменяющий допуск) — встроенные плагины и вебхуки дописывают в объект значения по умолчанию.
4. **Проверка схемы** — API-сервер сверяет поля и их типы с описанием вида объекта. Ошибка в поле — ответ 422.
5. **Validating admission** (проверяющий допуск) — плагины и политики только разрешают или отклоняют, обычно с ответом 403. Примеры: квоты, PodSecurity (06-3), вебхуки (09-2).
6. **Запись** — API-сервер пишет объект в etcd и отвечает клиенту.

Правило, которое объясняет всю архитектуру: **в etcd ходит только API-сервер**. Scheduler, контроллеры и kubelet — такие же клиенты API, как kubectl: они не вызывают друг друга и не отправляют сообщений. Каждый записывает результат в объект и читает чужие записи через watch.

### Хранение в etcd

**etcd** — распределённая key-value база, которая записывает данные только с согласия большинства членов. Для этого она использует алгоритм **Raft** (согласование реплик через выбор лидера). Нужное для записи большинство называют кворумом (§6).

Объект лежит под ключом `/registry/<ресурс>/<namespace>/<имя>`. **Namespace** (пространство имён) — логическая область имён внутри кластера. Значение встроенного объекта — бинарная запись в формате protobuf с префиксом `k8s\0`, а объекты CRD хранятся в JSON.

```
ключ:      /registry/configmaps/lab-01-1/demo
значение:  k8s\0 + protobuf-описание объекта ConfigMap
версии:    create_revision — ревизия создания ключа
           mod_revision    — ревизия последнего изменения
           version         — сколько раз ключ менялся
```

Схема 5. Что хранит etcd для одного объекта: ревизии общие на весь кластер, а версия своя у каждого ключа.

**Ревизия** (revision) — глобальный счётчик изменений etcd, и каждая запись любого ключа увеличивает его на единицу. Поле `metadata.resourceVersion` объекта — это `mod_revision` его ключа. Поэтому оно не номер версии объекта: между двумя правками одного объекта оно растёт на столько, сколько изменений сделали другие компоненты. С 1.35 значения встроенных ресурсов можно сравнивать как числа внутри одного вида ресурса. У агрегированных API (сторонних серверов API) надёжно только сравнение на равенство.

### Watch и informers

Как контроллеры узнают об изменениях, не опрашивая API-сервер? Клиент делает **list**: получает все объекты вида и `resourceVersion` списка. Затем открывает **watch** — долгий HTTP-запрос, в котором сервер присылает события `ADDED`, `MODIFIED` и `DELETED`, начиная с указанной версии.

```
клиент ── list ──────────────► apiserver     весь список + resourceVersion = 4307
клиент ── watch от 4307 ─────► apiserver
        ◄── MODIFIED (4330) ──              поток событий в одном соединении
        ◄── DELETED  (4338) ──
```

Схема 6. List даёт точку отсчёта, watch присылает всё, что случилось после неё.

В клиентских библиотеках это спрятано в **informer** — компоненте, который делает list и watch, хранит локальный кэш и переподключается при обрыве. Контроллеры читают объекты из своего кэша, а не из API-сервер, поэтому 40 контроллеров не заваливают API запросами.

Большой list тяжёл для API-сервер: он собирает весь ответ в памяти. Поэтому есть **streaming list** (WatchList, потоковый список) — watch с параметрами `sendInitialEvents=true` и `resourceVersionMatch=NotOlderThan`. Сервер присылает текущие объекты событиями `ADDED`, а затем событие `BOOKMARK` с версией, на которой список полон. Функция в стадии beta и с 1.34 включена по умолчанию.

### Leader election и Lease

В высокодоступном кластере работают несколько копий scheduler и controller-manager, но действует только одна. **Leader election** (выбор лидера) — способ договориться, какая копия главная. Копии борются за один объект **Lease** (аренда) — запись с именем держателя и временем последнего продления.

Лидер продлевает аренду, а если он замолчал, другая копия забирает её. Числа и опыт — в §6 и лабораторной работе 3. Есть и согласованный выбор лидера (coordinated leader election, объекты LeaseCandidate), но в 1.36 он в стадии beta и выключен по умолчанию.

## 3. Как управлять control plane

Компонентами control plane управляют через файлы на узле, а объектами кластера — через API. Здесь описаны оба способа и защита API-сервер от перегрузки.

### Остановка и запуск компонента

Static pod останавливают удалением файла из каталога манифестов: kubelet замечает изменение за секунды и останавливает контейнер. Верните файл, и kubelet запустит его снова. В лабораторной работе 3 мы переносим файл командой `mv` в `/root/` внутри узла.

Эта техника нужна только для опытов, а в рабочем кластере компонент останавливают так, чтобы остались копии, которые продолжат работу. Манифест вне каталога не вернётся сам: пока файла нет, kubelet его не запустит.

### Флаги компонентов

Параметры компонента записаны в его манифесте как аргументы команды. Посмотрим три флага API-сервер, которые определяют правила кластера.

- `--authorization-mode=Node,RBAC` — режимы авторизации (шаг 2 схемы 4).
- `--etcd-servers=https://127.0.0.1:2379` — адрес etcd.
- `--enable-admission-plugins=NodeRestriction` — плагины допуска сверх включённых по умолчанию.

Чтобы сменить флаг, правят файл манифеста: kubelet заметит изменение и пересоздаст контейнер. Правка mirror pod через `kubectl edit` ничего не даст: он только отражает файл.

### Изменение объекта без конфликта

Что будет, если два клиента одновременно правят один объект? Каждое обновление несёт `resourceVersion`, от которого оно сделано, и если объект с тех пор изменился, API-сервер отвечает **409 Conflict**. Это **optimistic concurrency** (оптимистичная конкуренция): блокировок нет, запись первого выигрывает, остальные перечитывают объект и повторяют.

Команды ведут себя по-разному. `kubectl replace` и `kubectl edit` отправляют целый объект с его версией и получают конфликт, если файл устарел. `kubectl patch` и обычный `apply` отправляют только изменения, и сервер применяет их к свежей версии, поэтому конфликты бывают редко. Спор двух владельцев за одно поле решает server-side apply (01-3 §3).

### Приоритеты запросов: APF

Перегрузить API-сервер можно одним неудачным клиентом. Защита — **API Priority and Fairness** (APF, приоритеты и справедливость запросов): запросы делятся на очереди по приоритетам. Когда очередь приоритета полна, шумный клиент получает ответ 429 Too Many Requests и не занимает весь сервер. Правила хранятся в объектах **FlowSchema** (кому какой приоритет) и **PriorityLevelConfiguration** (сколько ресурса получает приоритет). Их API — `flowcontrol.apiserver.k8s.io/v1`, а версия v1beta3 удалена в 1.32.

Выдержка из `kubectl get flowschemas` на стенде, от важных правил к общим:

| FlowSchema | Priority level | Порядок |
|---|---|---|
| exempt | exempt | 1 |
| system-leader-election | leader-election | 100 |
| system-node-high | node-high | 400 |
| system-nodes | system | 500 |
| kube-controller-manager | workload-high | 800 |
| kube-scheduler | workload-high | 800 |
| service-accounts | workload-low | 9000 |
| global-default | global-default | 9900 |
| catch-all | catch-all | 10000 |

Меньший порядок проверяется раньше. Запросы ваших CI и операторов (ServiceAccount) попадают в `workload-low`, запросы kubelet — в `system`. Если оператор начнёт заваливать API, получит 429 он, а узлы и выбор лидера продолжат работать. Метрики: `apiserver_flowcontrol_rejected_requests_total` и `apiserver_flowcontrol_current_inqueue_requests`.

## 4. Как увидеть состояние control plane

Состояние видно с пяти сторон: что отправляет kubectl, что лежит в etcd, живы ли компоненты, кто лидер и кто писал объект.

### Что отправляет kubectl

Флаг `-v=6` показывает каждый HTTP-запрос kubectl: глагол, адрес и код ответа, а флаг `-v=8` добавляет тела запросов (00-2). Первый `apply` объекта состоит из двух запросов: `GET` возвращает 404, затем `POST` создаёт объект. Повторный `apply` с изменением читает объект, считает разницу и отправляет `PATCH`. Опыт — лабораторная работа 1, шаг 1.

### Карточка инструмента: etcdctl

**Назначение:** **etcdctl** — консольный клиент etcd (etcd command-line client). Он читает ключи и ревизии, проверяет здоровье и членов кластера, делает снимки базы. В курсе им только читают свой кластер: запись в `/registry` мимо API-сервер обходит проверки и ломает объекты.

**Как работает:** etcdctl отправляет запросы по gRPC (вызову процедур поверх HTTP/2) на порт 2379 etcd. etcd пускает только клиентов с сертификатом, который подписал его собственный центр сертификации. Это **mTLS** (mutual TLS) — взаимная проверка сертификатов: клиент проверяет сервер, а сервер клиента.

```
хост ── kubectl exec ──► pod etcd-lab-control-plane
                           │ etcdctl --cacert --cert --key
                           ▼
                    127.0.0.1:2379  (gRPC, mTLS)  ──► etcd ──► ключи /registry/…
```

Схема 7. etcdctl запускается внутри пода etcd и ходит на локальный порт. Смотрите на сертификаты: без них etcd закрывает соединение.

**Откуда берёт данные:** из работающего etcd по адресу из `--endpoints` (по умолчанию `127.0.0.1:2379`). Сертификаты лежат на узле control plane в `/etc/kubernetes/pki/etcd` и видны внутри пода etcd. Локальной базы у etcdctl нет.

**Основные команды.** Переменная `E` собирает адрес и сертификаты, переменная `X` — запуск внутри пода etcd. В лабораторных работах их задаёт шаг 3 работы 1.

```bash
E='etcdctl --endpoints=https://127.0.0.1:2379 --cacert=/etc/kubernetes/pki/etcd/ca.crt'
E+=' --cert=/etc/kubernetes/pki/etcd/server.crt --key=/etc/kubernetes/pki/etcd/server.key'
X='kubectl -n kube-system exec etcd-lab-control-plane --'
$X $E endpoint health                     # отвечает ли etcd на запрос
$X $E endpoint status -w table            # лидер, версия, размер базы, ревизия
$X $E member list -w table                # члены кластера etcd (на стенде один)
$X $E get /registry/configmaps/lab-01-1/demo -w json  # один ключ с его ревизиями
$X $E get /registry/configmaps --prefix --keys-only   # имена всех ключей с префиксом
$X $E get /registry/pods --prefix --count-only        # только число ключей
$X $E watch /registry/configmaps/lab-01-1 --prefix    # поток изменений, выход Ctrl-C
```

В блоке две первые строки собирают переменную `E`, а третья задаёт `X`. Следующие три команды проверяют состояние etcd, а остальные читают ключи и следят за ними. Снимки базы (`snapshot save`) и восстановление разбирает 10-2.

**Команды для скриптов:**

- `endpoint health` завершается с ненулевым кодом, если etcd не отвечает.
- `-w json` печатает ответ в JSON для `jq`; другие форматы — `table`, `fields`, `simple`.
- `--print-value-only` выводит только значение ключа.
- `--command-timeout=10s` ограничивает время команды (по умолчанию 5 с), `--dial-timeout` — время подключения (по умолчанию 2 с).
- Адрес и сертификаты можно задать переменными `ETCDCTL_ENDPOINTS`, `ETCDCTL_CACERT`, `ETCDCTL_CERT`, `ETCDCTL_KEY`.
- `get` несуществующего ключа не считается ошибкой: код 0, вывод пустой.

**Частые ошибки:**

- `context deadline exceeded`: неверный адрес, etcd не запущен или нет кворума.
- `tls: bad certificate` или `x509: certificate signed by unknown authority`: не заданы или перепутаны `--cacert`, `--cert`, `--key`.
- Пустой вывод `get`: опечатка в ключе или забыт `--prefix`.
- `mvcc: required revision has been compacted`: запрошена ревизия, которую etcd уже удалил при компакции (10-2).
- Секреты читаются открытым текстом: etcd по умолчанию не шифрует их, поэтому снимки базы защищают как пароли.

**Установка:** на стенде ничего ставить не нужно, etcdctl уже есть в образе etcd. Для работы с хоста в Ubuntu ставят пакет `etcd-client`, в Manjaro — `etcd` командой `sudo pacman -S etcd`. Версию проверяет `etcdctl version`. Версия клиента в пакете дистрибутива может отличаться от версии etcd в кластере.

### Объект в etcd

Объект читают из etcd вручную через etcdctl. Доступ к базе требует клиентских сертификатов из каталога `/etc/kubernetes/pki/etcd`, а команда запускается внутри пода etcd.

```bash
kubectl -n kube-system exec etcd-lab-control-plane -- etcdctl \
  --endpoints=https://127.0.0.1:2379 --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt --key=/etc/kubernetes/pki/etcd/server.key \
  get /registry/configmaps/lab-01-1/demo -w json
```

| Часть команды | Значение |
|---|---|
| `kubectl exec etcd-lab-control-plane` | выполнить команду внутри пода etcd |
| `--endpoints` | адрес etcd на самом узле |
| `--cacert`, `--cert`, `--key` | сертификаты для TLS |
| `get /registry/…` | прочитать ключ объекта |
| `-w json` | вывести ответ в JSON с ревизиями |

В выводе читают `create_revision`, `mod_revision` и `version` (схема 5). В лабораторных работах сертификаты собраны в переменную `E`, чтобы не повторять их.

### Здоровье компонентов

API-сервер отвечает на проверки `/livez` (жив ли процесс) и `/readyz` (готов ли принимать запросы). Команда `kubectl get --raw /readyz` возвращает `ok`, а с параметром `?verbose` перечисляет отдельные проверки, включая etcd. По этому адресу проверяют балансировщик перед несколькими API-сервер (§6). С 1.36 компоненты по умолчанию отдают и страницы `/statusz` (версия, время работы) и `/flagz` (действующие флаги); функция в стадии beta.

Mirror pod в `kube-system` нельзя считать источником правды: после остановки static pod он может остаться в API со статусом `Completed`. Правду о процессах говорит узел: `crictl ps` показывает реальные контейнеры (00-2).

### Лидеры и аренды

Кто сейчас лидер, показывают объекты Lease в `kube-system`.

```bash
kubectl -n kube-system get lease
```

Результат:


В каждом объекте есть поле `metadata.managedFields`. **Менеджер поля** (field manager) — имя клиента, который записал это поле. Для пода, созданного командой `kubectl run`, менеджеров двое: `kubectl-run` пишет `spec`, а `kubelet` пишет `status` (подробности — 01-3 §4). Временные метки в `status.conditions` показывают, сколько заняли шаги пути (лабораторная работа 2, шаг 3).

## 5. Что ломается и как найти причину

Каждый компонент отвечает за свой шаг пути запроса, и когда он стоит, остальные работают, но цепочка рвётся в предсказуемом месте.

### Что видно при остановке компонента

Таблица ниже собрана по опытам лабораторной работы 3.

| Остановлен | Работающие поды | Новые поды и правки | Что видно |
|---|---|---|---|
| scheduler | работают | создаются, но Pending | нет событий о планировании |
| controller-manager | работают | scale и удаление ничего не меняют | READY 2/4, живой под один |
| API-сервер (или etcd) | работают и отдают трафик | kubectl: connection refused | kubelet сам перезапускает контейнеры |

### Scheduler и controller-manager

Под в Pending без единого события о планировании значит, что scheduler не работает. Если scheduler жив, но места нет, в событиях стоит `FailedScheduling` с причиной по каждому узлу (05-1, 05-3). Mirror pod планировщика при этом может висеть в API как `Completed`, поэтому проверяйте процесс на узле через `crictl ps --name kube-scheduler`.

Когда стоит controller-manager, объекты принимаются, но не исполняются. Deployment получает новое `replicas`, а ReplicaSet нет, и удалённый под не заменяется. Статус Deployment и ReplicaSet остаётся прежним и показывает два готовых пода, хотя жив один. Status — это последний отчёт контроллера, а не правда о кластере.

### Что не работает без API

Работающие поды живут, потому что kubelet, контейнеры и kube-proxy не зависят от API-сервер во время работы. Перестаёт работать всё, что требует решения контроллера.

- Перенос подов с упавшего узла на другой: его делает контроллер, по умолчанию через 300 с.
- Обновление endpoints: новые и упавшие поды не попадают в Service и не уходят из него.
- HPA, Job и CronJob, а также любой деплой и откат.
- Продление токенов ServiceAccount: номинальный срок токена 1 ч, продлевает его kubelet через API. По умолчанию API-сервер выписывает такие токены с запасом до 1 года (`--service-account-extend-token-expiration=true`), поэтому 401 при долгой недоступности API получат только кластеры с выключенным запасом.

### Порядок поиска при недоступном API

Когда `kubectl` не отвечает, идите от клиента к хранилищу.

1. Прочтите текст ошибки: `connection refused` значит, что процесс не слушает порт, таймаут — что виновата сеть или балансировщик. Ответ 5xx говорит, что API-сервер жив, но неисправен.
2. Проверьте `/readyz?verbose` на каждом узле control plane: видно, какая проверка не проходит.
3. На узле выполните `crictl ps -a`; если контейнер API-сервер или etcd в `Exited`, смотрите `crictl logs`.
4. Если etcd не стартует, проверьте диск и кворум (10-2).
5. Если узлы control plane здоровы, проверьте health-check балансировщика: он должен опрашивать `/readyz`.

### Ошибки 409 и 410

Ответ 409 Conflict говорит, что объект изменился после вашего чтения (§3), и исправление — перечитать объект и повторить правку.

Ответ 410 Expired приходит на watch с версии, которой уже нет. Etcd периодически делает **compaction** (уплотнение): удаляет старые ревизии, и по умолчанию API-сервер запрашивает его каждые 5 минут. Клиент обязан сделать новый list и открыть watch заново, и самописные скрипты на `watch` должны это уметь.

## 6. Пределы и значения по умолчанию

Здесь собраны числа, которые определяют время реакции кластера и его границы.

### Выбор лидера

Три параметра контролируют аренду у scheduler и controller-manager.

- `--leader-elect-lease-duration` — 15 с, срок аренды.
- `--leader-elect-renew-deadline` — 10 с, за это время лидер обязан продлить аренду.
- `--leader-elect-retry-period` — 2 с, как часто копии пробуют занять аренду.

Новый экземпляр после рестарта ждёт, пока истечёт аренда прежнего лидера. На стенде controller-manager после возврата навёл порядок за 21 с, из них около 15 с — ожидание аренды. Слишком короткие значения опасны при медленном etcd: лидер не успеет продлить аренду и потеряет её без причины.

### Etcd

Четыре границы etcd важны для эксплуатации.

- События (Events) живут 1 ч, значение `--event-ttl` по умолчанию. На пустом стенде в etcd 838 ключей, из них 402 — события.
- Compaction API-сервер запрашивает каждые 5 минут.
- **Кворум** (quorum) — большинство членов: N/2 с округлением вниз плюс 1. Для 3 членов это 2, для 5 это 3.
- Три члена переживают потерю одного, пять — потерю двух. Четыре не лучше трёх: кворум там тоже 3.
- Размер одного запроса к etcd по умолчанию не больше 1,5 МиБ, поэтому объект API крупнее примерно 1,5 МиБ etcd не примет.
- Квота базы по умолчанию 2 ГиБ, рекомендуемый максимум 8 ГиБ (10-2).

### Нагрузка на API-сервер

Основную нагрузку создают тяжёлые list-запросы и тысячи watch-соединений. Три механизма смягчают её.

- **Watch cache** — кэш объектов в памяти API-сервер. List с `resourceVersion=0` отдаётся из кэша. Обычный list тоже читается из кэша (consistent reads from cache, GA в 1.34): API-сервер только узнаёт у etcd текущую ревизию.
- **Пагинация** — параметры `limit` и `continue` режут большой list на страницы.
- **APF** (§3) отвечает 429 шумным клиентам. Общий предел одновременных запросов — сумма `--max-requests-inflight` (400) и `--max-mutating-requests-inflight` (200), то есть 600; APF делит его между приоритетами.

В 1.37 стал stable устойчивый запуск watch cache: пока кэш не готов, API-сервер отвечает 429 и не перегружает etcd.

### Высокая доступность

В рабочем кластере control plane занимает 3 или 5 узлов. API-сервер не хранит состояние, поэтому работают все экземпляры за балансировщиком с проверкой `/readyz`. Etcd образует кластер Raft с кворумом (см. выше), а scheduler и controller-manager работают по одному активному (§2).

Время реакции на отказ узла задают числа узла, а не control plane. Узел с остановленным kubelet становится NotReady примерно за 50 секунд, а поды с него контроллер выселяет через 300 секунд. Числа и опыт — в 01-2 §6 и лабораторной работе 4.

### Пределы масштаба

Документация Kubernetes называет предельный размер кластера, который проверяют тесты масштабирования. За этими границами кластер работает, но время ответа API и нагрузку на etcd никто не гарантирует.

- **Узлы** — не больше 5000.
- **Поды на узле** — не больше 110, это и значение `maxPods` kubelet по умолчанию.
- **Поды в кластере** — не больше 150 000.
- **Контейнеры в кластере** — не больше 300 000.

В большом кластере события выносят в отдельный экземпляр etcd, потому что их больше всего (лабораторная работа 1, шаг 5).

### Лабораторная работа 1. Объект в etcd и resourceVersion, 409 Conflict

**Цель.** Проследить объект от запроса kubectl до ключа в etcd, связать `resourceVersion` с ревизией etcd и получить 409 Conflict.

**Что понадобится.**

- Стенд 00-1, namespace `lab-01-1`.
- jq на хосте (00-2).
- Доступ `kubectl exec` к поду `etcd-lab-control-plane`; команды etcd только читают.

**Схема опыта.**

```
kubectl apply ──► apiserver ──► etcd:  /registry/configmaps/lab-01-1/demo
                                      create_revision / mod_revision / version
Смотрим: resourceVersion объекта  ==  mod_revision ключа в etcd
Конфликт: replace по устаревшему файлу ──► 409
```

Схема 8. Одно число видно с двух сторон: в объекте API и в ключе etcd.

#### Шаг 1. Что отправляет kubectl

Команды создают файл ConfigMap и дважды применяют его с флагом `-v=6`. **ConfigMap** — объект для конфигурации в виде пар «ключ — значение» (04-1). Перед вторым применением данные в файле изменены.

```bash
cd ~/lab/k8s/01-1
kubectl create configmap demo2 --from-literal=color=blue --dry-run=client -o yaml > cm2.yaml
kubectl apply -f cm2.yaml -v=6 2>&1 | grep '"Response"' | grep configmaps
sed -i 's/blue/red/' cm2.yaml
kubectl apply -f cm2.yaml -v=6 2>&1 | grep '"Response"' | grep configmaps
```

| Часть команды | Значение |
|---|---|
| `create configmap … --dry-run=client -o yaml` | собрать YAML без отправки в кластер |
| `apply -f cm2.yaml -v=6` | применить файл и показать HTTP-запросы |
| `2>&1` | объединить поток ошибок с обычным: kubectl пишет логи в stderr |
| `grep '"Response"'` | оставить строки с ответами сервера |
| `grep configmaps` | убрать запросы за схемой API |
| `sed -i 's/blue/red/'` | изменить значение в файле |

Результат (адреса сокращены):

```
"Response" verb="GET"   url="…/configmaps/demo2"  status="404 Not Found"
"Response" verb="POST"  url="…/configmaps?fieldManager=kubectl-client-side…"  status="201 Created"
"Response" verb="GET"   url="…/configmaps/demo2"  status="200 OK"
"Response" verb="PATCH" url="…/configmaps/demo2?fieldManager=kubectl-client-side…"  status="200 OK"
```

Разбор:

1. Первый `apply`: `GET` вернул 404, объекта нет, и затем `POST` создал его с ответом `201 Created`.
2. Второй `apply`: `GET` вернул 200, kubectl прочитал текущий объект и посчитал разницу.
3. `PATCH` с кодом 200 отправил только разницу, а не весь объект.
4. В адресе `fieldManager=kubectl-client-side-apply` — имя менеджера полей (§4). Client-side и server-side apply разобраны в 01-3 §3.
5. В начале полного вывода kubectl дважды обращается к `/openapi/v3` за схемой для проверки. Мы убрали эти строки командой `grep configmaps`.

| Часть команды | Значение |

#### Шаг 3. Найти тот же объект в etcd

Команды собирают параметры подключения к etcd в переменную `E` и читают ключ объекта, а вторая команда выводит начало значения, чтобы увидеть формат.

```bash
E='etcdctl --endpoints=https://127.0.0.1:2379'
E+=' --cacert=/etc/kubernetes/pki/etcd/ca.crt'
E+=' --cert=/etc/kubernetes/pki/etcd/server.crt'
E+=' --key=/etc/kubernetes/pki/etcd/server.key'
kubectl -n kube-system exec etcd-lab-control-plane -- $E \
  get /registry/configmaps/lab-01-1/demo -w json \
  | jq -c '{rev: .header.revision, create: .kvs[0].create_revision,
            mod: .kvs[0].mod_revision, version: .kvs[0].version}'
kubectl -n kube-system exec etcd-lab-control-plane -- $E \

```

| Часть команды | Значение |
|---|---|
| `E+=' …'` | дописать сертификаты к команде `etcdctl` (карточка — в §4) |
| `exec … -- $E get …` | выполнить `etcdctl` внутри пода etcd |
| `jq -c '{…}'` | собрать из ответа одну строку с четырьмя числами |
| `.header.revision` | текущая ревизия etcd в момент ответа |
| `--print-value-only` | вывести только значение ключа, без имени |
| `od -c \| head -4` | показать первые 64 байта символами |

Результат:

```

0000000   k   8   s  \0  \n 017  \n 002   v   1 022  \t   C   o   n   f
0000020   i   g   M   a   p 022 263 001  \n 241 001  \n 004   d   e   m
```

Разбор:

2. `version` равна 1: ключ записан один раз.
3. `rev` — ревизия всей базы в момент чтения. Она равна 4306, потому что после создания объекта никто больше не писал.
4. Значение начинается с `k 8 s \0`: это префикс формата. Дальше видны имена `v1`, `ConfigMap`, `demo`, `lab-01-1` и начало `uid` — protobuf, а не JSON.

#### Шаг 4. Изменить объект и сравнить ревизии

Команды меняют значение и снова читают версию из API и из etcd.

```bash
kubectl patch cm demo -p '{"data":{"color":"green"}}'
kubectl get cm demo -o jsonpath='rv={.metadata.resourceVersion}{"\n"}'
kubectl -n kube-system exec etcd-lab-control-plane -- $E \
  get /registry/configmaps/lab-01-1/demo -w json | jq -c '.kvs[0] | {mod_revision, version}'
```

| Часть команды | Значение |
|---|---|
| `patch cm demo -p '{…}'` | изменить только поле `data.color` |
| `.kvs[0] \| {mod_revision, version}` | оставить две нужные величины |

Результат:

```
configmap/demo patched
rv=4307
{"mod_revision":4307,"version":2}
```

Разбор:

1. `rv` вырос с 4306 до 4307, `mod_revision` — так же: каждая запись увеличила общий счётчик на единицу.
2. `version` равна 2, потому что ключ записан второй раз; эта величина своя у каждого ключа.
3. Если кластер занят, `rv` растёт быстрее. При повторном прогоне на стенде значение выросло с 5263 до 5265 за одну правку: между ними кто-то записал lease узла или событие.

#### Шаг 5. Посчитать ключи в etcd

#### Шаг 6. Получить 409 Conflict

Команды сохраняют снимок объекта, меняют объект «другим клиентом» и пытаются заменить его по устаревшему снимку.

```bash
cd ~/lab/k8s/01-1
kubectl get cm demo -o yaml > cm-old.yaml
kubectl patch cm demo -p '{"data":{"color":"red"}}'
sed -i 's/color: green/color: yellow/' cm-old.yaml
kubectl replace -f cm-old.yaml
```

| Часть команды | Значение |
|---|---|
| `get cm demo -o yaml > cm-old.yaml` | снимок вместе с `resourceVersion` |
| `patch … red` | «другой клиент» меняет объект после снимка |
| `sed -i …` | правим снимок: green на yellow |
| `replace -f cm-old.yaml` | отправить объект целиком с устаревшей версией |

Результат (сообщение одно, здесь перенесено):

```
Error from server (Conflict): error when replacing "cm-old.yaml": Operation cannot be
fulfilled on configmaps "demo": the object has been modified; please apply your changes
to the latest version and try again
```

Разбор:

1. `Conflict` — код ответа 409.
2. В снимке `resourceVersion` равна 4307, а на сервере объект уже новее, поэтому API-сервер не стал перезаписывать чужую правку.
3. Фраза `apply your changes to the latest version` — инструкция клиенту перечитать и повторить; так делают контроллеры.
4. Команда `patch` в той же ситуации конфликта не даёт: сервер применяет её к свежей версии.

**Итог.**

| Что узнали | Где видно |
|---|---|
| `kubectl apply` — это GET, затем POST или PATCH | шаг 1, `-v=6` |
| `resourceVersion` равна `mod_revision` ключа в etcd | шаг 3 |
| Ревизия общая на весь кластер, `version` своя у ключа | шаг 4 |
| Значение в etcd — protobuf с префиксом `k8s\0` | шаг 3, `od -c` |
| Устаревшая версия объекта даёт 409 | шаг 6 |

**Уборка.**

```bash

rm -f ~/lab/k8s/01-1/cm2.yaml ~/lab/k8s/01-1/cm-old.yaml
```

**Вопросы для самопроверки.**

1. Почему `resourceVersion` объекта выросла на 2, хотя вы изменили его один раз?
2. Что должен сделать клиент, получив 409?
3. Почему `kubectl patch` не получил конфликт, а `kubectl replace` получил?
4. Почему не стоит писать в etcd напрямую, в обход API-сервер?

<details>
<summary>Ответ</summary>

1. Ревизия общая на весь кластер, и между вашей правкой и чтением другие компоненты тоже писали в etcd: lease узла, событие.
2. Перечитать объект, заново применить свою правку к свежей версии и отправить снова.
3. `replace` отправляет объект целиком вместе со старой версией, а `patch` отправляет только разницу, и сервер применяет её к текущей версии.
4. Запись минует аутентификацию, авторизацию, admission и проверку схемы, а остальные компоненты не получат события watch в том виде, как ждут. Поэтому в etcd пишет только API-сервер, а ключи читают для диагностики.

</details>

### Лабораторная работа 2. Watch своими глазами

**Цель.** Прочитать поток событий изменений, получить 410 Expired и измерить, за какое время под проходит путь от создания до Ready.

**Что понадобится.**

- Стенд 00-1, namespace `lab-01-1`, jq на хосте.

- Доступ на чтение к файлу манифеста API-сервер в `lab-control-plane`.

**Схема опыта.**


#### Шаг 1. Прочитать поток событий

Команды создают ConfigMap, запускают watch в фоне с записью в файл и порождают два события. Фоновый процесс завершится сам через 10 с, а его PID записан в файл.

```bash
cd ~/lab/k8s/01-1
kubectl create configmap demo --from-literal=color=blue
RV=$(kubectl get cm demo -o jsonpath='{.metadata.resourceVersion}')
kubectl get --raw \
  "/api/v1/namespaces/lab-01-1/configmaps?watch=1&resourceVersion=$RV&timeoutSeconds=10" \
  > watch.json &
echo $! > watch.pid
sleep 1
kubectl patch cm demo -p '{"data":{"color":"black"}}'
kubectl delete cm demo
wait $(cat watch.pid)
jq -r '"\(.type) \(.object.metadata.name) rv=\(.object.metadata.resourceVersion) \(.object.data)"' \
  watch.json
```

| Часть команды | Значение |
|---|---|
| `RV=$(… resourceVersion)` | запомнить версию, с которой начнётся watch |
| `get --raw "…?watch=1"` | открыть watch прямым запросом к API |
| `resourceVersion=$RV` | присылать события после этой версии |
| `timeoutSeconds=10` | закрыть соединение через 10 с |
| `> watch.json &` | писать поток в файл, работать в фоне |
| `echo $! > watch.pid` | сохранить PID фонового процесса |
| `wait $(cat watch.pid)` | дождаться завершения watch |
| `jq -r '"…"'` | сократить каждое событие до одной строки |

Результат (числа у вас другие, `jq` печатает данные JSON-ом):

```
MODIFIED demo rv=4336 {"color":"black"}
DELETED demo rv=4338 {"color":"black"}
```

Разбор:

1. Событие `ADDED` не пришло: объект был создан до `RV`, watch показывает только то, что произошло после.
2. `MODIFIED` пришло после `patch`, и версия `rv=4336` выше `RV`.
3. `DELETED` пришло после `delete`. Объект в событии содержит последнее значение, а версия `rv=4338` — ревизию удаления.
4. Так работают `kubectl get pods -w` и все контроллеры: они держат открытое соединение и получают события.

### Лабораторная работа 3. Остановка scheduler, controller-manager и API-сервер

**Цель.** Остановить по очереди три компонента control plane и увидеть, какой шаг пути запроса пропадает и что остаётся рабочим.

**Что понадобится.**

- Стенд 00-1 с приложением `orders` (00-1), namespace `lab-01-1`.
- Образ `busybox:1.37`.
- Команда `docker` на хосте и права на `docker exec` в `lab-control-plane`.

**Схема опыта.**

```
lab-control-plane:/etc/kubernetes/manifests/  ──mv──►  /root/     (и обратно)
  kube-scheduler.yaml              шаги 1–2   новые поды Pending
  kube-controller-manager.yaml     шаги 3–4   реплики не меняются, status устарел
  kube-apiserver.yaml              шаги 5–7   нет API, поды и трафик живы
```

Схема 10. Каждый компонент выключается переносом файла и включается возвратом.

**Риски.** Работа выключает компоненты control plane в узле стенда.

- **Что меняется:** внутри контейнера `lab-control-plane` файлы манифестов переносятся из `/etc/kubernetes/manifests` в `/root/` и обратно. Kubelet узла останавливает и запускает static pod. Хост, образы и другие кластеры не затрагиваются.
- **Надолго ли:** пока файл вне каталога, компонент стоит. Каждая остановка занимает несколько минут. Файл сам не вернётся.
- **Безопасность:** привилегий сверх `docker exec` не нужно. Новых портов и учётных данных не появляется.
- **Влияние на систему:** во время шагов 5–6 kubectl не работает, деплой и изменения кластера невозможны. Приложение `orders` продолжает отвечать. Если стендом пользуется кто-то ещё, он увидит отказы. Нагрузка — короткий всплеск CPU при перезапуске трёх процессов.
- **Откат:** вернуть файл командой `mv` (она в каждом шаге «Вернуть…») и проверить, что в каталоге манифестов четыре файла. Уборка делает эту проверку обязательной.


| Часть команды | Значение |
|---|---|
| `SECONDS=0` | обнулить счётчик секунд |
| `until [ … = 4 ]; do sleep 1; done` | опрашивать, пока готовых реплик не станет 4 |
| `get deploy web` | показать итог |
| `echo "прошло ${SECONDS} с"` | вывести затраченное время |

Результат: Deployment показал `web 4/4`, на стенде измерено 21 с с момента возврата файла.

```
прошло 21 с
```

Разбор:

1. Около 15 с из 21 новый экземпляр ждал, пока истечёт аренда прежнего лидера (§6), а остальное ушло на запуск процесса и создание подов.
2. После старта контроллер увидел расхождение «нужно 4, есть 1», обновил ReplicaSet и создал три пода. Так накопленная работа выполнилась разом.
3. Измерьте свой стенд: число зависит от момента остановки относительно продления аренды.

#### Шаг 6. Убить контейнер без API

Команды находят работающий контейнер `busybox` на узлах, убивают его процесс и смотрят, кто его вернёт, пока API недоступен. Запомните имя пода из колонки POD: оно понадобится в шаге 7.

```bash
for W in lab-worker lab-worker2 lab-worker3; do
  C=$(docker exec $W crictl ps --name '^busybox$' -q | head -1)
  [ -n "$C" ] && break
done
echo "$W $C"
PID=$(docker exec $W crictl inspect -o go-template --template '{{.info.pid}}' $C)
docker exec $W kill -9 $PID
sleep 12
docker exec $W crictl ps -a --name '^busybox$'
```

| Часть команды | Значение |
|---|---|
| `for W in … break` | найти первый узел с работающим `busybox` |
| `crictl ps --name '^busybox$' -q` | идентификатор контейнера |
| `crictl inspect … '{{.info.pid}}'` | PID процесса контейнера на узле |
| `kill -9 $PID` | убить процесс сигналом SIGKILL |
| `crictl ps -a` | показать и завершённые контейнеры |

Результат (имя контейнера `busybox` совпадает с образом, так его называет `kubectl create deploy`; ваши идентификаторы другие):

```

03f257e41fa60   30ecbe15090…  11 seconds ago   Running   busybox   1        …  web-78bbb77d7c-p5d9f
0923431263e46   30ecbe15090…  3 minutes ago    Exited    busybox   0        …  web-78bbb77d7c-p5d9f
```

Разбор:

1. Старый контейнер в `Exited` с `ATTEMPT 0`, новый — `Running` с `ATTEMPT 1`.
2. Перезапустил его kubelet без API-сервер: политику перезапуска исполняет узел, а не control plane.
3. Новый контейнер в том же поде (`POD` совпадает): под остался на месте.

#### Шаг 7. Вернуть API-сервер

Команды возвращают манифест, ждут готовности API и несколько раз читают под, контейнер которого вы убили. Задайте `P` именем пода из колонки POD шага 6.

```bash
docker exec lab-control-plane mv /root/kube-apiserver.yaml /etc/kubernetes/manifests/
until kubectl get --raw /readyz >/dev/null 2>&1; do sleep 1; done
P=<имя пода из колонки POD>
for i in 1 2 3; do sleep 10; kubectl get pods --no-headers | grep "$P"; done
```

| Часть команды | Значение |
|---|---|
| `until kubectl get --raw /readyz …` | ждать, пока API-сервер ответит `ok` |
| `P=<…>` | имя пода, чей контейнер убит |
| `for i in 1 2 3; do sleep 10; …` | три чтения с паузой 10 с |

Результат: API-сервер ответил на `/readyz` через 3 с. Сразу после этого под показывал `RESTARTS 0`, через 10 с — `1 (39s ago)`.

Разбор:

1. API вернулся, но status пода сначала старый, потому что kubelet ещё не отправил накопленное.
2. Через 10 с kubelet досылает статусы, и `RESTARTS` становится 1. В API статус пода обновился примерно через 13 с после возврата API-сервер.
3. Всё, что произошло без API, не потерялось: kubelet запомнил это и записал позже.

**Итог.**

| Что узнали | Где видно |
|---|---|
| Без scheduler поды в Pending без событий планирования | шаг 1 |
| Без controller-manager реплики не меняются, status врёт | шаг 3 |
| Новый лидер ждёт истечения аренды: около 15 с из 21 | шаг 4 |
| Без API-сервер приложение работает, а kubectl нет | шаг 5 |
| Контейнер перезапускает kubelet без API | шаг 6 |
| После возврата API status догоняет за секунды | шаг 7 |

**Уборка.** Проверяем, что все четыре манифеста на месте, затем удаляем Deployment, namespace и каталог работы и возвращаем namespace по умолчанию.

```bash
docker exec lab-control-plane ls /etc/kubernetes/manifests
docker exec lab-control-plane ls /root
kubectl get pods -n kube-system -l tier=control-plane
kubectl delete deploy web
kubectl config set-context --current --namespace=default
kubectl delete ns lab-01-1
rm -r ~/lab/k8s/01-1
```

Первая команда должна показать четыре файла: `etcd.yaml`, `kube-apiserver.yaml`, `kube-controller-manager.yaml`, `kube-scheduler.yaml`. Вторая не должна показывать файлов `kube-*.yaml`, потому что их вернули. Третья показывает четыре пода control plane в `Running`. Если файл остался в `/root`, верните его командой `mv` из соответствующего шага, прежде чем продолжать. Удаление namespace может занять около 30 с по той же причине, что в работе 2.

**Вопросы для самопроверки.**

1. Под в Pending, событий нет. Какой компонент не работает и чем это отличается от нехватки места?
2. Почему Deployment показывает `READY 2/4`, хотя жив один под?
3. Почему `curl` к приложению работал при остановленном API-сервер, и что перестало работать?
4. Из чего сложились 21 с до восстановления после возврата controller-manager?
5. Кто перезапустил убитый контейнер, пока API не было?

<details>
<summary>Ответ</summary>

1. Не работает scheduler: он не обработал под. Если бы места не хватало, в событиях была бы запись `FailedScheduling` с причиной по каждому узлу.
2. Status Deployment и ReplicaSet пишет controller-manager, а он остановлен, и последний отчёт устарел.
3. Трафик идёт через Envoy, kube-proxy и поды, а они не зависят от API-сервер. Не работают деплой, масштабирование, перенос подов с упавшего узла, обновление endpoints, HPA, Job.
4. Около 15 с новый экземпляр ждал истечения аренды старого лидера, остальное — запуск процесса и создание подов.
5. Kubelet на узле: перезапуск по `restartPolicy` выполняет узел, а не control plane.

</details>

Мы выяснили, что решения принимает control plane, а исполняет их узел: scheduler пишет в объект `nodeName`, и kubelet по watch узнаёт, что под его. Последний опыт показал, что kubelet работает без API и сам перезапускает контейнеры. Поэтому следующая часть, 01-2, спускается на узел. Она показывает, что делает kubelet от binding до Running, как устроены песочница, CNI и cgroups пода и когда узел без kubelet становится NotReady. Только после этого имеет смысл разбирать сами объекты API (01-3).
