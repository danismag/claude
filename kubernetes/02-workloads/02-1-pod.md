# 02-1. Pod

> Модуль 02 «Workloads» · часть 1 из 5 · ~1,5 ч чтения + ~1 ч лабы · Нужно: стенд 00-1 (контекст `kind-lab`), kubectl из 00-2, доступ узлов к образу `busybox:1.37` · Опирается на: 01-2 (узел и kubelet), 01-3 (API-объекты)

## Где мы на карте

Эта часть открывает модуль 02 и разбирает под — самый маленький объект, который Kubernetes планирует и запускает. Мы проследим, что происходит внутри пода от создания до остановки. Часть опирается на модуль 01: кто принимает объекты (control plane, 01-1), кто запускает контейнеры (kubelet на узле, 01-2) и как устроены объекты API (01-3).

Следующие части строятся на поде: Deployment, StatefulSet, DaemonSet и Job (02-2…02-4) не запускают контейнеры сами, а создают поды по шаблону и заменяют их. Пробы и остановка пода (02-5) продолжают то, что здесь описано как жизненный цикл.

```
Deployment / StatefulSet / DaemonSet / Job     02-2 … 02-4: создают и заменяют поды
                      │
                      ▼
                     Pod                       02-1 (эта часть): что внутри, как живёт и падает
                      │  kubelet просит containerd запустить (01-2)
                      ▼
        init-контейнеры → sidecar → основные контейнеры
```

Схема 1. Место пода в иерархии: контроллеры сверху создают поды, kubelet снизу запускает их контейнеры.

## 1. Какую задачу решает под

Под отвечает на вопрос, как запустить вместе несколько тесно связанных процессов. Разберём, что он объединяет и почему его почти никогда не создают напрямую.

### Контейнеры, которые живут вместе

**Под** (Pod) — наименьшая единица, которую Kubernetes создаёт и планирует: один или несколько контейнеров, всегда работающих на одном узле. **Контейнер** (container) — процесс с собственной файловой системой и ограничениями ядра. Одного контейнера часто мало, потому что приложению нужен прокси рядом, агент для логов или шаг подготовки перед стартом. Такие контейнеры не имеют смысла по отдельности, и под связывает их в одно целое.

Под масштабируют и переносят целиком, поэтому в один под кладут только то, что должно жить и умирать вместе. Фронтенд и бэкенд в один под не кладут: им нужны разное число реплик и разные обновления.

### Что общего внутри пода

Контейнеры пода делят сеть, тома и часть пространств имён ядра, а остальное у каждого своё.

- **Сеть.** У пода один IP-адрес и один **network namespace** — изолированный сетевой стек ядра. Контейнеры видят друг друга по `localhost` и не могут занять один порт.
- **Тома.** **Том** (volume) — каталог, который монтируют в один или несколько контейнеров пода; через общий том контейнеры обмениваются файлами. С 1.36 (GA) источником тома может быть и OCI-образ (image volume): его файлы монтируются только для чтения (04-2).
- **IPC** (inter-process communication, межпроцессное взаимодействие). Разделяемая память и семафоры общие.
- **PID.** По умолчанию процессы раздельные, а флаг `shareProcessNamespace: true` делает их общими.
- **Пользователи.** **User namespace** — пространство имён ядра, которое отображает uid и gid процессов на другие uid и gid узла. По умолчанию под работает в user namespace узла, а поле `hostUsers: false` (GA в 1.36) даёт поду свой (06-2).
- **Файловая система образа.** У каждого контейнера своя.

```
                      Pod  (один IP, один узел)
   ┌────────────────────────────────────────────────────────────┐
   │  песочница (pause) держит network namespace и IPC          │
   │   ┌───────────────┐   localhost   ┌───────────────┐        │
   │   │  контейнер A  │◄─────────────►│  контейнер B  │        │
   │   │  своя ФС      │               │  своя ФС      │        │
   │   └───────┬───────┘               └───────┬───────┘        │
   │           └────────── общий том ──────────┘                │
   └────────────────────────────────────────────────────────────┘
```

Схема 2. Общее (сеть, том, IPC) показано связями, своё (файловая система) — рамками контейнеров.

Перед контейнерами kubelet создаёт **песочницу** (pod sandbox) — пустой контейнер `pause`, который держит network namespace, пока живёт под. Когда песочница и сеть готовы, под получает условие `PodReadyToStartContainers` (§2).

### Почему голый под не используют

Под, который создали напрямую, никто не охраняет: если узел пропал, под исчезает вместе с ним, а удалённый под никто не вернёт. kubelet перезапускает упавшие контейнеры, но только на том же узле и в том же поде.

Поэтому поды создают контроллеры (02-2…02-4): они держат нужное число копий и заменяют потерянные. Голые поды нужны только для опытов, отладки и разовых задач.

## 2. Как устроен жизненный цикл пода

Состояние пода описывают три слоя: фаза всего пода, состояния отдельных контейнеров и условия готовности. Поверх этих слоёв работают порядок запуска и правила перезапуска.

### Фазы пода

**Фаза** (phase) — грубая сводка о положении пода в поле `status.phase`; всего фаз пять.

- **Pending** — API принял под, но не все контейнеры запущены. Под ждёт **scheduler** (компонент, который выбирает узел для пода, 01-1), загрузки образа, томов или init-контейнеров.
- **Running** — под назначен на узел, все контейнеры созданы, и хотя бы один работает, стартует или перезапускается.
- **Succeeded** — все контейнеры завершились с кодом 0 и больше не запустятся.
- **Failed** — все контейнеры завершились, и хотя бы один — с ошибкой; так же отмечают выселенный под.
- **Unknown** — состояние не получить, обычно нет связи с узлом.

```
 создан ──► Pending ──► Running ──┬──► Succeeded   все контейнеры вышли с кодом 0
                │                 └──► Failed      вышли все, хотя бы один с кодом ≠ 0
                └──────────────────────► Failed     под выселен или не может стартовать
                                Unknown: узел не отвечает (фазу не определить)
```

Схема 3. Переходы фаз: фаза не откатывается, и из Succeeded и Failed под уже не выходит.

### Состояния контейнера

У каждого контейнера есть своё **состояние** (container state) в поле `status.containerStatuses`; состояний три.

- **waiting** — контейнер ещё не работает. Причина в `reason`: `ContainerCreating`, `PodInitializing`, `ErrImagePull`, `ImagePullBackOff`, `CreateContainerConfigError`, `CrashLoopBackOff`.
- **running** — процесс запущен, есть время `startedAt`.
- **terminated** — процесс завершён. Есть `exitCode`, `reason` (`Completed`, `Error`, `OOMKilled`, `StartError`) и время `finishedAt`.

Поле `lastState` хранит состояние предыдущего запуска, поэтому `OOMKilled` остаётся именно там, когда контейнер уже перезапущен (05-1).

```
        ┌────────────────────────────────────────────┐
        │  перезапуск по restartPolicy (после паузы) │
        ▼                                            │
    waiting ──────► running ──────► terminated ──────┘
  (образ, конфиг,   (есть          (exitCode, reason;
   пауза back-off)   startedAt)     в lastState после перезапуска)
```

Схема 4. Состояния одного контейнера; колонка STATUS в `kubectl get pods` показывает `reason` самого «важного» из них.

### Условия пода

**Условия** (conditions) — список шагов готовности в поле `status.conditions`, где у каждого условия есть статус `True` или `False` и время последнего изменения.

```
PodScheduled  →  PodReadyToStartContainers  →  Initialized  →  ContainersReady  →  Ready
 узел выбран      песочница и сеть готовы        init выполнены    контейнеры         под в
                                                                   готовы             endpoints
```

Схема 5. Порядок условий: последнее, `Ready`, включает под в список адресов Service.

**Service** — стабильный адрес для набора подов (03-2), который отправляет трафик только на поды с `Ready=True`. Условие `ContainersReady` зависит от **проб** (probes) — периодических проверок контейнера, которые делает kubelet (02-5). Разрыв между временем `PodReadyToStartContainers` и `Initialized` показывает, сколько работали init-контейнеры.

### Порядок запуска и остановки

kubelet запускает контейнеры в строгом порядке: сначала по очереди идут init-контейнеры, затем все основные стартуют вместе. Нативные sidecar-контейнеры (§3) стоят в очереди init-контейнеров, но kubelet не ждёт их завершения, поэтому они не блокируют очередь надолго. Остановка идёт в обратном порядке.

```
запуск:    init-1 ─► init-2 ─► sidecar ─► (все основные контейнеры вместе)
остановка: (все основные контейнеры) ─► sidecar ─► … в обратном порядке
```

Схема 6. Запуск идёт слева направо, остановка — в обратном порядке; подробности остановки — 02-5.

### Перезапуск и back-off

**restartPolicy** — поле пода, которое решает, перезапускать ли завершённые контейнеры; обычно значение одно на весь под. С 1.35 (beta, функция `ContainerRestartRules`) его можно переопределить для отдельного контейнера, но в курсе мы этим не пользуемся.

Значений у поля три, и каждое подходит своим контроллерам.

| restartPolicy | Перезапуск | Где применяется |
|---|---|---|
| `Always` (по умолчанию) | всегда | Deployment, StatefulSet, DaemonSet |
| `OnFailure` | при коде не 0 | Job |
| `Never` | никогда | Job, одноразовые поды |

**Job** — контроллер, который запускает под до успешного завершения (02-4).

Перезапуск делает kubelet на том же узле и в том же поде, а между попытками выдерживает растущую паузу — **back-off**. Пока идёт пауза, STATUS равен `CrashLoopBackOff`: это не отдельная ошибка, а сообщение «контейнер падает, жду».

```
запуск 1 ─ падение ─ пауза 10 с ─ запуск 2 ─ падение ─ пауза 20 с ─ запуск 3 ─ …
          паузы: 10 → 20 → 40 → 80 → 160 → 300 с (потолок)
          если контейнер проработал 10 минут без падений — счёт паузы сбрасывается
```

Схема 7. Back-off: пауза удваивается от 10 с до потолка в 300 с. Числа — из документации Kubernetes (Pod Lifecycle).

## 3. Как управлять контейнерами пода

Состав пода задают списки контейнеров в манифесте: кроме основных, есть init-контейнеры, нативные sidecar и отладочные контейнеры. Отдельно разберём, что под знает о себе и что в нём можно менять на ходу.

### Init-контейнеры

**Init-контейнер** (init container) — контейнер из списка `initContainers`, который выполняется до основных и должен завершиться с кодом 0. Init-контейнеры идут по очереди, и следующий стартует только после успеха предыдущего. Пока init не закончился, STATUS пода показывает прогресс вида `Init:0/1`, и под не попадает в Service.

Если init упал, kubelet перезапускает его по `restartPolicy` пода, для `Always` — с back-off, и статус становится `Init:CrashLoopBackOff`. При `restartPolicy: Never` упавший init делает весь под `Failed`.

Init нужен для разовой подготовки: применить миграции базы, скачать сертификат или клонировать репозиторий, выставить права на том, изменить `sysctl`. Клонирование в init заменяет том `gitRepo`, который в 1.36 отключён окончательно. Ожидание зависимости тоже делают в init, но это слабая защита: init ждёт только при старте, а потом зависимость может пропасть. Поэтому приложение должно уметь переподключаться само.

```yaml
initContainers:
- name: wait-db
  image: busybox:1.37
  command: ["sh", "-c", "until nc -z -w 1 db 5432; do sleep 2; done"]
```

Фрагмент манифеста: init крутит проверку порта, пока `nc` не вернёт успех; рабочий пример — в лабораторной работе 1.

### Нативные sidecar-контейнеры

**Sidecar** — вспомогательный контейнер, который должен работать всё время рядом с основным: прокси сервисной сетки, агент логов, обновление сертификатов. Раньше его клали вторым в список `containers`, и у такого способа три недостатка.

- Нет порядка запуска: приложение может стартовать раньше прокси и остаться без сети.
- Нет порядка остановки: прокси может умереть, пока приложение ещё отвечает.
- Job не завершается: основной контейнер закончил работу, а sidecar живёт бесконечно.

**Нативный sidecar** (native sidecar) — init-контейнер с `restartPolicy: Always`. Функция включена по умолчанию с 1.29 (beta) и стала stable в 1.33, поэтому на кластере стенда версии 1.36 она доступна.

```yaml
initContainers:
- name: log-shipper
  image: busybox:1.37
  restartPolicy: Always        # эта строка делает init-контейнер sidecar'ом
containers:
- name: main
  image: busybox:1.37
```

Фрагмент манифеста: единственное отличие от обычного init — строка `restartPolicy: Always` на уровне контейнера.

У нативного sidecar четыре свойства:

1. Он стартует в порядке init-контейнеров, но kubelet не ждёт его завершения.
2. Следующий контейнер стартует, как только sidecar запущен. Если у sidecar есть `startupProbe`, kubelet сначала ждёт её успеха, а `readinessProbe` старт следующего контейнера не задерживает.
3. Он работает всё время жизни пода и перезапускается при падении.
4. При остановке пода он завершается после основных контейнеров и не мешает Job закончиться. Несколько sidecar останавливаются в порядке, обратном списку.

```
 старый способ (в containers)         нативный (в initContainers + Always)
 ────────────────────────────         ─────────────────────────────────────
 main ─────────────┐ вышел            sidecar ═══════════════════╗ остановлен
 sidecar ══════════╪═══► работает     main ──────────┐ вышел     ║ после main
                   ▼     вечно                       ▼           ▼
        Job: Running навсегда                 Job: Complete
```

Схема 8. Судьба Job'а с sidecar: старый sidecar держит под живым, нативный останавливается после основного контейнера.

### Downward API

**Downward API** — механизм, которым под узнаёт о себе без запросов к API-серверу: данные приходят через переменные окружения или файлы тома. Права доступа к API (RBAC) и токен не нужны, поэтому API-сервер не нагружается, а механизм работает, даже когда API недоступен.

```yaml
env:
- name: MY_POD
  valueFrom: {fieldRef: {fieldPath: metadata.name}}
- name: MY_MEM_LIMIT
  valueFrom: {resourceFieldRef: {resource: limits.memory}}
volumes:
- name: podinfo
  downwardAPI:
    items: [{path: labels, fieldRef: {fieldPath: metadata.labels}}]
```

Фрагмент манифеста: `fieldRef` берёт поле самого пода (имя, узел, IP, метки), а `resourceFieldRef` — запрос или лимит контейнера.

Применение простое: имя пода идёт в логи и трейсы, лимит памяти задаёт размер heap у JVM, а запрос CPU подсказывает число воркеров.

Два пути доставки ведут себя по-разному. Переменные окружения фиксируются при старте контейнера и больше не меняются, а файлы тома с метками и аннотациями kubelet обновляет на лету.

### Ephemeral-контейнеры

**Ephemeral-контейнер** (ephemeral container) — временный отладочный контейнер, который добавляют в уже работающий под командой `kubectl debug -it <pod> --image=busybox:1.37 --target=<контейнер>`. У него не может быть портов, проб и ресурсов, а изменить или удалить его нельзя: он живёт до пересоздания пода. Подробно и с практикой — 00-2 §5 и лабораторная работа 3 в 00-2.

### Что можно менять в живом поде

Спецификация пода почти неизменяема: метки и аннотации в `metadata` менять можно, а в `spec` API разрешает только такие правки:

- `image` основных и init-контейнеров;
- `activeDeadlineSeconds` — задать или уменьшить;
- `terminationGracePeriodSeconds`;
- `tolerations` — только добавить новые;
- `schedulingGates` — только убрать.

Остальные правки требуют пересоздания пода. Исключение — ресурсы контейнеров: их меняют через отдельный **подресурс** (subresource) `resize` — дополнительную точку API у объекта. Изменение ресурсов на месте стало stable в 1.35, практика — 05-1.

Смена образа основного контейнера перезапускает только этот контейнер, а сам под остаётся на месте. Deployment при обновлении так не делает: он создаёт новые поды, а не правит старые (02-2).

## 4. Как увидеть состояние пода

Состояние пода видно на трёх уровнях подробности: краткая колонка в списке, сводка `describe` и сырые поля объекта. Отдельно разберём коды выхода и сообщение о завершении.

### Колонка STATUS

Колонка `STATUS` в `kubectl get pods` показывает не фазу, а `reason` самого заметного состояния контейнера; для init-контейнеров это прогресс вида `Init:1/2`. Под в фазе `Running` может показывать `CrashLoopBackOff`, а в фазе `Pending` — `ImagePullBackOff`. Поэтому слово из STATUS всегда сверяют с полями `containerStatuses`.

### describe и события

Команда `kubectl describe pod <имя>` собирает в один вывод всё нужное. Блок `State` показывает текущее состояние контейнера, `Last State` — предыдущее, с `Exit Code`, `Reason` и `Message`. Внизу идёт список **событий** (events) — записей компонентов о том, что они делали с подом: `Scheduled`, `Pulling`, `Failed`, `BackOff`. API-сервер хранит события 1 ч (флаг `--event-ttl`, значение по умолчанию), поэтому смотреть их нужно сразу.

### Точная выборка через jsonpath

Если нужны конкретные поля, берут сырой объект: `kubectl get pod <имя> -o yaml` или `-o jsonpath=…`. **JSONPath** — язык шаблонов, которым kubectl выбирает поля из объекта; в поде нужны такие места:

- `status.phase` — фаза пода.
- `status.conditions` — условия с временем.
- `status.containerStatuses[*].state` и `.lastState` — состояния основных контейнеров.
- `status.initContainerStatuses[*]` — то же для init и sidecar.

### Коды выхода

**Код выхода** (exit code) — число, с которым процесс завершился. **Сигнал** (signal) — уведомление ядра процессу: SIGTERM просит завершиться, SIGKILL убивает без возможности отказаться. Если процесс убит сигналом, код равен 128 плюс номер сигнала. Первые четыре строки таблицы проверяет лабораторная работа 2, остальные разобраны в 05-1 и 02-5.

| Команда | exitCode | reason | Смысл |
|---|---|---|---|
| `exit 0` | 0 | `Completed` | нормальное завершение |
| `exit 3` | 3 | `Error` | код приложения |
| `sh -c nosuchcmd` | 127 | `Error` | shell не нашёл команду |
| `command: ["/nonexistent"]` | 128 | `StartError` | runtime не запустил процесс |
| нехватка памяти | 137 | `OOMKilled` | SIGKILL от OOM killer (05-1) |
| не успел за grace period | 137 | `Error` | SIGKILL после тайм-аута (02-5) |
| завершён сигналом SIGTERM | 143 | `Error` | 128 + 15 |

**OOM killer** — механизм ядра, который убивает процесс при нехватке памяти в **cgroup** (control group) — группе процессов с общими лимитами ресурсов (01-2). **Grace period** — время между SIGTERM и SIGKILL при остановке, по умолчанию 30 с. Код 137 без `OOMKilled` почти всегда значит «не завершился вовремя» или «убит liveness-пробой». Код 143 бывает не всегда: процесс с PID 1 без обработчика SIGTERM игнорирует этот сигнал.

Код 126 — файл найден, но не исполняется: права, формат, архитектура. Разница между 127 и 128 важна. При 127 контейнер запустился (это был shell) и не нашёл команду. При 128 он не запустился вовсе, а причина лежит в `state.terminated.message`.

### Сообщение о завершении

Иногда контейнер падает сразу, и `kubectl logs --previous` пуст или недоступен. Тогда помогает **сообщение о завершении** (termination message). Это текст, который kubelet читает из файла `terminationMessagePath`, по умолчанию `/dev/termination-log`. Приложение пишет туда причину перед выходом, а kubelet кладёт её в `state.terminated.message`.

Политика `terminationMessagePolicy: FallbackToLogsOnError` добавляет запасной путь. Если файл пуст и код выхода не 0, kubelet берёт хвост лога контейнера — не больше 2048 байт или 80 строк, что меньше. Сообщение видно в `describe` и после ротации логов. Для своих сервисов эту политику стоит включать всегда: она ничего не стоит.

## 5. Что ломается и как найти причину

Поломки пода делятся по моменту: до запуска процесса, после запуска, в init-контейнере и при завершении Job. Для каждого класса свой порядок поиска.

### Ошибки до запуска процесса

Часть ошибок случается до старта процесса: kubelet не может подготовить контейнер. Логов у такого контейнера нет, причину ищут в `describe` и событиях.

| STATUS | Типичное сообщение | Причина |
|---|---|---|
| `CreateContainerConfigError` | `couldn't find key … in Secret` | нет Secret, ConfigMap или ключа |
| `ImagePullBackOff` | `ErrImagePull … not found` | нет тега, нет доступа, неверный реестр |
| `ContainerCreating` долго | `FailedMount`, `FailedCreatePodSandBox` | том не смонтирован или сетевой плагин не дал IP |
| `Pending` без узла | `FailedScheduling` | не хватает ресурсов, taints, affinity, PVC |

**Secret** хранит чувствительные данные, **ConfigMap** — обычную конфигурацию (04-1); контейнер берёт из них переменные и файлы. При `CreateContainerConfigError` под ждёт и чинится сам: kubelet повторяет создание контейнера, как только нужный ключ появился. Для `ImagePullBackOff` проверяют имя и тег, реестр, `imagePullSecrets` (коды `401`/`403`) и лимиты реестра (`429`). Томами занимается 04-2, сетью пода — 03-1, планированием — 05-3. Методика целиком — 11-2.

### Падение после запуска

Если процесс стартовал и упал, смотрят код выхода и `Last State`. Дальше порядок такой:

1. Код и `reason` из `lastState` — таблица кодов выше.
2. `kubectl logs <под> --previous` — лог упавшего запуска.
3. `message` из `state.terminated` — файл `termination-log` или хвост лога.
4. События пода — `BackOff`, `Killing`, `Unhealthy`.
5. Если логов нет вовсе, копия пода с командой `sleep` и ручной запуск (`kubectl debug --copy-to`).

### Зависший init

Под в `Init:0/1` значит, что init-контейнер ещё не завершился. Ищут причину в его логах: `kubectl logs <под> -c <имя init>`. Если init ждёт зависимость, лог показывает, чего именно. Если статус `Init:CrashLoopBackOff`, init падает, и работает тот же порядок, что для обычного контейнера. Основной контейнер при этом не запускается и логов не имеет.

### Job, который не завершается

Симптом: основной контейнер вышел с кодом 0, а под показывает `NotReady`, Job остаётся `Running` часами. Причина — sidecar в списке `containers`: Job ждёт завершения всех контейнеров. Исправление — перевести sidecar в нативный (§3). Страховка от зависших Job'ов — `activeDeadlineSeconds` и `ttlSecondsAfterFinished` (02-4). Опыт — лабораторная работа 3.

## 6. Пределы и значения по умолчанию

Ниже собраны числа, которые встречались в части. Значения взяты из документации Kubernetes для версии стенда 1.36.

### Перезапуск и back-off

- `restartPolicy` — `Always`, если не указано другое.
- Пауза между перезапусками — 10 с, затем удвоение до потолка 300 с.
- Потолок с 1.35 (beta) настраивается в конфигурации kubelet: поле `crashLoopBackOff.maxContainerRestartPeriod`, от 1 до 300 с.
- Сброс счётчика — после 10 минут работы без падений.
- Перезапуск идёт только на том же узле.

### Размеры сообщения о завершении

- Файл `terminationMessagePath` — по умолчанию `/dev/termination-log`.
- Сообщение одного контейнера — не больше 4096 байт.
- Сумма сообщений всех контейнеров пода — не больше 12 КиБ; лимит делится поровну между контейнерами.
- Запасной хвост лога при `FallbackToLogsOnError` — не больше 2048 байт или 80 строк.

### Ресурсы пода с init и sidecar

Планировщик считает эффективный запрос пода как большее из двух чисел. Первое — наибольший запрос среди обычных init-контейнеров; к запросу каждого прибавляются запросы sidecar, запущенных до него. Второе — сумма запросов основных контейнеров и всех sidecar. Так же считается эффективный лимит. Поэтому тяжёлый init-контейнер с запросом 4 CPU делает «дорогим» весь под при планировании, хотя работает секунды. Лимиты и запросы подробно — 05-1.

### Лабораторная работа 1. Init-контейнер и условия пода

**Цель.** Увидеть, как init-контейнер блокирует запуск основного, и прочитать условия пода по порядку.

**Что понадобится.** Стенд 00-1, namespace `lab-02-1`, образ `busybox:1.37`.

**Схема опыта.**

```
Pod wait-db                                       Pod db + Service db
┌──────────────────────────────┐                 ┌────────────────────┐
│ init: wait-db ── nc db 5432 ─┼── пока имени нет │ nc слушает 5432    │
│ app:  ждёт своей очереди     │   ошибка         └────────────────────┘
└──────────────────────────────┘
```

Схема 9. Пока Service `db` не существует, init повторяет проверку, и контейнер `app` не стартует.

#### Шаг 1. Создать под, которому нечего ждать

Команда создаёт под с init-контейнером, который ждёт TCP-порт `db:5432`, и показывает статус и лог.

```bash
kubectl apply -f - <<'EOF'
apiVersion: v1
kind: Pod
metadata: {name: wait-db}
spec:
  initContainers:
  - name: wait-db
    image: busybox:1.37
    command:
    - sh
    - -c
    - |
      until nc -z -w 1 db 5432; do echo waiting for db; sleep 2; done
      echo db is up
  containers:
  - name: app
    image: busybox:1.37
    command: ["sh", "-c", "echo app started; sleep infinity"]
EOF
sleep 10
kubectl get pod wait-db
kubectl logs wait-db -c wait-db --tail=2
```

| Часть команды | Значение |
|---|---|
| `initContainers` | список контейнеров, которые выполняются до основных |
| `nc -z -w 1 db 5432` | проверить порт без передачи данных, ожидание 1 с |
| `until … do … done` | повторять цикл, пока проверка не вернёт успех |
| `sleep infinity` | основной контейнер остаётся работать |
| `logs -c wait-db` | лог init-контейнера, а не основного |
| `--tail=2` | последние две строки лога |

Результат:

```
NAME      READY   STATUS     RESTARTS   AGE
wait-db   0/1     Init:0/1   0          12s
nc: bad address 'db'
waiting for db
```

Разбор:

1. `Init:0/1` — выполнено ноль init-контейнеров из одного. Основной контейнер ещё не создан.
2. `0/1` в READY — основных контейнеров готово ноль из одного.
3. `nc: bad address 'db'` — имя `db` не разрешается: такого Service ещё нет.
4. `waiting for db` — цикл повторяет проверку каждые 2 с.

Команда запускает под-«базу» с `nc` на порту 5432 и публикует его как Service `db`. Затем ждёт готовности `wait-db`.

### Лабораторная работа 2. Почему контейнер не работает

**Цель.** Прочитать код выхода, сообщение о завершении и сообщения об ошибках до запуска процесса.

**Что понадобится.** Namespace `lab-02-1`, образ `busybox:1.37`, реестр стенда `localhost:5001` (для шага 3).

**Схема опыта.**

```
Шаг 1: Pod exits (Never)   ok / fail / notfound / noexec ─► exitCode и reason
Шаг 2: msg-file, msg-logs  причина падения без kubectl logs ─► state.terminated.message

```

#### Шаг 1. Коды выхода

Команда создаёт под из четырёх контейнеров с разными командами и читает код и причину каждого.

```bash
kubectl apply -f - <<'EOF'
apiVersion: v1
kind: Pod
metadata: {name: exits}
spec:
  restartPolicy: Never
  containers:
  - {name: ok,       image: busybox:1.37, command: ["sh", "-c", "exit 0"]}
  - {name: fail,     image: busybox:1.37, command: ["sh", "-c", "exit 3"]}
  - {name: notfound, image: busybox:1.37, command: ["sh", "-c", "nosuchcmd"]}
  - {name: noexec,   image: busybox:1.37, command: ["/nonexistent"]}
EOF
sleep 10
T='{range .status.containerStatuses[*]}'
T+='{.name}: exit={.state.terminated.exitCode} '
T+='reason={.state.terminated.reason}{"\n"}{end}phase={.status.phase}{"\n"}'
kubectl get pod exits -o jsonpath="$T"
```

| Часть команды | Значение |
|---|---|
| `restartPolicy: Never` | не перезапускать контейнеры, чтобы увидеть первый исход |
| `exit 3` | завершиться с кодом 3 |
| `nosuchcmd` | команды нет: shell вернёт 127 |
| `/nonexistent` | файла нет: runtime не сможет запустить процесс |
| `containerStatuses[*]` | статусы всех основных контейнеров |
| `phase={.status.phase}` | фаза всего пода в конце вывода |

Результат:

```

notfound: exit=127 reason=Error

```

Разбор:

1. `fail` — код приложения 3, причина просто `Error`.
2. `noexec` — 128 и `StartError`: процесс не запустился, детали лежат в `message`.
3. `notfound` — 127: shell запустился и не нашёл команду.
4. `ok` — 0 и `Completed`.
5. `phase=Failed` — один контейнер вышел с ошибкой, и фаза всего пода `Failed`, хотя `ok` завершился успешно.
6. Порядок строк алфавитный: статусы выводятся не в порядке манифеста.

|---|---|
| `?(@.name=="noexec")` | выбрать из списка контейнер с этим именем |
| `.state.terminated.message` | текст ошибки, который записал runtime |

Результат (одна строка, здесь сокращена и перенесена):

#### Шаг 2. Сообщение о завершении

Команда создаёт два пода. Первый пишет причину в `/dev/termination-log`, второй пишет только в stderr, но включает `FallbackToLogsOnError`.

```bash
kubectl apply -f - <<'EOF'
apiVersion: v1
kind: Pod
metadata: {name: msg-file}
spec:
  restartPolicy: Never
  containers:
  - name: app
    image: busybox:1.37
    command:
    - sh
    - -c
    - echo 'config /etc/app.yaml not found' > /dev/termination-log; exit 2
---
apiVersion: v1
kind: Pod
metadata: {name: msg-logs}
spec:
  restartPolicy: Never
  containers:
  - name: app
    image: busybox:1.37
    terminationMessagePolicy: FallbackToLogsOnError
    command: ["sh", "-c", "echo 'panic: cannot connect to db:5432' >&2; exit 1"]
EOF
sleep 15
kubectl get pods msg-file msg-logs
T='exit={.status.containerStatuses[0].state.terminated.exitCode} '
T+='message={.status.containerStatuses[0].state.terminated.message}{"\n"}'
for p in msg-file msg-logs; do echo -n "$p: "; kubectl get pod $p -o jsonpath="$T"; done
kubectl logs msg-file
```

| Часть команды | Значение |
|---|---|
| `> /dev/termination-log` | записать причину в файл сообщения |
| `terminationMessagePolicy: FallbackToLogsOnError` | при пустом файле и коде не 0 взять хвост лога |
| `>&2` | писать в stderr, а не в файл сообщения |
| `containerStatuses[0]` | первый контейнер пода |
| `kubectl logs msg-file` | обычный лог первого пода |

Результат:

```
NAME       READY   STATUS   RESTARTS   AGE
msg-file   0/1     Error    0          15s
msg-logs   0/1     Error    0          15s
msg-file: exit=2 message=config /etc/app.yaml not found
msg-logs: exit=1 message=panic: cannot connect to db:5432
```

Команда `kubectl logs msg-file` ничего не печатает: приложение не писало в stdout.

Разбор:

1. Оба пода в STATUS `Error`: код не 0, перезапуска нет.
2. `msg-file` — сообщение пришло из файла `/dev/termination-log`.
3. `msg-logs` — файл пуст, поэтому kubelet взял строку из stderr.
4. Лог `msg-file` пуст, но причина падения всё равно видна — через `message`.

#### Шаг 3. Ошибки до запуска процесса

Команда создаёт Secret без нужного ключа и два пода: один ссылается на отсутствующий ключ, второй — на отсутствующий тег образа.

```bash
kubectl create secret generic app --from-literal=user=orders
kubectl apply -f - <<'EOF'
apiVersion: v1
kind: Pod
metadata: {name: bad-secret}
spec:
  containers:
  - name: app
    image: busybox:1.37
    command: ["sleep", "infinity"]
    env:
    - name: DB_PASSWORD
      valueFrom: {secretKeyRef: {name: app, key: password}}
---
apiVersion: v1
kind: Pod
metadata: {name: bad-image}
spec:
  containers:
  - name: app
    image: localhost:5001/orders-api:9.9
    command: ["sleep", "infinity"]
EOF
sleep 15
kubectl get pods bad-secret bad-image
kubectl get pod bad-secret -o jsonpath='{.status.containerStatuses[0].state.waiting}{"\n"}'
kubectl get pod bad-image -o jsonpath='{.status.containerStatuses[0].state.waiting}{"\n"}'
```

| Часть команды | Значение |
|---|---|
| `--from-literal=user=orders` | Secret с единственным ключом `user` |
| `secretKeyRef … key: password` | взять переменную из ключа `password`, которого нет |
| `orders-api:9.9` | тег, которого нет в реестре стенда |
| `state.waiting` | поле состояния ожидания: `reason` и `message` |

Результат:

```
NAME         READY   STATUS                       RESTARTS   AGE
bad-secret   0/1     CreateContainerConfigError   0          15s
bad-image    0/1     ImagePullBackOff             0          15s
```

Сообщения о состоянии ожидания (каждое — одна строка, здесь перенесены и сокращены):

```
{"message":"couldn't find key password in Secret lab-02-1/app",
 "reason":"CreateContainerConfigError"}
{"message":"Back-off pulling image \"localhost:5001/orders-api:9.9\": ErrImagePull:
 rpc error: code = NotFound desc = failed to pull and unpack image … : not found",
 "reason":"ImagePullBackOff"}
```

Разбор:

1. `CreateContainerConfigError` — в сообщении названы Secret и ключ, которых нет.
2. `ImagePullBackOff` — kubelet после неудачи (`ErrImagePull`) повторяет загрузку с растущей паузой.
3. `NotFound … not found` — реестр отвечает, но такого тега нет. Если бы реестр был недоступен, в сообщении стояла бы ошибка соединения.
4. Логов у обоих подов нет: контейнер не создан. Причину ищут в `describe` и `state.waiting`.

Чиним `bad-secret`, не пересоздавая под: добавляем недостающий ключ.

```bash
kubectl patch secret app -p '{"stringData":{"password":"s3cret"}}'
sleep 5
kubectl get pod bad-secret
```

| Часть команды | Значение |
|---|---|
| `patch secret app` | изменить существующий Secret |
| `stringData` | ключи в открытом виде, API сам закодирует их |
| `kubectl get pod bad-secret` | проверить состояние пода |

Результат: STATUS меняется на `Running`. На стенде статус сменился примерно через 2 с после патча.

Разбор: kubelet сам повторил создание контейнера, как только ключ появился. Под пересоздавать не пришлось.

**Итог.**

| Что узнали | Где видно |
|---|---|
| Код 127 и 128 различаются по тому, запустился ли контейнер | шаг 1, `notfound` и `noexec` |
| Один упавший контейнер делает фазу пода `Failed` | шаг 1, `phase=Failed` |
| Причину падения можно получить без логов | шаг 2, `message` |
| Ошибки конфигурации и образа читаются из `state.waiting` | шаг 3 |
| `CreateContainerConfigError` чинится без пересоздания пода | шаг 3, patch |

**Уборка.**

```bash
kubectl delete pod exits msg-file msg-logs bad-secret bad-image
kubectl delete secret app
```

**Вопросы для самопроверки.**

1. Почему фаза пода `exits` равна `Failed`, хотя контейнер `ok` завершился с кодом 0?
2. В каком случае у пода с `restartPolicy: Always` вы увидите `CrashLoopBackOff` вместо `Error`?
3. Куда смотреть при `ImagePullBackOff` в первую очередь: в логи или в `describe`?

<details>
<summary>Ответы</summary>

1. Фаза `Failed` ставится, когда завершились все контейнеры и хотя бы один с ошибкой. Успех остальных контейнеров этого не меняет: достаточно одного кода не 0.
2. Когда контейнер падает снова и снова: после первого падения kubelet ждёт паузу (10 с, затем 20 с и т. д.), и в эти паузы STATUS равен `CrashLoopBackOff`. При `Never` перезапуска нет, поэтому остаётся `Error`.
3. В `describe` и в `state.waiting.message`. Логов нет, потому что контейнер не создан.

</details>

### Лабораторная работа 3. Sidecar: старый и нативный способ

**Цель.** Убедиться, что Job со старым sidecar не завершается, а с нативным — завершается, и увидеть остановку sidecar после основного контейнера.

**Что понадобится.** Namespace `lab-02-1`, образ `busybox:1.37`.

**Схема опыта.**

```
Job old-sidecar:     containers: main(3 с) + log-shipper(вечный)   ─► Running навсегда
Job native-sidecar:  initContainers: log-shipper(Always)
                     containers:     main(3 с)                     ─► Complete
```

Схема 11. Две Job'ы с одинаковой работой в 3 секунды; отличается только место sidecar.

#### Шаг 1. Запустить обе Job'ы

Команда создаёт два Job'а и через 25 с показывает их и их поды.

```bash
kubectl apply -f - <<'EOF'
apiVersion: batch/v1
kind: Job
metadata: {name: old-sidecar}
spec:
  backoffLimit: 0
  template:
    spec:
      restartPolicy: Never
      containers:
      - name: main
        image: busybox:1.37
        command: ["sh", "-c", "echo work; sleep 3; echo done"]
      - name: log-shipper
        image: busybox:1.37
        command: ["sh", "-c", "while true; do sleep 1; done"]
---
apiVersion: batch/v1
kind: Job
metadata: {name: native-sidecar}
spec:
  backoffLimit: 0
  template:
    spec:
      restartPolicy: Never
      initContainers:
      - name: log-shipper
        image: busybox:1.37
        restartPolicy: Always
        command:
        - sh
        - -c
        - |
          trap 'echo sidecar got TERM; exit 0' TERM
          echo sidecar up
          while true; do sleep 1; done
      containers:
      - name: main
        image: busybox:1.37
        command: ["sh", "-c", "echo work; sleep 3; echo done"]
EOF
sleep 25
kubectl get jobs,pods -l 'batch.kubernetes.io/job-name in (old-sidecar,native-sidecar)'
```

| Часть команды | Значение |
|---|---|
| `backoffLimit: 0` | не пересоздавать под при ошибке |
| `restartPolicy: Never` | контейнеры пода не перезапускаются |
| `restartPolicy: Always` у init | делает `log-shipper` нативным sidecar |
| `trap … TERM` | при SIGTERM напечатать строку и выйти с кодом 0 |
| `-l 'batch.kubernetes.io/job-name in (…)'` | выбрать поды этих двух Job'ов по метке |

Результат:

```
NAME                       STATUS     COMPLETIONS   DURATION   AGE
job.batch/native-sidecar   Complete   1/1           7s         25s
job.batch/old-sidecar      Running    0/1           25s        25s

NAME                       READY   STATUS      RESTARTS   AGE
pod/native-sidecar-rjhg9   0/2     Completed   0          25s
pod/old-sidecar-wr995      1/2     NotReady    0          25s
```

Разбор:

1. `native-sidecar` — `Complete` за 7 с: в это время входят запуск пода, 3 с работы `main` и остановка sidecar.
2. `old-sidecar` — `Running` и `0/1`: `main` давно вышел, но под ждёт `log-shipper`, который не завершится сам.
3. `1/2 NotReady` — один контейнер из двух ещё работает, под не готов.
4. `0/2 Completed` у нативного пода — оба контейнера остановлены, под завершён.

#### Шаг 2. Проверить остановку нативного sidecar

Команда читает лог sidecar из завершённого пода.

```bash
kubectl logs job/native-sidecar -c log-shipper
```

| Часть команды | Значение |
|---|---|
| `job/native-sidecar` | взять под, созданный этим Job'ом |
| `-c log-shipper` | выбрать контейнер-sidecar |

Результат:

```
sidecar up
sidecar got TERM
```

Разбор:

1. `sidecar up` — sidecar стартовал первым, по порядку init-контейнеров.
2. `sidecar got TERM` — kubelet отправил ему SIGTERM, когда `main` уже завершился. Остановка пошла в обратном порядке запуска.

**Итог.**

| Что узнали | Где видно |
|---|---|
| Старый sidecar не даёт Job завершиться | `old-sidecar` — `Running` |
| Нативный sidecar останавливается после основного контейнера | лог `sidecar got TERM` |
| Нативный sidecar не мешает Job закончиться | `native-sidecar` — `Complete` |

**Уборка.**

```bash
kubectl delete job old-sidecar native-sidecar
```

**Вопросы для самопроверки.**

1. Почему `old-sidecar` останется `Running`, пока вы его не удалите?
2. Зачем в sidecar стоит `trap … TERM`?

<details>
<summary>Ответы</summary>

1. Job ждёт завершения всех контейнеров пода. Sidecar в `containers` работает вечно, и страховки нет: ни `activeDeadlineSeconds`, ни `ttlSecondsAfterFinished` в этом Job'е не заданы.
2. Shell в роли PID 1 без обработчика игнорирует SIGTERM. Тогда контейнер дожил бы до конца grace period (по умолчанию 30 с, 02-5) и был бы убит сигналом SIGKILL с кодом 137. Обработчик даёт чистое завершение с кодом 0.

</details>

### Лабораторная работа 4. Что под знает о себе: Downward API

**Цель.** Передать поду его имя, узел, IP, лимит памяти и метки и проверить, что обновляется на лету.

**Что понадобится.** Namespace `lab-02-1`, образ `busybox:1.37`.

**Схема опыта.**

```
metadata.name, spec.nodeName, status.podIP ─┐
limits.memory, requests.cpu ────────────────┼─► переменные MY_*   (фиксируются при старте)
metadata.labels ────────────────────────────┴─► файл /etc/podinfo/labels  (обновляется)
```

Схема 12. Один источник — объект пода, два пути доставки: переменные и файл.

#### Шаг 1. Передать данные в контейнер

Команда создаёт под с пятью переменными из Downward API и томом с метками, затем читает его лог.

```bash
kubectl apply -f - <<'EOF'
apiVersion: v1
kind: Pod
metadata: {name: downward, labels: {app: demo}}
spec:
  containers:
  - name: app
    image: busybox:1.37
    command:
    - sh
    - -c
    - env | grep ^MY_ | sort; cat /etc/podinfo/labels; echo; sleep infinity
    resources:
      requests: {cpu: 100m, memory: 32Mi}
      limits: {memory: 64Mi}
    env:
    - {name: MY_POD, valueFrom: {fieldRef: {fieldPath: metadata.name}}}
    - {name: MY_NODE, valueFrom: {fieldRef: {fieldPath: spec.nodeName}}}
    - {name: MY_IP, valueFrom: {fieldRef: {fieldPath: status.podIP}}}
    - name: MY_MEM_LIMIT
      valueFrom: {resourceFieldRef: {resource: limits.memory}}
    - name: MY_CPU_REQ_M
      valueFrom: {resourceFieldRef: {resource: requests.cpu, divisor: 1m}}
    volumeMounts: [{name: podinfo, mountPath: /etc/podinfo}]
  volumes:
  - name: podinfo
    downwardAPI:
      items: [{path: labels, fieldRef: {fieldPath: metadata.labels}}]
EOF
kubectl wait --for=condition=Ready pod/downward
kubectl logs downward
```

| Часть команды | Значение |
|---|---|
| `fieldRef … metadata.name` | имя пода |
| `fieldRef … spec.nodeName` | имя узла |
| `fieldRef … status.podIP` | IP пода |
| `resourceFieldRef … limits.memory` | лимит памяти в байтах |
| `divisor: 1m` | выразить CPU в милли-ядрах |
| `downwardAPI … metadata.labels` | том с файлом меток |

Результат:

```
MY_CPU_REQ_M=100
MY_IP=10.244.2.15
MY_MEM_LIMIT=67108864
MY_NODE=lab-worker
MY_POD=downward
app="demo"
```

Разбор:

1. `MY_CPU_REQ_M=100` — запрос `100m`, поделённый на делитель `1m`.
2. `MY_MEM_LIMIT=67108864` — 64 МиБ в байтах (64 × 1024 × 1024).
3. `MY_IP`, `MY_NODE`, `MY_POD` — значения полей пода. У вас IP и узел другие.
4. `app="demo"` — содержимое файла `labels`: по строке `ключ="значение"`.

#### Шаг 2. Сменить метку и сравнить

Команда добавляет метку и перечитывает файл.

```bash
kubectl label pod downward tier=demo
sleep 5
kubectl exec downward -- cat /etc/podinfo/labels; echo
```

| Часть команды | Значение |
|---|---|
| `kubectl label pod downward tier=demo` | добавить метку `tier=demo` |
| `exec downward -- cat …` | прочитать файл внутри контейнера |

Результат:

```
app="demo"
tier="demo"
```

Разбор: файл уже содержит новую метку. На стенде файл обновился примерно через 1 с после `kubectl label`. kubelet синхронизирует Downward-том при обновлении пода. Для томов с ConfigMap задержка больше (04-1). Переменные окружения остаются прежними: они зафиксированы при старте контейнера, и новую метку подхватит только перезапуск.

**Итог.**

| Что узнали | Где видно |
|---|---|
| Под получает данные о себе без доступа к API | шаг 1, `MY_*` |
| Лимиты передаются числом: память в байтах, CPU с делителем | `MY_MEM_LIMIT`, `MY_CPU_REQ_M` |
| Файл тома обновляется, переменные — нет | шаг 2 |

**Уборка.** Удаляем под и весь namespace, возвращаем текущий namespace kubectl по умолчанию.

```bash
kubectl delete pod downward
kubectl config set-context --current --namespace=default
kubectl delete ns lab-02-1
```

**Вопросы для самопроверки.**

1. Почему после `kubectl label` изменился файл, а переменная окружения нет?
2. Зачем приложению знать лимит памяти через Downward API, а не читать его из cgroup?

<details>
<summary>Ответы</summary>

1. Переменные окружения процесс получает при старте и больше не меняет. Файл тома kubelet обновляет, когда меняется под.
2. Значение удобно передать в параметры запуска (например, размер heap) в манифесте. Читать cgroup нужно кодом, который понимает файловую систему cgroup v1 и v2.

</details>
