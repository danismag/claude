# 02-1. Pod

> Модуль 2 «Workloads» · часть 1 из 5 · 🟢🟡🔴 · ~1,5 ч чтения + ~45 мин лабы · Нужно: стенд 00-1

---

## Зачем это DevOps-у

Под — единица, с которой вы имеете дело при каждом инциденте: `kubectl get pods` показывает `Init:0/1`, `CrashLoopBackOff`, `CreateContainerConfigError`, `ImagePullBackOff`, `Error`, `Completed`, и по одному этому слову нужно понимать, на каком шаге жизни пода он застрял. Второе — многоконтейнерные поды: init для ожидания зависимостей и миграций, sidecar для прокси, логов и секретов. С 1.29 у sidecar'ов появился нативный механизм, и старый способ ломает Job'ы — это частый вопрос на собеседовании и частая проблема в CI.

В сквозном сценарии orders-api ждёт PostgreSQL сам (цикл в `startup()`, 00-1); в этой части разбираем альтернативу — init-контейнер — и что видно, когда под не стартует.

---

## 1. Что такое под 🟢

Под — один или несколько контейнеров с общими сетевым namespace (один IP, общий `localhost`), IPC и томами, которые всегда планируются на один узел вместе (01-2). Под — **не** единица масштабирования «контейнера»: масштабируют весь под. В один под кладут то, что не имеет смысла отдельно (приложение + прокси, приложение + агент логов), а не «фронт и бэк».

Голые поды в проде почти не создают: под не переживает потерю узла и не пересоздаётся при удалении. Ими управляют контроллеры — Deployment, StatefulSet, DaemonSet, Job (02-2…02-4).

## 2. Фазы пода и состояния контейнеров 🟢

`status.phase` — грубая сводка:

| Фаза | Значит |
|---|---|
| `Pending` | под принят, но хотя бы один контейнер не запущен: ждёт scheduler, pull образа, тома, init-контейнеры |
| `Running` | под на узле, хотя бы один контейнер работает (или перезапускается) |
| `Succeeded` | все контейнеры завершились с 0 и не будут перезапущены |
| `Failed` | все завершились, хотя бы один — не с 0 (или под выселен) |
| `Unknown` | нет связи с узлом |

Колонка `STATUS` в `kubectl get pods` — не фаза, а самое «интересное» состояние контейнера: `waiting.reason` или `terminated.reason`. Состояния контейнера:

| Состояние | Типовые `reason` |
|---|---|
| `waiting` | `ContainerCreating`, `PodInitializing`, `ErrImagePull`, `ImagePullBackOff`, `CreateContainerConfigError`, `CrashLoopBackOff`, `RunContainerError` |
| `running` | — (есть `startedAt`) |
| `terminated` | `Completed` (0), `Error` (≠0), `OOMKilled` (137), `StartError` (128), `ContainerCannotRun` |

Плюс `lastState` — как завершился **предыдущий** экземпляр (именно там видно `OOMKilled`, 05-1).

`status.conditions` — шаги готовности (проверено на поде с init-контейнером):

```
PodScheduled=True                 2026-10-14T09:07:55Z
PodReadyToStartContainers=True    2026-10-14T09:07:56Z     ← sandbox и сеть созданы
Initialized=True                  2026-10-14T09:08:18Z     ← все init-контейнеры завершились успешно
ContainersReady=True              2026-10-14T09:08:18Z
Ready=True                        2026-10-14T09:08:18Z     ← под в endpoints Service
```

22 секунды между sandbox и `Initialized` — init-контейнер ждал БД.

## 3. Коды выхода 🟢🟡

Проверено (под с `restartPolicy: Never` и пятью контейнерами):

| Команда | `exitCode` | `reason` | Что значит |
|---|---|---|---|
| `exit 0` | 0 | `Completed` | нормальное завершение |
| `exit 3` | 3 | `Error` | код приложения |
| `sh -c nosuchcmd` | 127 | `Error` | shell не нашёл команду |
| `command: ["/nonexistent"]` | 128 | `StartError` | runc не смог запустить процесс: `exec: "/nonexistent": stat /nonexistent: no such file or directory` — сообщение в `state.terminated.message` |
| превышен лимит памяти | 137 | `OOMKilled` | SIGKILL от OOM killer (05-1) |
| SIGKILL после grace period | 137 | `Error` | не завершился за `terminationGracePeriodSeconds` (02-5) |
| SIGTERM обработан по умолчанию | 143 | `Error` | 128 + 15 |

`137` без `OOMKilled` — почти всегда «не успел завершиться» или liveness-проба убила. `126` — файл найден, но не исполняется (права, не тот формат, архитектура). Разница `127` и `128`: в первом случае контейнер запустился (shell) и не нашёл команду, во втором — не запустился вовсе.

## 4. restartPolicy и back-off 🟢

| `restartPolicy` | Перезапуск | Для чего |
|---|---|---|
| `Always` (дефолт) | всегда | сервисы — Deployment, StatefulSet, DaemonSet (только он и разрешён) |
| `OnFailure` | при коде ≠ 0 | Job |
| `Never` | никогда | Job, одноразовые поды |

Перезапуск делает kubelet **на том же узле, в том же поде** — с растущей паузой 10 → 20 → 40 → 80 → 160 → 300 с (замер — 05-1, шаг 3), сброс после 10 минут работы. Пока идёт пауза, статус — `CrashLoopBackOff`. Это не ошибка сама по себе, а «контейнер падает, жду».

## 5. Init-контейнеры 🟡

Выполняются **по очереди, до основных**; каждый должен завершиться с 0. Упал — kubelet перезапускает его по `restartPolicy` пода (для `Always` — с back-off), статус `Init:CrashLoopBackOff`. Пока init не завершился, под `Init:0/1` и в Service не попадает.

Применение: ждать зависимость, применить миграции БД, скачать конфиг/сертификат, выставить права на том, `sysctl` (с привилегиями — только init, не основной контейнер).

```yaml
initContainers:
- name: wait-db
  image: busybox:1.37
  command: ["sh", "-c", "until nc -z -w 1 db 5432; do echo waiting for db; sleep 2; done; echo db is up"]
```

Проверено: пока сервиса `db` нет, лог init — `nc: bad address 'db'` / `waiting for db`, под `Init:0/1`; после `kubectl expose` — `db is up`, основной контейнер стартует.

Init для ожидания зависимостей — спорная практика: под ждёт только при старте. Если БД пропадёт потом, приложение всё равно должно уметь переподключаться — orders-api делает это сам (`startup()` с повторами, readiness проверяет БД). Init полезнее для одноразовой подготовки (миграции, файлы).

Ресурсы: эффективный request пода = max(max(init), sum(основные + sidecar'ы)). Тяжёлый init-контейнер с request 4 CPU делает «дорогим» весь под при планировании.

## 6. Sidecar-контейнеры: старый способ и нативный 🟡🔴

Sidecar — вспомогательный контейнер, который должен работать **всё время** рядом с основным: прокси mesh (Envoy, Istio), агент логов, обновление сертификатов, Vault agent.

**Старый способ** — второй контейнер в `containers`. Проблемы:

- нет порядка старта: приложение может начать раньше прокси и не достучаться до сети;
- нет порядка остановки: прокси может умереть раньше приложения, которое ещё отдаёт ответы;
- **Job не завершается**: основной контейнер закончил, sidecar работает бесконечно — под `NotReady`, Job `Running` навсегда.

**Нативный sidecar** (stable с 1.33, по умолчанию включён с 1.29) — контейнер в `initContainers` с `restartPolicy: Always`:

```yaml
initContainers:
- name: log-shipper
  image: busybox:1.37
  restartPolicy: Always            # ← это и делает его sidecar'ом
  command: ["sh", "-c", "trap 'echo sidecar got TERM; exit 0' TERM; echo sidecar up; while true; do sleep 1; done"]
containers:
- name: main
  image: busybox:1.37
  command: ["sh", "-c", "echo work; sleep 3; echo done"]
```

Свойства: запускается по порядку init-контейнеров, но kubelet не ждёт его завершения — после старта (или после успешной `startupProbe`) идёт дальше; работает всё время жизни пода; при остановке пода завершается **после** основных контейнеров, в обратном порядке; не мешает Job'у завершиться.

Проверено (два Job'а с одинаковой работой на 3 секунды):

```
NAME                       STATUS     COMPLETIONS   DURATION   AGE
job.batch/native-sidecar   Complete   1/1           7s         25s
job.batch/old-sidecar      Running    0/1           25s        25s

NAME                       READY   STATUS      RESTARTS   AGE
pod/native-sidecar-rjhg9   0/2     Completed   0          25s
pod/old-sidecar-wr995      1/2     NotReady    0          25s
```

Лог нативного sidecar'а — `sidecar up` / `sidecar got TERM`: kubelet корректно остановил его после `main`. Старый Job так и будет висеть — до `activeDeadlineSeconds` (02-4) или ручного удаления.

## 7. Сообщение о завершении: CrashLoop без логов 🟡

Частая ситуация: контейнер падает сразу при старте, `kubectl logs --previous` пуст или недоступен (05-1). Что ещё есть:

- `state.terminated.message` — содержимое файла `terminationMessagePath` (по умолчанию `/dev/termination-log`), до 4096 байт. Приложение пишет туда причину перед выходом.
- `terminationMessagePolicy: FallbackToLogsOnError` — если файл пуст и код ≠ 0, kubelet берёт последние строки лога (до 2048 байт / 80 строк).

Проверено:

```
msg-file: exit=2 message=config /etc/app.yaml not found          ← из /dev/termination-log; в логах пусто
msg-logs: exit=1 message=panic: cannot connect to db:5432        ← FallbackToLogsOnError, взято из stderr
```

Это видно в `kubectl describe pod` → `Last State: Terminated … Message:` — без доступа к логам и после ротации. Для своих сервисов `FallbackToLogsOnError` стоит включать всегда: это бесплатно.

## 8. Под не стартует: ошибки до запуска процесса 🟢🟡

Проверено:

| STATUS | `state.waiting.message` | Причина |
|---|---|---|
| `CreateContainerConfigError` | `couldn't find key password in Secret lab-02-1/app` | нет Secret/ConfigMap или ключа в нём; под ждёт и сам починится, когда ключ появится |
| `ImagePullBackOff` | `Back-off pulling image "localhost:5001/orders-api:9.9": ErrImagePull: … not found` | нет тега, нет доступа (`401`/`403` — `imagePullSecrets`), неверный реестр, лимит Docker Hub (`429`) |
| `ContainerCreating` долго | событие `FailedMount` / `FailedCreatePodSandBox` | том не смонтирован (04-2) / CNI не выдал IP (03-1) |
| `Pending` без узла | событие `FailedScheduling` | ресурсы, taints, affinity, PVC (05-1, 05-2) |

`CreateContainerConfigError` и `ImagePullBackOff` — проблемы **конфигурации**, а не приложения: смотреть `describe`, не логи. Методика целиком — 11-1.

## 9. Downward API 🟡

Под может узнать о себе без доступа к API — через переменные и файлы:

```yaml
env:
- {name: MY_POD,       valueFrom: {fieldRef: {fieldPath: metadata.name}}}
- {name: MY_NODE,      valueFrom: {fieldRef: {fieldPath: spec.nodeName}}}
- {name: MY_IP,        valueFrom: {fieldRef: {fieldPath: status.podIP}}}
- {name: MY_MEM_LIMIT, valueFrom: {resourceFieldRef: {resource: limits.memory}}}
- {name: MY_CPU_REQ_M, valueFrom: {resourceFieldRef: {resource: requests.cpu, divisor: 1m}}}
volumes:
- name: podinfo
  downwardAPI: {items: [{path: labels, fieldRef: {fieldPath: metadata.labels}}]}
```

Проверено:

```
MY_CPU_REQ_M=100
MY_IP=10.244.2.15
MY_MEM_LIMIT=67108864
MY_NODE=lab-worker
MY_POD=downward
app="demo"
```

Применение: имя пода в логах и трейсах, лимит памяти для настройки heap (`MY_MEM_LIMIT` → `-Xmx`), число воркеров из CPU request (05-1 §3). Переменные фиксируются при старте контейнера; файлы тома (labels, annotations) обновляются на лету.

## 10. Ephemeral containers 🟡

Отладочный контейнер, добавленный в работающий под: `kubectl debug -it <pod> --image=busybox --target=<container>`. Нет портов, probes, ресурсов; нельзя удалить — живёт до пересоздания пода. Подробно с проверкой — 00-2 §6.

## 🔥 Кейс из прода: «миграционный Job висит неделю, а деплой проходит»

**Контекст.** В Helm-чарте orders-api — Job миграций БД как pre-upgrade hook. В кластере включили service mesh с автоматической инъекцией Envoy-sidecar'а во все поды namespace. Первый же деплой «завис»: Helm ждал hook 5 минут и упал по таймауту, следующий деплой с `--no-hooks` прошёл, миграции «как будто применились». Через неделю — 40 Job'ов миграций в статусе `Running`, у каждого под `1/2 NotReady`.

**Разбор.**
1. `kubectl get pod <migrate> -o jsonpath='{.status.containerStatuses[*].name}'` — `migrate istio-proxy`; `migrate` в `terminated: Completed`, `istio-proxy` — `running`.
2. Sidecar инжектирован старым способом — в `containers`. Job ждёт завершения всех контейнеров пода; прокси не знает, что работа закончена, и работает бесконечно (шаг 3 лабы, `old-sidecar`).
3. Миграции применились (код 0 у `migrate`), но Helm считал hook незавершённым.

**Фикс.**
- Включили в mesh инъекцию **нативным** sidecar'ом (`initContainers` + `restartPolicy: Always`; в Istio — `ENABLE_NATIVE_SIDECARS=true`, в других mesh — аналогичные флаги). Job завершается, sidecar останавливается после основного контейнера (шаг 3, `native-sidecar`).
- Для Job'ов, где mesh не нужен, — аннотация отключения инъекции.
- `activeDeadlineSeconds` и `ttlSecondsAfterFinished` у всех Job'ов (02-4) — зависшие не копятся.

**Что запомнить.**
- Sidecar в `containers` + Job = Job никогда не завершится.
- Нативный sidecar — `initContainers` с `restartPolicy: Always`: запускается до основных, останавливается после, не мешает Job'у.
- Код выхода основного контейнера и статус Job — разные вещи; смотрите оба.

## 💼 Вопросы с собеседования

### 🟢 Junior

**1. Что такое под и зачем в нём несколько контейнеров?**
Минимальная единица планирования: контейнеры с общим IP, `localhost` и томами, всегда на одном узле. Несколько контейнеров — когда они не имеют смысла по отдельности: приложение + прокси/агент логов/обновлятель сертификатов (sidecar) или подготовка перед стартом (init).

**2. Что значит статус CrashLoopBackOff?**
Контейнер завершается снова и снова, kubelet перезапускает его с растущей паузой (10 с → … → 5 мин). Смотреть: `kubectl describe pod` (Last State, exit code, reason, message), `kubectl logs --previous`, события.

**3. Чем отличаются фазы Pending, Running, Succeeded, Failed?**
Pending — под принят, но контейнеры ещё не запущены (scheduler, образ, тома, init). Running — на узле, хотя бы один контейнер работает. Succeeded — все завершились с 0. Failed — все завершились, хотя бы один с ошибкой.

### 🟡 Middle

**4. Чем init-контейнер отличается от sidecar?**
Init выполняется до основных, по очереди, должен завершиться с 0; под не Ready, пока init не закончил. Sidecar работает всё время рядом с основным. Нативный sidecar — init-контейнер с `restartPolicy: Always`: стартует до основных, kubelet не ждёт его завершения, останавливается после основных.

**5. Под в `CreateContainerConfigError`. Что проверяете?**
`kubectl describe pod` → сообщение: нет ConfigMap/Secret или ключа, на который ссылается `env`/`envFrom`/том. Создать/исправить объект — kubelet повторит создание контейнера сам, пересоздавать под не нужно.

**6. Контейнер падает при старте, логов нет. Где искать причину?**
`describe` → Last State: exit code и `message` (termination message: файл `/dev/termination-log` или хвост логов при `FallbackToLogsOnError`). 127 — нет команды, 128 `StartError` — runc не смог запустить (нет бинарника, права, архитектура), 137 — OOM или kill. Затем `kubectl debug --copy-to` с заменой команды на `sleep` и ручной запуск.

### 🔴 Senior

**7. Почему Job с sidecar'ом mesh'а может никогда не завершиться и как это исправить?**
Sidecar в `containers` работает бесконечно, Job ждёт завершения всех контейнеров пода. Исправление: нативный sidecar (`initContainers` + `restartPolicy: Always`, stable с 1.33) — kubelet останавливает его после завершения основных контейнеров; либо отключить инъекцию для Job'ов; страховка — `activeDeadlineSeconds`.

**8. Как считаются ресурсы пода с init- и sidecar-контейнерами при планировании?**
Эффективный request = max(наибольший request среди обычных init-контейнеров (с учётом уже запущенных до него sidecar'ов), сумма основных + всех sidecar'ов). Тяжёлый init делает «дорогим» весь под; sidecar'ы добавляются к сумме основных постоянно.

**9. Зачем downward API, если можно сходить в API за информацией о поде?**
Не нужны права RBAC и токен, нет нагрузки на apiserver, работает при недоступности API. Имя пода и узла — в логи и трейсы, лимиты — для настройки рантайма (heap, воркеры). Переменные фиксируются при старте, файлы тома (labels/annotations) обновляются.

## ⚠️ Подводные камни

- Колонка STATUS — не фаза пода, а причина состояния одного из контейнеров.
- `exit 137` без `OOMKilled` — не память, а SIGKILL после grace period или от liveness.
- Init-контейнер ждёт зависимость только при старте; приложение всё равно должно переподключаться.
- Sidecar в `containers` ломает Job'ы и не гарантирует порядок старта/остановки.
- `CreateContainerConfigError` чинится созданием Secret/ConfigMap — под пересоздавать не нужно, но и сам он «не поймёт» опечатку в имени.
- Termination message ограничен 4096 байтами, fallback из логов — 2048 байт / 80 строк.
- Переменные downward API и любые `env` фиксируются при старте контейнера.
- Ephemeral container нельзя удалить — только пересоздать под.
