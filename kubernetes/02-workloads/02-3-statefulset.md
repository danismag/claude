## Где мы на карте

Эта часть разбирает второй контроллер модуля 02: StatefulSet. Deployment (02-2) запускает одинаковые безымянные поды, а StatefulSet даёт каждому поду имя, адрес и диск, которые переживают пересоздание. Часть опирается на 02-1 (жизненный цикл пода) и 02-2 (шаблон пода, ревизии и порядок выката).

Хранилищем и сетью StatefulSet пользуется, но не объясняет их: тома, PV и StorageClass разобраны в 04-2, DNS кластера — в 03-3, бэкапы — в 04-3. Здесь мы смотрим только на то, как контроллер связывает под, том и DNS-имя.

```
Deployment (02-2)        StatefulSet (02-3, эта часть)       DaemonSet, Job (02-4)
поды анонимны            поды с именем, адресом и диском     поды по узлам и задачам
        │                          │
        └─────────── создают и заменяют поды (02-1) ───────────┘
                                   │
                  том (04-2) ── DNS (03-3) ── бэкапы (04-3)
```

Схема 1. Место StatefulSet среди контроллеров: он создаёт те же поды, но добавляет им идентичность; тома, DNS и бэкапы лежат в соседних частях.

## 1. Какую задачу решает StatefulSet

StatefulSet решает задачу запуска приложений, которым важно, кто они такие: базы данных, брокеры сообщений, кластеры с выбором лидера. Разберём, чего таким приложениям не хватает в Deployment, что даёт StatefulSet и чего он не делает.

### Приложению с состоянием нужна идентичность

**Идентичность** (identity) — набор свойств, по которым экземпляр узнают снаружи и по которым он узнаёт себя: имя, сетевой адрес и данные на диске. У базы данных с репликой это значит, что реплика знает адрес основного сервера, а основной знает, какие данные лежат у реплики. Если после перезапуска имя или диск изменились, кластер баз данных считает экземпляр чужим.

Поды Deployment этих свойств не имеют. Имя содержит случайный суффикс, новый под получает новый IP и может запуститься на любом узле. Один общий том на все поды тоже не подходит: два экземпляра базы не должны писать в одни и те же файлы.

### Что даёт StatefulSet

**StatefulSet** — контроллер, который запускает набор подов по шаблону и сохраняет за каждым подом его идентичность при пересоздании. Он даёт четыре гарантии:

- стабильное имя: поды называются по порядковому номеру, например `web-0`, `web-1`, `web-2`;
- стабильный адрес: у каждого пода есть своё DNS-имя, которое не меняется при пересоздании;
- свой том: каждый под получает отдельный том и снова получает его после пересоздания;
- порядок: поды создаются, удаляются и обновляются по очереди.

Сравним с Deployment по основным свойствам.

| Свойство | Deployment | StatefulSet |
|---|---|---|
| Имя пода | случайный суффикс | порядковый номер |
| После пересоздания | новое имя, любой узел | то же имя, тот же том |
| DNS | один адрес на всех | отдельное имя на каждый под |
| Тома | общий или без томов | свой том на каждый под |
| Порядок | все поды сразу | по очереди |
| Гарантия | не меньше N подов | не больше одного пода с этим именем |

Последняя строка таблицы важнее остальных. Deployment при сомнениях запускает лишний под, чтобы не потерять мощность. StatefulSet при сомнениях ждёт, потому что два пода с одним именем и одним диском не должны работать одновременно. Эту гарантию называют **at-most-once** (не более одного раза), и она объясняет поведение при отказе узла (§5).

### Чего StatefulSet не делает

StatefulSet не делает базу данных отказоустойчивой. Он не настраивает репликацию и не выбирает лидера. Клиентов при падении основного сервера он тоже не переключает. Это работа самого приложения или **оператора** — программы в кластере, которая управляет приложением вместо человека (09-1).

StatefulSet даёт только стабильные имена, диски и порядок, а три копии базы без репликации остаются тремя независимыми базами. Бэкапы тоже не входят в его задачи (04-3).

## 2. Как устроен StatefulSet

StatefulSet работает не один: ему нужны Service для DNS-имён и шаблон томов для дисков. Разберём, как три объекта связаны, как контроллер выбирает имена и порядок.

### Три объекта вместе

Рабочий StatefulSet состоит из трёх частей. Первая — сам StatefulSet, вторая — **headless Service** (служба без виртуального IP) для DNS, третья — **шаблон томов** `volumeClaimTemplates`, из которого контроллер создаёт заявки на диски. Связь между ними задают два поля: `serviceName` указывает на Service, а `volumeClaimTemplates` описывает диск.

```
 headless Service web  (clusterIP: None)    ◄── serviceName: web
        │  выбирает поды по метке app=web
        ▼
 StatefulSet web  (replicas: 3, volumeClaimTemplates: data)
   ├── Pod web-0 ── PVC data-web-0 ── PV
   ├── Pod web-1 ── PVC data-web-1 ── PV
   └── Pod web-2 ── PVC data-web-2 ── PV
```

Схема 2. Один StatefulSet создаёт поды и по одному PVC на под; Service даёт им DNS-имена.

**PersistentVolumeClaim, PVC** — заявка пода на постоянный том: объём, режим доступа и класс хранилища. **PersistentVolume, PV** — сам том, который кластер выделяет под заявку. Подробно они разобраны в 04-2, а здесь нужно запомнить одно: PVC — отдельный объект API, и его жизнь не обязана совпадать с жизнью пода.

### Имена и порядковые номера

**Порядковый номер** (ordinal) — число от 0 до N−1 в имени пода. Имя состоит из имени StatefulSet и номера: `web-0`, `web-1`, `web-2`. Под с этим именем всегда один, а имя хоста внутри контейнера равно имени пода.

Контроллер добавляет подам две метки. Метка `statefulset.kubernetes.io/pod-name` хранит имя пода, и по ней отдельный Service выбирает ровно один под. Метка `apps.kubernetes.io/pod-index` хранит номер (stable с 1.32): по ней фильтруют логи и метрики. Поле `spec.ordinals.start` (stable с 1.31) сдвигает начало нумерации, например для переноса части подов в другой кластер.

### DNS-имена и headless Service

**Headless Service** — Service с `clusterIP: None`: у него нет виртуального IP, и DNS отдаёт адреса подов напрямую. Для StatefulSet этого мало: кроме общего имени Service, каждый готовый под получает своё имя вида `web-1.web.<namespace>.svc.cluster.local`. Имя пода и имя Service, из которых оно складывается, лежат в полях `hostname` и `subdomain` пода.

```
запрос: web.lab-02-3.svc.cluster.local      ──► IP всех готовых подов
запрос: web-1.web.lab-02-3.svc.cluster.local ──► IP только пода web-1
```

Схема 3. Две формы DNS-запроса к headless Service: по имени Service получают все адреса, по имени пода — один.

Поле `serviceName` StatefulSet должен совпадать с именем Service, иначе записей на отдельные поды не будет. Неготовые поды из DNS исключаются: у Service поле `publishNotReadyAddresses` по умолчанию равно `false`. Для кластеров, которым нужно найти соседей до их готовности (выбор лидера, etcd), ставят `true`.

Записи нового пода появляются в DNS с задержкой. Неудачный запрос запоминается (**negative caching** — кэширование отрицательного ответа), и CoreDNS держит такой ответ около 30 секунд (документация StatefulSet). Приложение, которое стартует и сразу ищет соседей, должно повторять запрос.

### Тома: volumeClaimTemplates

**Шаблон томов** `volumeClaimTemplates` — список заготовок PVC. Для каждого пода контроллер создаёт заявку по имени `<шаблон>-<под>`: для шаблона `data` и пода `web-1` получится `data-web-1`. Если заявка с таким именем уже есть, контроллер использует её, а не создаёт новую, и так под после пересоздания находит свой диск.

Заявку создаёт контроллер StatefulSet, а не Helm и не пользователь. Поэтому PVC не принадлежат ни поду, ни самому StatefulSet по умолчанию: они остаются, когда исчезают и поды, и StatefulSet. Что с ними делать при масштабировании и удалении, решает политика хранения (§3).

### Порядок: podManagementPolicy

**podManagementPolicy** — поле, которое задаёт порядок создания и удаления подов при масштабировании. Значения два, и менять поле после создания StatefulSet нельзя.

- **OrderedReady** (по умолчанию) — под N+1 создаётся, только когда под N стал Ready; при удалении порядок обратный, от старшего номера к младшему.
- **Parallel** — все поды создаются и удаляются одновременно, готовность предыдущих не ждут.

```
OrderedReady  создание:  web-0 ─► Ready ─► web-1 ─► Ready ─► web-2
              удаление:  web-2 ─► исчез ─► web-1 ─► исчез ─► web-0
Parallel      создание:  web-0, web-1, web-2 — одновременно
```

Схема 4. Порядок масштабирования при двух политиках; на обновление политика не влияет, поды обновляются по очереди (§3).

OrderedReady подходит приложениям, которым нужен запущенный предшественник: второй экземпляр присоединяется к первому. Parallel нужен, когда порядок не важен, а подов много: ждать готовности каждого пода тогда дорого. Опыт с обоими режимами — лабораторная работа 2.

## 3. Как управлять StatefulSet

Управление сводится к трём действиям: менять число подов, обновлять шаблон и решать, что делать с дисками. Разберём их по очереди.

### Масштабирование и политика хранения PVC

Число подов меняют командой `kubectl scale sts <имя> --replicas=N`. При уменьшении контроллер удаляет поды с наибольшими номерами, а заявки на диски по умолчанию оставляет. При возврате к прежнему числу поды получают свои старые заявки со старыми данными.

Это поведение задаёт поле `persistentVolumeClaimRetentionPolicy` (stable с 1.32). Оно содержит два ключа: `whenScaled` — что делать с PVC при уменьшении числа подов, `whenDeleted` — что делать при удалении StatefulSet. Каждый ключ принимает `Retain` (оставить, по умолчанию) или `Delete` (удалить).

| Событие | Retain (по умолчанию) | Delete |
|---|---|---|
| Удалён под | PVC остаётся, под берёт его | PVC остаётся |
| Уменьшено число подов | PVC остаются | PVC лишних подов удаляются |
| Увеличено число подов | старые PVC со старыми данными | новые пустые PVC |
| Удалён StatefulSet | все PVC остаются | все PVC удаляются |

Удаление пода политика не затрагивает: заявка остаётся и при `Delete`, в том числе при замене пода после отказа узла. Контроллер реализует `Delete` через ссылки владельца (**owner references**) на PVC: когда под или StatefulSet исчезает, сборщик мусора удаляет заявку.

Значение `Retain` безопасно: данные не пропадут из-за опечатки в `replicas`. Цена — осиротевшие PVC копятся и занимают место, а в облаке за их диски платят. Значение `Delete` на `whenScaled` подходит кластерным приложениям, у которых вернувшаяся реплика с устаревшими данными вредна. Опыт — лабораторная работа 2.

### Обновление по умолчанию: RollingUpdate

Стратегия `RollingUpdate` (по умолчанию) пересоздаёт поды по одному, от старшего номера к младшему, и следующий под обновляется только после готовности предыдущего. Контроллер делает снимок каждой версии шаблона в объект **ControllerRevision** (ревизия контроллера) и ставит на поды метку `controller-revision-hash`. Предыдущих ревизий хранится 10 (поле `revisionHistoryLimit`).

Порядок обновления защищает от массовой поломки: если новая версия не стартует, страдает только один под, а остальные продолжают работать. Поле `minReadySeconds` (по умолчанию 0) добавляет паузу: под должен проработать без падений столько секунд, прежде чем контроллер перейдёт к следующему.

### Канарейка через partition

**Partition** — поле `updateStrategy.rollingUpdate.partition`, которое ограничивает обновление: меняются только поды с номером не меньше partition. Значение по умолчанию — 0, то есть обновляются все. При трёх подах и `partition: 2` обновится один `web-2`, а `web-0` и `web-1` останутся на старой версии.

```
partition: 2          web-0 (v1)   web-1 (v1)   web-2 (v2)   ◄── канарейка
проверили, снимаем:   web-0 (v1)   web-1 (v2)   web-2 (v2)
partition: 0          web-0 (v2)   web-1 (v2)   web-2 (v2)
```

Схема 5. Partition как встроенная канарейка: сначала обновляется старший под, затем остальные по убыванию номера.

Если старый под ниже partition удалить, он вернётся на старой версии. Это удобно для проверки, но опасно, если забыть partition: шаблон новый, а часть подов остаётся старой. Если partition больше `replicas`, обновление не затрагивает ни одного пода. Опыт — лабораторная работа 3.

### Ускорение: maxUnavailable

Поле `rollingUpdate.maxUnavailable` задаёт, сколько подов может быть недоступно во время обновления; значение по умолчанию 1, нуль API-сервер отклоняет. Оно принимает число или процент, а проценты округляются вверх. Поле работает, только если включён **функциональный гейт** (feature gate) `MaxUnavailableStatefulSet` — флаг компонентов кластера, который включает новую функцию. Этот гейт в статусе beta с 1.35.

Считаются поды с номерами от 0 до `replicas − 1`, и любой недоступный под в этом диапазоне расходует лимит. Документация описывает обновление пачками при `podManagementPolicy: Parallel` и значении больше 1. В 1.36 гейт выключен по умолчанию из-за регрессии 1.35 (kubernetes#137409), а в 1.37 его снова включили. При выключенном гейте API-сервер молча отбрасывает поле, поэтому лабораторная работа 3 сначала проверяет, сохранилось ли оно.

### Ручное обновление: OnDelete

Стратегия `OnDelete` не обновляет поды сама: новая версия применяется, когда вы удаляете под. Она нужна, когда обновление каждого экземпляра — ручная процедура, например переключение основного сервера БД на реплику перед обновлением. Автоматика в этом случае только мешает.

В Kubernetes 1.37 появилась пробная стратегия `Recreate` (alpha, гейт `StatefulSetRecreateStrategy`); на стенде 1.36 её нет.

## 4. Как увидеть состояние StatefulSet

Состояние видно в трёх местах: в статусе самого объекта, в подах и заявках и в ревизиях. Отдельно проверяют DNS-имена, и у этой проверки есть известная ловушка.

### Статус StatefulSet

Команда `kubectl rollout status sts/<имя>` ждёт завершения выката и сообщает, сколько подов обновлено. Поля `status` читают через `kubectl get sts <имя> -o jsonpath=…`. Нужны шесть из них:

- `replicas` — сколько подов создано;
- `readyReplicas` — сколько подов в состоянии Ready;
- `currentRevision` — ревизия, на которой работает основная часть подов;
- `updateRevision` — ревизия, к которой идёт выкат;
- `updatedReplicas` — сколько подов уже на `updateRevision`;
- `currentReplicas` — сколько подов на `currentRevision`.

Если `currentRevision` и `updateRevision` различаются, выкат ещё идёт или остановился. Для partition это нормальное состояние: ревизии разные, пока вы не снимете ограничение.

### Поды и заявки

Какой под на какой ревизии, показывает метка `controller-revision-hash`. Время создания и готовности пода видно в `kubectl get pods -o custom-columns=…`: по разнице времён проверяют порядок создания. Заявки на диски выводит `kubectl get pvc`, а сироты (PVC без подов) видны по тому, что число PVC больше числа подов.

### Ревизии

Ревизии лежат в объектах ControllerRevision. Команда `kubectl get controllerrevisions` перечисляет их, а `kubectl rollout history sts/<имя>` показывает номера ревизий. Имя ревизии совпадает с хешем в метке пода, поэтому по хешу находят версию, на которой застрял под.

### Проверка DNS: getent вместо nslookup

DNS-имена подов проверяют из любого пода командой `getent hosts <под>.<service>`. Она использует системный распознаватель libc, как приложения, и применяет search-домены из `resolv.conf`. Команду `nslookup` из busybox для этой задачи брать нельзя: она не применяет search-домены. Запрос `web-1.web` уходит в публичный DNS как есть, а `.web` — реальный домен верхнего уровня, и публичный DNS отвечает адресом-предупреждением `127.0.53.53` о коллизии имён. Подробнее о search-доменах и `ndots` — 03-3.

## 5. Что ломается и как найти причину

У StatefulSet три типичные поломки: выкат застрял на плохой ревизии, под не уходит с упавшего узла, а DNS-имён подов нет. Диски создают четвёртый класс проблем.

### Сломанная ревизия не откатывается сама

Выкат остановился на сломанной ревизии, и после возврата шаблона под остался сломанным. Так происходит из-за порядка OrderedReady: контроллер ждёт, пока текущий под станет Ready, прежде чем идти дальше. Сломанный под Ready не станет, поэтому контроллер никогда не заменит его, даже когда `currentRevision` и `updateRevision` уже совпали. Это известная проблема kubernetes#67250, документация называет её **forced rollback** (принудительный откат).

```
шаблон v2 → v3 (ломаем):     web-2 CrashLoopBackOff   web-0, web-1 не тронуты
шаблон v3 → v2 (откат):      web-2 всё ещё на v3, контроллер ждёт его Ready
kubectl delete pod web-2:    новый web-2 создаётся из ревизии v2
```

Схема 6. Откат шаблона не заменяет сломанный под; под нужно удалить вручную.

Порядок работы такой: вернуть шаблон (`kubectl rollout undo sts/<имя>` или правкой манифеста), затем удалить вручную каждый под, который уже запустился со сломанной ревизией. Контроллер пересоздаст их по текущему шаблону. У Deployment такой проблемы нет: исправленный шаблон просто создаёт новый ReplicaSet (02-2). Опыт — лабораторная работа 3.

### Под не уходит с упавшего узла

Когда узел перестаёт отвечать, под StatefulSet остаётся в `Terminating` или `Unknown` и не пересоздаётся на другом узле. Контроллер не знает, умер узел или потерял связь, и два пода с одним именем и одним диском означают порчу данных. Так at-most-once работает в действии.

Под освободит одно из четырёх событий:

- узел вернулся, и kubelet подтвердил остановку;
- объект Node удалён;
- под удалён принудительно командой `kubectl delete pod <имя> --force --grace-period=0`;
- на узел поставлен taint `node.kubernetes.io/out-of-service` с эффектом `NoExecute`.

Последние три способа безопасны только при уверенности, что узел выключен. Иначе старый под продолжит писать на диск. Диски с привязкой к узлу (local-path, local PV) вообще не переедут: PV остаётся на упавшем узле.

### Нет DNS-записей пода

Если `web-1.web` не резолвится, причины ищут в таком порядке:

1. Совпадает ли `serviceName` StatefulSet с именем Service.
2. Headless ли Service, то есть `clusterIP: None`.
3. Совпадает ли селектор Service с метками подов.
4. Готов ли под: неготовые поды в DNS не попадают, если не включён `publishNotReadyAddresses`.
5. Не проверяете ли вы busybox `nslookup` (§4).

Если под только что создан, подождите около 30 секунд: сказывается negative caching (§2).

### Осиротевшие PVC и застрявший Pending

Под в `Pending` с событием о PVC значит, что заявка не получила том. Причина — нет подходящего StorageClass либо том привязан к узлу, на котором нет места или стоит taint (04-2). Обратная ситуация — заявки без подов: они остаются после scale down и после удаления StatefulSet при `Retain`. Следите за ними регулярно: диск в облаке стоит денег, пока существует PVC.

## 6. Пределы и значения по умолчанию

Ниже собраны значения из документации Kubernetes 1.36 и ограничения, которые видны на стенде.

### Значения по умолчанию

- `replicas` — 1.
- `podManagementPolicy` — `OrderedReady`.
- `updateStrategy.type` — `RollingUpdate`; `partition` — 0; `maxUnavailable` — 1, если гейт включён (в 1.36 выключен).
- `persistentVolumeClaimRetentionPolicy` — `Retain` для обоих ключей.
- `revisionHistoryLimit` — 10; документация советует 5–10 и не советует 0, потому что без ревизий откат невозможен.
- `minReadySeconds` — 0.
- `terminationGracePeriodSeconds` пода — 30 с; нулевое значение небезопасно, так как нарушает at-most-once.

### Что менять нельзя

Спецификацию StatefulSet после создания изменять можно только в полях `replicas`, `ordinals`, `template`, `updateStrategy`, `revisionHistoryLimit`, `persistentVolumeClaimRetentionPolicy` и `minReadySeconds`; остальные правки API отклоняет. Шаблон `volumeClaimTemplates` неизменяем, поэтому размер диска увеличивают через сами PVC, если StorageClass разрешает расширение (04-2). Смена `podManagementPolicy` и `serviceName` тоже требует пересоздания StatefulSet.

Применение манифеста перезаписывает ручное масштабирование: если в Git записано `replicas: 3`, а вы выполнили `scale` до 5, следующий `apply` вернёт 3.

### Ограничения хранилища

Размер в `resources.requests.storage` — запрос, а не квота. На стенде StorageClass local-path создаёт каталог на диске узла, и ёмкость PVC не ограничивается (лабораторная работа 1, шаг 6). База может занять весь диск узла, поэтому лимиты на диск задают отдельно (05-2).

### StatefulSet или оператор

StatefulSet подходит, когда достаточно имён и дисков. Если нужны репликация, переключение и бэкапы, берут оператор (CloudNativePG для PostgreSQL, Strimzi для Kafka) или управляемую БД вне кластера. Оператор обычно сам создаёт StatefulSet или поды, а на себя берёт то, чего StatefulSet не делает.

| Задача | StatefulSet сам | С оператором |
|---|---|---|
| Имена, тома, порядок | да | да |
| Репликация и переключение | свои скрипты | встроено |
| Бэкапы и восстановление | CronJob, свои скрипты | описываются в CR |
| Обновление версии БД | OnDelete и инструкция | с автоматическим switchover |
| Сложность | меньше частей | ещё один компонент |

Для одиночной БД на стенде или в dev достаточно StatefulSet. Для продакшена решение «БД в кластере или вне» — тема 04-3 и модуля 12.

#### Шаг 1. Создать манифест

Команда пишет манифест в файл: headless Service и StatefulSet из трёх подов с томом по 100 МиБ. Каждый под при первом старте пишет в свой том файл `born` с именем и временем, а затем отдаёт каталог `/data` по HTTP.

```bash
cat > ~/lab/k8s/02-3/sts.yaml <<'EOF'
apiVersion: v1
kind: Service
metadata: {name: web}
spec:
  clusterIP: None
  selector: {app: web}
  ports: [{name: http, port: 80}]
---
apiVersion: apps/v1
kind: StatefulSet
metadata: {name: web}
spec:
  serviceName: web
  replicas: 3
  selector: {matchLabels: {app: web}}
  template:
    metadata: {labels: {app: web}}
    spec:
      terminationGracePeriodSeconds: 2
      containers:
      - name: web
        image: busybox:1.37
        env: [{name: VERSION, value: v1}]
        command:
        - sh
        - -c
        - |
          [ -f /data/born ] || echo "$(hostname) $(date +%T)" > /data/born
          echo $VERSION > /data/version
          httpd -f -p 80 -h /data
        readinessProbe: {httpGet: {path: /born, port: 80}, periodSeconds: 2}
        volumeMounts: [{name: data, mountPath: /data}]
  volumeClaimTemplates:
  - metadata: {name: data}
    spec:
      accessModes: [ReadWriteOnce]
      resources: {requests: {storage: 100Mi}}
EOF
```

| Часть манифеста | Значение |
|---|---|
| `clusterIP: None` | Service без виртуального IP, то есть headless |
| `serviceName: web` | StatefulSet привязан к Service `web` для DNS-имён |
| `terminationGracePeriodSeconds: 2` | быстрая остановка: `sh` как PID 1 не обрабатывает SIGTERM |
| `echo … > /data/born` | записать файл при первом старте; при втором его не трогают |
| `httpd -f -p 80 -h /data` | отдавать каталог `/data` по HTTP на порту 80 |
| `readinessProbe … /born` | под готов, когда файл `born` отдаётся |
| `volumeClaimTemplates` | шаблон PVC `data`, 100 МиБ, один писатель |

Команда ничего не печатает: она только создаёт файл.

| Часть команды | Значение |
|---|---|
| `scale sts web --replicas=1` | изменить желаемое число подов до одного |
| `get pods -w` | следить за изменениями списка подов |
| `get pvc` | список заявок на тома |

Результат наблюдения: сначала `web-2` переходит в `Terminating`, и только примерно через 3 секунды то же происходит с `web-1`; вся остановка занимает около 6 секунд. Результат второй команды:

```
NAME         STATUS
data-web-0   Bound
data-web-1   Bound
data-web-2   Bound
```

Разбор:

1. Поды удаляются в обратном порядке: `web-2`, затем `web-1`, а контроллер ждёт полной остановки каждого.
2. Заявок по-прежнему три: политика `Retain` по умолчанию не удаляет PVC при уменьшении числа подов.

#### Шаг 2. Вернуть число подов

Команда возвращает три пода и читает файлы `born` у `web-1` и `web-2`.

```bash
kubectl scale sts web --replicas=3
kubectl rollout status sts/web
for p in web-1 web-2; do kubectl exec $p -- cat /data/born; done
```

| Часть команды | Значение |
|---|---|
| `scale … --replicas=3` | вернуть три пода |
| `for p in web-1 web-2` | перебрать два пода |
| `cat /data/born` | прочитать файл, созданный при первом старте |

Результат (время у вас будет другим):

```
web-1 09:22:54
web-2 09:22:58
```

Разбор: время в файлах совпадает со временем первого старта этих подов в шаге 1, потому что вернувшиеся поды получили старые заявки со старыми данными. Для БД это удобно, а для кластерного приложения (Kafka, Elasticsearch) реплика с устаревшими данными может быть вредна.

#### Шаг 3. Включить удаление PVC при уменьшении

Команда меняет политику так, чтобы PVC лишних подов удалялись, уменьшает число подов до двух и снова увеличивает до трёх.

```bash
kubectl patch sts web -p \
  '{"spec":{"persistentVolumeClaimRetentionPolicy":{"whenScaled":"Delete","whenDeleted":"Retain"}}}'
kubectl scale sts web --replicas=2
sleep 12
kubectl get pvc -o custom-columns=NAME:.metadata.name,STATUS:.status.phase
kubectl scale sts web --replicas=3
kubectl rollout status sts/web
kubectl exec web-2 -- cat /data/born
```

| Часть команды | Значение |
|---|---|
| `patch sts web -p '…'` | точечно изменить поле политики |
| `whenScaled: Delete` | удалять PVC подов, которых больше нет |
| `whenDeleted: Retain` | при удалении StatefulSet PVC оставлять |
| `sleep 12` | дать сборщику мусора время удалить заявку |

Результат (после уменьшения до двух подов):

```
NAME         STATUS
data-web-0   Bound
data-web-1   Bound
```

После возврата до трёх подов `web-2` выводит новый файл, например `web-2 09:24:15`.

Разбор:

1. Заявка `data-web-2` удалена вместе с подом: политика `whenScaled: Delete` сработала.
2. Новый `web-2` получил новую пустую заявку, поэтому записал в `born` новое время, а не `09:22:58`.
3. Время в файле у вас будет другим: важно, что оно не равно прежнему.

#### Шаг 4. Удалить StatefulSet

Команда удаляет StatefulSet и смотрит, что осталось от дисков.

```bash
kubectl delete sts web
kubectl get pvc -o custom-columns=NAME:.metadata.name,STATUS:.status.phase
```

| Часть команды | Значение |
|---|---|
| `delete sts web` | удалить контроллер вместе с подами |
| `get pvc` | проверить заявки |

Результат: после удаления StatefulSet заявки `data-web-0`, `data-web-1` и `data-web-2` остаются в списке в статусе `Bound`.

Разбор: при `whenDeleted: Retain` у заявок нет ссылки владельца на StatefulSet, поэтому сборщик мусора их не тронул. Так накапливаются осиротевшие PVC, и поэтому их нужно искать и убирать (§3). Удаление namespace сразу удалит всё.

```bash
kubectl delete pvc --all
```

Команда удаляет все заявки текущего namespace, чтобы следующий опыт начался с пустых томов.

#### Шаг 5. Сравнить OrderedReady и Parallel

Команда создаёт копию манифеста с `podManagementPolicy: Parallel`, запускает её и измеряет время, затем повторяет с исходным манифестом.

```bash
sed 's/^  serviceName: web$/  serviceName: web\n  podManagementPolicy: Parallel/' \
  ~/lab/k8s/02-3/sts.yaml > ~/lab/k8s/02-3/sts-par.yaml
t0=$(date +%s)
kubectl apply -f ~/lab/k8s/02-3/sts-par.yaml
kubectl rollout status sts/web
echo "Parallel: $(( $(date +%s)-t0 ))s"
kubectl get pods -l app=web -o custom-columns=POD:.metadata.name,CREATED:.metadata.creationTimestamp
kubectl delete sts web
kubectl delete pvc --all
t0=$(date +%s)
kubectl apply -f ~/lab/k8s/02-3/sts.yaml
kubectl rollout status sts/web
echo "OrderedReady: $(( $(date +%s)-t0 ))s"
```

| Часть команды | Значение |
|---|---|
| `sed 's/…/…/'` | вставить строку `podManagementPolicy: Parallel` после `serviceName` |
| `t0=$(date +%s)` | запомнить время старта в секундах |
| `$(( $(date +%s)-t0 ))` | вычислить прошедшие секунды |
| `delete pvc --all` | убрать диски, чтобы оба запуска стартовали с нуля |

Результат (на стенде автора):

- Parallel: 8 с, все три пода созданы в одну секунду.
- OrderedReady: 14 с.

Разбор:

1. При `Parallel` поды стартуют одновременно, поэтому общее время близко к времени одного пода.
2. При `OrderedReady` времена складываются: каждый следующий под ждёт готовности предыдущего.
3. Разница растёт с числом подов: при 20 подах она станет заметной.

**Итог.**

| Что узнали | Где видно |
|---|---|
| Уменьшение числа подов удаляет поды в обратном порядке и оставляет PVC | шаг 1 |
| Вернувшиеся поды получают старые данные | шаг 2 |
| `whenScaled: Delete` удаляет PVC и даёт пустой том при возврате | шаг 3 |
| Удаление StatefulSet не удаляет PVC при `Retain` | шаг 4 |
| `Parallel` запускает поды быстрее, чем `OrderedReady` | шаг 5, 8 с против 14 с |

**Уборка.**

```bash
kubectl delete sts web
kubectl delete pvc --all
rm -f ~/lab/k8s/02-3/sts-par.yaml
```

Команды удаляют StatefulSet, его заявки и временный манифест; Service `web` остаётся для следующей работы.

**Вопросы для самопроверки.**

1. Почему после уменьшения до одного пода все три PVC остались?
2. Что произойдёт с данными при возврате числа подов, если `whenScaled: Delete`?
3. Влияет ли `podManagementPolicy: Parallel` на обновление шаблона?

<details>
<summary>Ответы</summary>

1. Политика хранения по умолчанию `Retain`, поэтому контроллер не удаляет заявки при масштабировании.
2. Заявки лишних подов удаляются, а при возврате создаются новые пустые, поэтому под начнёт с чистого тома.
3. Нет, политика влияет только на масштабирование. Обновление идёт по одному поду от старшего номера к младшему, пока вы не разрешите пачки через `maxUnavailable` (§3).

</details>

### Лабораторная работа 3. Partition, сломанная ревизия и maxUnavailable

**Цель.** Обновить один под через partition. Затем сломать выкат, вернуть шаблон и исправить застрявший под вручную. В конце проверить обновление пачками через `maxUnavailable`.

**Что понадобится.** Манифест из шага 1 работы 1, namespace `lab-02-3`, образ `busybox:1.37`.

**Схема опыта.**

```
шаг 1: partition=2          web-0 v1   web-1 v1   web-2 v2
шаг 2: partition=0          web-0 v2   web-1 v2   web-2 v2
шаг 3: ломаем шаблон        web-2 CrashLoopBackOff, web-0 и web-1 нетронуты
       откатываем шаблон    web-2 всё ещё сломан
шаг 4: удаляем web-2        web-2 v2 на рабочей ревизии
шаг 5: maxUnavailable=2     поды обновляются парами, если гейт включён
```

Схема 9. Пять шагов работы: канарейка, полный выкат, застрявший откат, ручная починка, пачки.

#### Шаг 1. Обновить только один под

Команда создаёт StatefulSet, включает partition и меняет значение переменной версии в шаблоне. Затем она печатает версию и ревизию каждого пода.

```bash
kubectl apply -f ~/lab/k8s/02-3/sts.yaml
kubectl rollout status sts/web
kubectl patch sts web -p \
  '{"spec":{"updateStrategy":{"rollingUpdate":{"partition":2}}}}'
kubectl set env sts/web VERSION=v2
sleep 15
for p in web-0 web-1 web-2; do
  echo "$p $(kubectl get pod $p -o jsonpath='{.metadata.labels.controller-revision-hash}')" \
    "$(kubectl exec $p -- cat /data/version)"
done
T='current={.status.currentRevision} update={.status.updateRevision} '
T+='updated={.status.updatedReplicas}{"\n"}'
kubectl get sts web -o jsonpath="$T"
kubectl rollout status sts/web --timeout=5s
```

| Часть команды | Значение |
|---|---|
| `partition: 2` | обновлять только поды с номером 2 и выше |
| `set env sts/web VERSION=v2` | изменить переменную в шаблоне: это новая ревизия |
| `controller-revision-hash` | метка пода с хешем его ревизии |
| `cat /data/version` | версия, которую скрипт записал при старте |
| `rollout status --timeout=5s` | показать состояние выката и не ждать дольше 5 с |

Результат (хеши ревизий в выводе заменены обозначениями `<h1>`, `<h2>`, `<h3>` — у вас будут свои значения):

```
web-0 web-<h1> v1
web-1 web-<h1> v1
web-2 web-<h2> v2
current=web-<h1> update=web-<h2> updated=1
partitioned roll out complete: 1 new pods have been updated...
```

Разбор:

1. `web-2` на новой ревизии и версии `v2`, а `web-0` и `web-1` остались на `v1`: partition защитил их.
2. `current` и `update` различаются, потому что выкат остановлен ограничением, а не завершён.
3. `updated=1` — обновлён один под из трёх.
4. Сообщение `partitioned roll out complete` говорит, что для заданного partition выкат закончен.

#### Шаг 2. Снять partition

Команда обнуляет partition и ждёт обновления остальных подов; затем перечисляет ревизии.

```bash
kubectl patch sts web -p '{"spec":{"updateStrategy":{"rollingUpdate":{"partition":0}}}}'
kubectl rollout status sts/web
kubectl get controllerrevisions
```

| Часть команды | Значение |
|---|---|
| `partition: 0` | обновлять все поды |
| `rollout status sts/web` | ждать, пока обновление завершится |
| `get controllerrevisions` | список сохранённых ревизий шаблона |

Результат: обновление заканчивается примерно за 6 секунд, поды обновляются по очереди — сначала `web-1`, затем `web-0`. В списке ревизий две строки с именами `web-<h1>` и `web-<h2>`.

Разбор:

1. Порядок обновления от старшего номера к младшему сохранился: `web-2` уже был готов.
2. Каждая версия шаблона хранится отдельной ревизией; по хешу в имени ревизии находят версию пода.

#### Шаг 3. Сломать выкат и откатить шаблон

Команда подставляет в шаблон команду, которая сразу завершается с ошибкой, ждёт 30 секунд и показывает поды. Затем возвращает предыдущую версию шаблона.

```bash
kubectl patch sts web --type=json -p \
  '[{"op":"replace","path":"/spec/template/spec/containers/0/command/2","value":"exit 1"}]'
sleep 30
kubectl get pods -l app=web
kubectl rollout undo sts/web
sleep 45
kubectl get pods -l app=web
T='current={.status.currentRevision} update={.status.updateRevision} '
T+='ready={.status.readyReplicas}{"\n"}'
kubectl get sts web -o jsonpath="$T"
H='{.metadata.labels.controller-revision-hash}'
kubectl get pod web-2 -o jsonpath="web-2 revision=$H{\"\\n\"}"
```

| Часть команды | Значение |
|---|---|
| `--type=json` | патч в формате JSON Patch: операции над путями |
| `command/2` | третий элемент команды, то есть скрипт запуска |
| `value":"exit 1"` | команда, которая сразу падает |
| `rollout undo sts/web` | вернуть шаблон предыдущей ревизии |
| `readyReplicas` | число готовых подов |

Результат первой проверки: `web-2` в `CrashLoopBackOff`, а `web-0` и `web-1` не тронуты — порядок обновления защитил их. Результат после отката шаблона:

```
web-0 1/1 Running 0
web-1 1/1 Running 0
web-2 0/1 CrashLoopBackOff 3
current=web-<h2> update=web-<h2> ready=2
web-2 revision=web-<h3>
```

Разбор:

1. Обновление остановилось на `web-2`: старший под обновляется первым, и выкат не пошёл дальше.
2. После отката `current` и `update` совпадают, обе указывают на рабочую ревизию.
3. Но `web-2` остался на сломанной ревизии `web-<h3>` и не готов: контроллер ждёт его Ready и сам его не заменит.
4. Команда `rollout undo` вернула шаблон, но не тронула уже запущенный сломанный под. Это поведение описано в документации как forced rollback (§5).

#### Шаг 4. Починить застрявший под

Команда удаляет сломанный под и проверяет, на какой ревизии появился новый.

```bash
kubectl delete pod web-2
kubectl wait --for=condition=Ready pod/web-2
H='{.metadata.labels.controller-revision-hash}'
kubectl get pod web-2 -o jsonpath="web-2 revision=$H{\"\\n\"}"
kubectl exec web-2 -- cat /data/version
```

| Часть команды | Значение |
|---|---|
| `delete pod web-2` | убрать под со сломанной ревизии |
| `wait --for=condition=Ready` | ждать готовности нового пода |
| `cat /data/version` | проверить версию в томе |

Результат:

```
web-2 revision=web-<h2>
v2
```

Разбор:

1. Новый `web-2` создан из текущей рабочей ревизии `web-<h2>`.
2. Файл `version` содержит `v2`: том тот же, скрипт записал версию заново при старте.
3. Вывод: после отката шаблона StatefulSet нужно удалить вручную поды, которые уже запустились со сломанной версией.

#### Шаг 5. Обновить пачками через maxUnavailable

Этот шаг вы выполняете сами, результаты в нём — ожидаемые.

В Kubernetes 1.36 гейт `MaxUnavailableStatefulSet` выключен по умолчанию (§3), поэтому сначала проверим, сохранил ли API-сервер поле. Затем создадим четыре пода, которые стартуют с задержкой 8 секунд, и обновим их.

```bash
cat > ~/lab/k8s/02-3/sts-burst.yaml <<'EOF'
apiVersion: apps/v1
kind: StatefulSet
metadata: {name: burst}
spec:
  serviceName: burst
  replicas: 4
  podManagementPolicy: Parallel
  updateStrategy:
    type: RollingUpdate
    rollingUpdate: {maxUnavailable: 2}
  selector: {matchLabels: {app: burst}}
  template:
    metadata: {labels: {app: burst}}
    spec:
      terminationGracePeriodSeconds: 2
      containers:
      - name: web
        image: busybox:1.37
        env: [{name: VERSION, value: v1}]
        command: ["sh", "-c", "sleep 8; httpd -f -p 80 -h /tmp"]
        readinessProbe: {tcpSocket: {port: 80}, periodSeconds: 1}
EOF
kubectl apply -f ~/lab/k8s/02-3/sts-burst.yaml
kubectl get sts burst -o jsonpath='{.spec.updateStrategy}{"\n"}'
kubectl rollout status sts/burst
kubectl set env sts/burst VERSION=v2
kubectl rollout status sts/burst
kubectl get pods -l app=burst \
  -o custom-columns=POD:.metadata.name,CREATED:.metadata.creationTimestamp
```

| Часть команды | Значение |
|---|---|
| `podManagementPolicy: Parallel` | режим, в котором документация описывает пачки |
| `maxUnavailable: 2` | допускать до двух недоступных подов |
| `sleep 8` | под становится готовым через 8 с после старта |
| `get sts burst … .spec.updateStrategy` | проверить, что поле не отброшено |
| `set env … VERSION=v2` | запустить обновление шаблона |

Ожидаемый результат на стенде 1.36, где гейт выключен: первая проверка выводит стратегию без поля `maxUnavailable` — `{"rollingUpdate":{"partition":0},"type":"RollingUpdate"}`. Поды в последнем списке пересозданы по одному, от `burst-3` к `burst-0`, с шагом не меньше 8 секунд. На кластере с включённым гейтом (1.37) стратегия содержит `"maxUnavailable":2`, а поды пересоздаются парами: сначала `burst-3` и `burst-2` в одну секунду, затем `burst-1` и `burst-0`.

Разбор:

1. Если в выводе первой проверки нет `maxUnavailable`, API-сервер отбросил поле, потому что гейт выключен; обновление тогда идёт по одному поду.
2. Если поле на месте, пары показывают, что лимит недоступных подов равен двум, а не одному.
3. Шаг между пачками не меньше 8 секунд, потому что каждый под становится готовым только после `sleep 8`.

**Итог.**

| Что узнали | Где видно |
|---|---|
| `partition` обновляет только старшие поды | шаг 1 |
| Выкат идёт по убыванию номера, ревизии хранятся отдельными объектами | шаг 2 |
| Откат шаблона не заменяет уже сломанный под | шаг 3 |
| Сломанный под нужно удалить вручную | шаг 4 |
| `maxUnavailable` ускоряет обновление, только если гейт включён | шаг 5 |

**Уборка.** Удаляем все созданные объекты, возвращаем namespace по умолчанию и убираем файлы.

```bash
kubectl delete sts web burst
kubectl delete pvc --all
kubectl config set-context --current --namespace=default
kubectl delete ns lab-02-3
rm -rf ~/lab/k8s/02-3
```

Команды удаляют StatefulSet и заявки, возвращают контекст, удаляют namespace с остатками (Service, поды, события) и каталог файлов. Namespace `orders` не затронут.

**Вопросы для самопроверки.**

1. Почему при `partition: 2` обновился именно `web-2`?
2. Почему после отката шаблона `web-2` остался в `CrashLoopBackOff`?
3. Чем сломанный выкат StatefulSet отличается от Deployment?
4. Как проверить, что `maxUnavailable` работает на вашем кластере?

<details>
<summary>Ответы</summary>

1. Partition ограничивает обновление подами с номером не меньше заданного, а выкат идёт от старшего номера к младшему.
2. При `OrderedReady` контроллер ждёт готовности пода и не заменяет сломанный под даже после возврата шаблона (kubernetes#67250). Нужно удалить под вручную.
3. У Deployment исправленный шаблон создаёт новый ReplicaSet, и застрявшей ревизии нет. У StatefulSet поды стоят в очереди по номерам, и один сломанный блокирует всё.
4. Прочитать `spec.updateStrategy` после создания: если API-сервер сохранил `maxUnavailable`, гейт включён; затем сравнить времена создания подов при обновлении.

</details>
