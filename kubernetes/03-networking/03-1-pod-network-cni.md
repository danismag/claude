## 1. Какую задачу решает сеть подов

Сеть подов даёт каждому поду адрес и связь с остальными подами, чтобы приложение не думало ни об узлах, ни о пробросе портов. Ниже разобраны три требования модели, граница между Kubernetes и CNI и четыре способа связать узлы.

### Три требования модели

Kubernetes предъявляет к сети три требования, и все они говорят об IP-адресах подов:

1. У каждого пода свой IP-адрес, уникальный во всём кластере.
2. Любой под достигает любой другой под по этому адресу без **NAT** (network address translation) — подмены адреса в заголовке пакета.
3. Агенты узла, например kubelet, достигают все поды своего узла.

Из второго требования следует, что под видит себя тем адресом, каким его видят остальные. Поэтому приложение может сообщить свой адрес другому сервису, а порты не нужно пробрасывать, как это делает `docker run -p`.

### Что остаётся на CNI

Kubernetes сам не строит сеть: он только раздаёт узлам подсети и вызывает плагин при создании пода. Интерфейсы, маршруты и туннели создаёт CNI (01-2): плагины и агент на каждом узле.

```
Kubernetes (control plane)           CNI (плагины и агент на узле)
 - выдаёт узлу подсеть podCIDR        - создаёт интерфейс в netns пода
 - хранит Pod и Node в API            - выбирает IP пода из подсети
 - не знает, как идут пакеты          - прописывает маршруты, туннели, eBPF
```

Схема 2. Разделение труда: Kubernetes определяет, что нужно, CNI определяет, как это сделано.

Поэтому «сеть кластера» зависит от выбранного CNI: у одного кластера поды связаны маршрутами, у другого — туннелями, а правила NetworkPolicy (03-6) выполняет тоже CNI. Если CNI не установлен, узел остаётся `NotReady`, а новые поды не получают IP.

### Четыре способа связать узлы

Способы различаются тем, что пакет пода несёт между узлами, и от этого зависят MTU (§5), правила firewall и вид трафика на проводе.

- **Маршрутизация** (routing) — каждый узел знает, через какой узел достижима подсеть соседа, и пакет идёт как есть. Так работает kindnet стенда и Calico в режиме BGP.
- **Оверлей** (overlay) — пакет пода кладут внутрь пакета между узлами. Такая **инкапсуляция** (encapsulation) нужна, когда сеть между узлами не знает подсетей подов. Примеры: VXLAN, Geneve, IP-in-IP.
- **eBPF** — программы в ядре сами пересылают пакеты, минуя часть сетевого стека. Так работает Cilium, а вместо veth он может создавать устройства **netkit** (для Cilium нужно ядро 6.8 и новее).
- **Сеть облака** — адрес пода берётся из подсети VPC, и облачная сеть сама знает маршруты. Примеры: AWS VPC CNI, Azure CNI.

```
маршрутизация:  [ IP пода -> IP пода ]                           пакет идёт как есть
оверлей:        [ IP узла -> IP узла | UDP | [ IP пода -> IP пода ] ]   пакет пода внутри
```

Схема 3. Два основных пути между узлами: в оверлее на проводе виден внешний пакет с адресами узлов, а адреса подов спрятаны внутри.

Сравнение путей пакета в Flannel VXLAN, Calico BGP и Cilium есть в курсе `networks` (08-2). Здесь мы берём из него только то, что нужно для эксплуатации.

## 2. Как устроена сеть пода

Сеть пода собирается в четыре этапа: containerd вызывает плагин, плагин создаёт интерфейс и берёт адрес, агент связывает узлы, а узел выпускает трафик наружу. Разберём каждый этап на примере стенда.

### Вызов CNI при создании песочницы

Когда kubelet просит создать песочницу, containerd создаёт network namespace пода и запускает плагины из каталога `/opt/cni/bin` по конфигу в `/etc/cni/net.d` (01-2). **Плагин** (plugin) — обычный исполняемый файл: containerd передаёт ему конфиг через stdin, а команду и параметры — через переменные окружения, например `CNI_COMMAND=ADD`, `CNI_NETNS` и `CNI_IFNAME`. Плагин печатает результат в JSON: выданные адреса и маршруты.

Команд у плагина немного: ADD подключает под к сети, DEL отключает, CHECK проверяет состояние. Конфиг может содержать цепочку плагинов (**chained plugins**), и каждый следующий получает результат предыдущего.

```
containerd: создал netns пода, читает /etc/cni/net.d
     │  stdin: JSON-конфиг    env: CNI_COMMAND=ADD, CNI_NETNS, CNI_IFNAME
     ▼
 плагин 1: интерфейс + IPAM ──результат: IP, маршруты──►  плагин 2: portmap  ──► итог в containerd
```

Схема 4. Вызов CNI: плагины работают по очереди, каждый видит результат предыдущего.

Типичная цепочка состоит из пяти шагов, и в разных CNI меняются только исполнители.

| Шаг | Кто делает | Что получается |
|---|---|---|
| Интерфейс | ptp, bridge, calico, cilium-cni | veth-пара: eth0 в поде, veth на узле |
| Адрес | IPAM: host-local, calico-ipam, облачный | IP из подсети узла или VPC |
| Маршруты | основной плагин | в поде default через шлюз, на узле /32 на veth |
| Доп. функции | portmap, bandwidth, tuning | hostPort, ограничение скорости, sysctl |
| Связь узлов | агент CNI (DaemonSet) | маршруты, BGP, туннели, eBPF |

### Интерфейс пода и адрес

Основной плагин создаёт **veth-пару** (virtual ethernet) — два виртуальных интерфейса, соединённых напрямую: что вошло в один, выходит из другого. Один конец, `eth0`, остаётся в network namespace пода, второй попадает в корневой namespace узла. В поде плагин прописывает default-маршрут на шлюз, а на узле — маршрут на адрес пода через его veth.

```
 узел lab-worker2, подсеть 10.244.3.0/24
 ┌─────────────────────────────────────────────────────────────┐
 │ netns пода                       корневой netns узла        │
 │  eth0 10.244.3.69/24  <==veth==>  vethe045ab2f              │
 │  default via 10.244.3.1           ip route:                 │
 │                                   10.244.3.69 dev vethe045ab2f │
 └─────────────────────────────────────────────────────────────┘
```

Схема 5. Один под на узле: шлюз пода — адрес узла на стороне veth, а маршрут к поду на узле ведёт в его veth.

Адрес пода выдаёт **IPAM** (IP address management) — модуль, который хранит, какие адреса заняты. Стандартный `host-local` берёт адрес из подсети узла и записывает по файлу на каждый выданный адрес. Подсеть узла приходит из объекта Node: поле `spec.podCIDR` заполняет контроллер узлов в kube-controller-manager. Он режет `--cluster-cidr` на куски с маской `--node-cidr-mask-size` (по умолчанию /24 для IPv4). Подсеть привязана к узлу до его удаления.

```
cluster-cidr 10.244.0.0/16  ──режем по /24──►
  lab-control-plane  10.244.0.0/24   узел 172.20.0.2
  lab-worker3        10.244.1.0/24   узел 172.20.0.4
  lab-worker         10.244.2.0/24   узел 172.20.0.3
  lab-worker2        10.244.3.0/24   узел 172.20.0.5
```

Схема 6. Подсети подов на стенде: по /24 на узел из общего /16. Calico, Cilium и облачные CNI часто игнорируют `podCIDR` и ведут свой IPAM.

### Шлюз пода и ARP

В плагине ptp все пакеты пода идут через шлюз, даже пакеты к соседу по узлу. Плагин настраивает в поде адрес с маской /24, но удаляет обычный маршрут подсети. Вместо него он ставит маршрут к шлюзу `10.244.2.1` прямо через `eth0` и маршрут всей подсети через этот шлюз.

```
маршруты в поде p-lab-worker:
  default via 10.244.2.1 dev eth0
  10.244.2.0/24 via 10.244.2.1 dev eth0
  10.244.2.1 dev eth0 scope link src 10.244.2.84
адреса и маршруты на узле lab-worker:
  veth пода: адрес 10.244.2.1/32 (адрес шлюза)
  10.244.2.84 dev veth… scope host
```

Схема 7. Маршруты ptp: под знает только шлюз, а узел знает каждый свой под отдельной строкой.

**ARP** (Address Resolution Protocol) — протокол, который по IP-адресу находит MAC-адрес соседа в том же сегменте. Под спрашивает по ARP только MAC шлюза, а отвечает узловой конец veth, потому что ptp назначает ему адрес шлюза с маской /32. Один и тот же адрес `.1` стоит на всех veth узла, и ответ всегда приходит с того veth, который соединён с подом. В IPv6 ту же роль играет протокол NDP.

Другие CNI решают ту же задачу иначе. Calico прописывает в поде шлюз `169.254.1.1`, которого нет ни на одном интерфейсе. На ARP-запрос за этот адрес узел отвечает через **proxy ARP** — режим, в котором ядро отвечает за чужой адрес. Плагин bridge подключает все поды узла к общему мосту `cni0`, поэтому поды одного узла обмениваются кадрами напрямую, без маршрутизации на узле.

### Связь между узлами: путь пакета

Узел пересылает пакеты подов как обычный Linux-маршрутизатор. Плагин ptp включает пересылку пакетов (`net.ipv4.ip_forward=1`), а путь выбирает таблица маршрутов узла. На схеме ниже — путь пакета между подами стенда на разных узлах.

```
p-lab-worker 10.244.2.84                                    p-lab-worker2 10.244.3.69
 1. eth0 пода ─veth─► lab-worker:  10.244.3.0/24 via 172.20.0.5 dev eth0
 2.                   eth0 lab-worker ── сеть Docker ──► eth0 lab-worker2
 3.                   lab-worker2: 10.244.3.69 dev vethe045ab2f ─veth─► eth0 пода
```

Схема 8. Путь пакета под → под: три решения о маршруте и ни одной подмены адреса.

Разбор пути по шагам:

1. Под отправляет пакет на MAC шлюза, и пакет появляется на узле-источнике из veth пода.
2. Узел-источник находит маршрут к подсети соседа и отправляет пакет через `eth0` на MAC узла-назначения; TTL уменьшается на 1.
3. Узел-назначение находит маршрут /32 к поду и передаёт пакет в его veth.
4. Ответ идёт тем же путём в обратную сторону, через маршруты к подсети `10.244.2.0/24`.

Адреса по дороге не меняются, но запись о соединении на обоих узлах всё равно появляется. Её заводит **conntrack** (connection tracking) — подсистема ядра, которая ведёт таблицу соединений, проходящих через узел. Поэтому общая таблица conntrack узла расходуется и трафиком между подами.

kindnet на стенде работает без оверлея: его агент на каждом узле прописывает маршрут «подсеть соседа — через IP соседа» (01-2). Пакет пода уходит с узла как есть, с адресами подов. Такой способ работает, только если все узлы стоят в одном L2-сегменте или маршрутизатор между ними знает подсети подов. Узлам в разных подсетях без такого маршрутизатора нужен оверлей или BGP.

Другие CNI решают эту задачу по-своему. Таблица ниже сравнивает типичные режимы по тому, что видно на проводе и что нужно открыть в firewall.

| CNI и режим | Между узлами | Накладные байты | Что открыть между узлами |
|---|---|---|---|
| Flannel VXLAN | туннель | 50 | UDP 8472 |
| Calico BGP | маршруты | 0 | TCP 179 |
| Calico IP-in-IP | туннель | 20 | IP-протокол 4 |
| Calico VXLAN | туннель | 50 | UDP 4789 |
| Cilium (туннель) | VXLAN или Geneve, eBPF | 50 | UDP 8472 или UDP 6081 |

NetworkPolicy в этой таблице не показана: её выполняют Calico и Cilium, а Flannel не выполняет вовсе (03-6). Порты и накладные байты взяты из документации проектов. Порт 8472 — значение ядра Linux по умолчанию для VXLAN, а 4789 — стандартный порт VXLAN по RFC 7348; Geneve использует UDP 6081.

### Выход наружу: SNAT и conntrack

Адреса подов (`10.244.x.x`) не маршрутизируются во внешней сети, поэтому узел подменяет адрес источника на свой. **SNAT** (source NAT) меняет адрес отправителя в пакете, а вариант **masquerade** берёт адрес исходящего интерфейса автоматически. Подмену делает ядро по таблице conntrack, и по той же таблице ответ возвращается нужному поду.

На стенде правила создаёт агент kindnet через iptables. В цепочку `POSTROUTING` таблицы nat он добавляет переход в свою цепочку `KIND-MASQ-AGENT` для всех пакетов, адресованных не самому узлу. В этой цепочке трафик внутри `cluster-cidr` пропускается без изменений, а всё остальное маскируется. Поэтому внешняя система видит адрес узла, а не пода (§5).

```
под 10.244.2.84 ──veth──► узел lab-worker: POSTROUTING -> KIND-MASQ-AGENT
   пакет на veth:   10.244.2.84 -> 1.1.1.1      (источник: под)
   пакет на eth0:   172.20.0.3  -> 1.1.1.1      (источник: узел, после MASQUERADE)
```

Схема 9. SNAT на узле: адрес источника меняется между veth и eth0. На стенде Docker ещё раз подменяет адрес на выходе с хоста, но это уже за пределами кластера.

Запись conntrack хранит соединение в двух направлениях: исходное (под → сервер) и ответное (сервер → узел). Правила таблицы nat проверяет только первый пакет соединения. Остальные пакеты ядро меняет по записи, а ответ сервера, пришедший на адрес узла, получает обратно адрес пода.

```
запись conntrack на узле lab-worker (упрощённо):
  tcp ESTABLISHED  src=10.244.2.84 dst=1.1.1.1    sport=39456 dport=80   <- исходное
                   src=1.1.1.1    dst=172.20.0.3 sport=80    dport=39456 <- ответное
```

Схема 10. Одна запись conntrack: по второй строке ядро узнаёт ответ сервера и возвращает его поду.

Порт источника masquerade старается сохранить, как в работе 3. Если два пода узла открыли соединение к одному серверу с одного порта, ядро меняет порт второго соединения. Размер таблицы ограничен параметром `nf_conntrack_max`. kube-proxy по умолчанию выставляет его из расчёта 32768 записей на ядро CPU, но не меньше 131072, а простаивающее TCP-соединение держит в таблице 24 часа (§6).

## 3. Как управлять сетью подов

Сетью управляют до создания кластера и через поля узла и пода. Разберём выбор CNI и подсетей, dual-stack, предел подов на узле, поды в сети узла и дополнительные функции.

### Выбор CNI и подсетей

CNI выбирают при создании кластера, а потом меняют с трудом: подсети узлов и адреса подов привязаны к плагину. kubeadm принимает подсеть подов в поле `networking.podSubnet` и ждёт, что вы поставите CNI отдельно. Пока CNI не установлен, узлы остаются `NotReady`, а CoreDNS висит в `Pending`.

kind ставит kindnet и подсеть `10.244.0.0/16` сам. Чтобы поставить другой CNI, в конфиге kind задают `networking.disableDefaultCNI: true` и при необходимости `networking.podSubnet`. Стенд курса остаётся на kindnet.

Подсеть узла нельзя менять на живом узле: после назначения поле `spec.podCIDR` неизменяемо. Размер подсети на узел задаёт `--node-cidr-mask-size` контроллера. Чтобы вырастить его, узлы приходится пересоздавать (§6).

### IPv6 и dual-stack

**Dual-stack** — режим, в котором под получает одновременно IPv4- и IPv6-адрес; в Kubernetes он стабилен с версии 1.23. Для него в `--cluster-cidr` задают два диапазона, и узел получает две подсети в `spec.podCIDRs`: по умолчанию /24 для IPv4 и /64 для IPv6. CNI тоже должен поддерживать оба семейства адресов.

В kind режим включают полем `networking.ipFamily: dual`, а подсеть подов IPv6 по умолчанию — `fd00:10:244::/56`. Адреса пода в dual-stack лежат в `status.podIPs`, а `status.podIP` хранит первый из них. Service выбирает семейства своими полями `ipFamilies` и `ipFamilyPolicy`. Стенд курса работает только на IPv4.

### Сколько подов на узле

Предел подов на узле задаёт поле `maxPods` в конфигурации kubelet, по умолчанию 110. Scheduler видит этот предел как `status.allocatable.pods` узла и не назначает больше. Рядом лежит поле `podsPerCore` (по умолчанию 0, то есть выключено), которое ограничивает число подов числом ядер.

Предел подов и размер подсети узла — два независимых лимита. Если подсеть меньше `maxPods`, адреса кончатся раньше. Поэтому подсеть узла выбирают с запасом, а `maxPods` меняют вместе с `--node-cidr-mask-size`.

### Под в сети узла

Иногда поду нужна сеть узла, а не своя. Для этого есть три механизма, и у каждого своя цена.

- **hostNetwork: true** — под работает в network namespace узла, и его IP равен IP узла. Так работают kube-proxy и kindnet. Порты конфликтуют с другими подами узла, а NetworkPolicy обычно на такой под не действует (03-6). Такому поду нужен `dnsPolicy: ClusterFirstWithHostNet`, иначе имена Service не разрешатся (03-3).
- **hostPort** — порт узла перенаправляется на порт пода правилом DNAT (подмена адреса назначения, 03-2), которое ставит плагин `portmap`. На узле такой порт занимает один под, и трафик обходит Service.
- **NodePort** — порт открывается на всех узлах и ведёт на Service (03-2). Диапазон по умолчанию — 30000–32767.

### Дополнительные функции CNI

Кроме адреса и маршрутов, CNI добавляет функции, которые включаются отдельно. Плагин `bandwidth` ограничивает скорость пода по аннотациям `kubernetes.io/ingress-bandwidth` и `kubernetes.io/egress-bandwidth`, но в конфиг kindnet он не входит. Egress gateway в Cilium и Istio закрепляет за подами фиксированный внешний IP, чтобы внешние системы видели стабильный адрес. Поду с несколькими интерфейсами нужен отдельный проект, например Multus: сам Kubernetes знает только один адрес на под (в dual-stack — два).

## 4. Как увидеть сеть пода

Сеть видна на пяти уровнях: адреса в объектах API, интерфейсы в поде, маршруты и veth на узле, пакеты на проводе и правила SNAT. Разберём каждый уровень и инструмент для него.

### Адреса пода и узла

Адрес пода хранится в статусе: `status.podIP` и список `status.podIPs` (два адреса в dual-stack). Адрес узла, на котором работает под, лежит в `status.hostIP` и в `status.hostIPs` (GA с 1.30). Колонка `IP` в `kubectl get pods -o wide` показывает `podIP`. У подов с `hostNetwork` этот адрес совпадает с адресом узла.

Подсеть узла лежит в `spec.podCIDR` (в dual-stack — `podCIDRs`) объекта Node. Сопоставление «под — подсеть — узел» даёт первый ответ на вопрос, из какой подсети пришёл адрес и не вышел ли он за неё.

### Сеть внутри пода

Внутри пода нужны три вещи: адрес интерфейса, default-маршрут и MTU. Их показывают `ip addr`, `ip route` и файл `/sys/class/net/eth0/mtu`; `traceroute` и `ping` проверяют путь до другого пода. Утилиты есть в образе busybox, а для образов без них подключают отладочный контейнер (00-2 §5).

В выводе `traceroute` каждая строка — один узел на пути. Первый хоп — шлюз пода, то есть узел-источник; следующий — узел-назначение, который отвечает адресом своего интерфейса. Последний хоп — сам под. Отсутствие лишних хопов говорит, что туннеля нет.

### Узел: маршруты, veth и IPAM

На узле смотрят таблицу маршрутов (`ip route`): строки «подсеть соседа — через IP узла» и строки «адрес пода — dev veth…». Чтобы найти veth пода, берут номер интерфейса из `ip -o link` в поде: имя вида `eth0@if12` означает, что второй конец пары — интерфейс с индексом 12 на узле. Для поиска по IP проще взять строку из таблицы маршрутов. Команда `ip route get <IP пода>` показывает, какой маршрут и какой интерфейс ядро выберет для этого адреса прямо сейчас.

IPAM `host-local` хранит выданные адреса в файлах: у kindnet они лежат в `/run/cni-ipam-state/kindnet`, у стандартной установки — в `/var/lib/cni/networks/<имя сети>`. Число файлов сравнивают с числом подов узла, чтобы поймать утечку (§5).

### Пакеты на проводе: tcpdump

Когда таблиц недостаточно, смотрят сами пакеты. На узле полезны три точки: veth пода, eth0 узла и все интерфейсы сразу (`-i any`). Сравнение адресов в этих точках показывает, где пакет менялся или пропал.

```
 под A ── eth0 ══veth═► [ точка 1: vethA ] ─ узел A ─ [ точка 2: eth0 узла A ] ───┐
                                                                                  │ сеть
 под B ◄─ eth0 ══veth══ [ точка 4: vethB ] ─ узел B ─ [ точка 3: eth0 узла B ] ◄──┘
```

Схема 11. Четыре точки захвата на пути пакета. Пакет виден в точке 2 и не виден в точке 3: его теряет сеть между узлами. Виден в точке 3 и не виден в точке 4: проблема на узле назначения.

На узлах kind нет `tcpdump`, поэтому его запускают из контейнера в network namespace узла (работа 2). На реальном узле хватает `sudo tcpdump -ni eth0 host <IP пода>` или `kubectl debug node/<узел>` (00-2).

### Правила SNAT

Правила маскарада видны в таблице nat узла: `iptables-save -t nat` показывает цепочки, а `grep` оставляет нужную. На стенде это цепочка `KIND-MASQ-AGENT`; у других CNI цепочка называется иначе, а у Cilium подмену может делать eBPF без iptables. Проверка в работе 3.

## 5. Что ломается и как найти причину

Поломки сети подов делятся по симптому на пять классов. Это под без IP, нет связи между узлами, зависающие большие пакеты, проблемы на выходе из кластера и нехватка адресов. Для каждого класса дан порядок поиска.

### Под не получает IP

Симптом: под висит в `ContainerCreating`, а в событиях стоит `FailedCreatePodSandBox … failed to setup network`. Сам под тут ни при чём: ошибка возникла в CNI при создании песочницы. Если CNI не установлен или не стартовал, узел показывает `NotReady` с причиной `cni plugin not initialized`.

Порядок поиска:

1. `kubectl describe pod` — текст события: какой плагин и какая ошибка.
2. Агент CNI на этом узле запущен? Для нового узла проверьте, что DaemonSet агента допускается taints узла.
3. В `/etc/cni/net.d` на узле есть конфиг, а в `/opt/cni/bin` — бинарники плагинов.
4. Хватает ли адресов в подсети узла: ошибка `no IP addresses available in range set` (§5).
5. Логи containerd и агента CNI на узле: `journalctl -u containerd`, `kubectl logs` пода агента.

### Поды на разных узлах не видят друг друга

Симптом: поды одного узла связаны, а между узлами пакеты пропадают. Причины сводятся к трём: нет маршрута или сессии BGP, firewall режет туннельный трафик, узлы стоят в разных подсетях при CNI без оверлея. Для kindnet и подобных CNI «разные подсети» — самая частая причина после добавления узлов.

Порядок поиска идёт по пути пакета из §2. Сначала сравнивают `ip route` на старом и новом узле и смотрят `ip route get <IP пода>` на каждом узле пути. Потом ставят захват в точках схемы 11. Пакет есть на eth0 отправителя и нет на eth0 получателя — виновата сеть между узлами. Для оверлея проверяют, проходит ли порт туннеля из таблицы §2, а для BGP — состояние сессий и анонсы.

Если пакет дошёл до eth0 узла-назначения, но не появился на veth пода, его отбросил сам узел. Проверяют пересылку `net.ipv4.ip_forward` и цепочку `FORWARD` в iptables узла. Частая причина — Docker, поставленный на узел: он меняет политику цепочки `FORWARD` на DROP, и чужие пакеты узел больше не пересылает.

### Большие пакеты зависают

Симптом: ping и маленькие запросы проходят, а большие ответы висят. Причина — **MTU** (maximum transmission unit), максимальный размер пакета без фрагментации. Оверлей добавляет заголовок, и пакет пода (1500 байт) не помещается в MTU узла (1500). Если ICMP-сообщение «fragmentation needed» заблокировано, **PMTUD** (path MTU discovery, автоподбор размера по ICMP) не работает, и соединение молча зависает (курс `networks` 02-1).

Проверка: `ping -s <размер> -M do` между подами, где размер плюс 28 байт заголовков не больше MTU. Ключа `-M` нет в ping из busybox, поэтому проверку запускают из образа с iputils, например netshoot. Пакет в 1500 байт даёт полезную нагрузку 1472. Лечится уменьшением MTU интерфейса пода на размер заголовка туннеля (§6).

### Выход наружу: чужой адрес и полная таблица conntrack

Симптом: БД или API партнёра отвергает подключение из кластера, хотя «для сервиса доступ открыт». Причина — SNAT: внешняя сторона видит адрес узла, а не пода. Захват на eth0 узла подтверждает, какой адрес ушёл наружу. При переезде пода на другой узел источник меняется, поэтому открывать доступ по IP приходится на все узлы или использовать egress gateway.

Второй симптом на выходе — новые соединения случайно не устанавливаются, хотя старые работают. Так проявляется переполненная таблица conntrack: ядро не может завести запись и отбрасывает первый пакет соединения. В журнале ядра узла тогда видна строка с текстом `table full, dropping packet`. Текущее число записей лежит в `/proc/sys/net/netfilter/nf_conntrack_count`, а предел — в `nf_conntrack_max` рядом. Лечат ростом предела или сокращением коротких соединений, например пулом подключений в приложении (курс `networks` 06-5).

### Адреса кончаются раньше подов

Симптом: поды висят в `ContainerCreating` с `no IP addresses available in range set`, хотя на узле меньше 110 подов. Причины две: подсеть узла меньше, чем нужно, или IPAM «протекает». Если плагин не получил DEL (например, containerd упал при удалении пода), файл адреса остаётся занятым.

Диагностика: число файлов IPAM на узле сравнивают с числом подов, которые не используют hostNetwork. Лишние файлы содержат ID песочниц, которых нет в `crictl pods`. Сброс — перезагрузка узла, если каталог лежит в `/run`, либо удаление осиротевших файлов. После этого ставят алерт на долю занятых адресов подсети (метрики IPAM есть у Calico и Cilium).

## 6. Пределы и значения по умолчанию

Ниже собраны числа, которые встречались в части. Значения со стенда измерены (работа 4), остальные взяты из документации.

### Адреса и подсети

- **cluster-cidr** — у kind `10.244.0.0/16`.
- **Маска подсети на узел** — `--node-cidr-mask-size`, по умолчанию /24 для IPv4 и /64 для IPv6.
- **Узлов в /16** — 256 при маске /24.
- **Адресов в /24** — 253 для подов: `host-local` не выдаёт адрес сети, шлюз `.1` и broadcast.
- **podCIDR** — после назначения неизменяем.

### Лимиты подов

- **maxPods** — 110 на узел (kubelet).
- **podsPerCore** — 0, то есть выключен.
- **hostNetwork-поды** — адрес из подсети не берут, поэтому занятых адресов меньше, чем подов: на стенде 108 при 110.
- **Предел задаётся min** — меньшее из maxPods, размера подсети и ресурсов узла.

### Туннели и порты

- **VXLAN** — накладные 50 байт поверх IPv4 и 70 байт поверх IPv6; MTU пода 1450 при MTU узла 1500.
- **IP-in-IP** — 20 байт.
- **Порты** — UDP 8472 (Flannel, Cilium), UDP 4789 (Calico VXLAN), UDP 6081 (Geneve), TCP 179 (BGP), протокол 4 (IP-in-IP).
- **MTU пода на стенде** — 1500.

### Таблица conntrack

- **nf_conntrack_max** — kube-proxy ставит 32768 записей на ядро CPU, но не меньше 131072 (`--conntrack-max-per-core`, `--conntrack-min`).
- **Простаивающее TCP-соединение** — 24 часа в таблице (`--conntrack-tcp-timeout-established`).
- **Значение 0 в этих ключах** — kube-proxy не трогает настройки ядра.

### Облачные CNI

- **AWS VPC CNI** — число подов ограничено ENI и их адресами. Формула из документации AWS: ENI × (IP на ENI − 1) + 2, где 2 — поды с hostNetwork. Для m5.large: 3 × (10 − 1) + 2 = 29.
- **Адреса VPC** — подсеть пода делит адреса с остальными ресурсами VPC, и они кончаются.
- **NAT** — между подами и VPC не нужен, наружу трафик идёт через шлюз.

## Лабораторные работы

Работы идут на стенде 00-1 в namespace `lab-03-1`. Подготовка общая: выбрать контекст, создать namespace и два пода-клиента на разных узлах. Под с **nodeName** привязан к узлу в обход scheduler'а — это удобно для опытов и не подходит для рабочих нагрузок (05-3).

Образ `localhost:5001/busybox:1.37` общий для стенда: его кладут в реестр командами из подготовки к лабораторным 02-1. Работы 2 и 3 запускают на хосте контейнеры Docker, поэтому Docker на хосте должен работать без `sudo`.

**Риски подготовки.** Контекст `kind-lab` в `~/.kube/config` не меняется: функция `k` добавляет `-n lab-03-1` к каждой команде. Остальное создаётся внутри кластера kind. Функция живёт только в текущем окне терминала: в новом окне определите её снова.

```bash
kubectl config use-context kind-lab
kubectl create ns lab-03-1
k() { kubectl -n lab-03-1 "$@"; }
for w in lab-worker lab-worker2; do
  k run p-$w --image=localhost:5001/busybox:1.37 \
    --overrides="{\"spec\":{\"nodeName\":\"$w\"}}" -- sleep infinity
done
k wait --for=condition=Ready pod --all
k get pods -o custom-columns=NAME:.metadata.name,NODE:.spec.nodeName,IP:.status.podIP
```

| Часть команды | Значение |
|---|---|
| `create ns lab-03-1` | создать namespace части |
| `k() { … }` | короткая команда `kubectl -n lab-03-1` |
| `k run p-$w` | создать под `p-lab-worker` и `p-lab-worker2` |
| `--overrides=…nodeName` | прибить под к узлу в обход scheduler'а |
| `wait --for=condition=Ready` | дождаться готовности подов |
| `custom-columns=…` | вывести имя, узел и IP пода |

Результат (адреса у вас будут другими):

```
NAME            NODE          IP
p-lab-worker    lab-worker    10.244.2.84
p-lab-worker2   lab-worker2   10.244.3.69
```

Разбор: два пода работают на разных узлах и взяли адреса из подсетей своих узлов: `10.244.2.0/24` у `lab-worker` и `10.244.3.0/24` у `lab-worker2`.

### Лабораторная работа 1. Сеть изнутри пода

**Цель.** Найти подсети узлов, прочитать адрес, маршрут и MTU пода, пройти трассировкой до пода на другом узле и увидеть его маршрут на узле.

**Что понадобится.** Стенд 00-1, namespace `lab-03-1` с двумя подами из подготовки. Около 15 минут.

**Схема опыта.**

```
lab-worker (10.244.2.0/24)                      lab-worker2 (10.244.3.0/24)
 p-lab-worker 10.244.2.84 ─ шлюз 10.244.2.1 ─► eth0 ═══► eth0 ─ veth ─► p-lab-worker2 10.244.3.69
        шаг 2: адрес, маршрут, MTU        шаг 3: ping и traceroute      шаг 4: маршрут на узле
```

Схема 12. Путь пакета между подами на разных узлах и места, где его смотрят в этой работе.

#### Шаг 1. Подсети узлов

Команда выводит подсеть пода (`spec.podCIDR`) и адрес каждого узла.

```bash
kubectl get nodes -o custom-columns=NODE:.metadata.name,PODCIDR:.spec.podCIDR,\
IP:.status.addresses[0].address
```

| Часть команды | Значение |
|---|---|
| `custom-columns=NODE:…` | задать свои колонки вывода |
| `.spec.podCIDR` | подсеть подов узла |
| `.status.addresses[0].address` | первый адрес узла (InternalIP) |

Результат:

```
NODE                PODCIDR         IP
lab-control-plane   10.244.0.0/24   172.20.0.2
lab-worker          10.244.2.0/24   172.20.0.3
lab-worker2         10.244.3.0/24   172.20.0.5
lab-worker3         10.244.1.0/24   172.20.0.4
```

Разбор:

1. Каждому узлу выдана своя /24 из `10.244.0.0/16`.
2. Подсети не совпадают с порядком имён узлов: распределяет их контроллер в порядке регистрации узлов.
3. Адреса узлов (`172.20.0.x`) — сеть Docker, в которой работает kind.

#### Шаг 2. Адрес, маршрут и MTU внутри пода

Команда запускает в поде три проверки: адрес `eth0`, default-маршрут и MTU интерфейса.

```bash
k exec p-lab-worker -- sh -c \
  "ip -4 addr show eth0 | grep inet; ip route | grep default; cat /sys/class/net/eth0/mtu"
```

| Часть команды | Значение |
|---|---|
| `exec p-lab-worker -- sh -c` | выполнить цепочку команд внутри пода |
| `ip -4 addr show eth0` | IPv4-адрес интерфейса пода |
| `ip route \| grep default` | оставить маршрут по умолчанию |
| `cat …/eth0/mtu` | MTU интерфейса |

Результат:

```
    inet 10.244.2.84/24 brd 10.244.2.255 scope global eth0
default via 10.244.2.1 dev eth0
1500
```

Разбор:

1. `10.244.2.84/24` — адрес из подсети `lab-worker`; маска /24 совпадает с `podCIDR`.
2. `default via 10.244.2.1` — всё, что не в подсети узла, под отправляет на шлюз. Это адрес узла на стороне veth.
3. `1500` — MTU пода равен MTU сети Docker: туннеля нет, и накладных байт нет.

#### Шаг 3. Путь до пода на другом узле

Команда сначала узнаёт IP второго пода, потом проверяет связь и трассирует путь.

```bash
IPB=$(k get pod p-lab-worker2 -o jsonpath='{.status.podIP}')
k exec p-lab-worker -- sh -c \
  "ping -c 3 -q $IPB | tail -2; traceroute -n -q 1 -w 1 $IPB"
```

| Часть команды | Значение |
|---|---|
| `IPB=$(…)` | сохранить IP второго пода в переменную |
| `ping -c 3 -q` | три пакета, только итог |
| `tail -2` | оставить две последние строки итога |
| `traceroute -n -q 1 -w 1` | без DNS, один пробный пакет на хоп, ожидание 1 с |

Результат (заголовок traceroute сокращён):

```
3 packets transmitted, 3 packets received, 0% packet loss
round-trip min/avg/max = 0.095/0.101/0.110 ms
traceroute to 10.244.3.69 …
 1  10.244.2.1  0.007 ms
 2  172.20.0.5  0.003 ms
 3  10.244.3.69  0.003 ms
```

Разбор:

1. Потерь нет, задержка около 0,1 мс: оба узла работают на одной машине.
2. Хоп 1, `10.244.2.1`, — шлюз пода, узел-источник.
3. Хоп 2, `172.20.0.5`, — узел-назначение; он отвечает адресом своего `eth0`, на который пришёл пакет.
4. Хоп 3 — сам под. Между узлами нет промежуточных маршрутизаторов и нет туннеля: узел-источник отправляет пакет напрямую на IP узла-назначения.

#### Шаг 4. Маршруты на узле назначения

Команды выводят на узле `lab-worker2` маршрут к поду и маршруты к подсетям соседей.

```bash
docker exec lab-worker2 ip route | grep "^$IPB "
docker exec lab-worker2 ip route | grep '^10.244.*via'
```

| Часть команды | Значение |
|---|---|

### Лабораторная работа 2. tcpdump на узле

**Риски.** Работа меняет хост и не меняет узлы.

- **Что меняется:** Docker на хосте скачивает образ `nicolaka/netshoot:v0.13` (около 540 МБ на диске) и запускает короткие контейнеры. Ключ `--net=container:` подключает контейнер к network namespace контейнера-узла kind, а не к сети хоста. Контейнер не привилегированный и ничего не монтирует с хоста.
- **Надолго ли:** Контейнеры удаляются сами (`--rm`), образ остаётся до уборки.
- **Безопасность:** Контейнер получает стандартный набор capabilities Docker: в нём есть NET_RAW, которого хватает tcpdump, и нет NET_ADMIN. В network namespace узла захват видит весь трафик этого узла, в том числе чужих подов, поэтому фильтр `host` оставляет в выводе только пакеты двух подов. Флаг `-p` не включает promiscuous mode, и режим интерфейса узла не меняется.
- **Влияние на систему:** Нагрузка ничтожна. Диск хоста: нужно ≥ 1 ГБ свободного места на разделе Docker.
- **Откат:** Блок «Уборка».

**Цель.** Увидеть пакеты между подами на проводе узла и убедиться, что между узлами идут адреса подов без NAT и без туннеля.

**Что понадобится.** Namespace `lab-03-1` с подами из подготовки, Docker на хосте и образ `nicolaka/netshoot:v0.13`: скачивается около 185 МБ, на диске занимает около 540 МБ. Около 20 минут.

**Карточка инструмента: tcpdump.**

**Назначение.** tcpdump печатает пакеты, проходящие через сетевой интерфейс. С его помощью проверяют, дошёл ли пакет и какие адреса в нём стоят.

**Как работает.** Утилита открывает в ядре raw-сокет и получает копии пакетов; фильтр выполняет само ядро.

```
интерфейс ──копия пакета──► ядро: фильтр BPF ──► tcpdump: разбор и печать
```

**Откуда берёт данные.** Из ядра через сокет AF_PACKET. Нужна capability NET_RAW, а видны только интерфейсы того network namespace, где запущена утилита.

**Основные команды.**

```bash
tcpdump -n -i eth0 host 10.244.3.69      # -n без DNS-запросов, один интерфейс, фильтр по адресу
tcpdump -n -t -i any -c 5 tcp port 80    # -t без времени, -i any все интерфейсы, -c 5 пакетов
tcpdump -n -e -i eth0 arp                # -e печатать MAC-адреса
tcpdump -n -p -i eth0 icmp               # -p не включать promiscuous mode
tcpdump -n -i eth0 -w /tmp/a.pcap        # -w записать в файл для Wireshark
```

**Команды для скриптов.** `-c N` и внешний `timeout N` ограничивают захват, `-l` включает построчный вывод для конвейера, `-w` пишет файл.

**Частые ошибки.**

- Нет `-n`: утилита ждёт DNS-ответов и тормозит вывод.
- Запущена не в том namespace: на хосте не видно интерфейсов пода.
- `-i any` показывает один пакет по несколько раз, на каждом интерфейсе.
- Нет фильтра: вывод тонет в чужом трафике.

**Установка.** Ubuntu — `sudo apt install tcpdump`, Manjaro — `sudo pacman -S tcpdump`. В узлах kind его нет: используем образ netshoot, где он есть.

**Схема опыта.**

```
p-lab-worker ─ping─► eth0 узла lab-worker ═══► eth0 узла lab-worker2 ─► vethXXXX ─► p-lab-worker2
                                               ▲                          ▲
                                  шаг 2: захват eth0               шаг 3: захват на veth
                     контейнер netshoot делит network namespace узла lab-worker2
```

Схема 13. Две точки захвата на узле назначения: eth0 (вход с провода) и veth целевого пода (выход к поду).

### Лабораторная работа 3. SNAT на выходе из кластера

**Риски.** Работа читает правила узла и запускает короткий контейнер захвата.

- **Что меняется:** Ничего на узлах и в кластере. На хосте запускается контейнер с `--net=container:`, как в работе 2.
- **Безопасность:** Захват `-i any` видит весь трафик узла, но вывод ограничен фильтром `tcp port 80 and host 1.1.1.1`. Запрос идёт во внешнюю сеть: подключайтесь только к адресам, которыми вы вправе пользоваться.
- **Откат:** Не нужен: контейнер удаляется сам.

**Цель.** Найти правило masquerade на узле и увидеть, как меняется адрес источника между veth и eth0.

**Что понадобится.** Namespace `lab-03-1`, образ netshoot из работы 2, доступ узлов к адресу `1.1.1.1` по порту 80. Около 15 минут.

**Схема опыта.**

```
p-lab-worker ──► vethX [шаг 2: источник 10.244.2.84] ─ POSTROUTING: MASQUERADE ─►
                 eth0 узла [источник 172.20.0.3] ─► Docker-хост ─► 1.1.1.1
          шаг 1: правило KIND-MASQ-AGENT на узле lab-worker
```

Схема 14. Место подмены: между veth пода и eth0 узла. Шаг 1 показывает правило, шаг 2 — результат.

#### Шаг 1. Правило masquerade на узле

Команда показывает правила цепочки `KIND-MASQ-AGENT` таблицы nat узла.

```bash
docker exec lab-worker iptables-save -t nat | grep -- '-A KIND-MASQ-AGENT'
```

| Часть команды | Значение |
|---|---|
| `docker exec lab-worker` | выполнить команду внутри узла |
| `iptables-save -t nat` | вывести правила таблицы nat |
| `grep -- '-A KIND-MASQ-AGENT'` | оставить правила этой цепочки |

Результат (строки длинные, приведены целиком):

```
-A KIND-MASQ-AGENT -d 10.244.0.0/16 -m comment --comment "kind-masq-agent: local traffic is not subject to MASQUERADE" -j RETURN
-A KIND-MASQ-AGENT -m comment --comment "kind-masq-agent: outbound traffic is subject to MASQUERADE (must be last in chain)" -j MASQUERADE
```

Разбор:

1. Первое правило: трафик к `10.244.0.0/16`, то есть к подам, возвращается из цепочки без изменений (`RETURN`). Поэтому адрес пода при общении подов не подменяется.
2. Второе правило: всё остальное маскируется (`MASQUERADE`). Оно должно быть последним в цепочке.
3. В цепочку трафик попадает из `POSTROUTING`; этот переход агент ставит сам.

#### Шаг 2. Адрес источника до и после узла

Команда в фоне запрашивает внешний адрес из пода, а на переднем плане ловит пакеты по всем интерфейсам узла.


| Часть команды | Значение |
|---|---|
| `wget -q -T 5 -O /dev/null` | тихий запрос с таймаутом 5 с и без сохранения |
| `--net=container:lab-worker` | захват в netns узла `lab-worker`, где работает под |
| `-i any` | все интерфейсы узла, в том числе veth и eth0 |
| `tcp port 80 and host 1.1.1.1` | только соединение пода с внешним адресом |

Результат (строки сокращены; у второй строки опущены имя интерфейса и направление):


Разбор:

1. Первая строка: пакет вошёл (`In`) в узел через veth пода, источник — адрес пода `10.244.2.84`.
2. Вторая строка: тот же пакет уходит наружу через `eth0` узла с источником `172.20.0.3`, то есть с адресом узла. В полном выводе в её начале стоят `eth0` и `Out`.

**Итог.**

| Что узнали | Где видно |
|---|---|
| Трафик в `cluster-cidr` не маскируется | шаг 1, правило RETURN |
| Весь прочий исходящий трафик маскируется адресом узла | шаг 1, шаг 2 |
| Внешние системы видят IP узла, а не пода | шаг 2 |

**Уборка.** Контейнер и фоновый пинг завершились сами. Удалять нечего.

**Вопросы для самопроверки.**

1. Почему для общения подов друг с другом правило RETURN стоит первым?
2. Что нужно сделать, чтобы внешняя БД пускала только сервис из кластера?
3. Как SNAT влияет на таблицу conntrack узла?

<details>
<summary>Ответы</summary>

1. Правила цепочки проверяются по порядку. Если бы MASQUERADE стоял первым, он подменил бы адрес и у трафика между подами, и NetworkPolicy и логи видели бы адрес узла.
2. Узел не подходит: адрес зависит от узла, на котором оказался под. Нужен фиксированный адрес: egress gateway CNI, выделенный пул узлов с taint или NAT-шлюз VPC.
3. Каждое исходящее соединение занимает запись в общей таблице узла. Тысячи соединений от подов исчерпывают `nf_conntrack_max` для всех подов узла (курс `networks` 06-5).

</details>

### Лабораторная работа 4. Потолок подов на узле

**Риски.** Работа создаёт большую нагрузку на один узел кластера.

- **Надолго ли:** До уборки (около 15 минут).
- **Влияние на систему:** Поды `pause` почти ничего не потребляют, но kubelet и containerd на `lab-worker3` около минуты работают под нагрузкой. Не запускайте на стенде выкатки других частей, пока идёт работа.
- **Откат:** Блок «Уборка».

**Цель.** Найти предел подов на узле, увидеть сообщение scheduler'а при превышении и сравнить число подов с числом занятых IP.

```bash
k create deploy many --image=registry.k8s.io/pause:3.10 --replicas=0
k patch deploy many -p \
  '{"spec":{"template":{"spec":{"nodeSelector":{"kubernetes.io/hostname":"lab-worker3"}}}}}'
k scale deploy many --replicas=115
sleep 60
k get deploy many
```

| Часть команды | Значение |
|---|---|
| `create deploy many --replicas=0` | создать Deployment без подов |
| `patch … nodeSelector` | разрешить подам только узел `lab-worker3` |
| `scale --replicas=115` | запросить 115 подов, больше предела |
| `sleep 60` | дать время запуститься подам |

Результат:

```
NAME   READY     UP-TO-DATE   AVAILABLE   AGE
many   106/115   115          106         60s
```

Разбор:

1. `106/115` — запустились 106 подов: 4 прежних плюс 106 дают 110.
2. Остальные 9 подов созданы, но не назначены на узел и ждут в Pending.

#### Шаг 3. Прочитать отказ scheduler'а

Команды считают поды узла и выводят последнее сообщение о неудачном планировании одного из ожидающих подов.

```bash
kubectl get pods -A --field-selector spec.nodeName=lab-worker3 --no-headers | wc -l
P=$(k get pods -l app=many --field-selector=status.phase=Pending -o name | head -1)
k get events --field-selector involvedObject.name=${P#pod/},reason=FailedScheduling \
  -o jsonpath='{.items[-1:].message}{"\n"}'
```

| Часть команды | Значение |
|---|---|
| `-l app=many` | поды нашего Deployment |
| `status.phase=Pending` | только ожидающие |
| `${P#pod/}` | убрать префикс `pod/` из имени |
| `reason=FailedScheduling` | события неудачного планирования |
| `.items[-1:].message` | текст последнего события |

Результат (сообщение сокращено):

```
110
0/4 nodes are available: 1 Too many pods, 1 node(s) had untolerated taint(s), 2 node(s) didn't match Pod's node affinity/selector. …
```

Разбор:

1. `110` — узел заполнен до предела.
2. `1 Too many pods` — узел `lab-worker3` отвергнут из-за предела подов.
3. `1 node(s) had untolerated taint(s)` — control-plane с taint, которого у подов нет.
4. `2 node(s) didn't match … selector` — `lab-worker` и `lab-worker2` не подходят под `nodeSelector`.

#### Шаг 4. Сравнить поды и занятые IP

Команды считают файлы IPAM на узле и показывают поды узла, которые работают в сети узла.

```bash
docker exec lab-worker3 sh -c 'ls /run/cni-ipam-state/kindnet | grep -c "^10\."'
kubectl get pods -A --field-selector spec.nodeName=lab-worker3 \
  -o jsonpath='{range .items[?(@.spec.hostNetwork==true)]}{.metadata.name}{"\n"}{end}'
```

| Часть команды | Значение |
|---|---|
| `ls /run/cni-ipam-state/kindnet` | список файлов IPAM на узле |
| `grep -c "^10\."` | посчитать файлы с именами-адресами подов |
| `?(@.spec.hostNetwork==true)` | фильтр: поды в сети узла |

Результат (имена подов у вас будут другими; значения второй команды ожидаемые):

```
108
kindnet-…
kube-proxy-…
```

Разбор:

1. `108` занятых адресов при 110 подах: разница равна числу подов с `hostNetwork`.
2. `kindnet` и `kube-proxy` работают в сети узла, поэтому берут адрес узла и IP из подсети пода не занимают.
3. Если бы файлов было заметно больше, чем подов без `hostNetwork`, это означало бы утечку IPAM (§5).

**Итог.**

| Что узнали | Где видно |
|---|---|
| Предел подов узла — 110 по умолчанию | шаг 1, `allocatable.pods` |
| Поды сверх предела ждут в Pending | шаги 2 и 3 |
| Scheduler пишет `Too many pods` | шаг 3, событие |
| Занятых IP меньше, чем подов, на число подов с hostNetwork | шаг 4 |

**Вопросы для самопроверки.**

1. Подсеть узла — /25, а `maxPods` равен 110. Хватит ли адресов?
2. Почему число файлов IPAM не равно числу подов узла?
3. Какие два лимита определяют число подов на узле и как их связать?

<details>
<summary>Ответы</summary>

1. Формально хватит: в /25 `host-local` выдаёт 125 адресов, а поды с hostNetwork адреса не занимают. При 108 подах с адресами запас всего 17 адресов: после 18 «протёкших» файлов IPAM адреса кончатся раньше `maxPods`. Подсеть выбирают с большим запасом.
2. Поды с `hostNetwork` не берут адрес из подсети. Лишние файлы сверх этого — признак утечки IPAM.
3. `maxPods` kubelet и размер подсети узла (`--node-cidr-mask-size`). Подсеть должна быть заметно больше `maxPods`, иначе адреса кончатся раньше.

</details>

Сеть подов даёт каждому поду адрес, но адреса подов недолговечны: под пересоздаётся и получает новый IP. Приложениям нужен стабильный адрес и распределение запросов по живым подам.
