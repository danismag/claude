Эта часть отвечает на вопрос, как клиент находит поды, адреса которых постоянно меняются. Часть опирается на 03-1: там мы видели, что каждый под получает свой IP и что пакет между подами проходит без трансляции адресов. Здесь появляется слой выше, **Service**, а также компонент kube-proxy, который превращает его в правила на каждом узле. Условия `Ready` и состояние завершения пода, от которых зависит состав адресов, разобраны в 02-1 и 02-5.

Следующие части строятся на Service. DNS (03-3) выдаёт ему имя, а Gateway API (03-4) направляет внешний трафик на него как на бэкенд. NetworkPolicy (03-6) решает, какие поды вообще могут к нему обратиться.

```
имя orders ─► DNS (03-3) ─► ClusterIP:80 ─► правила kube-proxy на узле ─► IP пода (03-1)
                                 ▲                    │
         Gateway API (03-4) ─────┘                    └─ NetworkPolicy (03-6) фильтрует пакеты
```

Схема 1. Путь запроса к Service: имя, виртуальный адрес, правила узла, адрес пода; смотрите на середину, там работает эта часть.

## 1. Какую задачу решает Service

Поды недолговечны, а клиентам нужен адрес, который не меняется. Service даёт такой адрес и сам следит за тем, какие поды сейчас за ним стоят.

### Постоянный адрес для временных подов

**Service** (служба) — объект API, который даёт группе подов один постоянный виртуальный адрес и одно DNS-имя. Поды приходят и уходят: контроллер заменяет упавший под новым, и у нового другой IP (02-2). Клиент не может записать в конфигурацию адрес пода, поэтому он ходит на адрес Service, а Service выбирает живой под. Группу подов Service определяет по меткам: условие выбора называется **selector**.

**ClusterIP** — виртуальный адрес Service из служебного диапазона кластера. Он не принадлежит ни одному сетевому интерфейсу и работает как адрес-приманка. Правила на каждом узле перехватывают пакеты к нему и подменяют адрес назначения на адрес пода. Поэтому ClusterIP нельзя проверить командой `ping`: Service обрабатывает только TCP, UDP и SCTP на описанных портах, а ICMP никто не перехватывает.

```
Service (selector app=orders, port 80 → targetPort http)
   │  контроллер EndpointSlice: поды по selector'у → адреса и их готовность
   ▼
EndpointSlice ──────────── список адресов подов, до 100 в одном срезе
   │  watch (наблюдение через API)
   ├──► kube-proxy на каждом узле ── правила: ClusterIP:80 → IP пода:8000
   └──► Envoy, mesh ───────────────── читают срезы сами и ходят прямо на IP подов
```

Схема 2. Из чего складывается Service: объект, срез с адресами и потребители среза.

### Типы Service

Тип Service определяет, откуда до него можно дойти. Типов пять, и три из них вкладываются друг в друга.

- **ClusterIP** — тип по умолчанию: виртуальный адрес, доступный только внутри кластера.
- **NodePort** — ClusterIP плюс порт на каждом узле из диапазона 30000–32767.
- **LoadBalancer** — NodePort плюс внешний балансировщик, который выдаёт облако или MetalLB (§3).
- **ExternalName** — DNS-псевдоним на внешнее имя: проксирования и правил на узлах нет.
- **Headless** (`clusterIP: None`) — адреса нет: DNS отдаёт IP подов, а kube-proxy ничего не настраивает (03-3).

```
LoadBalancer ┌──────────────────────────────────────────┐
             │ внешний адрес от облака или MetalLB       │
   NodePort  │  ┌────────────────────────────────────┐  │
             │  │ порт 30000–32767 на каждом узле     │  │
   ClusterIP │  │  ┌──────────────────────────────┐  │  │
             │  │  │ виртуальный адрес и порт      │  │  │
             │  │  └──────────────────────────────┘  │  │
             │  └────────────────────────────────────┘  │
             └──────────────────────────────────────────┘
```

Схема 3. Вложенность типов: внешний тип содержит внутренние, поэтому LoadBalancer тоже доступен по ClusterIP и NodePort. Подробно о типах — в курсе `networks`, 08-3.

### Как клиент находит Service

Клиент обращается к Service по DNS-имени. Внутри одного namespace хватает короткого `orders`, из другого namespace пишут `orders.lab-03-2`, а полное имя — `orders.lab-03-2.svc.cluster.local`. Как под разворачивает такие имена, разбирает 03-3. Кроме DNS, kubelet кладёт в каждый новый под переменные окружения вида `ORDERS_SERVICE_HOST`. Они есть только для Service своего namespace, созданных раньше пода, поэтому полагаться на них нельзя.

## 2. Как устроен Service

Сам объект Service ничего не пересылает. Работу делят три участника: контроллер EndpointSlice собирает адреса, kube-proxy пишет правила, а ядро узла пересылает пакеты.

### EndpointSlice: список адресов

**Эндпоинт** (endpoint) — адрес пода и порт, на который Service отправляет трафик. **EndpointSlice** (срез эндпоинтов) — объект API с частью этого списка. Контроллер EndpointSlice в kube-controller-manager создаёт срезы по selector'у и кладёт в каждый не больше 100 эндпоинтов. Срез связан со Service меткой `kubernetes.io/service-name`, поэтому его ищут именно по ней. Срезов у одного Service может быть несколько: адресов больше 100, dual-stack даёт по срезу на семейство адресов, а разные порты тоже расходятся по срезам.

Старый объект **Endpoints** (v1) хранил весь список одной записью и с версии 1.33 устарел. Команда `kubectl get endpoints` в 1.36 печатает `Warning: v1 Endpoints is deprecated in v1.33+; use discovery.k8s.io/v1 EndpointSlice`. Кроме того, в Endpoints помещается не больше 1000 адресов, остальные Kubernetes отбрасывает. Поэтому в скриптах и документации используйте только EndpointSlice.

```yaml
endpoints:
- addresses: ["10.244.2.10"]
  conditions: {ready: true, serving: true, terminating: false}
  nodeName: lab-worker
  targetRef: {kind: Pod, name: orders-6d8f7-x2k4p}
ports:
- {name: "", port: 8000, protocol: TCP}
```

Фрагмент среза: у каждого эндпоинта есть адрес, узел, ссылка на под и три условия; `port` здесь уже номер, а не имя из `targetPort`.

Три **условия** (conditions) говорят, что с эндпоинтом делать.

- `ready` — под Ready и не завершается; только такие адреса получают новые соединения.
- `serving` — под проходит проверку готовности, даже если он уже завершается.
- `terminating` — у пода выставлен `deletionTimestamp`, то есть его удаляют.

Если завершаются все поды Service, kube-proxy берёт адреса с `serving: true`, чтобы не оборвать трафик целиком. Для остальных случаев новые соединения идут только на `ready`.

### kube-proxy: правила на каждом узле

**kube-proxy** — компонент на каждом узле (в kubeadm и kind это DaemonSet), который наблюдает за Service и EndpointSlice и переписывает правила пересылки в ядре узла. Через него самого пакеты не идут: их обрабатывает ядро, поэтому остановка kube-proxy не рвёт уже установленные соединения, а лишь перестаёт обновлять правила.

Адрес назначения подменяет **DNAT** (destination NAT, трансляция адреса назначения): `ClusterIP:80` превращается в `IP пода:8000`. Под выбирают один раз, при первом пакете соединения. **Conntrack** (connection tracking) — таблица соединений ядра: она запоминает выбор и подменяет адреса в ответных пакетах, поэтому остальные пакеты этого соединения идут на тот же под. Отсюда главное свойство Service: он балансирует соединения, а не запросы, и работает на уровне L4.

```
API-сервер ── watch: Service, EndpointSlice ──► kube-proxy (узел)
                                                    │ пишет правила
                                                    ▼
клиент ──► ClusterIP:80 ──► ядро: DNAT ──► 10.244.2.10:8000 (под)
                              conntrack хранит выбор до конца соединения
```

Схема 4. Работа kube-proxy: он только программирует ядро, а пересылает пакеты само ядро. Режим задаёт поле `mode` в ConfigMap `kube-proxy` (ключ `config.conf`).

### Путь пакета в режиме iptables

В режиме **iptables** kube-proxy строит цепочки трёх уровней. Первая, `KUBE-SERVICES`, ищет совпадение по ClusterIP и порту. Для каждого Service есть цепочка `KUBE-SVC-<хеш>`, которая случайно выбирает эндпоинт, а для каждого эндпоинта — цепочка `KUBE-SEP-<хеш>` с правилом DNAT. Случайность задаёт модуль `statistic`: первое правило срабатывает с вероятностью 1/N, второе — с 1/(N−1) от остатка, и так далее, поэтому доли получаются равными.

```
KUBE-SERVICES         совпал ClusterIP:порт?
   └─► KUBE-SVC-<хеш>   одна цепочка на Service, случайный выбор
          ├─ вероятность 0,33 ─► KUBE-SEP-<хеш>  одна цепочка на эндпоинт:
          ├─ вероятность 0,5  ─► KUBE-SEP-<хеш>  DNAT на IP:порт пода
          └─ остаток          ─► KUBE-SEP-<хеш>
```

Схема 5. Три эндпоинта в режиме iptables: вероятности 1/3, 1/2 и остаток дают каждому по трети соединений. Разбор по шагам — в курсе `networks`, 08-3.

У схемы есть цена: правил столько же, сколько Service и эндпоинтов вместе, а kube-proxy переписывает весь набор целиком. Чем больше кластер, тем дольше длится каждое обновление.

### Режимы kube-proxy

Режимов три, и каждый хранит правила по-своему. Таблица сравнивает их по четырём признакам.

| Режим | Как хранит правила | Обновление | Статус в 1.36 |
|---|---|---|---|
| `iptables` | цепочки на Service и эндпоинт | пересборка всего набора | умолчание, режим стенда |
| `nftables` | таблица kube-proxy, словари | инкрементальное, атомарное | GA с 1.33 |
| `ipvs` | хеш-таблицы IPVS в ядре | инкрементальное | устарел с 1.35 |

**nftables** — преемник iptables в ядре Linux. kube-proxy кладёт Service в **verdict map** (словарь «ключ → переход к цепочке»), и поиск Service занимает постоянное время, а не растёт с числом правил. Режим стал beta в 1.31 и GA в 1.33, ему нужно ядро 5.13 или новее. Правила kube-proxy лежат в отдельной таблице `kube-proxy` (для IPv4 и IPv6 по одной), поэтому с чужими правилами он не пересекается. В 1.36 умолчание остаётся прежним, а kube-proxy 1.37 предупреждает, если `mode` не задан явно: переход умолчания на nftables готовится.

**ipvs** устарел в версии 1.35: при запуске kube-proxy выдаёт предупреждение. Документация Kubernetes обещает выключить режим по умолчанию в 1.40 (вернуть его можно гейтом `KubeProxyIPVS`) и удалить в 1.43, а ранний пост об устаревании называл удаление в 1.40. Поэтому для нового кластера ipvs не выбирают, а старый переводят на nftables заранее. Рецепты, которые советуют `mode: ipvs` для больших кластеров, устарели (чек-лист обновления — 10-3).

Существует и четвёртый вариант: CNI с eBPF (например, Cilium) заменяет kube-proxy целиком. В нашем стенде kube-proxy остаётся, поэтому здесь это одна фраза.

## 3. Как управлять Service

Поведение Service задают несколько полей спецификации. Разберём манифест, политики трафика, привязку клиента, предпочтение близких эндпоинтов и внешние балансировщики.

### Манифест и порты

В манифесте важны три вещи: selector, порт Service и порт пода.

```yaml
apiVersion: v1
kind: Service
metadata: {name: orders}
spec:
  selector: {app: orders}
  ports:
  - {name: http, port: 80, targetPort: http, protocol: TCP}
```

Фрагмент описывает Service `orders`: он выбирает поды с меткой `app=orders` и пересылает порт 80 на порт пода с именем `http`.

| Поле | Значение |
|---|---|
| `selector` | метки подов в том же namespace |
| `port` | порт Service, на который ходит клиент |
| `targetPort` | порт пода: число или имя порта контейнера |
| `name` | имя порта; обязательно, если портов несколько |

**targetPort** лучше задавать именем из `containerPort`. Имя переживёт смену номера порта в образе, а число придётся менять в двух местах. Имя порта содержит до 15 знаков.

### externalTrafficPolicy и internalTrafficPolicy

**externalTrafficPolicy** — поле Service, которое решает, куда отправлять трафик, пришедший снаружи через NodePort или LoadBalancer. Внешний трафик приходит на любой узел, и дальше значение поля выбирает один из двух путей.

| Значение | Куда идёт | IP клиента в поде | Узел без подов |
|---|---|---|---|
| `Cluster` (умолчание) | на любой под кластера | потерян, SNAT в адрес узла | пересылает дальше |
| `Local` | только на поды этого узла | сохранён | отбрасывает пакеты |

```
Cluster:  клиент ─► узел A ──SNAT──► под на узле B     IP клиента заменён адресом узла
Local:    клиент ─► узел A ─────────► под на узле A    IP клиента сохранён
          клиент ─► узел C (подов нет) ─► DROP         правило "has no local endpoints"
```

Схема 6. Две политики: при `Cluster` лишний прыжок и SNAT, при `Local` честный IP клиента, но узлы без подов превращаются в «чёрные дыры».

Политика `Local` требует от внешнего балансировщика знать, на каких узлах есть поды. Для `type: LoadBalancer` kube-proxy открывает порт `healthCheckNodePort`, и балансировщик проверяет по нему узлы: порт отвечает 200 на узле с готовым локальным эндпоинтом и 503 без него. У обычного NodePort такого порта нет, поэтому внешний балансировщик, который шлёт запросы на все узлы, теряет часть из них. Альтернатива `Local` — оставить `Cluster` и передавать IP клиента на уровне L7 (заголовок `X-Forwarded-For`) или через PROXY protocol.

Это случилось на нашем стенде. Envoy Gateway по умолчанию создаёт Service с `externalTrafficPolicy: Local`, а kind пробрасывает порт хоста на узел control-plane, где пода Envoy нет. Запросы висели до таймаута, поэтому `lab-up.sh` задаёт `Cluster` через объект EnvoyProxy (00-1 §5).

**internalTrafficPolicy: Local** — то же правило для трафика изнутри кластера: под ходит только к эндпоинтам своего узла. Так работают node-local агенты и кэши в DaemonSet. Если на узле нет готового эндпоинта, трафик отбрасывается.

### sessionAffinity

**sessionAffinity** — поле Service, которое привязывает клиента к одному поду. Значение `ClientIP` отправляет все новые соединения с одного IP на один и тот же эндпоинт, а `None` (умолчание) выбирает эндпоинт случайно для каждого соединения. Время привязки задаёт `sessionAffinityConfig.clientIP.timeoutSeconds`: по умолчанию 10800 с (3 часа), допустимо от 1 до 86400.

Привязка по IP ненадёжна. За SNAT или NAT все клиенты имеют один адрес и уходят в один под. При политике `Cluster` снаружи Service видит адрес узла, а не клиента. Привязка теряется при пересоздании пода. Настоящие сессии хранят в приложении (общее хранилище вроде Redis) или в L7-балансировщике (cookie).

С keepalive привязка возникает и без поля. HTTP/1.1 с пулом соединений и gRPC открывают одно долгое соединение, поэтому клиент нагружает один под, сколько бы реплик ни было. Для таких клиентов нужна L7-балансировка (Envoy, mesh) или клиентская балансировка по headless Service.

### trafficDistribution

**trafficDistribution** — поле Service, которое просит предпочитать близкие эндпоинты. Оно нужно в кластерах из нескольких зон: трафик между зонами стоит денег и добавляет задержку.

- `PreferSameZone` — предпочитать эндпоинты зоны клиента (GA с 1.35).
- `PreferSameNode` — предпочитать эндпоинты на том же узле (GA с 1.35).
- `PreferClose` — устаревший псевдоним `PreferSameZone`; сервер 1.36 предупреждает и советует новое имя.
- поле пусто — равномерно по всем готовым эндпоинтам.

Контроллер EndpointSlice записывает в срез подсказки (**hints**, поля `forZones` и `forNodes`), а kube-proxy фильтрует по ним эндпоинты. Это предпочтение, а не запрет: если в зоне нет готовых эндпоинтов, трафик уходит в другие зоны. Риск — перекос нагрузки: единственный под в зоне получает весь трафик клиентов этой зоны. Реплики должны стоять по зонам равномерно (05-3, topology spread).

### LoadBalancer

В облаке тип **LoadBalancer** заказывает у провайдера внешний балансировщик и записывает его адрес в `status.loadBalancer`. Без такого контроллера колонка `EXTERNAL-IP` остаётся `<pending>` бесконечно: сам kube-proxy внешних адресов не создаёт.

```
клиент ─► внешний IP балансировщика ─► NodePort на узлах ─► kube-proxy ─► поды
              ▲
   кто выдаёт адрес: облако | MetalLB (bare metal) | cloud-provider-kind (kind)
```

Схема 7. Внешний адрес выдаёт контроллер за пределами kube-proxy; дальше путь тот же, что у NodePort.

В kind LoadBalancer без дополнения не работает. **cloud-provider-kind** — отдельная программа проекта Kubernetes SIG, которую запускают на хосте рядом с кластером. Она следит за Service типа LoadBalancer и поднимает для каждого контейнер с Envoy в сети Docker `kind`, откуда берёт внешний адрес. Ей нужны доступ к сокету Docker и право добавлять адреса интерфейсам, а это права на уровне хоста. Поэтому стенд курса её не запускает, и LoadBalancer в нём остаётся `<pending>`. Для серверов без облака обычный выбор — MetalLB в режиме L2 или BGP.

Два поля настраивают поведение. `loadBalancerClass` выбирает реализацию, если в кластере их несколько. `allocateLoadBalancerNodePorts: false` не выделяет NodePort, когда балансировщик ходит на поды напрямую. Контроллер балансировщика может записать в статус `ipMode` (GA с 1.32): при `VIP` (умолчание) kube-proxy сам перехватывает внешний адрес, а при `Proxy` оставляет трафик балансировщику.

## 4. Как увидеть состояние Service

Состояние Service читают по звеньям цепочки: объект, срез, поды, правила узла. Каждое звено проверяется отдельной командой, поэтому место разрыва находится за несколько минут.

### Цепочка проверок

Команды идут от объекта к правилам узла. Подставьте имя своего Service и клиентского пода.

```bash
kubectl get svc <svc> -o wide                     # selector, порты, ClusterIP
kubectl get endpointslice -l kubernetes.io/service-name=<svc> -o wide   # адреса и порт
kubectl get pods -l <selector> -o wide            # метки совпадают? поды Ready?
kubectl exec <client> -- curl -sv http://<podIP>:<port>/   # под отвечает сам по себе?
kubectl exec <client> -- curl -sv http://<svc>/   # то же через ClusterIP
docker exec <узел> iptables-save | grep '<ns>/<svc>'   # правила kube-proxy в kind
```

Клиентскому поду нужен curl, например `nicolaka/netshoot:v0.13` из 03-1. Если Service пуст, уже вторая команда это покажет. Если под отвечает напрямую, но не через Service, ищите разрыв между срезом и правилами.

На реальном узле Ubuntu правила смотрят командой `sudo iptables-save` напрямую, без `docker exec`.

### Правила и состояние kube-proxy

Что лежит в ядре, зависит от режима. Команды ниже покажут режим, правила и счётчики.

```bash
kubectl -n kube-system get cm kube-proxy -o jsonpath='{.data.config\.conf}' | grep mode:
kubectl -n kube-system logs ds/kube-proxy | head -20
docker exec lab-worker iptables-save -t nat | grep 'lab-03-2/echo'     # режим iptables
docker exec lab-worker nft list table ip kube-proxy                    # режим nftables
docker exec lab-worker conntrack -L -d <ClusterIP>                     # соединения
```

Первая команда читает `mode` из конфигурации, вторая — лог (там строка вида `Using iptables Proxier` или `Using nftables Proxier`). Третья и четвёртая печатают правила узла, пятая — записи conntrack для ClusterIP. В узлах kind утилита `conntrack` уже есть, а на реальном узле её ставят пакетом `conntrack` в Ubuntu и `conntrack-tools` в Manjaro.

У самого kube-proxy два порта на узле: метрики на `127.0.0.1:10249` и проверка здоровья на порту 10256 всех адресов узла. Путь `/healthz` отвечает 503, пока узел удаляется, поэтому балансировщик успевает увести с него трафик (connection draining, GA с 1.31). Полезная метрика — `kubeproxy_sync_proxy_rules_duration_seconds`: время пересборки правил. Рост этого времени предупреждает, что iptables-режим не справляется с размером кластера.

### Условия эндпоинтов

Условия среза показывают, кого Service считает готовым. Команда печатает по строке на эндпоинт.

```bash
kubectl get endpointslice -l kubernetes.io/service-name=<svc> -o json | jq -c \
  '.items[].endpoints[] | {pod: .targetRef.name, ready: .conditions.ready,
    serving: .conditions.serving, terminating: .conditions.terminating}'
```

Что в выводе: `ready: false` при `serving: true` значит, что под уходит, но ещё отвечает; `ready: false` и `serving: false` значит, что проба готовности не проходит. Пример с реальным выводом — в лабораторной работе 3.

## 5. Что ломается и как найти причину

Почти все жалобы «Service не отвечает» сводятся к одному из звеньев: selector, срез, readiness, порт, политика трафика или правила узла. Первое различение делает сам симптом.

### Отказ или таймаут

Мгновенный отказ и таймаут указывают на разные места. Таблица сопоставляет симптом с причиной.

| Симптом | Что значит | Куда смотреть |
|---|---|---|
| `Connection refused` за миллисекунды | есть ответ: REJECT или RST | срез Service, поле targetPort |
| таймаут | пакеты теряются молча | NetworkPolicy (03-6), DROP, маршруты |
| `NXDOMAIN`, `Name or service not known` | имя не разрешилось | DNS (03-3), namespace |
| ответ только с части узлов | правила различаются по узлам | kube-proxy на узле, политика Local |

Отказ без подов выдаёт сам kube-proxy: он ставит правило REJECT для Service без готовых эндпоинтов. Таймаут говорит о другом: пакет дошёл до правила DROP или никуда не дошёл.

### Пустой срез

Срез пуст по одной из четырёх причин, и каждую легко отличить от остальных.

- Selector не совпал с метками подов: опечатка или лишняя метка.
- Поды лежат в другом namespace, а selector ищет только в namespace Service.
- Поды не проходят readiness, и у них `ready: false`.
- Подов нет: Deployment их не создал или они стоят в `Pending`.

Различить причины помогают `kubectl get pods --show-labels` и `kubectl describe endpointslice`.

### Неверный порт

Если адреса в срезе есть, а отказ остался, проверьте порт. Колонка `PORTS` в срезе показывает номер, в который превратился `targetPort`. Если процесс слушает другой порт, отказ даёт ядро пода, а не kube-proxy. Имя в `targetPort` должно совпадать с именем в `containerPort` у каждого пода, иначе эндпоинт получит неверный порт или не попадёт в срез.

### Трафик снаружи

Снаружи ломаются три вещи. Политика `Local` без подов на узле даёт таймаут (§3). Порты NodePort могут быть закрыты на межсетевом экране узла. В режиме nftables NodePort не отвечает на `127.0.0.1`: режим не включает `route_localnet`, на который опирается iptables-режим, поэтому к NodePort обращаются по IP узла. В 1.37 появился альфа-гейт `KubeProxyNFTablesLocalhostNodePorts`, который вместе с `--nodeport-addresses primary,localhost` возвращает доступ через localhost.

### Прилипание, UDP и обновления

Соединения прилипают к поду: keepalive и gRPC держат одно соединение, а не запрос. Это нормальное поведение kube-proxy, а не сбой. Для UDP при смене эндпоинтов kube-proxy чистит устаревшие записи conntrack; если этого не произошло, клиент шлёт датаграммы в удалённый под, пока запись не истечёт.

Во время выкатки под сначала выпадает из `ready`, затем получает SIGTERM. Если приложение закрывает порт мгновенно, а правила на узлах обновились не везде, часть запросов уходит в закрытый порт. Поэтому в 02-5 под ждёт в `preStop` несколько секунд.

## 6. Пределы и значения по умолчанию

В разделе собраны числа и сроки. Значения взяты из документации Kubernetes для версии стенда 1.36.

### Числа

- NodePort — диапазон 30000–32767, меняется флагом `--service-node-port-range` у kube-apiserver.
- EndpointSlice — до 100 эндпоинтов в срезе по умолчанию, флаг `--max-endpoints-per-slice` у kube-controller-manager допускает до 1000.
- Endpoints (v1) — не больше 1000 адресов на Service, остальные отбрасываются.
- `sessionAffinity: ClientIP` — таймаут 10800 с, допустимо 1–86400.
- kube-proxy — метрики `127.0.0.1:10249`, проверка здоровья порт 10256.
- Диапазоны в kind — ClusterIP `10.96.0.0/16`, поды `10.244.0.0/16`.
- Имена — порта до 15 знаков, Service до 63; с 1.36 (beta, включено по умолчанию, GA в 1.37) имя Service может начинаться с цифры.

### Диапазоны ClusterIP: ServiceCIDR

Адреса ClusterIP берутся из диапазона, который задаёт флаг `--service-cluster-ip-range` у kube-apiserver. С версии 1.33 (GA) диапазон хранится в объектах API: **ServiceCIDR** описывает сети, а **IPAddress** фиксирует каждый выданный адрес. Стартовый объект называется `kubernetes`. Если диапазон кончился, администратор добавляет второй объект, и перезапускать kube-apiserver не нужно.

```yaml
apiVersion: networking.k8s.io/v1
kind: ServiceCIDR
metadata: {name: extra}
spec:
  cidrs: ["10.97.0.0/16"]
```

Манифест добавляет сеть `10.97.0.0/16`; она не должна пересекаться с сетями узлов и подов. Пока в ServiceCIDR есть выданные адреса, finalizer держит объект в удалении, и он не исчезает. Посмотреть диапазоны и адреса можно командами `kubectl get servicecidr` и `kubectl get ipaddress`.

### Что устарело

Часть привычных рецептов в Kubernetes 1.36 уже небезопасна или устарела. Список даёт версии и замену.

- **Endpoints v1** — устарел в 1.33; замена EndpointSlice.
- **ipvs** — устарел в 1.35, удаление запланировано на 1.40–1.43; замена nftables.
- **PreferClose** — устаревший псевдоним, сервер 1.36 предупреждает; замена `PreferSameZone`.
- **externalIPs** — устарел в 1.36; замена LoadBalancer, NodePort или Gateway API.

Поле `spec.externalIPs` позволяет любому, кто создаёт Service, объявить чужой адрес своим и перехватить трафик (уязвимость CVE-2020-8554). API-сервер предупреждает о поле с 1.36, kube-proxy выключит его по умолчанию не раньше 1.40 (с возможностью вернуть), а полностью — не раньше 1.43. Пока поле работает, закройте его admission-плагином `DenyServiceExternalIPs`.

### Лабораторная работа 1. Service без эндпоинтов: селектор и порт

**Цель.** Научиться за пять минут находить, почему **Service** (служба, постоянный адрес для группы подов) не отвечает. Вы воспроизведёте две поломки с одинаковым симптомом `Connection refused` и отличите их по **EndpointSlice**.

**Что понадобится.**

- Стенд из 00-1: кластер kind с контекстом `kind-lab`, `kube-proxy` в режиме iptables.
- Образ `python:3.12-slim` (узлы скачают его при первом запуске пода).
- Namespace `lab-03-2` из подготовки.
- Около 10 минут на запуск подов и 40 минут на разбор результатов.

**Схема опыта.** Клиентский под ходит к Service по имени `orders`, а смотреть нужно на звено между Service и подами: именно там пропадают адреса.

```
client (под) ──► DNS: orders ──► ClusterIP:80 ──► правила kube-proxy на узле
                                                        │
                                  EndpointSlice orders ◄┘  ← сюда смотрим: пуст или нет
                                        │ адреса: IP подов + порт
                                        ▼
                          поды app=orders (2 шт., слушают :8000)

Поломка 1: selector app=order не совпадает с метками подов → список адресов пуст.
Поломка 2: targetPort 8080 → адреса есть, но на порту 8080 никто не слушает.
```

Схема показывает путь пакета: первая поломка рвёт его на EndpointSlice, а вторая — уже в самом поде.

**Риски.** Работа меняет только кластер стенда; одну настройку на хосте меняет подготовка в начале раздела.

- **Что меняется:** в кластере kind — Deployment, Service и клиентский под в namespace `lab-03-2`; на хосте — namespace по умолчанию у контекста `kind-lab` в `~/.kube/config` (подготовка).
- **Надолго ли:** до уборки; уборка удаляет объекты работы, а namespace и контекст возвращает последняя работа.
- **Безопасность:** привилегий не нужно; `docker exec … iptables-save` только читает правила узла.
- **Влияние на систему:** другие контексты kubectl и рабочие кластеры не затрагиваются.
- **Откат:** блок «Уборка» в конце работы.

#### Шаг 1. Запустить поды и Service с опечаткой в селекторе

Создаём Deployment из двух подов с меткой `app=orders` и Service, который ищет поды по метке `app=order`, — одна буква расходится намеренно. **Метка** (label) — это пара «ключ=значение», которую вешают на объект кластера. **Селектор** (selector) — условие, по которому Service выбирает поды по их меткам.

```bash
kubectl apply -f - <<'EOF'
apiVersion: apps/v1
kind: Deployment
metadata: {name: orders}
spec:
  replicas: 2
  selector: {matchLabels: {app: orders}}
  template:
    metadata: {labels: {app: orders}}
    spec:
      containers:
      - name: api
        image: python:3.12-slim
        command: ["python", "-m", "http.server", "8000"]
        ports: [{name: http, containerPort: 8000}]
        readinessProbe: {httpGet: {path: /, port: http}, periodSeconds: 2}
---
apiVersion: v1
kind: Service
metadata: {name: orders}
spec:
  selector: {app: order}          # опечатка: order вместо orders
  ports: [{port: 80, targetPort: http}]
EOF
kubectl rollout status deploy/orders
```

Разбор ключей манифеста:

| Часть манифеста | Значение |
|---|---|
| `replicas: 2` | два пода |
| `command: [python, -m, http.server, 8000]` | веб-сервер на порту 8000 |
| `ports: [{name: http, ...}]` | порту 8000 дано имя `http` |
| `readinessProbe` | проверка готовности: GET `/` каждые 2 с |
| `selector: {app: order}` | Service ищет метку `app=order`, а её нет |
| `port: 80` | порт Service |
| `targetPort: http` | порт пода — по имени `http` |

Результат:

```
deployment.apps/orders created
service/orders created
Waiting for deployment "orders" rollout to finish: 0 of 2 updated replicas are available...
…
deployment "orders" successfully rolled out
```

Разбор вывода:

1. Deployment создан. Строки `Waiting for…` идут, пока узлы скачивают образ и поды проходят проверку, поэтому при повторном запуске их может не быть. Последняя строка значит, что оба пода запущены и прошли проверку готовности (**Ready** — под готов принимать трафик).
2. Service создан без ошибок: Kubernetes не проверяет, что селектор что-то выбирает.
3. Приложение здорово, поэтому проблема только в связи Service с подами.

#### Шаг 2. Найти пустой EndpointSlice

Первым делом при жалобе «Service не отвечает» проверяют **эндпоинты** (endpoints) — адреса подов, на которые Service отправляет трафик. Контроллер хранит их в объектах **EndpointSlice** (срез эндпоинтов): по умолчанию один объект вмещает до 100 адресов. Старый объект v1 Endpoints с теми же адресами устарел с версии 1.33, поэтому смотрим только EndpointSlice. Выводим Service, его EndpointSlice и две строки из описания Service.

```bash
kubectl get svc,endpointslice
kubectl describe svc orders | grep -E 'Selector|Endpoints'
```

Разбор команд:

| Часть команды | Значение |
|---|---|
| `get svc,endpointslice` | показать объекты двух видов за один вызов |
| `describe svc orders` | подробное описание Service |
| `grep -E '…'` | оставить строки `Selector` и `Endpoints` |

Результат:

```
NAME             TYPE        CLUSTER-IP     EXTERNAL-IP   PORT(S)   AGE
service/orders   ClusterIP   10.96.88.241   <none>        80/TCP    1s

NAME                                          ADDRESSTYPE   PORTS     ENDPOINTS   AGE
endpointslice.discovery.k8s.io/orders-9vf5b   IPv4          <unset>   <unset>     1s
Selector:                 app=order
Endpoints:
```

Разбор вывода:

1. У Service есть **ClusterIP** (виртуальный адрес внутри кластера) `10.96.88.241`: его выдают всегда, даже если подов нет.
2. В EndpointSlice `orders-9vf5b` колонки `PORTS` и `ENDPOINTS` равны `<unset>`: адресов нет.

#### Шаг 3. Увидеть симптом глазами клиента

Запускаем клиентский под и подключаемся из него к Service по имени. Функция `probe` пытается открыть TCP-соединение и печатает результат вместе со временем попытки. Не закрывайте текущее окно терминала, потому что функция понадобится в следующих шагах.

```bash
kubectl run client --image=python:3.12-slim --restart=Never --command -- sleep infinity
kubectl wait --for=condition=Ready pod/client
probe() {
  kubectl exec client -- python -c '
import socket, sys, time
t = time.time()
try:
    socket.create_connection((sys.argv[1], int(sys.argv[2])), timeout=5)
    print("connected")
except Exception as e:
    print(type(e).__name__, e)
print(f"{time.time()-t:.3f}s")' "$@"
}
probe orders 80
```

Разбор команд:

| Часть команды | Значение |
|---|---|
| `run client --restart=Never` | одиночный под, без Deployment |
| `--command -- sleep infinity` | держать под живым, ничего не делая |
| `wait --for=condition=Ready` | ждать готовности пода |
| `probe orders 80` | подключиться к имени `orders`, порт 80 |
| `python -c '…' "$@"` | аргументы функции попадают в `sys.argv[1]` и `sys.argv[2]` |
| `timeout=5` | ждать соединения не дольше 5 с |

Результат:

```
ConnectionRefusedError [Errno 111] Connection refused
0.020s
```

Разбор вывода:

1. Имя `orders` разрешилось в ClusterIP, поэтому ошибки DNS нет.
2. `Connection refused` — это активный отказ: на пакет ответили, а не промолчали.
3. Отказ пришёл за 0,02 с, а таймаут в 5 с означал бы потерянные пакеты (NetworkPolicy, маршрутизация, 03-6).
4. Мгновенный отказ при пустом EndpointSlice говорит, что это не проблема сети.

#### Шаг 4. Найти правило REJECT на узле

Отказ создаёт **kube-proxy** (компонент на каждом узле, который программирует правила пересылки для Service). Для Service без эндпоинтов он ставит правило **REJECT**: пакет отбрасывается, а отправителю возвращается ответ «порт недоступен». Узлы kind — это контейнеры Docker, поэтому правила узла смотрим командой `iptables-save` через `docker exec`; команда их только читает.

```bash
docker exec lab-worker iptables-save | grep 'lab-03-2/orders'
```

Разбор команды:

| Часть команды | Значение |
|---|---|
| `docker exec lab-worker` | выполнить команду внутри узла `lab-worker` |
| `iptables-save` | вывести все правила iptables |
| `grep 'lab-03-2/orders'` | оставить правила нашего Service |

Результат:

```
-A KUBE-SERVICES -d 10.96.88.241/32 -p tcp -m comment --comment "lab-03-2/orders has no endpoints" -m tcp --dport 80 -j REJECT --reject-with icmp-port-unreachable
```

Строка вывода длинная, но приведена целиком: так её печатает `iptables-save`.

Разбор вывода:

1. `-A KUBE-SERVICES` — правило в цепочке `KUBE-SERVICES` таблицы `filter`. Цепочка с тем же именем есть и в таблице `nat`, но правила отказа kube-proxy пишет в `filter`; `grep` скрывает заголовок таблицы.
2. `-d 10.96.88.241/32 … --dport 80` — условие: адрес и порт нашего Service.
3. Комментарий `has no endpoints` — причина отказа, которую kube-proxy пишет сам.
4. `-j REJECT --reject-with icmp-port-unreachable` — действие: отказ с ICMP-ответом «порт недоступен», поэтому клиент сразу видит `Connection refused`.

#### Шаг 5. Исправить селектор

Приводим селектор в соответствие меткам подов, а затем проверяем, что EndpointSlice заполнился и клиент получает ответ.

```bash
kubectl patch svc orders -p '{"spec":{"selector":{"app":"orders"}}}'
kubectl get endpointslice -l kubernetes.io/service-name=orders
kubectl exec client -- python -c \
  'import urllib.request as u; print(u.urlopen("http://orders", timeout=5).status)'
```

Разбор команд:

| Часть команды | Значение |
|---|---|
| `patch svc orders -p '{…}'` | точечно изменить поле селектора |
| `-l kubernetes.io/service-name=orders` | найти EndpointSlice этого Service по метке |
| `urlopen("http://orders")` | HTTP-запрос по имени Service, порт 80 |
| `.status` | вывести код ответа |

Результат:

```

orders-9vf5b   IPv4          8000    10.244.3.8,10.244.2.10   12s
200
```

Разбор вывода:

1. Service изменён, и контроллер EndpointSlice сразу пересчитал адреса.
2. Тот же объект `orders-9vf5b` теперь содержит два адреса — IP двух подов.
3. В колонке `PORTS` стоит `8000`: имя `http` из `targetPort` превратилось в номер порта контейнера.
4. Код `200` значит, что запрос прошёл через ClusterIP до пода.

#### Шаг 6. Сломать targetPort

Теперь подставляем неверный **targetPort** — порт пода, на который Service пересылает трафик. Селектор верный и поды готовы, но на порту 8080 никто не слушает.

```bash

  -p '[{"op":"replace","path":"/spec/ports/0/targetPort","value":8080}]'
kubectl get endpointslice -l kubernetes.io/service-name=orders

```

Разбор команд:

| Часть команды | Значение |
|---|---|
| `--type=json` | патч в формате JSON Patch: операции над путями |
| `"op":"replace"` | заменить существующее значение |
| `"path":"/spec/ports/0/targetPort"` | поле `targetPort` у первого порта |
| `"value":8080` | новое значение, число вместо имени |

Результат:

```
service/orders patched
NAME           ADDRESSTYPE   PORTS   ENDPOINTS                AGE
orders-9vf5b   IPv4          8080    10.244.2.10,10.244.3.8   15s

…
```

Разбор вывода:

1. Адреса в EndpointSlice на месте, а порт изменился на `8080`.
2. Симптом прежний — `Connection refused` со временем ответа порядка миллисекунд (последняя строка), но причина другая.
3. Пакет дошёл до пода, и отказ послало ядро пода: на порту 8080 нет процесса, поэтому ядро ответило TCP RST, а не ICMP.
4. Различие читается по EndpointSlice: пусто — ищите селектор; адреса есть, но не готовы — ищите readiness; адреса готовы, порт чужой — ищите `targetPort`.

#### Шаг 7. Задать targetPort по имени

Возвращаем `targetPort: http`, потому что имя порта переживает смену номера в образе, а число — нет.


|---|---|

| `get endpointslice -l …` | проверить порт в EndpointSlice |
| `urlopen("http://orders")` | проверить ответ через Service |

Результат:

3. Ответ `200` подтверждает, что Service снова работает.

| Что узнали | Как проверить |
|---|---|
| Service без эндпоинтов отвечает мгновенным отказом | `probe orders 80`, время около 0,02 с |

```bash

```

```

```

Удаление пода `client` занимает около 30 с, потому что kubelet ждёт конца периода остановки (по умолчанию 30 с). Процесс `sleep` работает в контейнере как PID 1 и не обрабатывает SIGTERM, поэтому сам не завершается.

**Вопросы для самопроверки.**

1. Service создан, клиент получает отказ за 20 мс. Какую команду выполните первой и что она покажет?

<details><summary>Ответ</summary>

`kubectl get endpointslice -l kubernetes.io/service-name=<имя>`. Пустые `PORTS` и `ENDPOINTS` означают, что селектор не выбрал ни одного пода. Если адреса есть, проверьте их готовность (`kubectl describe endpointslice`, поле `Ready`), а затем `targetPort`.

</details>

2. Почему при пустом EndpointSlice клиент получает отказ, а не таймаут?

<details><summary>Ответ</summary>

kube-proxy ставит для такого Service правило REJECT с ICMP port unreachable, поэтому пакет не теряется, а отвергается сразу. Таймаут говорит о другом: пакеты молча отбрасываются (NetworkPolicy, маршруты, правило DROP).

</details>

3. Под Ready, селектор верный, адреса в EndpointSlice есть, а отказ остался. Где искать причину?

<details><summary>Ответ</summary>

В несовпадении порта: `targetPort` Service указывает на порт, где процесс не слушает. Сравните колонку `PORTS` в EndpointSlice с портом, который открывает приложение. Прямой запрос на IP пода и порт приложения подтвердит, что под отвечает.

</details>

4. Почему `targetPort` лучше задавать именем?

<details><summary>Ответ</summary>

Имя ссылается на порт в описании контейнера (`ports: [{name: http, …}]`). Если номер порта в образе изменится, достаточно поправить Deployment, а Service менять не нужно. Число приходится править в двух местах, и одно из них легко забыть.

</details>

5. Что произойдёт, если селектор верный, но все поды не проходят readiness?

<details><summary>Ответ</summary>

Адреса подов останутся в EndpointSlice, но с условием `ready: false`, и колонка `ENDPOINTS` в `kubectl get endpointslice` их всё равно покажет. Готовых адресов нет, поэтому kube-proxy поставит то же правило REJECT, и симптом совпадёт с опечаткой в селекторе. Отличие видно в `kubectl describe endpointslice` (`Ready: false`) и в `kubectl get pods`: в колонке `READY` будет `0/1`.

</details>

### Лабораторная работа 2. externalTrafficPolicy и IP клиента

**Цель.** Увидеть, как политика `externalTrafficPolicy` меняет доступность NodePort на узле без подов и какой IP клиента видит под.

**Что понадобится.**

- Стенд 00-1 и namespace `lab-03-2` из подготовки.
- Образы `localhost:5001/orders-api:2.0`, `curlimages/curl:8.11.1` и `alpine:3.20`.
- Порт 30081 свободен на узлах; Docker на хосте с доступом к сети `kind`.
- Около 30 минут.

**Риски.** Работа создаёт короткие контейнеры Docker на хосте и меняет Service в кластере стенда.

- **Что меняется:** в кластере — Deployment и Service с NodePort 30081; на хосте — контейнеры с флагом `--rm`, которые подключаются к сети `kind` и исчезают после запроса.
- **Надолго ли:** до уборки; контейнеры живут секунды.
- **Безопасность:** привилегии не нужны; NodePort 30081 открывается на узлах кластера, но не на хосте наружу.
- **Влияние на систему:** другие Service и namespace не затрагиваются.
- **Откат:** блок «Уборка» в конце работы.

**Схема опыта.** Клиент живёт вне кластера, как внешний балансировщик, и ходит на NodePort двух узлов. Поды стоят только на `lab-worker`, поэтому узлы ведут себя по-разному.

```
клиент (контейнер в сети kind, 172.20.0.8)
   ├──► lab-worker  172.20.0.3:30081 ──► поды echo (оба на этом узле)
   └──► lab-worker2 172.20.0.5:30081 ──► подов нет: Cluster пересылает, Local отбрасывает
```

Схема 8. Смотрите на второй узел: именно там политики расходятся.

#### Шаг 1. Создать поды на одном узле и Service типа NodePort

Команда создаёт Deployment из двух подов, закреплённых за `lab-worker`, и Service с портом узла 30081 и политикой `Cluster`.

```bash
kubectl apply -f - <<'EOF'
apiVersion: apps/v1
kind: Deployment
metadata: {name: echo}
spec:
  replicas: 2
  selector: {matchLabels: {app: echo}}
  template:
    metadata: {labels: {app: echo}}
    spec:
      nodeSelector: {kubernetes.io/hostname: lab-worker}
      containers:
      - name: api
        image: localhost:5001/orders-api:2.0
        ports: [{name: http, containerPort: 8000}]
        readinessProbe: {httpGet: {path: /ready, port: http}, periodSeconds: 2}
---
apiVersion: v1
kind: Service
metadata: {name: echo-np}
spec:
  type: NodePort
  externalTrafficPolicy: Cluster
  selector: {app: echo}
  ports: [{name: http, port: 80, targetPort: http, nodePort: 30081}]
EOF
kubectl rollout status deploy/echo
```

| Часть манифеста | Значение |
|---|---|
| `nodeSelector` | оба пода только на узле `lab-worker` |
| `readinessProbe` | под получает трафик после ответа на `/ready` |
| `type: NodePort` | открыть порт на каждом узле |
| `nodePort: 30081` | номер порта узла, заданный явно |
| `externalTrafficPolicy: Cluster` | начальная политика |

Ожидаемый результат:

```
deployment.apps/echo created
service/echo-np created
…
deployment "echo" successfully rolled out
```

Разбор вывода:

1. Deployment и Service созданы одной командой.
2. Последняя строка значит, что оба пода прошли проверку готовности.
3. Оба пода стоят на `lab-worker`, а у `lab-worker2` для этого Service подов нет.

#### Шаг 2. Сравнить Cluster и Local на двух узлах

Цикл по очереди ставит обе политики и обращается с внешнего клиента к NodePort каждого из двух узлов. Клиент — контейнер в сети Docker `kind`, то есть «снаружи» кластера.

```bash
for etp in Cluster Local; do
  kubectl patch svc echo-np -p "{\"spec\":{\"externalTrafficPolicy\":\"$etp\"}}"
  sleep 3
  for n in lab-worker lab-worker2; do
    IP=$(docker inspect -f '{{.NetworkSettings.Networks.kind.IPAddress}}' $n)
    code=$(docker run --rm --network kind curlimages/curl:8.11.1 \
      -s -m 3 -o /dev/null -w '%{http_code}' http://$IP:30081/version)
    echo "eTP=$etp node=$n($IP) -> $code"
  done
done
```

| Часть команды | Значение |
|---|---|
| `patch svc echo-np -p '{…}'` | сменить политику Service |
| `sleep 3` | дать kube-proxy время обновить правила |
| `docker inspect -f '{{…IPAddress}}'` | взять IP узла в сети `kind` |
| `docker run --rm --network kind` | одноразовый клиент в сети узлов |
| `curl -s -m 3 -o /dev/null` | тихий запрос, ждать не дольше 3 с |
| `-w '%{http_code}'` | напечатать только код ответа |

Результат:

Разбор вывода:

1. При `Cluster` отвечают оба узла: второй пересылает запрос на под соседнего узла. Политика уже стояла `Cluster`, поэтому первый `patch` печатает `(no change)`.
2. При `Local` узел `lab-worker` отвечает, потому что его поды локальны.
3. При `Local` узел `lab-worker2` даёт `000`: curl не получил ответа за 3 с, то есть пакеты отброшены молча.
4. Это таймаут, а не отказ: так выглядит «чёрная дыра» из схемы 6.

#### Шаг 3. Найти правило DROP на узле без подов

Сейчас в Service стоит `Local`. Команда читает правила узла `lab-worker2` и находит те, что отбрасывают пакеты.

```bash

```

| Часть команды | Значение |
|---|---|
| `docker exec lab-worker2` | выполнить команду внутри узла |
| `iptables-save` | вывести все правила iptables |
| `grep 'has no local endpoints'` | оставить правила отбрасывания |
| `head -2` | показать не больше двух строк |

Разбор вывода:

#### Шаг 4. Сравнить IP клиента при Local и Cluster

Клиент отправляет по одному запросу при каждой политике, а потом мы читаем журнал пода. Параметр в адресе (`?local`, `?cluster`) помогает найти нужные строки.

```bash
IP=$(docker inspect -f '{{.NetworkSettings.Networks.kind.IPAddress}}' lab-worker)
kubectl patch svc echo-np -p '{"spec":{"externalTrafficPolicy":"Local"}}'
docker run --rm --network kind alpine:3.20 sh -c \
  "ip -4 -o addr show eth0 | awk '{print \"client=\"\$4}'; \
   wget -q -O /dev/null http://$IP:30081/version?local"
kubectl patch svc echo-np -p '{"spec":{"externalTrafficPolicy":"Cluster"}}'
sleep 2
docker run --rm --network kind alpine:3.20 \
  wget -q -O /dev/null http://$IP:30081/version?cluster
kubectl logs -l app=echo --tail=50 --prefix | grep -E 'version\?(local|cluster)'
```

| Часть команды | Значение |
|---|---|
| `ip -4 -o addr show eth0` | адрес самого клиента |
| `awk '{print "client="$4}'` | напечатать его в виде `client=адрес` |
| `wget -q -O /dev/null` | тихий запрос без сохранения ответа |
| `logs -l app=echo --prefix` | журналы всех подов с именем пода в начале строки |
| `grep -E 'version\?(local\|cluster)'` | оставить две строки нашего опыта |

Результат (строки `service/echo-np patched` опущены):

```

[pod/echo-…-f7zb9/api] 10.244.2.1 "GET /version?cluster HTTP/1.1" 200 -
```

Разбор вывода:

1. Клиент имеет адрес `172.20.0.8`.
2. При `Local` под записал `172.20.0.8`: IP клиента сохранился.
3. При `Cluster` под записал `10.244.2.1`: kube-proxy выполнил SNAT, и под видит адрес узла в сети подов.
4. Для rate limiting, geo и аудита по IP нужен `Local` либо L7-заголовок `X-Forwarded-For`.

**Вопросы для самопроверки.**

1. Почему при `Local` второй узел дал `000`, а не мгновенный отказ?

<details><summary>Ответ</summary>

kube-proxy ставит там правило DROP, которое отбрасывает пакет без ответа, поэтому клиент ждёт до таймаута. Мгновенный отказ даёт REJECT — его kube-proxy ставит для Service без эндпоинтов вообще.

<details><summary>Ответ</summary>

Знать, на каких узлах есть поды. Для `type: LoadBalancer` балансировщик проверяет `healthCheckNodePort`: порт отвечает 200 на узле с готовым локальным эндпоинтом и 503 без него.

</details>

3. Как получить IP клиента, не включая `Local`?

<details><summary>Ответ</summary>

Передавать его на уровне L7: заголовок `X-Forwarded-For` у прокси либо PROXY protocol между балансировщиком и приложением. SNAT kube-proxy при этом не мешает.

</details>

### Лабораторная работа 3. Завершающийся под в EndpointSlice

**Цель.** Увидеть три условия эндпоинта (`ready`, `serving`, `terminating`) у пода, который удаляют, и понять, почему на этом строится плавная выкатка.

**Что понадобится.**

- Стенд 00-1 и namespace `lab-03-2` из подготовки.
- Образ `localhost:5001/orders-api:2.0` и `jq` на хосте (00-2).
- Знание `preStop` и grace period (02-5).
- Около 20 минут.

**Схема опыта.** Deployment держит три пода за Service `echo`. Мы удаляем один под, у которого в `preStop` стоит пауза 8 с, и за это время читаем срез.

```
Service echo ──► EndpointSlice: 3 эндпоинта
kubectl delete pod X ──► deletionTimestamp ──► preStop sleep 8 с ──► SIGTERM
                              │
                              └─ условия X: ready=false, serving=true, terminating=true
```

Схема 9. Пока идёт `preStop`, под уже не принимает новые соединения, но ещё отвечает на текущие; окно длится 8 с.

#### Шаг 1. Создать Deployment с preStop и Service

Команда создаёт три пода с паузой перед остановкой и Service, который их выбирает. Эти объекты нужны и следующим двум работам.

```bash
kubectl apply -f - <<'EOF'
apiVersion: apps/v1
kind: Deployment
metadata: {name: echo}
spec:
  replicas: 3
  selector: {matchLabels: {app: echo}}
  template:
    metadata: {labels: {app: echo}}
    spec:
      containers:
      - name: api
        image: localhost:5001/orders-api:2.0
        ports: [{name: http, containerPort: 8000}]
        readinessProbe: {httpGet: {path: /ready, port: http}, periodSeconds: 2}
        lifecycle: {preStop: {sleep: {seconds: 8}}}
---
apiVersion: v1
kind: Service
metadata: {name: echo}
spec:
  selector: {app: echo}
  ports: [{port: 80, targetPort: http}]
EOF
kubectl rollout status deploy/echo
```

| Часть манифеста | Значение |
|---|---|
| `replicas: 3` | три пода; планировщик обычно разносит их по узлам |
| `lifecycle.preStop.sleep` | kubelet ждёт 8 с перед SIGTERM |
| `targetPort: http` | порт пода по имени |

Ожидаемый результат:

```

…

```

Разбор вывода: три пода Ready, и у Service `echo` в срезе три эндпоинта. Пауза `sleep` выполняется самим kubelet и не требует команды `sleep` в образе.

#### Шаг 2. Удалить под и прочитать условия среза

Команда удаляет первый под без ожидания его исчезновения, ждёт 2 с и печатает условия всех эндпоинтов.


| Часть команды | Значение |
|---|---|
| `delete … --wait=false` | вернуть управление сразу, не ждать удаления |
| `get pods -l app=echo -o name \| head -1` | имя первого пода |
| `-l kubernetes.io/service-name=echo` | срез нашего Service |

Результат (суффиксы подов у вас другие):

4. Под `qmt9p` — замена от Deployment: она уже в срезе, потому что Deployment создаёт новый под сразу после удаления.
5. Строк четыре, а не три: терминирующий под остаётся в срезе, пока не завершится.

Разбор вывода:

2. Остались три готовых эндпоинта, включая замену.

| Что узнали | Где видно |
|---|---|
| Завершающийся под остаётся в срезе с `terminating: true` | шаг 2 |
| Для новых соединений он не выбирается | `ready: false` |


**Вопросы для самопроверки.**

1. Что произойдёт, если завершаются все поды Service?

<details><summary>Ответ</summary>

kube-proxy берёт эндпоинты с `serving: true`, пока они проходят проверку готовности, чтобы не оборвать трафик целиком. Новые соединения идут на уходящие поды, а не пропадают.

</details>

2. Чем `serving` отличается от `ready`?

<details><summary>Ответ</summary>

`ready` значит «под Ready и не завершается». `serving` значит «под проходит проверку готовности», даже если он завершается. Поэтому у уходящего пода `ready: false`, а `serving: true`.

</details>

3. Зачем в `preStop` стоит пауза, если Service уже убрал под из `ready`?

<details><summary>Ответ</summary>

Правила kube-proxy обновляются на всех узлах не мгновенно, и часть запросов ещё идёт на уходящий под. Пауза оставляет ему время ответить на них до SIGTERM (02-5).

</details>

### Лабораторная работа 4. kube-proxy в режиме nftables

**Цель.** Переключить kube-proxy стенда с iptables на nftables, найти Service в таблице `kube-proxy` и вернуть режим обратно.

**Что понадобится.**

- Стенд 00-1, Deployment и Service `echo` из работы 3.
- На хосте ядро 5.13 или новее: узлы kind используют ядро хоста.
- `jq` на хосте.
- Около 30 минут.

**Риски.** Работа меняет конфигурацию kube-proxy всего кластера стенда.

- **Что меняется:** ConfigMap `kube-proxy` в `kube-system` и режим на четырёх узлах; kube-proxy перезапускается по очереди.
- **Надолго ли:** на время работы; шаг 5 возвращает режим, уборка проверяет его. Аннотация `last-applied-configuration`, которую добавит `kubectl apply`, останется в ConfigMap; она безвредна.
- **Безопасность:** привилегии те же, что у администратора кластера; привилегированных контейнеров нет.
- **Влияние на систему:** затрагивает все namespace стенда, включая `orders` и вход через Envoy; при перезапуске правила на узле пересобираются секунды, установленные соединения сохраняются в conntrack. Если ядро хоста старше 5.13, kube-proxy в режиме nftables не поднимет правила, и Service перестанут работать во всём кластере до отката.
- **Откат:** шаг 5; если kube-proxy не стартует, выполните команды шага 5 сразу: они возвращают `mode: iptables` и перезапускают DaemonSet. Проверка — строка `Using iptables Proxier` в журнале kube-proxy.

**Схема опыта.** Режим читается из ConfigMap при старте kube-proxy. После перезапуска он стирает правила старого режима и создаёт таблицу нового.

```
ConfigMap kube-proxy (mode) ──► kube-proxy на узле ──► iptables: цепочки KUBE-*   (до)
                                                  └──► nftables: таблица kube-proxy (после)
```

Схема 10. Один и тот же Service описан двумя разными наборами правил; переключатель — поле `mode`.

```bash
echo "no affinity: $(cnt)"
kubectl patch svc echo -p '{"spec":{"sessionAffinity":"ClientIP"}}'
sleep 2
echo "ClientIP: $(cnt)"
kubectl patch svc echo -p '{"spec":{"sessionAffinity":"None"}}'
```

| Часть команды | Значение |
|---|---|
| `$(cnt)` | словарь «под: число ответов» |
| `sessionAffinity":"ClientIP"` | привязать клиента к одному поду |
| `sessionAffinity":"None"` | вернуть случайный выбор |

Результат:

```
no affinity: {'xcktj': 24, 'fl22g': 22, 'sxwfr': 14}
service/echo patched
ClientIP: {'fl22g': 60}
service/echo patched
```

Разбор вывода:

1. Без привязки каждое соединение выбирает под случайно: доли 24, 22 и 14 из 60 неравны, потому что выбор случаен.
2. С `ClientIP` все 60 соединений пришли в один под.
3. Имена подов у вас будут другими; важно, что отвечает один под из трёх.

#### Шаг 3. Разметить зоны и включить trafficDistribution

Узлам ставим зоны, а затем по очереди включаем три значения `trafficDistribution`.

```bash
kubectl label node lab-worker topology.kubernetes.io/zone=zone-a
kubectl label node lab-worker2 lab-worker3 topology.kubernetes.io/zone=zone-b
echo "default: $(cnt)"
for v in PreferClose PreferSameZone PreferSameNode; do
  kubectl patch svc echo -p "{\"spec\":{\"trafficDistribution\":\"$v\"}}"
  sleep 3
  echo "$v: $(cnt)"
done
```

| Часть команды | Значение |
|---|---|
| `label node … topology.kubernetes.io/zone=…` | зона узла: у kind своей зоны нет |
| `trafficDistribution":"$v"` | предпочтение близких эндпоинтов |
| `sleep 3` | дать контроллеру обновить подсказки в срезе |

Результат:

```
node/lab-worker labeled
node/lab-worker2 labeled
node/lab-worker3 labeled
default: {'sxwfr': 21, 'xcktj': 23, 'qmt9p': 16}
Warning: spec.trafficDistribution: "PreferClose" is deprecated; use "PreferSameZone"
service/echo patched
PreferClose: {'sxwfr': 60}
service/echo patched
PreferSameZone: {'sxwfr': 60}
service/echo patched
PreferSameNode: {'sxwfr': 60}
```

Разбор вывода:

1. Без `trafficDistribution` соединения расходятся по всем трём подам.
2. Сервер предупреждает, что `PreferClose` устарел, и предлагает `PreferSameZone`.
3. Со всеми тремя значениями отвечает один под, `sxwfr`: он стоит на `lab-worker`, как и клиент.
4. Результаты `PreferSameZone` и `PreferSameNode` совпали потому, что в `zone-a` один узел. Если добавить в зону второй узел с подом, значения разойдутся.

#### Шаг 4. Прочитать подсказки в EndpointSlice

Подсказки показывают, кому предназначен каждый эндпоинт. Команда печатает под, узел и поле `hints`.

```bash
kubectl get endpointslice -l kubernetes.io/service-name=echo -o json | jq -c \
  '.items[].endpoints[] | {pod: .targetRef.name[-5:], node: .nodeName, hints}'
```

Результат (две строки из трёх; список `forNodes` сокращён до `…`):

```
{"pod":"xcktj","node":"lab-worker3","hints":{"forNodes":[…],"forZones":[{"name":"zone-b"}]}}
{"pod":"sxwfr","node":"lab-worker","hints":{"forNodes":[…],"forZones":[{"name":"zone-a"}]}}
```

Разбор вывода:

1. `forZones` называет зону, клиенты которой должны ходить на эндпоинт.
2. `forNodes` называет узел для значения `PreferSameNode`.
3. kube-proxy на узле выбирает только эндпоинты, подсказки которых указывают на его зону или узел.
4. Риск: в `zone-a` один под, и он принимает весь трафик клиентов этой зоны.

**Итог.**

| Что узнали | Где видно |
|---|---|
| Без привязки выбор случаен, доли неравны | шаг 2 |
| `ClientIP` отправляет все соединения клиента в один под | `{'fl22g': 60}` |
| `PreferSameZone` и `PreferSameNode` сужают выбор до близких подов | `{'sxwfr': 60}` |
| `PreferClose` устарел | предупреждение в выводе |
| Подсказки хранятся в срезе | `hints.forZones`, `hints.forNodes` |

**Уборка.** Снимаем метки зон, удаляем объекты работ 3–5 и клиента, возвращаем namespace по умолчанию и удаляем namespace `lab-03-2`.

```bash
kubectl label node lab-worker lab-worker2 lab-worker3 topology.kubernetes.io/zone-
kubectl delete pod client
kubectl delete deploy/echo svc/echo
kubectl config set-context --current --namespace=default
kubectl delete ns lab-03-2
unset -f cnt
```

Ожидаемый результат: три строки `node/… unlabeled`, затем сообщения об удалении объектов и namespace, и `Context "kind-lab" modified.`. Удаление может занять около 30 с: `sleep` в клиентском поде не обрабатывает SIGTERM.

**Вопросы для самопроверки.**

1. Почему при `sessionAffinity: ClientIP` за NAT вся нагрузка уходит в один под?

<details><summary>Ответ</summary>

Привязка идёт по IP источника, а за NAT все клиенты выглядят одним адресом. Service видит один IP и отправляет его соединения в один под.

</details>

2. Чем опасен `PreferSameZone` при неравномерных репликах?

<details><summary>Ответ</summary>

Единственный под зоны принимает весь трафик клиентов этой зоны и может перегрузиться, пока соседние зоны простаивают. Реплики должны стоять по зонам равномерно (05-3).

</details>

3. Куда пойдёт трафик, если в зоне клиента нет готовых эндпоинтов?

<details><summary>Ответ</summary>

В другие зоны: `trafficDistribution` — предпочтение, а не запрет, поэтому Service остаётся доступным.

</details>
