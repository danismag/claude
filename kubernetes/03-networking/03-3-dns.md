## Где мы на карте

Эта часть показывает, как под находит другие поды и внешние системы по имени. В 03-2 мы разобрали Service: постоянный адрес и правила kube-proxy, которые превращают его в адреса подов. Здесь мы разбираем звено перед ним, потому что приложение обращается к Service по имени, а не по IP. Часть опирается на 03-1 (сеть подов и conntrack) и 02-3 (имена подов StatefulSet за headless Service).

Следующие части используют те же имена. Gateway API (03-4) ссылается на Service по имени, а диагностика сети по слоям (11-3) начинает поиск причины с DNS.

```
под ── getaddrinfo("orders-api.orders") ──► resolv.conf пода        эта часть, §2
                                                   │ UDP/53
                                                   ▼
                          ClusterIP kube-dns ─► правила kube-proxy   03-2
                                                   │
                                                   ▼
                          поды CoreDNS ── cluster.local ─► ответ из API
                                       └─ остальное ─────► DNS узла
```

Схема 1. Путь одного запроса: слева приложение и его настройки, справа CoreDNS; смотрите на стрелку от CoreDNS, которая делит запросы на «свои» и внешние.

## 1. Какую задачу решает DNS кластера

DNS кластера даёт стабильные имена объектам, адреса которых меняются. Разберём, какие имена создаёт Kubernetes, какие записи за ними стоят и чего DNS не делает.

### Имена вместо адресов

Поды живут недолго, и их IP-адреса меняются при каждой замене. **ClusterIP** (виртуальный адрес Service внутри кластера, 03-2) стабилен, но выдаётся случайно и не годится для конфигурации приложения. Поэтому Kubernetes связывает каждый Service с именем, а приложение хранит только имя.

**DNS** (Domain Name System) — служба, которая превращает имя в IP-адрес. В кластере её роль выполняет **CoreDNS**: DNS-сервер, который запущен подами в namespace `kube-system` и читает объекты Service и EndpointSlice через API. **EndpointSlice** (срез эндпоинтов) — объект со списком адресов подов, за которыми стоит Service (03-2).

Имя Service строится по шаблону `<service>.<namespace>.svc.cluster.local`. Последняя часть, `cluster.local`, называется **доменом кластера** (cluster domain); её задаёт kubelet в поле `clusterDomain`.

### Какие записи создаёт Kubernetes

Тип записи зависит от вида объекта. Для обычного Service CoreDNS отвечает ClusterIP, а для остальных объектов — так, как показывает список.

- **Обычный Service** — запись A (IPv4) или AAAA (IPv6) с адресом ClusterIP.
- **Headless Service** — Service без ClusterIP (`clusterIP: None`). Запись A содержит адреса всех готовых подов, поэтому клиент сам выбирает, к какому обращаться.
- **Под StatefulSet** — имя `<pod>.<service>.<namespace>.svc.cluster.local` за headless Service (02-3).
- **Именованный порт** — запись SRV (service record) вида `_http._tcp.<service>.<namespace>.svc.cluster.local`: она хранит номер порта и имя хоста.
- **ExternalName** — Service, у которого вместо ClusterIP стоит запись CNAME (псевдоним на другое имя).
- **Под** — имя вида `10-244-1-5.<namespace>.pod.cluster.local`, где IP записан через дефисы. Его создаёт плагин `kubernetes` с режимом `pods insecure`, и на практике это имя почти не нужно.

Запись типа PTR (обратное разрешение IP в имя) CoreDNS тоже отдаёт, но только для зон `in-addr.arpa` и `ip6.arpa` из своего Corefile (§2).

### Чего DNS не делает

DNS отвечает на вопрос «какие адреса у имени», но ничего не знает о состоянии подов за ними. Для обычного Service балансировку делает kube-proxy на узле, а DNS отдаёт один и тот же ClusterIP. Для headless Service список адресов получает сам клиент, поэтому порядок и повторные запросы остаются на его совести.

Ответы DNS кэшируются: клиент и CoreDNS хранят их до истечения **TTL** (time to live, срока жизни записи). Для записей кластера TTL равен 30 с (§2). Поэтому изменение адресов headless Service видно клиенту с задержкой до 30 с.

## 2. Как устроен DNS кластера

DNS кластера складывается из трёх частей: настройки резолвера в каждом поде, Service `kube-dns` и подов CoreDNS с их конфигурацией. Пройдём по ним в порядке запроса.

### Путь запроса

Приложение вызывает системную функцию `getaddrinfo`, которая читает `/etc/resolv.conf` пода и отправляет запрос по UDP на порт 53. Адрес назначения — ClusterIP Service `kube-dns`, поэтому дальше работают правила kube-proxy из 03-2: они подменяют адрес на IP одного из подов CoreDNS. Под CoreDNS либо отвечает сам, либо пересылает запрос дальше.

```
приложение ─► libc (getaddrinfo) ─► 10.96.0.10:53 (ClusterIP kube-dns)
                                          │ DNAT в правилах kube-proxy
                                          ▼
                              под CoreDNS (:53)
                      ┌───────────────────┴───────────────────┐
              имя в cluster.local                    любое другое имя
              плагин kubernetes                      плагин forward
              отвечает из памяти                     на DNS узла
```

Схема 2. Два пути в CoreDNS: внутренние имена CoreDNS знает сам, внешние отдаёт резолверу узла.

Service называется `kube-dns` по историческим причинам: так называлась прежняя реализация. Сам kube-dns устарел, а пакеты для него перестанут собираться после версии 1.40. Под этим именем сегодня работает CoreDNS: kubeadm 1.36 ставит CoreDNS v1.14.2, kubeadm 1.37 — v1.14.6.

### resolv.conf и dnsPolicy

Файл `/etc/resolv.conf` в поде создаёт **kubelet**: агент на узле, который запускает контейнеры (01-2). Содержимое зависит от поля **dnsPolicy** — политики DNS пода, которая выбирает источник настроек резолвера.

- **ClusterFirst** — значение по умолчанию. Резолвер указывает на `kube-dns`, а имена вне домена кластера CoreDNS пересылает на DNS узла.
- **ClusterFirstWithHostNet** — то же для пода с `hostNetwork: true`. Без него такой под тихо получает политику `Default`.
- **Default** — под получает копию `resolv.conf` узла. Название вводит в заблуждение: по умолчанию применяется не оно, а `ClusterFirst`.
- **None** — настройки не создаются, всё задаётся полем `dnsConfig` (§3).

Адрес `kube-dns` и домен кластера kubelet берёт из своей конфигурации: поля `clusterDNS` и `clusterDomain` (01-2). Вот файл пода с политикой по умолчанию на стенде.

```
search lab-03-3.svc.cluster.local svc.cluster.local cluster.local
nameserver 10.96.0.10
options ndots:5
```

Три строки читаются так: `nameserver` — адрес сервера, `search` — список доменов, которые резолвер дописывает к коротким именам, а `options` — параметры. Если на узле есть свои search-домены, kubelet добавляет их в конец списка.

### search и ndots

**Search-домен** (search domain) — суффикс, который резолвер дописывает к имени, чтобы короткое имя стало полным. Благодаря первым двум доменам из примера выше под в namespace `lab-03-3` обращается к соседнему Service как `orders-api` и к Service другого namespace как `orders-api.orders`.

**ndots** — число из `options`, которое решает, с чего начинать: с search-доменов или с самого имени. Правило такое. Если точек в имени меньше ndots и на конце нет точки, резолвер подставляет search-домены по очереди, а имя как есть пробует последним. Если точек не меньше ndots, порядок обратный. Kubernetes ставит `ndots:5`, чтобы работали имена вроде `postgres.orders.svc`, где точек всего две.

За удобство платят числом запросов. Клиент спрашивает адрес IPv4 (A) и IPv6 (AAAA) отдельными запросами, поэтому каждая попытка стоит два пакета. Число пакетов — это число попыток, умноженное на два.

Имя, которое заканчивается точкой, называется **FQDN** (fully qualified domain name, полное имя): резолвер считает его абсолютным и не трогает search-домены. Ниже счёт для пяти имён, измеренный на стенде в namespace `lab-03-3` (работа 1).

| Имя | Запросов | Что происходит |
|---|---|---|
| kernel.org | 8 | три search-домена с NXDOMAIN, затем само имя |
| iana.org. | 2 | точка на конце: сразу как есть |
| orders-api.orders | 4 | первый search-домен с NXDOMAIN, второй с ответом |
| postgres.orders.svc.cluster.local | 8 | четыре точки меньше пяти: три «склеенных» имени |
| postgres.orders.svc.cluster.local. | 2 | точка на конце: сразу как есть |

**NXDOMAIN** — ответ DNS «такого имени нет». Лишние NXDOMAIN отвечает сам CoreDNS за доли миллисекунды, но каждый такой запрос остаётся пакетом, записью в conntrack и работой для CoreDNS. Полное имя Service без точки на конце тоже стоит восьми запросов, и это неочевидно.

### CoreDNS и его Corefile

CoreDNS работает как Deployment `coredns` в `kube-system`, обычно в двух репликах с меткой `k8s-app=kube-dns`; Service `kube-dns` отправляет трафик на них. Конфигурация лежит в ConfigMap `coredns` и называется **Corefile**: в нём перечислены зоны и **плагины** (plugins) — модули, каждый из которых обрабатывает запрос по-своему. Вот Corefile стенда в сокращении.

```
.:53 {
    errors
    health { lameduck 5s }
    ready
    kubernetes cluster.local in-addr.arpa ip6.arpa {
       pods insecure
       fallthrough in-addr.arpa ip6.arpa
       ttl 30
    }
    prometheus :9153
    forward . /etc/resolv.conf { max_concurrent 1000 }
    cache 30 {
       disable success cluster.local
       disable denial cluster.local
    }
    loop
    reload
    loadbalance
}
```

Запрос проходит плагины в порядке их обработки внутри CoreDNS, а не в порядке строк файла. Что делает каждый плагин и на что он влияет в эксплуатации, показывает таблица.

| Плагин | Что делает | Что значит для эксплуатации |
|---|---|---|
| kubernetes | отвечает за cluster.local по данным API, TTL 30 с | новый Service виден сразу |
| forward | остальные имена идут на DNS узла | сломан DNS узла, сломан внешний DNS подов |
| cache 30 | кэш на 30 с, но не для cluster.local | внешние ответы кэшируются, внутренние всегда свежие |
| loop | находит петлю и останавливает CoreDNS | защищает от forward на самого себя |
| reload | перечитывает Corefile при изменении | правка ConfigMap применяется без перезапуска |
| health, ready | проверки для kubelet, lameduck 5 с | CoreDNS ещё 5 с отвечает при остановке |
| prometheus | метрики на порту 9153 | источник для мониторинга (§4) |
| errors | пишет ошибки в журнал | единственный вывод по умолчанию |

Плагин `kubernetes` держит данные в памяти и обновляет их через watch на Service и EndpointSlice (01-1), поэтому кэшировать внутренние ответы второй раз не нужно. Директива `fallthrough` отдаёт запрос следующему плагину, если имя в зоне не найдено; в стенде она относится только к обратным зонам.

## 3. Как управлять DNS

Управлять DNS можно на трёх уровнях: настройками одного пода, конфигурацией CoreDNS и объектами, которые подставляют внешние имена. Начнём с самого узкого.

### dnsConfig в манифесте пода

Поле `dnsConfig` дописывает или заменяет настройки резолвера пода. Для `ClusterFirst` оно добавляет строки к тем, что создал kubelet, а для `dnsPolicy: None` задаёт всё с нуля. Вот манифест пода с `ndots:2`.

```yaml
apiVersion: v1
kind: Pod
metadata: {name: client}
spec:
  dnsPolicy: ClusterFirst
  dnsConfig:
    options:
    - {name: ndots, value: "2"}
  containers:
  - {name: app, image: python:3.12-slim, command: [sleep, infinity]}
```

В `dnsConfig` можно указать три списка: `nameservers` (до трёх адресов), `searches` (до 32 доменов, не больше 2048 знаков суммарно) и `options`. С 1.34 в `searches` разрешена одиночная точка — это нужно клиентам, которые иначе подставляют лишний домен. Менять политику DNS в запущенном поде нельзя: поле неизменяемо, под пересоздают.

### Как уменьшить число запросов

Лучший способ — назвать внешний хост полным именем с точкой на конце, например `api.partner.com.`. Это правка в конфигурации приложения, и она не требует права на кластер. Дополнительные способы названы в списке.

- **FQDN с точкой** — резолвер не трогает search-домены; 2 запроса вместо 8.
- **ndots:2** в `dnsConfig` — внешние имена с двумя точками идут сразу, а `<service>.<namespace>` с одной точкой ещё ищется в search-доменах.
- **Пул соединений** — приложение резолвит имя один раз и переиспользует соединение, а не ищет адрес на каждый запрос.
- **autopath** — плагин CoreDNS, который сам перебирает search-домены на сервере и отвечает клиенту за один запрос. Он требует режим `pods verified`, больше памяти у CoreDNS и особого внимания к версиям.
- **NodeLocal DNSCache** — кэш на каждом узле (§6).

Значение `ndots:1` ломает короткие внутренние имена, и подробности в §5.

### Corefile через ConfigMap

Конфигурацию CoreDNS меняют правкой ConfigMap `coredns` в `kube-system`. Плагин `reload` замечает новый файл и перечитывает его без перезапуска подов. Изменение доходит до пода не сразу. Сначала kubelet обновляет том ConfigMap, это занимает до минуты (04-1), а затем `reload` проверяет файл раз в 30 с со случайным сдвигом. На стенде новая запись стала видна через 63 с, поэтому после правки ждите минуту и только потом ищите ошибку.

Ошибка в Corefile опасна. При ошибочном изменении `reload` оставляет прежнюю конфигурацию и пишет сообщение в журнал, но если CoreDNS перезапустится с неверным файлом, он не стартует. Перед правкой сохраните исходный Corefile в файл, как это делает работа 3.

### Внешние имена в кластере

Чтобы поды видели внутреннюю систему организации по имени, есть четыре пути, от самого простого к самому глубокому.

- **ExternalName** — Service с полем `externalName: legacy.corp.example`. CoreDNS отдаёт CNAME, а приложение ходит на `legacy.<namespace>`. Подходит для имён, которые DNS уже знает.
- **Service без selector и ручной EndpointSlice** — вы сами записываете внешний IP; приложение ходит на имя Service. Адрес меняется в одном объекте.
- **Плагин hosts** в Corefile — статическая запись «адрес имя» для узкого случая; её покажет работа 3.
- **Плагин forward для зоны** — блок `corp.internal:53 { forward . 10.0.50.2 }` отправляет всю зону на корпоративный DNS-сервер.

Первые два способа не требуют правки CoreDNS и поэтому безопаснее: ошибка в объекте Service затрагивает один namespace, а ошибка в Corefile — весь кластер.

## 4. Как увидеть состояние DNS

Состояние DNS читают на трёх уровнях: что видит приложение, сколько запросов уходит из пода и что происходит внутри CoreDNS. Начинать нужно с того, что видит приложение.

### Что видит приложение

Приложение резолвит имя через libc, поэтому проверять нужно тем же путём. Инструменты различаются тем, применяют ли они search-домены и ndots.

| Инструмент | Применяет search и ndots | Для чего |
|---|---|---|
| getent hosts, getent ahosts | да, через libc | как имя видит приложение |
| python socket.getaddrinfo | да | то же и время ответа |
| dig | нет, с флагом +search да | точный запрос к одному серверу |
| nslookup из busybox | нет | не используйте для проверки |

Утилита `nslookup` из busybox вводит в заблуждение: она не знает search-доменов и показывает ответ, которого приложение не получит. В 02-3 она вернула для имени `web-1.web` адрес `127.0.53.53`, хотя из libc имя разрешалось корректно. Образ с `dig` — `nicolaka/netshoot`; в слабом образе приложения `dig` обычно нет, а `getent` есть почти всегда.

### Сколько запросов уходит

Число запросов видно только на сетевом интерфейсе пода. Команда `kubectl debug` добавляет в запущенный под **эфемерный контейнер** (ephemeral container) — временный контейнер для отладки, который делит сеть с основными контейнерами пода. В нём запускают `tcpdump` на порт 53, а приложение в это время резолвит имя.

```
под client (одна сеть на все контейнеры)
┌──────────────────────────────────────────────┐
│ основной контейнер ── getaddrinfo ──┐        │
│ эфемерный контейнер: tcpdump -i eth0 ◄┘ UDP/53│
└───────────────────────┬──────────────────────┘
                        ▼ eth0
                 10.96.0.10 (kube-dns)
```

Схема 3. Захват внутри пода: tcpdump видит каждый пакет, который отправляет приложение, и поэтому сразу показывает лишние запросы.

Для работы `tcpdump` нужны права NET_RAW и NET_ADMIN; их даёт профиль `--profile=netadmin`. Подробный пример — в работе 1.

### Состояние CoreDNS

Здоровье CoreDNS читают по четырём источникам. Первый — адреса Service: если в EndpointSlice для `kube-dns` нет готовых подов, DNS не работает. Второй — журнал подов с меткой `k8s-app=kube-dns`. Третий — плагин `log`, который пишет каждый запрос с кодом ответа и флагами. Четвёртый — метрики на порту 9153.

```bash
kubectl -n kube-system get endpointslice -l kubernetes.io/service-name=kube-dns
kubectl -n kube-system logs -l k8s-app=kube-dns --tail=20
kubectl -n kube-system get pods -l k8s-app=kube-dns -o wide
```

Первая команда показывает адреса подов CoreDNS за Service, вторая — последние строки журнала всех реплик, а третья — узлы, на которых они работают. На стенде обе реплики стоят на `lab-control-plane`, поэтому потеря этого узла отключает DNS целиком.

Метрики CoreDNS полезны в трёх вариантах. Счётчик `coredns_dns_requests_total` показывает поток запросов по типам, `coredns_dns_responses_total` — ответы по кодам `rcode` (код ответа: NOERROR, NXDOMAIN, SERVFAIL), а гистограмма `coredns_dns_request_duration_seconds` — время ответа. Если доля NXDOMAIN растёт, приложения тратят запросы на перебор search-доменов (§5).

## 5. Что ломается и как найти причину

Сбои DNS делятся на три группы: DNS недоступен совсем, DNS отвечает, но запросов слишком много, и ответ приходит, но неверный. Каждая группа имеет свой признак и свой первый шаг.

### CoreDNS недоступен

Когда нет ни одной готовой реплики CoreDNS, у Service `kube-dns` пустой список адресов. kube-proxy отвечает на запросы к такому Service отказом `REJECT` (03-2), поэтому часть попыток резолвера падает сразу. Остальные ждут таймаут: по `man resolv.conf` резолвер glibc ждёт ответ 5 с и повторяет попытку до двух раз. Приложение с готовым пулом соединений живёт дольше, а новые соединения сразу получают ошибку `Temporary failure in name resolution`.

Работа 2 воспроизводит этот сбой и измеряет его. Причин обычно три. Реплики остановлены или не проходят проверку `ready`, узел с обеими репликами потерян, либо CoreDNS упёрся в лимит CPU и отвечает с таймаутами (05-1).

### Лишние запросы и ndots:1

Признак лишних запросов — высокая доля NXDOMAIN в метриках CoreDNS и рост нагрузки на CPU без роста полезного трафика. Подтверждает его захват из §4: внешнее имя без точки даёт 8 запросов, 6 из них с NXDOMAIN. На тысячах подов, которые ходят во внешний API на каждый запрос, это умножает нагрузку на CoreDNS в разы.

Простое решение, `ndots:1`, создаёт обратную проблему. Имя `orders-api.orders` с одной точкой теперь не меньше ndots, поэтому резолвер сначала спрашивает его как абсолютное. Запрос уходит во внешний DNS, получает NXDOMAIN (на стенде этот круг занял около 1,5 с), и только потом резолвер перебирает search-домены. Внутреннее имя утекает наружу и тратит время. Безопасный компромисс — `ndots:2` для конкретных сервисов и FQDN в конфигурации приложений.

### Цикл forward

Плагин `loop` останавливает CoreDNS, если находит, что запрос возвращается к нему самому. Классическая причина — узел с `systemd-resolved`: его `/etc/resolv.conf` указывает на локальный адрес `127.0.0.53`, CoreDNS копирует этот файл и пересылает запросы сам себе. Под уходит в `CrashLoopBackOff`, а в журнале видно слово `Loop`.

Лечат настройкой kubelet: `resolvConf: /run/systemd/resolve/resolv.conf` указывает на файл с настоящими серверами. На Ubuntu kubeadm делает это сам, если обнаружит `systemd-resolved`. Эта ловушка разобрана и в курсе по сетям (networks, 08-4).

### Блокировка и гонки conntrack

Если DNS пропал после включения NetworkPolicy (03-6), проверьте исходящий трафик к `kube-dns` на порт 53 по UDP и TCP. Политика «запретить всё» блокирует и его. Признак — таймауты, а не мгновенный отказ, потому что пакеты молча отбрасываются.

Редкие задержки ровно по 5 секунд связаны с конкурентной записью в conntrack (03-1). Клиент отправляет A и AAAA одновременно с одного порта, пакеты проходят преобразование адреса параллельно, и один из них теряется. Часть гонок исправлена в ядрах 5.x, но полностью проблему снимает отказ от conntrack для DNS: его даёт NodeLocal DNSCache (§6).

### Порядок поиска причины

Идите от клиента к серверу и останавливайтесь на первом найденном звене.

1. Прочитайте `resolv.conf` пода и проверьте `nameserver` и `ndots`.
2. Проверьте имя через libc (`getent hosts <имя>`) и точным запросом (`dig @10.96.0.10 <имя>.`).
3. Убедитесь, что в EndpointSlice `kube-dns` есть готовые адреса.
4. Прочитайте журнал и метрики CoreDNS: перезапуски, `Loop`, SERVFAIL, доля NXDOMAIN.
5. Проверьте NetworkPolicy на исходящий трафик к порту 53.
6. Сравните внешнее и внутреннее имя: если не работает только внешнее, смотрите DNS узла.

## 6. Пределы и значения по умолчанию

Значения DNS задают три слоя: клиентская библиотека, Kubernetes и CoreDNS. Ниже они собраны в одно место, затем разобраны способы выдержать нагрузку.

### Значения клиента и Kubernetes

Эти значения действуют на стороне пода, и менять их можно полем `dnsConfig`.

- **ndots** — 5 в Kubernetes; в самой glibc значение по умолчанию 1.
- **timeout** — 5 с на одну попытку (glibc).
- **attempts** — 2 попытки на сервер (glibc).
- **search** — до 32 доменов и до 2048 знаков в `dnsConfig`.
- **nameservers** — до 3 адресов в `dnsConfig`.
- **Образы на musl** (например, Alpine) читают `resolv.conf` по-своему, поэтому проверяйте число запросов в том образе, который реально запускается.

### Значения CoreDNS

Эти значения заданы в стандартном Corefile kubeadm и kind; размер кластера они не учитывают.

- **Реплики** — 2, requests CPU 100m и памяти 70 МиБ, лимит памяти 170 МиБ.
- **TTL** записей кластера — 30 с, кэш внешних ответов — 30 с.
- **forward** — до 1000 одновременных запросов на один сервер (`max_concurrent`).
- **reload** — проверка Corefile раз в 30 с со сдвигом до 15 с.
- **lameduck** — 5 с на остановку.

### Масштабирование

Две реплики на стенде достаточны, но в большом кластере CoreDNS упирается в CPU и в число запросов. Первое средство — больше реплик: **cluster-proportional-autoscaler** (отдельное дополнение, которое задаёт число реплик по числу узлов и ядер). Его линейная формула с параметрами `coresPerReplica: 256` и `nodesPerReplica: 16` берёт большее из двух значений.

Второе средство — настройки самого CoreDNS. На продакшн-кластерах реплики разносят по узлам правилом anti-affinity, добавляют PodDisruptionBudget (05-5) и класс приоритета `system-cluster-critical`, а requests ставят по реальному потреблению. Лимит CPU у CoreDNS часто вредит: под нагрузкой он вызывает троттлинг (05-1) и таймауты DNS у всего кластера.

### NodeLocal DNSCache

**NodeLocal DNSCache** — DaemonSet, который запускает на каждом узле кэширующий DNS-агент. Агент слушает локальный адрес `169.254.20.10` и адрес Service `kube-dns`, а запросы к ним перехватывают правила iptables с пометкой NOTRACK, которая выводит их из conntrack. Промахи кэша он отправляет в CoreDNS по TCP.

```
под ─► 169.254.20.10 (агент на том же узле, без conntrack)
              │ кэш: попадание ─► ответ сразу
              └─ промах ─► TCP ─► CoreDNS (kube-dns-upstream)
```

Схема 4. Кэш у самого пода: большинство запросов не покидает узел, а оставшиеся идут по TCP и не страдают от гонок conntrack.

Это даёт три выигрыша: меньше нагрузки на CoreDNS, ниже задержка и нет задержек по 5 с из-за conntrack. У способа есть цена — ещё один DaemonSet и точка отказа на каждом узле. NodeLocal DNSCache не входит в стенд, и в курсе он дан только теорией. Установка идёт по манифесту `nodelocaldns` из репозитория Kubernetes с подстановкой адресов кластера; в режиме kube-proxy ipvs отличается способ настройки kubelet.

### Лабораторная работа 1. Сколько запросов стоит одно имя

**Цель.** Увидеть, как `ndots:5` превращает одно имя в восемь запросов, и проверить, что помогает FQDN с точкой. Вы сравните поды с `ndots:5` и `ndots:1` и найдёте цену второго значения.

**Что понадобится.**

- Стенд 00-1, контекст `kind-lab`, namespace `lab-03-3` из подготовки.
- Образы `python:3.12-slim` и `nicolaka/netshoot:v0.13`.
- Демо-приложение в namespace `orders`.
- Около 5 минут на запуск подов и 30 минут на опыты.

**Схема опыта.** Два пода в одном namespace отличаются значением `ndots`. В каждый добавляется эфемерный контейнер с `tcpdump`, а под резолвит нужное имя.

```
под dns   (ndots:5) ─┐                        ┌─ NXDOMAIN от CoreDNS
под dns1  (ndots:1) ─┼─► tcpdump :53 ─► счёт ─┤  (search-домены)
                     │                        └─ ответ (имя найдено)
   смотрим на число строк «A?» и «AAAA?» в захвате
```

Схема показывает, где считаются запросы: на интерфейсе пода, до kube-proxy и CoreDNS.

**Риски.** Работа меняет только кластер стенда и один параметр на хосте.

- **Что меняется:** в кластере — поды и эфемерные контейнеры в `lab-03-3`; на хосте — namespace по умолчанию контекста `kind-lab` в `~/.kube/config`.
- **Надолго ли:** до уборки; эфемерный контейнер исчезает вместе с подом.
- **Безопасность:** отладочный контейнер получает NET_RAW и NET_ADMIN только в своём поде.
- **Влияние на систему:** другие контексты и namespace не затрагиваются, нагрузка на CoreDNS десятки запросов.
- **Откат:** блок «Уборка» этой работы.

#### Шаг 3. Посчитать запросы для внешнего имени

Определяем функцию `count`. Она добавляет в под эфемерный контейнер с `tcpdump`, резолвит имя через `getaddrinfo`, печатает число запросов и время и выводит список имён из захвата. Определение занимает много строк, поэтому вставьте его целиком и не закрывайте терминал.

```bash
i=0
py='import socket,sys,time
t=time.perf_counter()
socket.getaddrinfo(sys.argv[1],443)
print(f"{(time.perf_counter()-t)*1000:.0f}")'
count() {
  i=$((i+1))
  kubectl debug "$1" -c "td$i" --image=nicolaka/netshoot:v0.13 --profile=netadmin \
    -- timeout 7 tcpdump -n -l -i eth0 udp dst port 53
  sel="{.status.ephemeralContainerStatuses[?(@.name=='td$i')].state.running}"
  until kubectl get pod "$1" -o jsonpath="$sel" | grep -q started; do sleep 1; done
  sleep 1
  ms=$(kubectl exec "$1" -c "$1" -- python -c "$py" "$2")
  sleep 6
  n=$(kubectl logs "$1" -c "td$i" | grep -c ' A\| AAAA')
  echo "[$1] $2 -> $n queries, $ms ms"
  kubectl logs "$1" -c "td$i" | grep -oE '(A|AAAA)\? [^ ]+' | sed 's/^/      /'
}
count dns kernel.org
```

| Часть команды | Значение |
|---|---|
| `debug "$1" -c "td$i"` | добавить эфемерный контейнер с именем `td1`, `td2`… |
| `--profile=netadmin` | выдать права NET_RAW и NET_ADMIN для tcpdump |
| `timeout 7 tcpdump …` | слушать 7 секунд |
| `udp dst port 53` | считать только исходящие DNS-запросы |
| `exec … python -c "$py" "$2"` | резолвить имя и вернуть время в миллисекундах |
| `grep -oE '(A\|AAAA)\? [^ ]+'` | оставить тип запроса и имя |

Результат (тип A и AAAA в паре могут идти в другом порядке):

```
[dns] kernel.org -> 8 queries, 925 ms
      A? kernel.org.lab-03-3.svc.cluster.local.
      AAAA? kernel.org.lab-03-3.svc.cluster.local.
      A? kernel.org.svc.cluster.local.
      AAAA? kernel.org.svc.cluster.local.
      A? kernel.org.cluster.local.
      AAAA? kernel.org.cluster.local.
      A? kernel.org.
      AAAA? kernel.org.
```

Разбор вывода:

1. В имени `kernel.org` одна точка, меньше пяти, поэтому резолвер сначала подставил три search-домена.
2. На каждый домен ушло два запроса, A и AAAA. Все три получили NXDOMAIN от CoreDNS.
3. Последние два запроса, `kernel.org.` с точкой, — настоящий внешний вопрос; ответ дал DNS узла.
4. Восемь запросов ради одного имени. Время в миллисекундах шумное: сравнивайте число запросов, а не время.

Если захват пуст, повторите команду: первый `kubectl debug` на узле скачивает образ netshoot, и tcpdump может не успеть.

#### Уборка

Удаляем поды и функцию. Namespace остаётся для следующих работ.

```bash

unset -f count
unset i py
```

#### Вопросы для самопроверки

1. Сколько запросов уйдёт на `api.partner.com` из пода с настройками по умолчанию?

<details><summary>Ответ</summary>

Восемь: в имени две точки, меньше пяти, поэтому сначала идут три search-домена (по два запроса A и AAAA, все с NXDOMAIN), затем само имя. С точкой на конце (`api.partner.com.`) было бы два запроса.

</details>

2. Почему полное имя Service `postgres.orders.svc.cluster.local` без точки стоит восьми запросов?

<details><summary>Ответ</summary>

В нём четыре точки, а `ndots` равен пяти. Резолвер считает имя недостаточно полным и сначала дописывает к нему три search-домена. Эти склеенные имена не существуют, поэтому CoreDNS отвечает NXDOMAIN, и только четвёртая попытка проходит.

</details>

3. Что плохого в `ndots:1`?

<details><summary>Ответ</summary>

Короткие внутренние имена вида `<service>.<namespace>` содержат одну точку и поэтому сначала уходят во внешний DNS как абсолютные. Там они получают NXDOMAIN после задержки до апстрима (на стенде 1,5 с), после чего резолвер перебирает search-домены. Имя утекает наружу и тормозит.

</details>

4. Чем счёт запросов через `tcpdump` в поде надёжнее, чем замер времени?

<details><summary>Ответ</summary>

Время зависит от кэша CoreDNS и внешнего апстрима и меняется от запуска к запуску: на стенде `iana.org.` занял 3670 мс при двух запросах. Число пакетов на интерфейсе пода детерминировано и зависит только от `resolv.conf` и имени.

</details>

#### Вопросы для самопроверки

1. Почему при остановленном CoreDNS часть запросов падает мгновенно, а часть через 5 с?

<details><summary>Ответ</summary>

Без адресов за Service `kube-dns` kube-proxy отвечает на пакеты REJECT с ICMP, и резолвер видит отказ сразу. Если отказ не дошёл до сокета, резолвер ждёт таймаут 5 с (по умолчанию в glibc). Точное время заранее предсказать нельзя.

</details>

2. Что вы проверите первым, если DNS в кластере перестал работать?

<details><summary>Ответ</summary>

EndpointSlice Service `kube-dns`: есть ли готовые поды CoreDNS. Пустые `ENDPOINTS` значат, что реплик нет или они не проходят `ready`. Затем смотрят журнал подов `k8s-app=kube-dns` и состояние узла, на котором они работали.

</details>

3. Почему приложение с пулом соединений переживает короткую остановку DNS лучше?

<details><summary>Ответ</summary>

Имя резолвится при создании соединения. Уже открытые соединения используют IP-адрес и DNS не спрашивают. Пострадают только новые соединения и клиенты без пула, которые резолвят имя на каждый запрос.

</details>

4. Какие меры уменьшают риск такого сбоя на продакшн-кластере?

<details><summary>Ответ</summary>

Нужны две и более реплики CoreDNS на разных узлах, PodDisruptionBudget, класс приоритета `system-cluster-critical` и requests по реальному потреблению без жёсткого лимита CPU. Помогают также автоскейлер по числу узлов, NodeLocal DNSCache и алерты на долю SERVFAIL и NXDOMAIN.

</details>

### Лабораторная работа 3. Логи запросов и своя запись в CoreDNS

**Цель.** Научиться менять Corefile безопасно: включить журнал запросов, добавить свою запись и измерить, когда изменение вступает в силу. Вы также восстановите исходный файл.

```

        ▲                                                                   │
   вы меняете здесь                                           смотрим: запись видна из клиента
```

Схема показывает два ожидания подряд: это объясняет задержку в минуту.

**Риски.** Работа меняет конфигурацию CoreDNS, общую для всего кластера стенда.

- **Что меняется:** ConfigMap `coredns` в `kube-system`: сначала добавляется плагин `log`, затем плагин `hosts` с записью `legacy-db.corp.internal`.

- **Безопасность:** запись `hosts` указывает на документационный адрес `10.0.50.10`, трафик на него не идёт. Журнал `log` записывает имена, которые резолвят поды.
- **Влияние на систему:** на время ожидания DNS работает по старому файлу; при ошибке в новом файле CoreDNS оставит прежний, но не должен перезапускаться. Лишний журнал нагружает поды CoreDNS.
- **Откат:** блок «Уборка»; без копии файл можно собрать заново по §2.

```bash

  --from-file=Corefile=$HOME/lab/k8s/03-3/Corefile.orig --dry-run=client -o yaml \
  | kubectl apply -f -
kubectl -n kube-system get cm coredns -o jsonpath='{.data.Corefile}' \
  | diff - ~/lab/k8s/03-3/Corefile.orig && echo "Corefile restored"
kubectl config set-context --current --namespace=default
kubectl delete ns lab-03-3
rm -rf ~/lab/k8s/03-3
```

Результат (ожидаемый):

```
configmap/coredns configured
Corefile restored
Context "kind-lab" modified.
namespace "lab-03-3" deleted
```

Разбор вывода: строка `Corefile restored` значит, что ConfigMap совпал с исходным файлом. Конфигурация в подах обновится в течение минуты, поэтому проверьте журнал или имя `legacy-db.corp.internal` через минуту: оно не должно разрешаться. Удаление namespace занимает около 30 с.

#### Вопросы для самопроверки

1. Почему изменение Corefile вступило в силу через 63 с, а не сразу?

<details><summary>Ответ</summary>

Два ожидания идут подряд: kubelet обновляет том ConfigMap в поде (до минуты), а плагин `reload` проверяет файл раз в 30 с. Поэтому после правки Corefile нужно ждать минуту, и только потом искать ошибку.

</details>

2. Что означают флаги `aa` и `ra` в журнале CoreDNS?

<details><summary>Ответ</summary>

`aa` (authoritative answer) — ответ дал сам CoreDNS как хозяин зоны, у нас это плагин `kubernetes`. `ra` (recursion available) — ответ пришёл от рекурсивного сервера через `forward`, то есть имя внешнее.

</details>

3. Зачем в блоке `hosts` нужна директива `fallthrough`?

<details><summary>Ответ</summary>

Без неё плагин `hosts` считает себя хозяином зоны и отвечает на все остальные имена отказом. С `fallthrough` запрос, которого нет в списке, передаётся следующему плагину, например `forward`.

</details>

4. Как добавить внешнее имя в DNS кластера, не правя Corefile?

<details><summary>Ответ</summary>

Создать Service типа `ExternalName` (CNAME на нужное имя) или Service без selector с вручную заполненным EndpointSlice на внешний IP. Ошибка в таком объекте затронет один namespace, а ошибка в Corefile — весь кластер.

</details>

5. Почему перед правкой Corefile сохраняют копию?

<details><summary>Ответ</summary>

Ошибочный файл может не дать CoreDNS стартовать при перезапуске, и тогда DNS пропадёт во всём кластере. Копия в файле позволяет вернуть ConfigMap одной командой `apply`, не вспоминая прежнее содержимое.

</details>
