# 03-3. DNS в кластере

> Модуль 3 «Сеть» · часть 3 из 5 · 🟢🟡🔴 · ~1 ч чтения + ~45 мин лабы · Нужно: стенд 00-1, `nicolaka/netshoot:v0.13`. База — networks 08-4: имена сервисов и подов, `resolv.conf` и `dnsPolicy`, CoreDNS и его плагины, NodeLocal DNSCache, отладка. Здесь — измерения и операции, которые встречаются в эксплуатации.

---

## Зачем это DevOps-у

DNS в кластере ломается тихо: запросы во внешние API «на 50 мс дольше», CoreDNS под нагрузкой съедает CPU, после включения NetworkPolicy через минуту отваливается всё (03-5), а `nslookup` из отладочного пода врёт (02-3). На собеседовании — «как резолвится имя сервиса», «что такое ndots и чем он вреден», «что будет, если CoreDNS упадёт».

В сквозном сценарии orders-api ходит в `postgres` (короткое имя из `DATABASE_URL`), а в реальной жизни — ещё и во внешние API. Посчитаем, во что обходится каждое имя.

## 1. resolv.conf пода и ndots 🟢🟡

Проверено (под в namespace `lab-03-3`, `dnsPolicy: ClusterFirst` — дефолт):

```
search lab-03-3.svc.cluster.local svc.cluster.local cluster.local
nameserver 10.96.0.10
options ndots:5
```

`nameserver` — ClusterIP Service `kube-dns` (за ним поды CoreDNS). `ndots:5`: если в имени **меньше пяти точек** и на конце нет точки, резолвер сначала перебирает домены из `search`, и только потом пробует имя как есть. Сделано, чтобы работали короткие имена `postgres`, `orders-api.orders`, `postgres.orders.svc`.

Цена — лишние запросы. Замер на стенде: `tcpdump` в сетевом namespace пода-клиента, вызов `getaddrinfo` (A и AAAA — так делает почти любой клиент), проверено:

| Имя | Запросов к DNS | Что спрашивалось |
|---|---|---|
| `kernel.org` (внешнее, без точки) | **8** | `kernel.org.lab-03-3.svc.cluster.local.`, `…svc.cluster.local.`, `…cluster.local.` (каждое — A и AAAA, ответ NXDOMAIN), затем `kernel.org.` |
| `iana.org.` (FQDN с точкой) | 2 | `iana.org.` A и AAAA |
| `orders-api.orders` | 4 | `orders-api.orders.lab-03-3.svc…` (NXDOMAIN), `orders-api.orders.svc.cluster.local.` (ответ) |
| `postgres.orders.svc.cluster.local` (полное, **без** точки на конце) | **8** | 4 точки < 5 — сначала три «склеенных» имени вроде `postgres.orders.svc.cluster.local.svc.cluster.local.`, потом само имя |
| `postgres.orders.svc.cluster.local.` | 2 | сразу |

Полное имя сервиса без точки на конце — тоже 8 запросов: точек 4, а не 5. Внутрикластерные NXDOMAIN отвечает сам CoreDNS (плагин kubernetes) за доли миллисекунды, но каждый — лишний пакет, лишняя строка conntrack и лишняя работа CoreDNS. На тысячах подов, которые ходят во внешний API по каждому запросу, это кратно увеличивает нагрузку на CoreDNS.

### ndots:1 — не панацея 🔴

Под с `dnsConfig.options: [{name: ndots, value: "1"}]` (проверено):

| Имя | Запросов | Что |
|---|---|---|
| `wikipedia.org` | 2 | сразу как есть — хорошо |
| `orders-api.orders` | **6** | 1 точка ≥ ndots → сначала `orders-api.orders.` **уходит во внешний DNS** (там NXDOMAIN, задержка до апстрима — на стенде 1,5 с), затем search |

С `ndots:1` короткие внутренние имена вида `<сервис>.<namespace>` начинают ходить в интернет: медленнее и утечка внутренних имён наружу. Сбалансированные варианты:

- во внешние имена ходить по FQDN с точкой (`api.partner.com.`) — в конфиге приложения;
- `ndots:2` в `dnsConfig` для сервисов с большим внешним трафиком — `<сервис>.<namespace>` (1 точка) ещё ищется в search, внешние `api.partner.com` (2 точки) — сразу;
- NodeLocal DNSCache (networks 08-4 §2) — кэш на каждом узле, запросы не идут через сеть и conntrack.

## 2. CoreDNS стенда 🟡

Corefile kind (проверено, сокращено):

```
.:53 {
    errors
    health { lameduck 5s }
    ready
    kubernetes cluster.local in-addr.arpa ip6.arpa {
       pods insecure
       fallthrough in-addr.arpa ip6.arpa
       ttl 30
    }
    prometheus :9153
    forward . /etc/resolv.conf { max_concurrent 1000 }
    cache 30 {
       disable success cluster.local
       disable denial cluster.local
    }
    loop
    reload
    loadbalance
}
```

| Плагин | Что делает | На что влияет в эксплуатации |
|---|---|---|
| `kubernetes` | отвечает за `cluster.local` из watch на Service/EndpointSlice; `ttl 30` | новый Service виден сразу; клиенты кэшируют ответ до 30 с |
| `forward . /etc/resolv.conf` | всё остальное — на резолвер узла | внешний DNS = DNS узла; сломан DNS узла — сломан внешний DNS подов |
| `cache 30` + `disable … cluster.local` | кэш внешних ответов на 30 с; **внутренние не кэшируются** | внутренние ответы всегда свежие — плагин kubernetes и так держит их в памяти |
| `loop` | падает, если обнаружил петлю (forward сам на себя) | классика с `systemd-resolved` на узле: `/etc/resolv.conf` → `127.0.0.53` → CoreDNS в CrashLoop (кейс networks 08-4) |
| `reload` | перечитывает Corefile при изменении | изменение ConfigMap применяется без рестарта, но не сразу |
| `health`/`ready` | probes CoreDNS; `lameduck 5s` — graceful shutdown | |

Изменение Corefile (лаба, шаг 4): добавили статическую запись через плагин `hosts`:

```
    hosts {
       10.0.50.10 legacy-db.corp.internal
       fallthrough
    }
```

Проверено: запись стала видна из пода через **63 с** после `kubectl apply` ConfigMap — это доставка ConfigMap в том пода CoreDNS (до ~60 с, 04-1) плюс проверка `reload` (30 с). Ждите минуту, прежде чем решать, что «не работает». Для включения логов запросов — плагин `log` (так в лабе считали запросы); на проде не оставляйте — каждый запрос в лог.

## 3. Отказ CoreDNS 🟡

Проверено: `kubectl -n kube-system scale deploy coredns --replicas=0`:

```
orders-api.orders: gaierror: [Errno -3] Temporary failure in name resolution after 0.0 s
postgres.orders.svc.cluster.local.: gaierror: [Errno -3] Temporary failure in name resolution after 5.0 s
kube-dns endpoints: null
```

Без endpoints kube-proxy отвечает на запросы к `10.96.0.10` REJECT'ом (03-2) — часть запросов падает мгновенно, часть — по таймауту резолвера (glibc: `timeout:5`, `attempts:2` по умолчанию). Приложение с кэшем соединений проживёт дольше, новые соединения — сразу ошибки. После возврата CoreDNS (2 пода Ready за ~10 с) резолвинг восстановился сразу: `orders-api.orders 3.3 ms`.

CoreDNS — критичный компонент: 2+ реплики на разных узлах, PDB, `priorityClassName: system-cluster-critical`, requests с запасом; при росте кластера — горизонтальное масштабирование (cluster-proportional-autoscaler) или NodeLocal DNSCache. На стенде обе реплики CoreDNS на `lab-control-plane`.

## 4. Инструменты отладки DNS 🟢

| Инструмент | Применяет search/ndots? | Когда |
|---|---|---|
| `getent hosts/ahosts <имя>` | да (через libc, как приложение) | «как это имя видит приложение» |
| `python -c 'import socket; socket.getaddrinfo(...)'` | да | то же + время |
| `dig <имя>` | нет (+`+search` — да) | точный запрос к конкретному серверу, TTL, флаги |
| `nslookup` из busybox | **нет** — вводит в заблуждение (02-3: `web-1.web` → `127.0.53.53`) | лучше не использовать |
| `tcpdump -ni eth0 port 53` в netns пода | — | сколько запросов реально уходит |

Короткая последовательность: `cat /etc/resolv.conf` → `getent hosts <имя>` → `dig @10.96.0.10 <полное имя>.` → поды и логи CoreDNS (`kubectl -n kube-system logs -l k8s-app=kube-dns`) → endpoints `kube-dns` → NetworkPolicy на egress 53 (03-5).

## 🔥 Кейс из прода: «CoreDNS съедает 8 ядер, а сервисы жалуются на таймауты»

**Контекст.** Кластер на 80 узлов, 2 реплики CoreDNS с лимитом CPU 1 ядро. Сервис платёжной интеграции (60 подов) на каждый запрос резолвит `api.payments-provider.com` (HTTP-клиент без пула соединений). Под пиковой нагрузкой — таймауты DNS у всех сервисов кластера, `kubectl top` у CoreDNS — 1000m (упёрлись в лимит), троттлинг (05-1).

**Разбор.**
1. Метрики CoreDNS (`coredns_dns_requests_total` по `type` и `rcode`): 75% ответов — NXDOMAIN.
2. Захват в поде сервиса (шаг 1 лабы): каждое `api.payments-provider.com` (2 точки < 5) — 8 запросов, из них 6 — NXDOMAIN по search-доменам.
3. 60 подов × ~200 запросов в секунду × 8 = ~96 000 DNS-запросов в секунду на две реплики CoreDNS с лимитом в ядро.

**Фикс.**
- В конфиге сервиса — FQDN с точкой (`api.payments-provider.com.`) и пул HTTP-соединений с keepalive: DNS-запросы упали в сотни раз.
- NodeLocal DNSCache на всех узлах: кэш рядом с подом, меньше conntrack (и исчезли редкие 5-секундные задержки из-за гонки conntrack с UDP — networks 08-4).
- CoreDNS: снят CPU limit, requests по реальному потреблению, cluster-proportional-autoscaler, PDB, anti-affinity по узлам.
- Алерт на долю NXDOMAIN и на троттлинг CoreDNS.

**Что запомнить.**
- `ndots:5` превращает внешнее имя без точки в 8 запросов.
- Лечение — FQDN с точкой, пул соединений, NodeLocal DNSCache; `ndots:1` ломает короткие внутренние имена.
- CoreDNS — критический компонент: реплики, PDB, без CPU limit, мониторинг rcode.

## 💼 Вопросы с собеседования

### 🟢 Junior

**1. Как под находит Service по имени?**
`/etc/resolv.conf` пода указывает на ClusterIP `kube-dns`; CoreDNS (плагин kubernetes) отвечает на `<service>.<namespace>.svc.cluster.local`. Короткие имена работают благодаря `search`-доменам.

**2. Какое полное имя у Service и у пода StatefulSet?**
`<svc>.<ns>.svc.cluster.local`; под StatefulSet за headless Service — `<pod>.<svc>.<ns>.svc.cluster.local` (02-3).

### 🟡 Middle

**3. Что такое ndots:5 и чем он вреден?**
Если в имени меньше 5 точек и нет точки на конце, резолвер сначала перебирает `search`-домены. Внешнее `api.example.com` даёт 8 запросов (A и AAAA × 3 search + само имя), 6 из них — NXDOMAIN. Лечится FQDN с точкой, `dnsConfig.ndots` (осторожно), NodeLocal DNSCache.

**4. Что будет, если упадёт CoreDNS?**
Новые разрешения имён падают — мгновенно (REJECT от kube-proxy при пустом Service) или через таймаут резолвера (5 с × попытки). Работающие соединения живут, новые — нет; кэши клиентов какое-то время спасают. Поэтому 2+ реплики на разных узлах, PDB, приоритет.

**5. Почему `nslookup` в отладочном поде показывает не то, что видит приложение?**
busybox `nslookup` не применяет search-домены и ndots; приложение резолвит через libc. Проверять `getent hosts` или `dig +search`.

### 🔴 Senior

**6. Почему `ndots:1` может ухудшить ситуацию?**
Имена `<svc>.<ns>` (1 точка) начинают сначала уходить во внешний DNS как абсолютные: задержка до апстрима, NXDOMAIN, утечка внутренних имён; только потом — search. Компромисс — `ndots:2` для конкретных сервисов и FQDN для внешних имён.

**7. Как масштабировать DNS в большом кластере?**
NodeLocal DNSCache (DaemonSet с кэшем на link-local адресе на каждом узле, обходит conntrack для UDP), горизонтальный автоскейлинг CoreDNS пропорционально числу узлов/ядер, кэш внешних ответов, снятие CPU limit, мониторинг `coredns_dns_request_duration_seconds` и rcode, устранение лишних запросов на стороне приложений (FQDN, пулы соединений).

**8. Как добавить в кластерный DNS запись на внешнюю систему?**
Без правки CoreDNS: Service `ExternalName` (CNAME) или Service без selector'а с EndpointSlice на внешний IP. С правкой: плагин `hosts`/`file` или stub-зона через `forward corp.internal <IP DNS>`; изменение ConfigMap применяется через ~1 минуту (доставка тома + reload).

## ⚠️ Подводные камни

- Полное имя сервиса без точки (`svc.ns.svc.cluster.local`) — 4 точки < 5, тоже 8 запросов.
- busybox `nslookup` не использует search — не верьте ему.
- `ndots:1` отправляет `<svc>.<ns>` во внешний DNS.
- Изменение Corefile применяется через ~1 минуту, а не сразу.
- `log` в Corefile на проде — лог на каждый запрос.
- `loop` + `systemd-resolved` на узле (`127.0.0.53` в resolv.conf узла) = CoreDNS в CrashLoopBackOff.
- CPU limit у CoreDNS под нагрузкой = троттлинг = таймауты DNS у всего кластера.
- `forward . /etc/resolv.conf` — внешний DNS подов зависит от DNS узла.
