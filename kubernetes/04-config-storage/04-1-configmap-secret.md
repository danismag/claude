## 1. Какую задачу решают ConfigMap и Secret

Образ должен быть одним и тем же в тестовой и рабочей среде, а настройки у этих сред разные. Поэтому настройки хранят отдельно от образа, в объектах API.

### Конфигурация отдельно от образа

**ConfigMap** (карта конфигурации) — объект API с обычными настройками: пары «ключ — значение» или целые файлы. **Secret** (секрет) — такой же объект для чувствительных данных: паролей, токенов и ключей. Оба объекта живут в namespace, поэтому под не может сослаться на объект из другого namespace.

В образ кладут то, что меняется вместе с кодом: значения по умолчанию и схемы. В ConfigMap уходят значения, которые различаются между средами: адреса, флаги функций, уровни логов. В Secret уходят пароли, токены и сертификаты. Большие данные (модели, словари) не годятся ни туда, ни туда: лимит объекта — 1 МиБ, и каждый байт хранится в etcd.

### Чем Secret отличается от ConfigMap

Secret устроен почти как ConfigMap, а отличия невелики и касаются обращения с объектом.

- **Тип.** У Secret есть поле `type`, которое подсказывает формат ключей: `Opaque` для произвольных данных, `kubernetes.io/tls` для сертификата и ключа, `kubernetes.io/dockerconfigjson` для доступа к реестру образов.
- **Права.** На чтение Secret выдают отдельное право RBAC (06-1), и его можно не давать тем, кто читает ConfigMap.
- **Кодирование.** Значения в API записаны в **base64** — способе записать произвольные байты печатными символами. Это не шифрование: одна команда возвращает исходный текст.
- **Узел.** Файлы Secret kubelet держит в **tmpfs** — файловой системе в оперативной памяти, поэтому они не попадают на диск узла. Файлы ConfigMap лежат на диске узла.
- **Вывод.** Команда `describe` не показывает значений Secret, а `get -o yaml` показывает их в base64.

Шифрования в etcd у Secret нет по умолчанию. Включить его можно отдельной настройкой API-сервера (§3).

### Четыре способа передать значения в под

Значения попадают в контейнер переменными окружения или файлами тома. Способ определяет, увидит ли контейнер изменение объекта на живом поде (замеры — лабораторная работа 1).

| Способ | Что получает контейнер | Видит изменения |
|---|---|---|
| Переменные окружения | значения, зафиксированные при старте | нет, до пересоздания пода |
| Том | каталог, по файлу на ключ | да, с задержкой около минуты |
| Том с subPath | один файл в существующем каталоге | нет, никогда |
| Projected-том | файлы из нескольких источников | да, как обычный том |

Разберём, почему так, на устройстве тома.

## 2. Как устроены объекты и тома

Объект хранит ключи, том превращает их в файлы, а kubelet следит за изменениями. Отсюда видно, какие способы из таблицы обновляются, а какие нет.

### Поля объекта

В ConfigMap значения лежат в двух полях. **data** хранит строки в UTF-8, **binaryData** хранит произвольные байты в base64. В Secret поле `data` всегда содержит base64, а **stringData** (только для записи) принимает значения открытым текстом, и API сам кодирует их в `data`. Чтение `stringData` вернёт пустое поле.

Имя ключа состоит из букв, цифр, `-`, `_` и `.` и занимает не больше 253 символов. Поле **immutable** (неизменяемый) запрещает любые правки `data` после создания. Поле `type` у Secret тоже не меняется.

### Том и атомарная подмена

Том с ConfigMap или Secret — каталог, где на каждый ключ есть файл. Kubelet не пишет файлы прямо в каталог, а собирает версию в отдельном каталоге с меткой времени и переключает симлинк. Так приложение видит либо старую версию целиком, либо новую.

```
/etc/orders/                                 каталог тома в контейнере
├── config.json ──► ..data/config.json       симлинк на файл текущей версии
├── ..data ───────► ..2026_10_14_10_20_14.3300762722   симлинк на текущий каталог
└── ..2026_10_14_10_20_14.3300762722/        каталог одной версии
    └── config.json                          настоящий файл
```

Схема 2. Устройство тома. Смотрите на `..data`: при обновлении kubelet создаёт новый каталог версии и одной операцией переставляет этот симлинк.

Подмена симлинка — одна операция `rename`, поэтому половины файла приложение не увидит. Но из этого следует правило для приложений: следить нужно за каталогом, а не за файлом. Событие inotify на сам `config.json` не придёт, потому что файл остался на месте, а сменился симлинк выше.

### Обновление: том, переменные и subPath

Kubelet следит за объектами по **watch** — потоку изменений от API-сервера (01-1). Режим задаёт поле `configMapAndSecretChangeDetectionStrategy`, по умолчанию `Watch`. Тома kubelet обновляет при очередной синхронизации пода, а период синхронизации `syncFrequency` по умолчанию равен 1 минуте. Поэтому задержка до минуты и разная на разных подах: на стенде мы измерим 47, 63 и 80 секунд.

Переменные окружения процесс получает при старте и больше не меняет. **subPath** — поле монтирования, которое подключает к контейнеру один файл или подкаталог тома, а не весь том. Для файла kubelet делает привязку к конкретному файлу версии, которая была текущей при старте. Новые версии — это другие файлы, и привязка их не видит.

Чтобы применить новое значение через переменную или `subPath`, поды пересоздают. Стандартный приём — положить хэш конфигурации в аннотацию шаблона пода. Хэш меняется вместе с конфигурацией, шаблон меняется, и Deployment сам делает rolling update (02-2). В Helm это аннотация `checksum/config` (07-1), в Kustomize — суффикс-хэш в имени, который добавляет `configMapGenerator` (07-3).

### Projected-том и режим файлов

**Projected volume** (проецируемый том) собирает в один каталог файлы из нескольких источников: ConfigMap, Secret, Downward API (02-1) и токена ServiceAccount (06-1). Обновляется он так же, как обычный том. Применяют его, когда приложению нужны сертификат, настройки и токен в одном месте.

Файлы получают права `0644`. Параметр `defaultMode` меняет их для всего тома, а `mode` у отдельного ключа — для одного файла. Для приватного ключа ставят `0400`.

## 3. Как управлять конфигурацией и секретами

Объекты создают из литералов, файлов или манифестов, а подключают к поду в манифесте. Отдельно управляют неизменяемостью и шифрованием в etcd.

### Создать и подключить

Команды ниже создают ConfigMap и Secret разными способами. Каждая строка снабжена комментарием.

```bash
kubectl create configmap app --from-literal=LOG_LEVEL=info   # один ключ из значения в команде
kubectl create configmap app --from-file=config.json         # ключ config.json, значение из файла
kubectl create configmap app --from-env-file=app.env         # по ключу на каждую строку KEY=VALUE
kubectl create secret generic db --from-literal=password=x   # Secret типа Opaque
kubectl create secret tls web --cert=tls.crt --key=tls.key   # Secret типа kubernetes.io/tls
```

Команды отличаются источником значений: литерал, файл целиком или файл с парами. Secret создают так же, но значения в команде попадают в историю шелла, поэтому пароли лучше читать из файла (`--from-file`).

Подключение в манифесте выглядит так.

```yaml
env:
- name: FEATURE_DISCOUNT                  # переменная одного ключа
  valueFrom:
    configMapKeyRef: {name: app, key: FEATURE_DISCOUNT}
envFrom:
- secretRef: {name: db, optional: true}   # все ключи Secret как переменные
volumeMounts:
- {name: cfg, mountPath: /etc/orders}     # весь том в каталог
volumes:
- name: cfg
  configMap: {name: app, defaultMode: 0440}
```

Разбор фрагмента:

1. `configMapKeyRef` берёт один ключ в одну переменную, а `envFrom` — все ключи сразу.
2. `optional: true` разрешает поду стартовать без объекта или ключа. Без этого поле даёт `CreateContainerConfigError` (02-1).
3. `volumeMounts` монтирует весь том, поэтому обновления доходят до контейнера.
4. `defaultMode: 0440` задаёт права файлов тома.

Файл из Secret надёжнее переменной: переменные видны в `/proc/<pid>/environ`, попадают в аварийные дампы и наследуются дочерними процессами.

### Менять и защищать от случайных правок

Обычное изменение — `kubectl apply` или `kubectl patch`. Затем нужно сделать так, чтобы приложение применило значение: перечитать файл или перезапуститься (§2).

Для конфигурации, которая не должна меняться на ходу, ставят `immutable: true`. Такой объект нельзя править, а обратно в изменяемый его тоже не вернуть: остаётся удалить и создать заново. Выигрыш в нагрузке: kubelet перестаёт следить за такими объектами, и на кластерах с тысячами ConfigMap API-серверу становится легче. Обновление превращается в новый объект с версией в имени (`app-config-v42`) и rollout, а откат — возврат к прежнему имени.

### Шифрование в etcd: EncryptionConfiguration

API-сервер шифрует выбранные ресурсы перед записью в etcd. Правила описывает файл **EncryptionConfiguration** (конфигурация шифрования), который сервер читает по флагу `--encryption-provider-config`. В файле перечислены ресурсы и **провайдеры** — способы преобразовать значение при записи и чтении.

```yaml
apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
- resources: [secrets]
  providers:
  - secretbox:                  # первый провайдер шифрует новые записи
      keys:
      - name: key1
        secret: <32 случайных байта в base64>
  - identity: {}                # остальные только читают старые записи
```

Разбор файла:

1. `resources: [secrets]` — шифруются только Secret. В список можно добавить и другие ресурсы, например `configmaps`.
2. Первый провайдер, здесь `secretbox`, шифрует каждую новую запись.
3. `identity` — провайдер «ничего не делать». Пока он стоит в списке, API-сервер читает и старые открытые записи.
4. При чтении сервер по префиксу значения находит нужный провайдер и пробует по очереди ключи.

Провайдеры различаются по надёжности и скорости. Данные ниже взяты из документации Kubernetes.

| Провайдер | Алгоритм | Замечание |
|---|---|---|
| `identity` | нет | шифрования нет, это значение по умолчанию |
| `aescbc` | AES-CBC | документация не рекомендует: уязвим к padding oracle |
| `aesgcm` | AES-GCM | ключ меняют каждые 200 000 записей, нужна автоматика |
| `secretbox` | XSalsa20 и Poly1305 | сильный и быстрый, ключ 32 байта |
| `kms` v2 | оболочка с внешним ключом | рекомендуется, GA с 1.29 |

В etcd зашифрованное значение начинается с префикса `k8s:enc:<провайдер>:v1:<имя ключа>:`. Открытое значение начинается с `k8s\0` — меткой формата хранения, и в нём читается текст пароля.

Включение шифрует только новые записи. Старые остаются открытыми, пока объект не перезапишут, и для этого выполняют команду `kubectl get secrets -A -o json | kubectl replace -f -`. Она читает все Secret и записывает обратно без изменений, поэтому повторять её безопасно.

Ключ из файла защищает от утечки бэкапа и диска etcd. Но root на узле control plane получит и ключ: файл лежит рядом. Следующая ступень — **KMS**.

### Ротация, отключение и KMS v2

Ключ меняют в несколько шагов, потому что серверов API-сервера может быть несколько и перезапускаются они не одновременно.

1. Добавьте новый ключ вторым в список ключей провайдера и примените файл на всех серверах.
2. Поставьте новый ключ первым и снова примените файл на всех серверах.
3. Перезапишите все Secret командой `replace`.
4. Уберите старый ключ.

Если сразу поставить новый ключ первым, один сервер запишет данные ключом, которого другой ещё не знает, и тот не прочитает часть Secret. Флаг `--encryption-provider-config-automatic-reload=true` избавляет от перезапусков: сервер перечитывает файл раз в минуту, а время применения показывает метрика `apiserver_encryption_config_controller_automatic_reload_last_timestamp_seconds`.

Отключают шифрование в обратном порядке: ставят `identity` первым, применяют файл, перезаписывают все Secret, и только потом убирают флаг. Ключ удаляют в самую последнюю очередь: если стереть его раньше, зашифрованные Secret станут нечитаемыми навсегда.

**KMS** (Key Management Service) — внешняя служба, которая хранит главный ключ и сама шифрует. Провайдер `kms` v2 работает по схеме **envelope encryption** (конвертное шифрование). Данные шифрует **DEK** (data encryption key) — ключ данных. Самого DEK шифрует **KEK** (key encryption key) — главный ключ, который никогда не покидает KMS. API-сервер не хранит KEK, и root на control plane не получает его вместе с диском.

```
Secret ──► API-сервер ── DEK из seed + случайные данные ──► шифрует значение ──► etcd
               │
               └─ запрос на шифрование DEK ──► плагин KMS ──gRPC, unix-сокет──► KMS (Vault, облако)
                                                                                  хранит KEK
```

Схема 3. KMS v2: в etcd лежат данные, зашифрованные DEK, и сам зашифрованный DEK. Смотрите на KEK: он остаётся вне кластера.

Плагин KMS работает на хостах control plane и общается с API-сервером по gRPC через unix-сокет. Конфигурация провайдера выглядит так.

```yaml
providers:
- kms:
    apiVersion: v2
    name: myKmsPlugin                       # имя нельзя менять после включения
    endpoint: unix:///var/run/kmsplugin/socket.sock
    timeout: 3s                             # ожидание ответа плагина, 3 с по умолчанию
- identity: {}
```

В KMS v2 сервер получает новый DEK на каждую запись из начального значения (seed) и случайных данных, поэтому обращений к KMS мало. Публичное имя текущего KEK называется `key_id`. Сервер опрашивает плагин раз в минуту, а при сбое каждые 10 секунд и три минуты работает по последнему верному состоянию. Если `key_id` изменился, данные считаются устаревшими и перешифровываются при следующей записи. Менять KEK рекомендуется не реже раза в 90 дней, и перезапуск API-сервера для этого не нужен.

KMS v1 в этом курсе не применяют. Он объявлен устаревшим в 1.28 и выключен по умолчанию с 1.29: включить его можно только флагом `--feature-gates=KMSv1=true`. Все новые настройки делают на KMS v2, а у managed-кластеров (EKS, GKE, AKS, Yandex Cloud) KMS-шифрование включается настройкой кластера. KMS на стенде не проверяется: плагин и внешняя служба потребовали бы отдельной установки.

Внешние хранилища секретов (External Secrets Operator, Secrets Store CSI Driver, Sealed Secrets, SOPS) выносят значения из Git и из кластера. Их разбирает курс security.

## 4. Как увидеть состояние

Состояние видно на трёх уровнях: что хранит объект, что видит контейнер и что лежит в etcd. На каждом уровне свой инструмент.

### Что видит объект и под

Команды показывают объект, его значения и то, что получил контейнер.

```bash
kubectl get cm,secret                                      # объекты namespace
kubectl describe secret db                                 # ключи и размеры, без значений
kubectl get secret db -o jsonpath='{.data.password}' | base64 -d   # значение в открытом виде
kubectl exec api -- ls -la /etc/orders                     # файлы тома и симлинки
kubectl exec api -- env                                    # переменные окружения контейнера
```

Что смотреть в выводе:

1. `describe secret` печатает имена ключей и размеры в байтах, а значения скрывает.
2. `base64 -d` доказывает, что base64 не защита: любой с правом `get` получает пароль.
3. `ls -la` в томе показывает симлинки `..data` и каталог версии, то есть какая версия сейчас активна.
4. `env` показывает, что контейнер получил при старте, а не текущее состояние ConfigMap.

### Что лежит в etcd

Значение объекта читают прямо из etcd. Так проверяют, действует ли шифрование. Команда использует etcdctl из карточки в 01-1 и запускается внутри пода etcd.

```bash
E='etcdctl --endpoints=https://127.0.0.1:2379'
E+=' --cacert=/etc/kubernetes/pki/etcd/ca.crt'
E+=' --cert=/etc/kubernetes/pki/etcd/server.crt'
E+=' --key=/etc/kubernetes/pki/etcd/server.key'
X='kubectl -n kube-system exec etcd-lab-control-plane --'
$X $E get /registry/secrets/lab-04-1/db --print-value-only | strings
```

Первые четыре строки собирают команду etcdctl, пятая задаёт запуск внутри пода etcd, а последняя читает ключ Secret и оставляет печатные символы. Если шифрования нет, в выводе читаются имя ключа и пароль. Если оно включено, читается только префикс `k8s:enc:secretbox:v1:key1:` и набор байтов.

### Работает ли шифрование

Сервер считает, какие провайдеры реально использует. Метрика `apiserver_storage_transformation_operations_total` имеет метку `transformer_prefix`: пока в ней встречается `identity`, часть записей читается без шифрования. Когда после перезаписи всех Secret метка `identity` перестаёт расти, старых открытых записей не осталось. Команда подсчёта зашифрованных значений в etcd — шаг 5 лабораторной работы 3.

### Кто может прочитать

Список тех, кто получает значение Secret, шире, чем кажется.

- Любой с правом `get`, `list` или `watch` на Secret. Право `list` отдаёт значения всех Secret namespace.
- Любой, кто может создать под в namespace: под монтирует любой Secret из этого namespace. Это обходит запрет на `get` (06-1).
- Любой, кто может выполнить `exec` в под с Secret в переменных окружения или в файле.
- Любой с доступом к etcd, к его бэкапам (10-2) и к диску узла control plane.
- Root на узле, где смонтирован Secret: tmpfs виден ему целиком.
- Журнал аудита на уровне `RequestResponse`: он пишет тела запросов открытым текстом, поэтому для Secret ставят уровень `Metadata` (06-4).

## 5. Что ломается и как найти причину

Поломки делятся на три группы: под не стартует из-за объекта, под работает со старым значением, шифрование ломает сам API-сервер.

### Под не стартует из-за объекта

Если объекта или ключа нет, под получает статус `CreateContainerConfigError` или зависает в `ContainerCreating`. Причину пишет `describe pod` в событиях. Сообщение `couldn't find key … in Secret` указывает на ключ, а событие `FailedMount` с текстом `configmap "…" not found` — на отсутствующий ConfigMap в томе.

Под чинится сам: kubelet повторяет создание контейнера, как только объект или ключ появились (опыт — 02-1). Поле `optional: true` отключает проверку, но тогда приложение запустится без значений, и ошибку вы увидите позже и в другом месте.

### Значение не обновилось

Тот, кто поменял ConfigMap и не увидел эффекта, обычно встретил одну из четырёх причин.

1. Значение передано переменной окружения или через `subPath`. Они не обновляются без пересоздания пода.
2. Прошло меньше минуты. Том обновляется с задержкой, и у разных подов она разная.
3. Приложение читает файл один раз при старте. Ему нужно перечитывать его по сигналу, по таймеру или по событию на каталог.
4. Объект `immutable`. Правка отклонена с ошибкой `field is immutable when immutable is set`.

Проверка идёт сверху вниз: сначала откуда берётся значение (`describe pod`), затем что лежит в файле (`exec … cat`), затем что в объекте (`get -o yaml`).

### Отказ при создании и ошибка размера

Объект больше 1 МиБ API не принимает: `Too long: may not be more than 1048576 bytes`. Решение — вынести данные из ConfigMap: в образ, в том или в объектное хранилище.

### Шифрование ломает API-сервер

Ошибка в `EncryptionConfiguration` или в монтировании файла не даёт API-серверу стартовать. Тогда `kubectl` не отвечает, а причину читают в логе контейнера через `crictl` на узле (00-2, 01-2). Типичные случаи: файла нет внутри пода (не примонтирован каталог), ключ не 32 байта в base64 или неверный отступ в YAML. Откат — вернуть сохранённый манифест static pod: kubelet перезапустит API-сервер сам (01-2).

Вторая беда тише. Если ключ потерян или удалён раньше, чем перезаписаны Secret, часть объектов не читается, а контроллеры, которым нужны токены, перестают работать. Документация оставляет один выход: удалить нечитаемую запись прямо из etcd. В 1.37 для этого добавлено безопасное удаление через API (beta, KEP-3926); на стенде версии 1.36 его нет. Поэтому порядок шагов в лабораторной работе 3 обязателен.

## 6. Пределы и значения по умолчанию

Ниже собраны числа этой части. Значения проверены на стенде или взяты из документации Kubernetes 1.36.

### Размеры и имена

- Размер ConfigMap и Secret — не больше 1 МиБ (1 048 576 байт). Измерено на стенде.

- Права файлов тома по умолчанию — `0644`.
- Поле `immutable` по умолчанию не задано, а поле `optional` равно `false`.

### Время

- Обновление тома — до минуты; измерено 47, 63 и 80 с. Период синхронизации kubelet (`syncFrequency`) — 1 минута.
- Режим слежения `configMapAndSecretChangeDetectionStrategy` — `Watch`.
- Перезапуск API-сервера после правки манифеста — около 44 с на стенде автора.
- Перечитывание файла шифрования при автоперезагрузке — раз в минуту.

- Шифрования нет: действует провайдер `identity`.

### Лабораторная работа 1. Обновление конфигурации: переменная, том, subPath

**Цель.** Измерить, через сколько секунд приложение видит изменение ConfigMap при трёх способах подключения, и увидеть устройство тома.

**Что понадобится.** Стенд 00-1, namespace `lab-04-1`, образ `localhost:5001/orders-api:2.0`.

**Схема опыта.**

```
ConfigMap app ──► переменная FEATURE_DISCOUNT   (env, фиксируется при старте)
              ├─► том /etc/orders               (файл config.json)
              └─► subPath /etc/orders-subpath/config.json
patch ConfigMap ──► засечь секунды до изменения каждого значения
```

Схема 4. Один ConfigMap подключён тремя способами. Смотрите, какое из трёх значений изменится после `patch`.

#### Шаг 1. Создать ConfigMap и под

Команда создаёт ConfigMap с переменной и файлом, затем под orders-api, который подключает их тремя способами.

```bash
kubectl create configmap app --from-literal=FEATURE_DISCOUNT=off \
  --from-literal=config.json='{"discount_percent": 0, "banner": "welcome"}'
kubectl apply -f - <<'EOF'
apiVersion: v1
kind: Pod
metadata: {name: api}
spec:
  containers:
  - name: api
    image: localhost:5001/orders-api:2.0
    env:
    - name: FEATURE_DISCOUNT
      valueFrom: {configMapKeyRef: {name: app, key: FEATURE_DISCOUNT}}
    volumeMounts:
    - {name: cfg, mountPath: /etc/orders}
    - {name: cfg, mountPath: /etc/orders-subpath/config.json, subPath: config.json}
  volumes:
  - name: cfg
    configMap: {name: app, items: [{key: config.json, path: config.json}]}
EOF
kubectl wait --for=condition=Ready pod/api
```

| Часть команды | Значение |
|---|---|
| `--from-literal=…` | два ключа: переменная и файл с JSON |
| `configMapKeyRef` | взять один ключ в переменную окружения |
| `mountPath: /etc/orders` | весь том, обновляется |
| `subPath: config.json` | один файл, не обновляется |
| `items: […]` | положить в том только ключ `config.json` |
| `wait --for=condition=Ready` | дождаться готовности пода |

Результат: `pod/api created`, затем `pod/api condition met`.

Разбор: под готов, когда все три способа подключены. Дальше будем читать значения через эндпоинт `/config` приложения и через файлы.

#### Шаг 2. Задать функцию чтения значений и посмотреть исходное состояние

|---|---|
| `show() { … }` | функция шелла, её можно вызывать повторно |

#### Шаг 3. Изменить ConfigMap и засечь время

Команда меняет оба значения, запоминает время и каждые 2 секунды вызывает `show`, пока том не покажет новое значение.

1. `volume=15` — том обновился через 80 с. Это в пределах «минута плюс кэш».

#### Шаг 4. Измерить разброс задержки

Команда меняет значение ещё два раза и каждый раз измеряет, через сколько секунд файл тома обновился.

1. Почему `env` остаётся `off`, даже когда файл тома давно обновился?
2. Почему приложению надёжнее следить за каталогом, а не за файлом `config.json`?

<details>
<summary>Ответ</summary>

1. Переменные окружения процесс получает при старте и больше не меняет. Новое значение появится только в новом контейнере.

3. Положить хэш ConfigMap в аннотацию шаблона пода (Helm `checksum/config` или хэш в имени от Kustomize). Шаблон изменится, и Deployment сам сделает rolling update (07-1, 07-3).

### Лабораторная работа 2. Ограничения и хранение Secret

**Цель.** Проверить `immutable` и лимит 1 МиБ, затем убедиться, что base64 не защищает пароль, а в etcd он лежит открытым текстом.

**Что понадобится.** Стенд 00-1, namespace `lab-04-1`, `strings` и `jq` на хосте.

**Схема опыта.**

```
ConfigMap frozen ── immutable: true ──► правка data и снятие флага отклонены
ConfigMap big    ── 1,1 МБ ──────────► отклонён, лимит 1 МиБ
Secret db ── API: base64 ──► base64 -d ──► пароль
          └─ etcd: открытый текст ──► видно пароль в значении ключа
```

Схема 5. Три проверки: неизменяемость, размер и то, где пароль виден без прав на Secret.

#### Шаг 1. Сделать ConfigMap неизменяемым

Команды создают ConfigMap, включают `immutable`, затем пытаются изменить данные и снять флаг.

```bash
kubectl create configmap frozen --from-literal=k=v1
kubectl patch configmap frozen -p '{"immutable":true}'
kubectl patch configmap frozen -p '{"data":{"k":"v2"}}'
kubectl patch configmap frozen -p '{"immutable":false}'
```

| Часть команды | Значение |
|---|---|
| `{"immutable":true}` | сделать объект неизменяемым |
| `{"data":{"k":"v2"}}` | изменить значение |
| `{"immutable":false}` | попытаться вернуть изменяемость |

Результат (первая строка — подтверждение, остальные — отказы; начало сообщения сокращено):

```
configmap/frozen patched
… data: Forbidden: field is immutable when immutable is set
… Forbidden: field is immutable when immutable is set
```

Разбор:

1. Первая команда включила флаг, и API это принял.
2. Вторая команда правит данные и получает `Forbidden`: после флага `data` менять нельзя.
3. Третья команда снимает флаг и тоже получает `Forbidden`. Назад дороги нет: объект удаляют и создают заново.

#### Шаг 2. Превысить лимит размера

Команда создаёт файл из 1 100 000 символов и пытается загрузить его в ConfigMap.

```bash

kubectl create configmap big --from-file=$HOME/lab/k8s/04-1/big.txt

```

| Часть команды | Значение |
|---|---|
| `head -c 1100000 /dev/urandom` | взять случайные байты |
| `base64 -w0` | записать их печатными символами без переносов |
| `head -c 1100000 > …` | обрезать ровно до 1 100 000 символов |
| `create configmap big --from-file=…` | попытка загрузить файл в ConfigMap |

Результат:

```

```

Разбор: API отклонил объект за 1 048 576 байт, то есть 1 МиБ. Лимит одинаков для ConfigMap и Secret.

#### Шаг 4. Найти пароль в etcd

Команды собирают подключение к etcd (карточка etcdctl в 01-1) и читают значение ключа Secret, оставляя печатные символы.

```bash
E='etcdctl --endpoints=https://127.0.0.1:2379'
E+=' --cacert=/etc/kubernetes/pki/etcd/ca.crt'
E+=' --cert=/etc/kubernetes/pki/etcd/server.crt'
E+=' --key=/etc/kubernetes/pki/etcd/server.key'
X='kubectl -n kube-system exec etcd-lab-control-plane --'
$X $E get /registry/secrets/lab-04-1/db --print-value-only \
  | strings | grep -E 'S3cr3t|password'
```

| Часть команды | Значение |
|---|---|
| `E`, `X` | подключение к etcd и запуск внутри его пода |
| `/registry/secrets/lab-04-1/db` | ключ etcd для Secret `db` |
| `--print-value-only` | вывести значение без имени ключа |
| `strings` | оставить из двоичных данных печатные строки |
| `grep -E 'S3cr3t\|password'` | найти имя ключа и значение |

Результат:

```
password
S3cr3t-P@ss
```

Разбор: в etcd пароль лежит открытым текстом. Так же он читается из бэкапа etcd или с диска control plane. Этот шаг показывает, зачем нужна работа 3.

**Итог.**

| Что узнали | Где видно |
|---|---|
| `immutable` необратим, и данные в нём не изменить | шаг 1 |
| Лимит ConfigMap и Secret — 1 МиБ | шаг 2 |
| base64 не защищает значение | шаг 3 |
| Без шифрования Secret в etcd читается как текст | шаг 4 |

**Уборка.** Secret `db` останется для работы 3, а ненужные ConfigMap удаляем.

```bash
kubectl delete configmap frozen
```

**Вопросы для самопроверки.**

1. Как обновить значение в `immutable` ConfigMap и ничего не сломать?
2. Кто, кроме пользователей с правом `get secret`, может прочитать пароль из шага 4?
3. Почему лимит в 1 МиБ нельзя обойти разбиением файла на много ключей?

<details>
<summary>Ответ</summary>

1. Создать новый ConfigMap с другим именем (например, с номером версии), переключить на него манифест и сделать rollout. Старый объект остаётся для отката.
2. Любой с доступом к etcd, к его бэкапам и к диску узла control plane, а также root на узле, где смонтирован Secret.
3. Лимит действует на весь объект, то есть на сумму всех ключей. Большие данные выносят в образ, том или объектное хранилище.

</details>

### Лабораторная работа 3. Шифрование Secret в etcd

**Риски.**

- **Что меняется.** Манифест static pod `kube-apiserver` на узле `lab-control-plane`: добавляются флаг и две записи о томе. Создаётся каталог `/etc/kubernetes/enc` с ключом шифрования, а резервная копия манифеста лежит в `/root` узла вне каталога манифестов. Все Secret кластера перезаписываются дважды.
- **Надолго ли.** API-сервер перезапускается три раза и каждый раз недоступен около 45 секунд, `kubectl` в это время отвечает ошибками. Шифрование действует между шагами 3 и 5. Вся работа занимает около 30 минут.
- **Безопасность.** Ключ из 32 случайных байтов создаётся на хосте, передаётся в узел через stdin и не попадает в вывод, в историю и в аргументы команд. Файл с ключом имеет права `0600`. Ключ существует только на стенде и удаляется на шаге 6.
- **Влияние на систему.** Работающие поды продолжают работать, включая `orders`, но контроллеры и `kubectl` теряют API на время каждого перезапуска. Перезапись Secret меняет `resourceVersion` у всех Secret кластера: на стенде это безопасно, на рабочем кластере вызовет события у операторов и Helm. Не запускайте другие работы курса одновременно.
- **Откат.** Шаги 5 и 6 возвращают узел в исходное состояние. Ключ нельзя удалять, пока в etcd остались зашифрованные Secret: шаг 5 проверяет это числом. Если API-сервер не стартует, верните манифест командой `docker exec lab-control-plane cp /root/kube-apiserver.yaml.bak /etc/kubernetes/manifests/kube-apiserver.yaml`. В крайнем случае пересоздайте стенд скриптами `lab-down.sh` и `lab-up.sh` (00-1).

**Цель.** Включить шифрование Secret ключом `secretbox`, убедиться по etcd, что новые и перезаписанные Secret зашифрованы, и безопасно вернуть кластер в исходное состояние.

**Что понадобится.** Стенд 00-1, namespace `lab-04-1` с Secret `db` из работы 2, Docker на хосте, `strings`.

**Схема опыта.**

```
хост ──docker exec──► lab-control-plane
                       ├─ /etc/kubernetes/enc/enc.yaml         ключ и порядок провайдеров
                       └─ /etc/kubernetes/manifests/kube-apiserver.yaml   флаг и том
kube-apiserver (static pod) ──► etcd: новые записи k8s:enc:secretbox:v1:key1:
```

Схема 6. Меняется один манифест и один файл на узле. Смотрите на префикс записи в etcd: он показывает, что запись зашифрована.

#### Шаг 1. Сохранить манифест и подготовить каталог

Команды задают переменные и копируют манифест API-сервера в `/root` узла, вне каталога манифестов.

```bash
CP=lab-control-plane
F=/etc/kubernetes/manifests/kube-apiserver.yaml
docker exec $CP cp $F /root/kube-apiserver.yaml.bak
docker exec $CP mkdir -p /etc/kubernetes/enc
```

| Часть команды | Значение |
|---|---|
| `CP`, `F` | имя узла и путь манифеста API-сервера |
| `cp $F /root/…bak` | резервная копия вне каталога манифестов |
| `mkdir -p …/enc` | каталог для файла шифрования |

Результат: команды ничего не печатают.

Разбор: копия лежит в `/root`, потому что kubelet запускает любой `.yaml` из каталога манифестов. Копия внутри него стала бы вторым API-сервером.

#### Шаг 2. Создать файл EncryptionConfiguration

Команда генерирует случайный ключ и записывает файл на узел через stdin.

```bash
KEY=$(head -c 32 /dev/urandom | base64)
ENC=/etc/kubernetes/enc/enc.yaml
docker exec -i $CP sh -c "cat > $ENC; chmod 600 $ENC" <<EOF
apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
- resources: [secrets]
  providers:
  - secretbox:
      keys:
      - name: key1
        secret: $KEY
  - identity: {}
EOF
unset KEY
```

| Часть команды | Значение |
|---|---|
| `head -c 32 /dev/urandom \| base64` | 32 случайных байта, как требует `secretbox` |
| `docker exec -i … cat > …` | записать stdin в файл на узле |
| `chmod 600` | читать файл может только root |
| `$KEY` в heredoc | подставить ключ в файл, не показывая его |
| `unset KEY` | убрать ключ из переменных шелла |

Результат: команды ничего не печатают.

Разбор: ключ не печатается и нигде не сохраняется, кроме файла на узле. Порядок провайдеров: `secretbox` шифрует, `identity` позволяет читать старые записи.

#### Шаг 3. Подключить файл к API-серверу

Команды добавляют в манифест флаг, монтирование и том, затем ждут, пока API-сервер снова ответит.

```bash
FLAG='    - --encryption-provider-config=/etc/kubernetes/enc/enc.yaml'
MNT='    - {mountPath: /etc/kubernetes/enc, name: enc, readOnly: true}'
VOL='  - {hostPath: {path: /etc/kubernetes/enc, type: DirectoryOrCreate}, name: enc}'
docker exec $CP sed -i "s|^    - --etcd-servers=.*|&\n$FLAG|" $F
docker exec $CP sed -i "s|^    volumeMounts:|&\n$MNT|" $F
docker exec $CP sed -i "s|^  volumes:|&\n$VOL|" $F
docker exec $CP grep -n -E 'encryption|/enc|name: enc' $F
sleep 20
until kubectl get --raw /readyz >/dev/null 2>&1; do sleep 2; done
```

| Часть команды | Значение |
|---|---|
| `FLAG`, `MNT`, `VOL` | три строки для вставки в манифест |
| `s\|…etcd-servers=.*\|&\n$FLAG\|` | дописать флаг сразу после флага etcd |
| `^    volumeMounts:` | добавить монтирование каталога в контейнер |
| `^  volumes:` | добавить том `hostPath` с каталогом ключа |
| `grep -n -E …` | показать добавленные строки |
| `until kubectl get --raw /readyz` | ждать, пока API-сервер снова готов |

Результат: `grep` показывает три добавленные строки (флаг, монтирование и том). Перезапуск занимает около 44 секунд.

Разбор: kubelet заметил правку манифеста и пересоздал static pod (01-2). Пока API-сервер перезапускался, `kubectl` возвращал ошибки подключения, и цикл `until` дождался ответа `/readyz`. Если цикл не заканчивается больше 2 минут, откатывайте манифест (блок «Риски»).

#### Шаг 4. Сравнить старый и новый Secret

Команды создают новый Secret, читают оба из etcd, затем перезаписывают все Secret кластера и читают старый ещё раз. Функция `ec` показывает начало значения и признак открытого пароля. Переменные `E` и `X` из работы 2; если вы открыли новый терминал, задайте их заново.

```bash
ec() {
  $X $E get /registry/secrets/lab-04-1/$1 --print-value-only | head -c 40 | od -c | head -2
  echo "   contains plaintext: $($X $E get /registry/secrets/lab-04-1/$1 --print-value-only \
    | strings | grep -c S3cr3t)"
}
kubectl create secret generic db2 --from-literal=password='S3cr3t-P@ss'
ec db
ec db2
kubectl get secret db2 -o jsonpath='{.data.password}' | base64 -d; echo
kubectl get secrets -A -o json | kubectl replace -f - > /dev/null
ec db
```

| Часть команды | Значение |
|---|---|
| `head -c 40 \| od -c` | показать первые 40 байт символами |
| `grep -c S3cr3t` | посчитать строки с открытым паролем |
| `create secret generic db2` | новая запись, уже под шифрованием |
| `get secrets -A -o json \| replace -f -` | прочитать все Secret и записать обратно |

Результат (пробелы между символами сжаты, смещения `od` опущены):

```
k 8 s \0 \n \f \n 002 v 1 022 006 S e c r e t …     contains plaintext: 1
k 8 s : e n c : s e c r e t b o x : v 1 : k e y 1 : …   contains plaintext: 0
S3cr3t-P@ss
k 8 s : e n c : s e c r e t b o x : v 1 : k e y 1 : …   contains plaintext: 0
```

Разбор:

1. Первая строка — старый Secret `db`. Он начинается с `k8s\0` и содержит пароль открытым текстом (`plaintext: 1`).
2. Вторая строка — новый `db2`. Он начинается с `k8s:enc:secretbox:v1:key1:`, пароля в нём нет.
3. Третья строка — API отдаёт `db2` расшифрованным: клиент шифрования не замечает.
4. Четвёртая строка — после перезаписи старый `db` тоже зашифрован.

#### Шаг 5. Проверить метрики и отключить шифрование

Первая команда читает метрику: какие префиксы использует сервер. Остальные отключают шифрование в безопасном порядке: `identity` первым, перезапуск API-сервера, перезапись, проверка.

```bash
kubectl get --raw /metrics | grep '^apiserver_storage_transformation_operations_total' \
  | grep -o 'transformer_prefix="[^"]*"' | sort -u
docker exec $CP sh -c "awk '/providers:/{print; print \"  - identity: {}\"; next} \
/^  - identity: \{\}/{next} {print}' /etc/kubernetes/enc/enc.yaml \
> /tmp/enc.new && mv /tmp/enc.new /etc/kubernetes/enc/enc.yaml"
docker exec $CP mv $F /root/kas.tmp; sleep 15
docker exec $CP mv /root/kas.tmp $F; sleep 10
until kubectl get --raw /readyz >/dev/null 2>&1; do sleep 2; done
kubectl get secrets -A -o json | kubectl replace -f - > /dev/null
echo "encrypted secrets left: $($X $E get /registry/secrets --prefix --print-value-only \
  | grep -ac 'k8s:enc:')"
```

| Часть команды | Значение |
|---|---|
| `grep -o 'transformer_prefix=…' \| sort -u` | список используемых провайдеров |
| `awk '/providers:/{…}'` | переставить `identity` на первое место |
| `mv $F /root/kas.tmp; sleep 15` | убрать манифест: kubelet остановит API-сервер |
| `mv /root/kas.tmp $F` | вернуть манифест: сервер стартует с новым файлом |
| `replace -f -` | записать все Secret открытыми |
| `grep -ac 'k8s:enc:'` | посчитать зашифрованные значения в etcd |

Результат:

```
transformer_prefix="identity"
transformer_prefix="k8s:enc:secretbox:v1:"
encrypted secrets left: 0
```

Разбор:

1. В метрике два префикса: `identity` и `k8s:enc:secretbox:v1:`. Это значит, что сервер читал и открытые, и зашифрованные записи.
2. После перестановки `identity` первым новые записи не шифруются, а старые читаются ключом `key1`.
3. Перезапуск нужен, чтобы сервер перечитал файл: автоперезагрузка не включена.
4. `encrypted secrets left: 0` — зашифрованных значений не осталось, и ключ можно удалять. Пока число больше нуля, удалять ключ нельзя.

#### Шаг 6. Вернуть исходный манифест и удалить ключ

Команды возвращают сохранённый манифест, дожидаются API-сервера и удаляют файл ключа и копию.

```bash
docker exec $CP cp /root/kube-apiserver.yaml.bak $F
sleep 25
until kubectl get --raw /readyz >/dev/null 2>&1; do sleep 2; done
docker exec $CP sh -c "grep -c encryption $F; rm -rf /etc/kubernetes/enc \
  /root/kube-apiserver.yaml.bak; ls /etc/kubernetes/manifests"
curl -s -o /dev/null -w '%{http_code}\n' -H 'Host: orders.localhost' \
  http://127.0.0.1:8088/api/orders
```

| Часть команды | Значение |
|---|---|
| `cp …bak $F` | вернуть исходный манифест без шифрования |
| `grep -c encryption $F` | посчитать упоминания шифрования в манифесте |
| `rm -rf /etc/kubernetes/enc …` | удалить файл ключа и резервную копию |
| `ls /etc/kubernetes/manifests` | убедиться, что в каталоге только манифесты кластера |
| `curl … /api/orders` | проверить, что приложение отвечает через Gateway |

Результат: `0`, затем список из четырёх файлов манифестов (`etcd`, `kube-apiserver`, `kube-controller-manager`, `kube-scheduler`) и код `200`.

Разбор: ноль упоминаний значит, что манифест исходный. Четыре файла — это штатные static pods control plane (01-2). Код 200 подтверждает, что приложение работало всё время, пока API был недоступен: поды живут и без API-сервера.

**Итог.**

| Что узнали | Где видно |
|---|---|
| Включение шифрует только новые записи | шаг 4, `db` и `db2` |
| API отдаёт значение расшифрованным | шаг 4, третья строка |
| Старые записи шифруются после перезаписи | шаг 4, четвёртая строка |
| Метрика показывает используемые провайдеры | шаг 5 |
| Отключают в обратном порядке, ключ удаляют последним | шаги 5 и 6 |

**Уборка.** Шаги 5 и 6 вернули узел в исходное состояние. Остаётся удалить namespace и вернуть namespace по умолчанию.

```bash
kubectl config set-context --current --namespace=default
kubectl delete ns lab-04-1
rmdir ~/lab/k8s/04-1
unset CP F E X
```

Первая команда возвращает namespace по умолчанию, вторая удаляет всё созданное работами 1–3, третья убирает пустой каталог, четвёртая очищает переменные шелла.

**Вопросы для самопроверки.**

1. Почему после включения шифрования старый Secret остался открытым?
2. Что случится, если удалить ключ до перезаписи Secret?
3. Чем KMS v2 защищает лучше, чем ключ в файле?

<details>
<summary>Ответ</summary>

1. API-сервер шифрует только то, что записывает. Старый объект остаётся как есть, пока его не перезапишут (`get -o json | replace`).
2. Зашифрованные Secret станут нечитаемыми, а контроллеры, которым нужны токены, перестанут работать. Документация оставляет один выход: удалить нечитаемые записи из etcd.
3. Главный ключ (KEK) хранится во внешнем KMS и не лежит на диске control plane. Root на узле получает только зашифрованные DEK, а не ключ, которым они зашифрованы.

</details>
