## 1. Какую задачу решает бэкап

Бэкап возвращает данные, которые нельзя получить заново: заказы клиентов, состояние базы, объекты кластера. Разберём, от каких аварий он защищает, как их измеряют двумя числами и где его хранят.

### Какие аварии он закрывает

**Бэкап** (backup) — копия данных, из которой их можно восстановить после потери оригинала. Копии нужны не только на случай пожара в дата-центре. Чаще данные теряются из-за людей: кто-то удаляет PVC, namespace или таблицу, а миграция портит столбец.

Репликация эти аварии не закрывает. **Реплика** (replica) — вторая копия базы, которая повторяет все изменения первой. Команда `DROP TABLE` доходит до реплики почти мгновенно, поэтому реплика защищает от отказа узла, но не от ошибки человека.

### RPO и RTO

Качество бэкапа измеряют двумя числами. **RPO** (Recovery Point Objective) — сколько данных можно потерять: время от последней точки восстановления до аварии. **RTO** (Recovery Time Objective) — сколько сервис может лежать: время от аварии до рабочего состояния.

```
 бэкап N        авария                       сервис снова работает
    │              │                                  │
────●──────────────✕──────────────────────────────────●────► время
    │◄──── RPO ───►│◄─────────── RTO ────────────────►│
    данные за этот отрезок потеряны     сервис недоступен
```

Схема 2. RPO считают от последнего бэкапа до аварии, RTO — от аварии до возврата сервиса. При расписании «раз в 15 минут» RPO достигает 15 минут.

RPO задаёт частота бэкапов, а RTO — скорость восстановления. Оба числа требует бизнес, а инженер проверяет, что оборудование и процедура их выдерживают: RTO нельзя вычислить, его только измеряют на отрепетированном восстановлении.

### Правило 3-2-1

**Правило 3-2-1** требует трёх копий данных на двух разных носителях, причём одна копия лежит вне площадки. Для Kubernetes оно значит, что бэкап лежит не на том же PVC, не на том же узле и не в том же кластере. Лучше, когда он не лежит и в том же облачном аккаунте: злоумышленник с доступом к кластеру удалит и данные, и копии рядом с ними.

## 2. Как устроен бэкап

Данные кластера копируют четырьмя способами, и у каждого свой уровень из схемы 1. Разберём каждый по порядку и сравним их в конце.

### Логический бэкап: pg_dump

**Логический бэкап** (logical backup) — выгрузка содержимого базы в виде команд или записей, а не файлов диска. Для PostgreSQL его делает утилита `pg_dump`, а результат называется **дамп** (dump). Формат `custom` сжимает данные и позволяет восстановить отдельные таблицы утилитой `pg_restore`.

```
 PostgreSQL ◄── pg_dump (по сети) ── Job ──► файл .dump ──► pg_restore ──► новая БД
```

Схема 3. Дамп снимается по сети из работающей базы и читается в базу любой совместимой версии. Смотреть нужно на то, что копия не зависит от диска сервера.

Дамп согласован внутри себя: `pg_dump` читает базу в одной транзакции. Его можно загрузить в другую версию PostgreSQL или в другой кластер. Цена такая: восстановление медленное, потому что база пересоздаёт индексы и проверяет ограничения. На базе в 200 ГБ оно занимает часы.

### Снапшот тома: CSI VolumeSnapshot

Снапшот (snapshot, 04-2) — моментальный снимок тома, который делает хранилище. В Kubernetes его описывает объект VolumeSnapshot, а выполняет CSI-драйвер. Создание занимает секунды, потому что хранилище копирует только изменения.

Снапшот восстанавливает том целиком и привязан к типу хранилища. Без заморозки базы он **crash-consistent** — как после внезапного отключения питания: PostgreSQL запустится и доиграет журнал, но приложение, которое держит данные в памяти, может потерять их. Стенд такой способ показать не может: драйвер local-path снапшоты не поддерживает (04-2).

Две новинки полезны в больших кластерах. VolumeGroupSnapshot (04-2) — снимок сразу нескольких PVC в один момент, нужный базе с отдельными томами для данных и журнала; он стал GA в Kubernetes 1.36. **Changed block tracking** — API CSI, которое отдаёт только изменённые блоки тома для инкрементальных бэкапов. Оно в стадии beta и работает только с блочными томами.

### Физический бэкап и WAL

**Физический бэкап** (physical backup) копирует файлы базы, а не её содержимое. К нему добавляют архив **WAL** (write-ahead log) — журнал, в который PostgreSQL сначала записывает каждое изменение. Базовая копия плюс журнал позволяют вернуть базу на любой момент: это **PITR** (point-in-time recovery, восстановление на момент времени).

Метод даёт RPO в секунды и быстрое восстановление, но требует той же мажорной версии PostgreSQL. Его не пишут вручную: инструменты pgBackRest, WAL-G и Barman работают через оператор, например CloudNativePG (09-1), или через управляемую БД облака.

### Velero: объекты API и данные томов

**Velero** — инструмент, который копирует объекты Kubernetes и данные их томов в объектное хранилище. Он читает объекты через API-сервер, как обычный клиент, и не трогает etcd. Поэтому он восстанавливает один namespace, не затрагивая остальные.

```
  kubectl delete ns / авария
                                ┌───────────────────── кластер ─────────────────────┐
  velero CLI ─► Backup (CRD) ─► │ Velero server ── читает объекты через API         │
                                │ node-agent (DaemonSet) ── Kopia читает файлы тома │
                                └───────────────┬───────────────────────────────────┘
                                                ▼
                          BackupStorageLocation: бакет S3 (объекты + данные)
```

Схема 4. Velero состоит из сервера и агента на каждом узле. Смотреть нужно на путь данных: объекты и файлы тома уходят в бакет, вне кластера.

Три понятия нужны для работы с Velero:

- **BackupStorageLocation** — адрес и учётные данные бакета S3, куда Velero кладёт бэкапы.
- **node-agent** — DaemonSet Velero (02-4), который читает файлы томов прямо на узле.
- **File System Backup (FSB)** — копирование файлов тома агентом с библиотекой **Kopia**: она делит файлы на блоки, сжимает и не хранит повторы.

FSB нужен, когда у драйвера нет снапшотов, как у local-path на стенде; документация Velero v1.18 называет его качество beta. Он копирует файлы смонтированного тома, поэтому для базы данных даёт только crash-consistent копию: на нагруженной БД его дополняют дампом.

### Сравнение способов

Способы различаются тем, что они возвращают, как быстро и как переносятся.

| Способ | RPO | Скорость восстановления | Переносимость |
|---|---|---|---|
| Дамп `pg_dump` | интервал дампов | медленно | любая версия, любой кластер |
| Снапшот тома | интервал снапшотов | секунды–минуты | то же хранилище |
| Физический бэкап и WAL | секунды | быстро, плюс проигрыш WAL | та же мажорная версия |
| Velero с FSB | интервал бэкапов | зависит от объёма | другой кластер, другое хранилище |
| Реплика | почти 0 | переключение | не бэкап |

Для маленького сервиса хватает дампа по расписанию. Для продовой базы берут физический бэкап с WAL или управляемую БД, а Velero добавляют ради объектов кластера и быстрого переноса namespace. Решение «база в кластере или вне» сводится к вопросу, кто отвечает за эти бэкапы и их проверку: оператор в кластере (09-1) или облачная служба.

## 3. Как управлять бэкапом

Бэкап должен выполняться сам, оставлять проверяемый результат и не ломать нормальную работу. Начнём с дампа по расписанию, затем разберём восстановление, копию вне кластера и команды Velero.

### CronJob с дампом

Дамп по расписанию запускает CronJob (02-4): он создаёт Job, а Job запускает под с `pg_dump`. Поля расписания и политик описаны в 02-4, здесь важны те, от которых зависит надёжность бэкапа.

```yaml
spec:
  schedule: "*/15 * * * *"
  timeZone: Europe/Moscow
  concurrencyPolicy: Forbid
  startingDeadlineSeconds: 300
  jobTemplate:
    spec:
      backoffLimit: 1
      activeDeadlineSeconds: 600
      ttlSecondsAfterFinished: 86400
```

Фрагмент манифеста. `Forbid` не даёт запуститься второму дампу, пока идёт первый; `activeDeadlineSeconds: 600` останавливает зависший дамп через 10 минут, иначе он блокирует все следующие.

Скрипт внутри контейнера тоже влияет на надёжность. Каждая строка закрывает отдельный сбой:

1. `sh -e` — любая ошибка `pg_dump` завершает Job с ошибкой, а не оставляет пустой файл при коде 0.
2. `--format=custom` — сжатие и возможность `pg_restore --list` как проверки читаемости.
3. Запись в `.tmp` и `mv` — оборванный дамп не подменяет готовый, потому что переименование атомарно.
4. Имя с меткой времени — новый дамп не перезаписывает единственную копию.
5. Ротация `tail -n +8` — хранится 7 последних дампов, диск не растёт без границы.

Клиент `pg_dump` должен быть той же версии, что сервер, или новее: старый клиент отказывается снимать дамп с нового сервера.

### Запуск по требованию

Любой CronJob запускают вне расписания командой `kubectl create job --from=cronjob/<имя>`. Так делают бэкап перед рискованной миграцией или обновлением. Новый Job берёт шаблон из CronJob, поэтому в нём те же образ, проверки и том.

### Восстановление

Восстановление идёт по фиксированной процедуре из четырёх шагов, и порядок в ней важен.

1. Остановить приложение, которое пишет в базу (`scale --replicas=0`).
2. Создать пустую базу: восстановленный том или новый StatefulSet.
3. Загрузить последний дамп утилитой `pg_restore`.
4. Вернуть приложение и проверить данные.

Приложение останавливают потому, что при старте на пустой базе оно создаёт свои начальные записи, а клиенты добавляют новые. Загрузка дампа с флагом `--clean` затёрла бы всё это или столкнулась бы с ним. Записи, сделанные после последнего дампа, восстановление не вернёт: это и есть RPO.

### Копия вне кластера

Бэкап на PVC того же кластера не переживёт потерю узла или кластера. Копию выносят в объектное хранилище S3 с версионированием и защитой от удаления (Object Lock). Учётная запись для записи бэкапов получает права только на запись, а для чтения выдают другой ключ. Дамп шифруют утилитой `age` или `gpg`, а срок хранения задают правилами бакета: например, 7 дневных, 4 недельных и 12 месячных копий. На стенде вынос выглядит скромнее: `kubectl cp` на хост (работа 1) и S3-шлюз в кластере (работа 3).

### Команды Velero

Velero управляется через CLI и объекты CRD. Основные команды собраны в карточке инструмента в начале работы 3.

Данные томов Velero берёт в двух режимах. В режиме по умолчанию (opt-in) копируются только тома, которые перечислены в аннотации пода `backup.velero.io/backup-volumes`. Флаг `--default-volumes-to-fs-backup` меняет правило: копируются все тома, кроме исключённых.

## 4. Как увидеть состояние бэкапа

Бэкап, о котором ничего не известно, не считается бэкапом. Нужны ответы на три вопроса: был ли запуск, свежий ли файл и восстанавливается ли он.

### Запуск и результат

Состояние запусков показывают объекты `CronJob` и `Job`: `kubectl -n <ns> get cronjob,job` выводит время последнего расписания и число завершённых запусков, а `kubectl logs job/<имя>` — вывод скрипта. Код 0 у Job подтверждает только то, что скрипт дошёл до конца. Поэтому скрипт печатает итоговую строку с именем и размером файла.

Для Velero состояние читают командами `velero backup get` и `velero backup describe`. Поле `Phase` показывает стадию бэкапа: среди значений есть `InProgress`, `Completed`, `PartiallyFailed` и `Failed`. Фаза `PartiallyFailed` значит, что часть объектов или томов не сохранена, поэтому её считают ошибкой.

### Проверка восстановлением

Единственная настоящая проверка бэкапа — восстановить его. Её автоматизируют отдельным Job. Он берёт последний дамп, запускает во втором экземпляре PostgreSQL в том же поде, загружает дамп и проверяет три вещи:

- **свежесть** — возраст файла меньше заданного порога, например часа;
- **читаемость** — `pg_restore` завершился без ошибок;
- **правдоподобие** — число строк в ключевой таблице не меньше ожидаемого.

Job запускают по расписанию, а на его провал ставят оповещение. Раз в квартал полезны учения: восстановление на полноразмерной копии с замером RTO.

### Где лежит бэкап

Расположение бэкапа проверяют так же, как и его содержимое. На стенде PVC с бэкапами создаёт драйвер local-path и привязывает к узлу, где под впервые использует том (WaitForFirstConsumer, 04-2). Если база и бэкапы оказались на одном узле, потеря узла уничтожает оба. Узел PV читают из его `nodeAffinity`, а узел пода — из поля `spec.nodeName`.

## 5. Что ломается и как найти причину

Большинство потерянных бэкапов умирает тихо: расписание работает, Job «успешен», а восстановить нечего. Ниже собраны типовые причины и способ найти каждую.

### Пустой или битый дамп при коде 0

Скрипт `pg_dump > файл` без `set -e` создаёт пустой файл, когда утилита падает, например после смены пароля. Job завершается с кодом 0, а мониторинг показывает «CronJob успешен». Находят проблему по логу Job и по размеру файла, а предотвращают флагом `-e`, проверкой `pg_restore --list` и автоматическим восстановлением в тестовую базу. Версия клиента тоже важна: `pg_dump` 16 отказывается снимать дамп с сервера 17, и это видно в логе Job.

### Бэкап рядом с данными

Бэкап на том же узле, PVC или в том же кластере умирает вместе с оригиналом. Проверка простая: сравните узел PV с бэкапом и узел PV с базой. Если узел один, добавьте копию вне кластера.

### Восстановление при работающем приложении

Если приложение работает во время `pg_restore`, оно создаёт записи в пустой или частично загруженной базе. Тогда данные смешиваются или теряются, а ошибки нет. Признак: после восстановления число строк не равно числу в дампе. Лечит это порядок процедуры: сначала остановить писателей.

### Velero восстановил объекты, а данных нет

Velero в режиме opt-in не копирует тома без аннотации. Восстановление завершается статусом `Completed`, PVC появляется, но пустой. Находят это в `velero backup describe --details`: раздел о томах пуст или в нём нет нужного тома. Исправляют аннотацией пода `backup.velero.io/backup-volumes` и новым бэкапом. Старый бэкап уже не вернуть: данных в нём не было.

### Velero не видит бакет

Когда `velero backup-location get` показывает `Unavailable`, смотрят лог сервера: `kubectl -n <ns> logs deploy/velero`. Частые причины: неверный `s3Url`, неверные ключи в файле учётных данных и отсутствие `s3ForcePathStyle=true` для хранилища вне AWS. Без последнего клиент AWS ищет бакет по имени хоста вида `velero.s3.lab-04-3.svc`, такого имени нет в DNS кластера, и падает любой запрос. Если хранилище отвергает контрольные суммы запросов, в настройки расположения добавляют `checksumAlgorithm=""`: по умолчанию плагин считает CRC32.

## 6. Пределы и значения по умолчанию

Ниже собраны числа этой части. Значения CronJob взяты из 02-4, значения Velero — из документации версии v1.18.

### CronJob и Job

- `concurrencyPolicy` — `Allow`, если не указано другое; для дампов ставят `Forbid`.
- `successfulJobsHistoryLimit` — 3, `failedJobsHistoryLimit` — 1 (в манифесте работы 1 оба заданы как 3).
- `startingDeadlineSeconds` — не задан: пропущенный запуск может стартовать позже без ограничения.
- `backoffLimit` у Job — 6; в бэкап-Job ставим 1, чтобы ошибка не повторялась пачкой.
- `ttlSecondsAfterFinished` — не задан, и завершённый Job живёт вечно; в манифесте стоит 86400 с (сутки).

### Velero

- Срок хранения бэкапа (`--ttl`) — 720 часов, то есть 30 дней.
- Namespace установки — `velero`, если не задан флаг `--namespace`; в работе 3 это `lab-04-3`.
- Режим томов — opt-in по аннотации; режим «все тома» включает `--default-volumes-to-fs-backup`.
- FSB не поддерживает `hostPath`; тома `local` поддерживает.
- Kopia шифрует репозиторий одним общим ключом, поэтому доступ к бакету даёт возможность расшифровать данные.
- Пока FSB работает на живой базе, данные тома могут быть согласованы только на уровне «после сбоя питания».

### Снапшот etcd и Velero

Снапшот etcd (10-2) и бэкап Velero защищают разные уровни.

| Свойство | Снапшот etcd | Velero |
|---|---|---|
| Что копирует | всё хранилище etcd | выбранные объекты API и тома |
| Данные томов | нет | да, при FSB или снапшоте |
| Гранулярность | весь кластер | namespace, метка, ресурс |
| Восстановление | остановить API, заменить данные | velero restore при работающем API |
| Перенос | тот же кластер и версия | другой кластер |

Снапшот etcd возвращает кластер целиком и нужен после потери control plane. Velero возвращает namespace и данные его томов и работает, когда кластер жив. Ни один из них не заменяет дамп базы с проверенным восстановлением.

Версия Kubernetes 1.37 на этих механизмах не меняет ничего, что нужно курсу.

#### Шаг 1. Создать PVC и CronJob

Команда создаёт PVC для бэкапов и CronJob с дампом каждые 15 минут.

```bash
cat > ~/lab/k8s/04-3/backup.yaml <<'EOF'
apiVersion: v1
kind: PersistentVolumeClaim
metadata: {name: pg-backups, namespace: orders}
spec:
  accessModes: [ReadWriteOnce]
  resources: {requests: {storage: 1Gi}}
---
apiVersion: batch/v1
kind: CronJob
metadata: {name: pg-backup, namespace: orders}
spec:
  schedule: "*/15 * * * *"
  timeZone: Europe/Moscow
  concurrencyPolicy: Forbid
  startingDeadlineSeconds: 300
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 3
  jobTemplate:
    spec:
      backoffLimit: 1
      activeDeadlineSeconds: 600
      ttlSecondsAfterFinished: 86400
      template:
        spec:
          restartPolicy: Never
          containers:
          - name: dump
            image: postgres:17.6-alpine
            env:
            - {name: PGHOST, value: postgres}
            - {name: PGUSER, valueFrom: {secretKeyRef: {name: postgres, key: POSTGRES_USER}}}
            - name: PGPASSWORD
              valueFrom: {secretKeyRef: {name: postgres, key: POSTGRES_PASSWORD}}
            - {name: PGDATABASE, valueFrom: {secretKeyRef: {name: postgres, key: POSTGRES_DB}}}
            - {name: PGCONNECT_TIMEOUT, value: "10"}
            command:
            - sh
            - -ec
            - |
              f=/backups/orders-$(date -u +%Y%m%dT%H%M%SZ).dump
              pg_dump --format=custom --no-owner --file="$f.tmp"
              mv "$f.tmp" "$f"
              pg_restore --list "$f" > /dev/null
              ls -1t /backups/*.dump | tail -n +8 | xargs -r rm
              echo "backup ok: $f $(du -h "$f" | cut -f1)"; ls -l /backups
            volumeMounts: [{name: backups, mountPath: /backups}]
          volumes: [{name: backups, persistentVolumeClaim: {claimName: pg-backups}}]
EOF
kubectl apply -f ~/lab/k8s/04-3/backup.yaml
```

| Часть команды | Значение |
|---|---|
| `concurrencyPolicy: Forbid` | не запускать второй дамп, пока идёт первый |
| `activeDeadlineSeconds: 600` | остановить зависший дамп через 10 минут |
| `secretKeyRef` | взять логин и пароль из Secret `postgres` (04-1) |
| `sh -ec` | завершить скрипт при первой ошибке |
| `mv "$f.tmp" "$f"` | атомарно подменить файл готовым дампом |
| `pg_restore --list` | проверить, что дамп читается |
| `tail -n +8 \| xargs -r rm` | удалить все дампы, кроме семи последних |

Результат:

```
persistentvolumeclaim/pg-backups created
cronjob.batch/pg-backup created
```

Разбор: оба объекта созданы. PVC остаётся в статусе `Pending`, пока его не использует первый под: драйвер local-path ждёт потребителя (04-2).

#### Шаг 2. Добавить данные и запустить дамп вручную

|---|---|
| `psql -c "INSERT …"` | выполнить один SQL-запрос в базе `orders` |
| `create job --from=cronjob/pg-backup` | создать Job по шаблону CronJob |
| `wait --for=condition=Complete` | ждать успешного завершения Job до 180 с |

Разбор:

#### Шаг 3. Проверить бэкап восстановлением

Команда запускает Job, который поднимает временный PostgreSQL в своём поде, загружает в него последний дамп и считает строки.

```bash
cat > ~/lab/k8s/04-3/backup-verify.yaml <<'EOF'
apiVersion: batch/v1
kind: Job
metadata: {name: pg-backup-verify, namespace: orders}
spec:
  backoffLimit: 0
  activeDeadlineSeconds: 600
  template:
    spec:
      restartPolicy: Never
      containers:
      - name: verify
        image: postgres:17.6-alpine
        env:
        - {name: POSTGRES_PASSWORD, value: verify-only}
        - {name: PGUSER, value: postgres}
        - {name: PGPASSWORD, value: verify-only}
        - {name: MIN_ROWS, value: "2"}
        command:
        - sh
        - -ec
        - |
          f=$(ls -1t /backups/*.dump | head -1)
          age=$(( $(date +%s) - $(stat -c %Y "$f") ))
          echo "latest: $f, age ${age}s"
          [ "$age" -lt 3600 ] || { echo "FAIL: backup older than 1h"; exit 1; }
          docker-entrypoint.sh postgres >/tmp/pg.log 2>&1 &
          until pg_isready -q -h 127.0.0.1; do sleep 1; done
          createdb -h 127.0.0.1 verify
          pg_restore -h 127.0.0.1 --no-owner --exit-on-error -d verify "$f"
          rows=$(psql -h 127.0.0.1 -d verify -tAc "select count(*) from orders")
          echo "restored rows: $rows"
          [ "$rows" -ge "$MIN_ROWS" ] && echo "VERIFY OK" || { echo "FAIL: too few rows"; exit 1; }
        volumeMounts: [{name: backups, mountPath: /backups, readOnly: true}]
      volumes: [{name: backups, persistentVolumeClaim: {claimName: pg-backups}}]
EOF
kubectl apply -f ~/lab/k8s/04-3/backup-verify.yaml
kubectl -n orders wait --for=condition=Complete job/pg-backup-verify --timeout=180s
kubectl -n orders logs job/pg-backup-verify
```

| Часть команды | Значение |
|---|---|
| `stat -c %Y` | время изменения файла в секундах с 1970 года |
| `[ "$age" -lt 3600 ]` | отклонить бэкап старше часа |
| `docker-entrypoint.sh postgres &` | запустить временный сервер в фоне |
| `createdb verify` | создать пустую базу для проверки |
| `pg_restore --exit-on-error` | остановиться на первой ошибке загрузки |
| `readOnly: true` | смонтировать PVC с бэкапами только на чтение |

Результат:

```
latest: /backups/orders-20261014T103535Z.dump, age 54s
restored rows: 5
VERIFY OK
```

Разбор:

1. `age 54s` — дамп свежий, проверка свежести пройдена.
2. `restored rows: 5` — дамп читается, а таблица содержит строки. Пять строк — три исходные и две вставленные на шаге 2.
3. `VERIFY OK` — число строк не меньше `MIN_ROWS`, поэтому содержимое правдоподобно.
4. В прогоне автора проверка заняла 6 секунд. Её можно запускать сразу после дампа: второй потребитель PVC с режимом RWO допустим на том же узле (04-2).

Команда сравнивает узел, к которому привязан PV с бэкапами, и узел пода базы.

| Часть команды | Значение |
|---|---|
| `.spec.volumeName` | имя PV, к которому привязан PVC |
| `.spec.nodeAffinity.required…values[0]` | узел, к которому local-path привязал PV |

#### Шаг 5. Скопировать бэкап на хост

Команда запускает вспомогательный под с PVC в режиме чтения, копирует последний дамп на хост и сравнивает контрольные суммы.

```bash
mkdir -p ~/lab/k8s/04-3/backups
kubectl -n orders run bk-copy --image=busybox:1.37 --restart=Never --overrides='{
  "spec":{"containers":[{"name":"c","image":"busybox:1.37","command":["sleep","300"],
  "volumeMounts":[{"name":"b","mountPath":"/backups","readOnly":true}]}],
  "volumes":[{"name":"b","persistentVolumeClaim":{"claimName":"pg-backups"}}]}}'
kubectl -n orders wait --for=condition=Ready pod/bk-copy
F=$(kubectl -n orders exec bk-copy -- sh -c 'ls -1t /backups/*.dump | head -1')
kubectl -n orders cp bk-copy:$F ~/lab/k8s/04-3/backups/$(basename $F)
sha256sum ~/lab/k8s/04-3/backups/*.dump
kubectl -n orders exec bk-copy -- sha256sum $F
```

| Часть команды | Значение |
|---|---|
| `run bk-copy --overrides` | создать под с нужным томом, которого нет у `run` |
| `sleep 300` | держать под 5 минут, достаточно для копирования |
| `kubectl cp` | скопировать файл из пода на хост через `tar` |
| `sha256sum` | посчитать контрольную сумму файла на хосте и в поде |

Результат (суммы сокращены):

```
0a55d369…  /home/…/04-3/backups/orders-20261014T103535Z.dump
0a55d369…  /backups/orders-20261014T103535Z.dump
```

Разбор: суммы на хосте и в поде совпадают, копия целая. Команда `kubectl cp` требует `tar` в образе пода, поэтому в distroless-образах она не работает.

**Итог.**

| Что узнали | Где видно |
|---|---|
| Надёжность дампа задают `-e`, временный файл, имя с временем и ротация | скрипт в `backup.yaml` |
| Бэкап проверяют восстановлением: свежесть, читаемость, число строк | `VERIFY OK` |
| Бэкап на PVC того же узла не переживает потерю узла | узлы PV и пода совпали |
| Копию на хост проверяют контрольной суммой | суммы совпали |

**Уборка.** Удаляем проверочный Job и вспомогательный под. CronJob, PVC и дамп нужны работе 2, поэтому их удаляет её уборка; если работу 2 вы не выполняете, сразу выполните её уборку. Дамп на хосте в `~/lab/k8s/04-3/backups` остаётся.

```bash

kubectl -n orders delete pod bk-copy --now --ignore-not-found
```

**Вопросы для самопроверки.**

1. Почему Job бэкапа без `sh -e` может завершиться с кодом 0 и пустым файлом?
2. Что проверяет Job `pg-backup-verify` и чего он не проверяет?
3. Чем опасно хранить дампы на PVC того же узла, что и база?

<details>
<summary>Ответы</summary>

1. Без `-e` shell продолжает работу после ошибки `pg_dump`. Перенаправление уже создало пустой файл, а код выхода определяет последняя команда, поэтому Job «успешен».
2. Он проверяет свежесть (возраст меньше часа), читаемость (`pg_restore` без ошибок) и число строк. Он не проверяет бизнес-смысл данных и не доказывает, что приложение заработает с этой базой.
3. Потеря узла уничтожает том базы и том бэкапов одновременно: бэкап не переживает аварию, от которой должен защищать.

</details>

#### Шаг 3. Восстановить по процедуре

Команды выполняют четыре шага процедуры: останавливают приложение, создают пустую базу, загружают дамп и возвращают приложение.

```bash
echo "t=+$(( $(date +%s)-T0 ))s new empty postgres ready"
```

| Часть команды | Значение |
|---|---|
| `scale deploy orders-api --replicas=0` | остановить приложение, которое пишет в базу |
| `apply -f …/postgres.yaml` | создать Secret, Service и StatefulSet базы; PVC создаст StatefulSet |
| `rollout status sts/postgres` | ждать готовности нового пода |
| `$(( $(date +%s)-T0 ))` | секунды с момента аварии |

Результат:

```
t=+13s new empty postgres ready
```

Разбор: пустая база появилась через 13 секунд. Образ был в кэше узла, поэтому запуск быстрый. Теперь запускаем Job, который загружает последний дамп.

```bash
kubectl apply -f - <<'EOF'
apiVersion: batch/v1
kind: Job
metadata: {name: pg-restore, namespace: orders}
spec:
  backoffLimit: 0
  template:
    spec:
      restartPolicy: Never
      containers:
      - name: restore
        image: postgres:17.6-alpine
        env:
        - {name: PGHOST, value: postgres}
        - {name: PGUSER, valueFrom: {secretKeyRef: {name: postgres, key: POSTGRES_USER}}}
        - {name: PGPASSWORD, valueFrom: {secretKeyRef: {name: postgres, key: POSTGRES_PASSWORD}}}
        - {name: PGDATABASE, valueFrom: {secretKeyRef: {name: postgres, key: POSTGRES_DB}}}
        command:
        - sh
        - -ec
        - |
          f=$(ls -1t /backups/*.dump | head -1); echo "restoring $f"
          pg_restore --clean --if-exists --no-owner --exit-on-error --dbname="$PGDATABASE" "$f"
          psql -tAc "select count(*) from orders"
        volumeMounts: [{name: backups, mountPath: /backups}]
      volumes: [{name: backups, persistentVolumeClaim: {claimName: pg-backups}}]
EOF
kubectl -n orders wait --for=condition=Complete job/pg-restore --timeout=180s
L=$(kubectl -n orders logs job/pg-restore | tr '\n' ' ')
echo "t=+$(( $(date +%s)-T0 ))s restore done: $L"
```

| Часть команды | Значение |
|---|---|
| `ls -1t … \| head -1` | выбрать самый свежий дамп |
| `pg_restore --clean --if-exists` | удалить существующие объекты перед загрузкой, без ошибок если их нет |
| `--exit-on-error` | остановиться на первой ошибке |
| `tr '\n' ' '` | склеить строки лога в одну, результат в переменную `L` |

Результат:

```
t=+16s restore done: restoring /backups/orders-20261014T103535Z.dump 5
```

Разбор: восстановление заняло 3 секунды, и в базе пять строк, как в дампе. Scheduler сам поставил Job на узел с PVC `pg-backups` (04-2).

Последним действием возвращаем приложение и ждём, пока API ответит.

```bash
kubectl -n orders scale deploy orders-api --replicas=2
kubectl -n orders rollout status deploy/orders-api
until api | grep -q orders; do sleep 1; done
echo "t=+$(( $(date +%s)-T0 ))s API OK: $(api | jq -c '[.orders[].item]')"
```

| Часть команды | Значение |
|---|---|
| `scale --replicas=2` | вернуть исходное число реплик приложения |
| `rollout status deploy/orders-api` | ждать готовности реплик |
| `until api \| grep -q orders` | опрашивать API до первого корректного ответа |

Результат:

```
t=+18s API OK: ["book","pen","lamp","mug","desk"]
```

Разбор:

1. RTO равен 18 секундам. Это нижняя оценка: база крошечная, образ в кэше, команды отрепетированы.
2. Запись `after-backup` потеряна. Это RPO аварии: всё, что записано после времени в имени дампа.
3. На базе в 200 ГБ логическое восстановление идёт часами, поэтому для больших баз берут физические бэкапы с WAL (§2).

#### Шаг 4. Посчитать RPO

Сравните список «до аварии» и «после восстановления» и подставьте расписание в формулу: максимальный RPO равен интервалу между дампами. Какой RPO получится при расписании `*/15` и при ежесуточном?

Вывод для себя: при `*/15` потеряются до 15 минут записей, при ежесуточном дампе — до суток. Чтобы RPO стал минутным, нужен архив WAL (§2).

**Итог.**

| Что узнали | Где видно |
|---|---|
| Потеря PVC базы не затрагивает отдельный PVC с дампами | `pg-backups` пережил аварию |
| Процедура: остановить писателей, пустая БД, `pg_restore`, вернуть приложение | шаг 3 |
| RTO на малой базе — 18 с | строка `API OK` |
| RPO — записи после последнего дампа | пропала `after-backup` |

**Уборка.** Удаляем Job'ы, CronJob и PVC с бэкапами, возвращаем манифесты стенда и стираем строки, которые добавила работа 1. Дамп на хосте остаётся.

```bash
kubectl -n orders delete job pg-restore backup-manual-1 --ignore-not-found
kubectl delete -f ~/lab/k8s/04-3/backup.yaml
kubectl apply -f ~/lab/k8s/orders-api/k8s/
kubectl -n orders rollout status deploy/orders-api
kubectl -n orders exec postgres-0 -- psql -U orders -d orders \
  -c "DELETE FROM orders WHERE item IN ('mug', 'desk', 'after-backup')"
curl -s http://orders.localhost:8088/api/orders | jq -c '[.orders[].item]'
```

Команда `DELETE` убирает заказы `mug` и `desk` из работы 1, а `after-backup` уже потерян при аварии. Последняя команда должна вернуть тот же список заказов, что подготовка перед работой 1: стенд вернулся в исходное состояние.

**Вопросы для самопроверки.**

1. Почему приложение останавливают до загрузки дампа?
2. Что определяет RPO в этой работе и как его уменьшить?
3. Почему измеренные 18 секунд нельзя считать RTO продовой базы?

<details>
<summary>Ответы</summary>

1. На пустой базе приложение создаёт начальные записи, а клиенты добавляют новые. Загрузка с `--clean` затёрла бы их или конфликтовала бы с ними.
2. RPO определяет интервал между дампами. Чаще дампы уменьшают его до минут, а до секунд его сводит только архив WAL.
3. База крошечная, образ в кэше, команды отрепетированы. На реальной базе загрузка и пересоздание индексов занимают часы.

</details>

### Лабораторная работа 3. Velero: бэкап namespace и восстановление

Эту работу вы выполняете сами, результаты в ней — ожидаемые.

**Риски.**

- **Что меняется:** установка Velero создаёт набор CRD группы `velero.io` и ClusterRoleBinding с правами `cluster-admin` для ServiceAccount Velero.
- **Нагрузка:** агент Velero (DaemonSet) монтирует с каждого узла `/var/lib/kubelet/pods` и `/var/lib/kubelet/plugins`. Лимитов у агента по умолчанию нет, а сервер Velero запрашивает 500m CPU и 128 МиБ памяти с лимитом 1 CPU и 512 МиБ.
- **Узел:** шаг 7 временно кладёт файл снапшота в `/var/lib/etcd` узла `lab-control-plane`.
- **Хост:** создаётся каталог с бинарным файлом Velero и файлами ключей с правами 600.
- **Откат:** уборка удаляет Velero, CRD, оба namespace и файлы ключей.

**Цель.** Поставить Velero с S3-хранилищем в кластере, сделать бэкап namespace вместе с данными тома, удалить namespace и восстановить его, затем сравнить результат со снапшотом etcd.

**Что понадобится.**

- Стенд 00-1; namespace `lab-04-3` и `lab-04-3-demo` создают шаги работы.
- Доступ с хоста к GitHub и Docker Hub, около 1 ГиБ диска.
- Velero v1.18.4 — последний релиз на GitHub от 28 сентября 2026 года.
- Плагин `velero-plugin-for-aws` v1.14.4 — ветка v1.14.x совместима с Velero v1.18.x по таблице репозитория плагина.
- S3-шлюз `versity/versitygw:v1.8.0` и клиент `amazon/aws-cli:2.37.0`.

Разработчики проверили Velero v1.18 на Kubernetes 1.33–1.35. Ожидаемая совместимость в README — «1.18 и новее», так что версия 1.36 на стенде в неё входит, хотя отдельно не проверялась.

Хранилищем служит **VersityGW** (Versity S3 Gateway) — шлюз, который отдаёт каталог файловой системы по протоколу S3: каждый подкаталог корня становится бакетом. Раньше учебные стенды брали MinIO, но его community-версия перешла на выпуск только исходного кода, а репозиторий `minio/minio` архивирован 25 апреля 2026 года. Для Velero подходит любое S3-совместимое хранилище, поэтому команды работы меняются только в адресе и ключах.

**Карточка инструмента: Velero.**

**Назначение.** Velero копирует объекты Kubernetes и данные томов в хранилище S3 и возвращает их на живой кластер. Он восстанавливает один namespace, но не сам кластер: для потери control plane нужен снапшот etcd (10-2).

**Как работает.** Команда `velero` создаёт в API-сервере объекты Backup и Restore. Сервер Velero читает объекты через API и пишет их архив в бакет, а агент на узле копирует файлы томов в тот же бакет.

```
velero CLI ─► Backup / Restore (CRD в API-сервере)
                     │ контроллеры сервера Velero (Deployment)
 объекты namespace ──┴─► архив в бакете S3 ◄── node-agent + Kopia: файлы томов
```

Схема 7. Velero не трогает etcd: объекты он читает как обычный клиент API. Смотрите на бакет: в нём лежат и объекты, и данные томов.

**Откуда берёт данные.** Объекты — через API-сервер по текущему контексту kubectl. Файлы томов — агент с узла, где смонтирован том. Адрес бакета и ключи хранит объект BackupStorageLocation, который создала установка.

**Основные команды.** Флаг `--namespace` указывает namespace установки: по умолчанию Velero ищет его в `velero`.

```bash
# бэкап одного namespace; --wait ждёт завершения
velero backup create demo --include-namespaces lab-04-3-demo --wait
# фаза, состав и тома, которые скопированы; без --details вывод короче
velero backup describe demo --details
# список бэкапов и их фаз
velero backup get
# восстановление из бэкапа в тот же или другой кластер
velero restore create --from-backup demo
# доступен ли бакет: фаза Available или Unavailable
velero backup-location get
# удалить Velero вместе с CRD и namespace установки
velero uninstall
```

**Команды для скриптов.** `backup create --wait` ждёт конца бэкапа и печатает итоговую фазу; проверяйте её в выводе `backup get -o json` через `jq`, а не по коду выхода.

**Частые ошибки.**

- Бэкап без аннотации тома или флага `--default-volumes-to-fs-backup`: объекты вернутся, а том окажется пустым (§5).
- Клиент и сервер разных версий: ставьте их из одного релиза.
- Бакет без `s3ForcePathStyle=true` или с неверным регионом: фаза `Unavailable` (§5).

**Установка.** В Ubuntu и Manjaro одинаково: готовый бинарный файл со страницы релизов проекта. В шаге 1 работы он скачивается в `~/lab/k8s/04-3/bin` и проверяется контрольной суммой.

**Схема опыта.**

```
 namespace lab-04-3                          namespace lab-04-3-demo
 ┌──────────────────────────────┐            ┌────────────────────────┐
 │ VersityGW (бакет velero)     │◄── Kopia ──┤ Deployment + PVC       │
 │ Velero server + node-agent   │            │ ConfigMap, файл note   │
 └──────────────────────────────┘            └────────────────────────┘
   delete ns lab-04-3-demo  ──►  velero restore  ──►  объекты и файл вернулись
```

Схема 8. Velero и шлюз S3 живут в `lab-04-3`, бэкапится `lab-04-3-demo`. Бакет лежит внутри кластера: на стенде это учебная замена хранилища вне кластера.

#### Шаг 1. Скачать клиент Velero

Команда скачивает CLI в каталог работы, сверяет контрольную сумму с файлом релиза и распаковывает бинарный файл.

```bash
mkdir -p ~/lab/k8s/04-3/bin && cd ~/lab/k8s/04-3/bin
V=v1.18.4
BASE=https://github.com/vmware-tanzu/velero/releases/download/$V
curl -fLO $BASE/velero-$V-linux-amd64.tar.gz
curl -fLO $BASE/CHECKSUM
sha256sum -c --ignore-missing CHECKSUM
tar xzf velero-$V-linux-amd64.tar.gz --strip-components=1 velero-$V-linux-amd64/velero
./velero version --client-only
```

| Часть команды | Значение |
|---|---|
| `V=v1.18.4` | закреплённая версия клиента и сервера |
| `curl -fLO` | скачать файл по имени, следуя редиректам, с ошибкой при коде 4xx |
| `CHECKSUM` | файл релиза с суммами SHA-256 всех архивов |
| `sha256sum -c --ignore-missing` | сверить только скачанные файлы с файлом сумм |
| `--strip-components=1` | положить бинарь прямо в текущий каталог |
| `version --client-only` | показать версию клиента, не обращаясь к кластеру |

Ожидаемый результат:

```
velero-v1.18.4-linux-amd64.tar.gz: OK
Client:
	Version: v1.18.4
	…
```

Разбор: строка `OK` подтверждает целостность архива. Клиент и сервер Velero должны быть одной версии, поэтому та же `v1.18.4` закреплена в шаге 3.

#### Шаг 2. Поднять шлюз S3 и создать бакет

Команды создают namespace, генерируют ключи доступа и собирают из них Secret и файл учётных данных для Velero.

```bash
cd ~/lab/k8s/04-3
kubectl create ns lab-04-3
umask 077
printf 'lab04user' > s3-user
openssl rand -hex 16 > s3-pass
kubectl -n lab-04-3 create secret generic s3-creds \
  --from-file=ROOT_ACCESS_KEY_ID=s3-user --from-file=ROOT_SECRET_ACCESS_KEY=s3-pass
printf '[default]\naws_access_key_id=%s\naws_secret_access_key=%s\n' \
  "$(cat s3-user)" "$(cat s3-pass)" > credentials-velero
```

| Часть команды | Значение |
|---|---|
| `umask 077` | новые файлы доступны только владельцу |
| `openssl rand -hex 16` | сгенерировать случайный пароль, а не писать его в команду |
| `--from-file=KEY=файл` | положить содержимое файла в ключ Secret |
| `ROOT_ACCESS_KEY_ID` | переменная, из которой VersityGW читает корневой ключ |
| `printf … > credentials-velero` | собрать файл ключей в формате AWS для Velero |

Секрет и файл ключей создаются без пароля в командной строке. Теперь манифест шлюза и Job, который создаёт бакет через API S3.

```bash
cat > s3.yaml <<'EOF'
apiVersion: apps/v1
kind: Deployment
metadata: {name: s3, namespace: lab-04-3}
spec:
  replicas: 1
  selector: {matchLabels: {app: s3}}
  template:
    metadata: {labels: {app: s3}}
    spec:
      containers:
      - name: versitygw
        image: versity/versitygw:v1.8.0
        args: ["--port", ":7070", "posix", "/data"]
        envFrom: [{secretRef: {name: s3-creds}}]
        ports: [{containerPort: 7070}]
        resources: {limits: {memory: 512Mi, cpu: "500m"}}
        volumeMounts: [{name: data, mountPath: /data}]
      volumes: [{name: data, emptyDir: {sizeLimit: 1Gi}}]
---
apiVersion: v1
kind: Service
metadata: {name: s3, namespace: lab-04-3}
spec:
  selector: {app: s3}
  ports: [{port: 7070, targetPort: 7070}]
---
apiVersion: batch/v1
kind: Job
metadata: {name: s3-mb, namespace: lab-04-3}
spec:
  backoffLimit: 6
  template:
    spec:
      restartPolicy: OnFailure
      containers:
      - name: mb
        image: amazon/aws-cli:2.37.0
        args: ["s3", "mb", "s3://velero", "--endpoint-url", "http://s3:7070"]
        env:
        - {name: AWS_DEFAULT_REGION, value: us-east-1}
        - name: AWS_ACCESS_KEY_ID
          valueFrom: {secretKeyRef: {name: s3-creds, key: ROOT_ACCESS_KEY_ID}}
        - name: AWS_SECRET_ACCESS_KEY
          valueFrom: {secretKeyRef: {name: s3-creds, key: ROOT_SECRET_ACCESS_KEY}}
EOF
kubectl apply -f s3.yaml
kubectl -n lab-04-3 rollout status deploy/s3 --timeout=180s
kubectl -n lab-04-3 wait --for=condition=Complete job/s3-mb --timeout=120s
kubectl -n lab-04-3 logs job/s3-mb
```

| Часть команды | Значение |
|---|---|
| `--port :7070 posix /data` | слушать порт 7070 и хранить бакеты в каталоге `/data` |
| `envFrom: secretRef` | передать ключи Secret как переменные окружения |
| `emptyDir: sizeLimit: 1Gi` | данные бакета живут, пока жив под; лимит 1 ГиБ |
| `resources.limits` | не больше 512 МиБ памяти и 0,5 ядра |
| `s3 mb s3://velero` | создать бакет `velero` запросом API S3 |
| `--endpoint-url http://s3:7070` | обращаться к шлюзу в кластере, а не к AWS |

Ожидаемый результат:

```
deployment "s3" successfully rolled out
job.batch/s3-mb condition met
make_bucket: velero
```

Разбор: шлюз готов, бакет `velero` создан. Job при необходимости повторяет попытки до 6 раз, пока шлюз не начнёт отвечать. Если под шлюза падает с `xattr check failed`, файловая система под `emptyDir` не поддерживает расширенные атрибуты, в которых VersityGW хранит метаданные объектов.

#### Шаг 3. Установить Velero

Команда ставит сервер Velero, агента на узлах и плагин AWS и указывает на шлюз как на хранилище S3.

```bash
~/lab/k8s/04-3/bin/velero install --namespace lab-04-3 \
  --provider aws \
  --image velero/velero:v1.18.4 \
  --plugins velero/velero-plugin-for-aws:v1.14.4 \
  --bucket velero \
  --secret-file ~/lab/k8s/04-3/credentials-velero \
  --backup-location-config \
    region=us-east-1,s3ForcePathStyle=true,s3Url=http://s3.lab-04-3.svc:7070 \
  --use-volume-snapshots=false \
  --use-node-agent \
  --wait
~/lab/k8s/04-3/bin/velero backup-location get --namespace lab-04-3
```

| Часть команды | Значение |
|---|---|
| `--namespace lab-04-3` | установить Velero в свой namespace, а не в `velero` |
| `--provider aws` | использовать плагин S3, он подходит и для других S3-хранилищ |
| `--bucket velero` | бакет, созданный на шаге 2 |
| `region=us-east-1` | регион подписи запросов; у VersityGW он такой по умолчанию |
| `s3ForcePathStyle=true` | адресовать бакет по пути, а не по имени хоста |
| `s3Url=http://s3…:7070` | адрес Service шлюза внутри кластера |
| `--use-volume-snapshots=false` | не создавать место для снапшотов: драйвер local-path их не умеет |
| `--use-node-agent` | поставить агента для копирования файлов томов |
| `--wait` | дождаться готовности сервера Velero и агента |

Ожидаемый результат:

```
Velero is installed! … Use 'kubectl logs deployment/velero -n lab-04-3' to view the status.
NAME      PROVIDER   BUCKET/PREFIX   PHASE       LAST VALIDATED   ACCESS MODE   DEFAULT
default   aws        velero          Available   …                ReadWrite     true
```

Разбор:

1. `Velero is installed!` — созданы CRD, сервер, агент и расположение бэкапов по умолчанию.
2. Фаза `Available` значит, что Velero достучался до бакета. При `Unavailable` смотрите лог `deployment/velero`, значение `s3Url` и регион (§5).
3. Флаг `--namespace` нужно повторять в каждой команде `velero`, иначе клиент ищет namespace `velero`.

#### Шаг 4. Создать данные для бэкапа

Команда создаёт namespace с PVC, ConfigMap и Deployment, который пишет файл на том. Аннотация пода включает копирование тома.

```bash
kubectl create ns lab-04-3-demo
kubectl apply -f - <<'EOF'
apiVersion: v1
kind: ConfigMap
metadata: {name: app-config, namespace: lab-04-3-demo}
data: {mode: demo}
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata: {name: data, namespace: lab-04-3-demo}
spec:
  accessModes: [ReadWriteOnce]
  resources: {requests: {storage: 100Mi}}
---
apiVersion: apps/v1
kind: Deployment
metadata: {name: writer, namespace: lab-04-3-demo}
spec:
  replicas: 1
  selector: {matchLabels: {app: writer}}
  template:
    metadata:
      labels: {app: writer}
      annotations:
        backup.velero.io/backup-volumes: data
    spec:
      containers:
      - name: app
        image: busybox:1.37
        command:
        - sh
        - -c
        - '[ -f /data/note.txt ] || echo "lab-04-3 data v1" > /data/note.txt; sleep infinity'
        volumeMounts: [{name: data, mountPath: /data}]
      volumes: [{name: data, persistentVolumeClaim: {claimName: data}}]
EOF
kubectl -n lab-04-3-demo rollout status deploy/writer --timeout=120s
kubectl -n lab-04-3-demo exec deploy/writer -- cat /data/note.txt
```

| Часть команды | Значение |
|---|---|
| `backup.velero.io/backup-volumes: data` | включить копирование тома `data` в бэкап |
| `[ -f /data/note.txt ] \|\| echo …` | записать файл, только если его ещё нет |
| `exec deploy/writer -- cat …` | прочитать файл из тома |

Ожидаемый результат:

```
deployment "writer" successfully rolled out
lab-04-3 data v1
```

Разбор: в томе лежит файл `note.txt` со строкой `lab-04-3 data v1`. Проверка «файл есть» в команде нужна, чтобы после восстановления под не перезаписал данные тома своими.

#### Шаг 5. Сделать бэкап

Команда создаёт бэкап namespace `lab-04-3-demo` и показывает его состав.

```bash
VEL=~/lab/k8s/04-3/bin/velero
$VEL backup create demo-1 --namespace lab-04-3 \
  --include-namespaces lab-04-3-demo --wait
$VEL backup describe demo-1 --namespace lab-04-3 --details \
  | grep -E '^Phase|Pod Volume|lab-04-3-demo/'
```

| Часть команды | Значение |
|---|---|
| `backup create demo-1` | создать бэкап с именем `demo-1` |
| `--include-namespaces` | взять объекты только этого namespace |
| `--wait` | дождаться завершения бэкапа |
| `describe --details` | показать список объектов и томов |
| `grep -E …` | оставить фазу, заголовок раздела томов и строку пода |

Ожидаемый результат:

```
Backup request "demo-1" submitted successfully.
…
Backup completed with status: Completed. …
Phase:  Completed
	Pod Volume Backups - kopia:
			lab-04-3-demo/writer-…: data (…)
```

Разбор:

1. `Completed` — все объекты и том сохранены. `PartiallyFailed` означало бы потерю части данных.
2. Раздел `Pod Volume Backups - kopia` со строкой пода и тома `data` подтверждает копирование данных тома. Если вместо него стоит `<none included>`, на поде забыта аннотация, и восстановление вернёт пустой PVC (§5).
3. Объекты и файлы тома лежат в бакете `velero` шлюза S3, а не в etcd.

#### Шаг 6. Потерять namespace и восстановить его

Команда удаляет namespace целиком, затем восстанавливает его из бэкапа и читает файл.

```bash
kubectl delete ns lab-04-3-demo --wait=true
kubectl get ns lab-04-3-demo
$VEL restore create demo-1-r1 --namespace lab-04-3 --from-backup demo-1 --wait
kubectl -n lab-04-3-demo get pvc,pod,cm
kubectl -n lab-04-3-demo rollout status deploy/writer --timeout=180s
kubectl -n lab-04-3-demo exec deploy/writer -- cat /data/note.txt
```

| Часть команды | Значение |
|---|---|
| `delete ns --wait=true` | удалить namespace и его объекты, включая PVC |
| `restore create --from-backup` | создать объекты из бэкапа |
| `get pvc,pod,cm` | убедиться, что вернулись PVC, под и ConfigMap |
| `exec … cat` | проверить, что данные тома вернулись |

Ожидаемый результат:

```
Error from server (NotFound): namespaces "lab-04-3-demo" not found
Restore completed with status: Completed. …
persistentvolumeclaim/data   Bound   …
pod/writer-…                 1/1     Running   …
configmap/app-config         1       …
configmap/kube-root-ca.crt   1       …
lab-04-3 data v1
```

Разбор:

1. После удаления namespace исчезли объекты и PVC. Local-path с политикой `Delete` (04-2) удалил и каталог тома на узле.
2. Velero создал PVC и добавил поду вспомогательный init-контейнер: он ждёт, пока агент вернёт файлы в том, и только потом пускает основной контейнер.
3. Файл `note.txt` со строкой `lab-04-3 data v1` вернулся: восстановление включает данные, а не только объекты.
4. PVC получил прежнее имя, а драйвер local-path выдал под него новый PV: при FSB данные возвращаются в новый том.

#### Шаг 7. Сравнить со снапшотом etcd

Команда снимает снапшот etcd (подробности — 10-2) и показывает его состав, чтобы сравнить с бэкапом Velero.

```bash
kubectl -n kube-system exec etcd-lab-control-plane -- etcdctl \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key \
  snapshot save /var/lib/etcd/lab-04-3.db
kubectl -n kube-system exec etcd-lab-control-plane -- \
  etcdutl snapshot status /var/lib/etcd/lab-04-3.db -w table
$VEL backup describe demo-1 --namespace lab-04-3 | grep -A1 -E '^(Namespaces|Total items)'
```

| Часть команды | Значение |
|---|---|
| `exec etcd-lab-control-plane -- etcdctl` | запустить клиент etcd в поде etcd |
| `--cacert --cert --key` | сертификаты клиента, как в 10-2 |
| `snapshot save …` | записать снапшот в каталог данных узла |
| `etcdutl snapshot status -w table` | показать ревизию, число ключей и размер файла |
| `grep -A1 -E '^(Namespaces\|Total items)'` | оставить охват и число объектов бэкапа Velero |

Ожидаемый результат (числа у вас другие):

```
Snapshot saved at /var/lib/etcd/lab-04-3.db
| HASH | REVISION | TOTAL KEYS | TOTAL SIZE |
| …    | …        | … (сотни)  | … МБ       |
Namespaces:
  Included:  lab-04-3-demo
--
Total items to be backed up:  …  (десятки)
Items backed up:              …
```

Разбор:

1. Снапшот etcd содержит все ключи кластера: все namespace, Secret, события и служебные объекты. Бэкап Velero содержит только объекты `lab-04-3-demo`.
2. В снапшоте нет данных тома: файл `note.txt` лежал на диске узла, а не в etcd.
3. Снапшот восстанавливают на остановленном control plane, заменив каталог данных (10-2), и он возвращает весь кластер на момент снимка. Velero возвращает один namespace на работающем кластере и даже в другом.

Файл снапшота лежит на узле, поэтому его удаляют сразу.

```bash
docker exec lab-control-plane rm -f /var/lib/etcd/lab-04-3.db
```

Команда удаляет файл снапшота из каталога etcd на узле. Вывода у неё нет.

**Итог.**

| Что узнали | Где видно |
|---|---|
| Velero хранит объекты и файлы томов в бакете S3, а не в etcd | бакет `velero` шлюза |
| Без аннотации (opt-in) данные тома не копируются | раздел `Pod Volume Backups` в `describe` |
| Восстановление возвращает namespace целиком вместе с данными | шаг 6, файл `note.txt` |
| Снапшот etcd охватывает кластер, Velero — выбранные объекты | шаг 7 |

**Уборка.** Удаляем Velero вместе с CRD, ClusterRoleBinding и его namespace, затем демо-namespace и файлы с ключами. Каталог `bin` с клиентом можно оставить.

```bash
VEL=~/lab/k8s/04-3/bin/velero
kubectl delete ns lab-04-3-demo --ignore-not-found
$VEL uninstall --namespace lab-04-3 --force
kubectl delete ns lab-04-3 --ignore-not-found
kubectl get crd | grep velero.io
rm -f ~/lab/k8s/04-3/credentials-velero ~/lab/k8s/04-3/s3-user ~/lab/k8s/04-3/s3-pass
```

Команда `velero uninstall` удаляет CRD, ClusterRoleBinding и сам namespace `lab-04-3`, поэтому следующая `delete ns` нужна только на случай сбоя. Команда `get crd` не должна вернуть ничего. Шлюз S3 исчезает вместе с namespace, а его данные лежали в `emptyDir` и удаляются с подом.

**Вопросы для самопроверки.**

1. Что вернул бы `velero restore`, если бы на поде не было аннотации тома?
2. Почему Velero не заменяет снапшот etcd, а снапшот etcd не заменяет Velero?
3. Почему бакет шлюза S3 внутри кластера не удовлетворяет правилу 3-2-1?

<details>
<summary>Ответы</summary>

1. Восстановление завершилось бы статусом `Completed`, объекты и PVC вернулись бы, но том оказался бы пустым: данные не копировались.
2. Снапшот etcd возвращает весь кластер целиком и нужен при потере control plane, но не содержит данных томов. Velero возвращает выбранные объекты и тома на живом кластере, но не восстановит сам кластер.
3. Бакет живёт в том же кластере и на том же узле, поэтому авария кластера уничтожает данные и бэкап одновременно. Нужно хранилище вне кластера.

</details>
