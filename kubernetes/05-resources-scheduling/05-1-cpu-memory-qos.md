Эта часть открывает модуль 05 и объясняет, во что превращаются числа в поле `resources`. Часть опирается на 01-2, где kubelet создаёт cgroup для каждого пода, и на 02-1, где разобраны код выхода 137 и пауза между перезапусками. Следующие части строятся на этом. Часть 05-2 меняет те же числа у работающего пода и ограничивает их квотами namespace. Планировщик (05-3) выбирает по ним узел, автомасштабирование (05-4) считает от requests, а вытеснение kubelet (05-5) выбирает жертву по превышению requests.

```
manifest: resources
   │
   ├─ scheduler ─────► сумма requests ≤ allocatable узла      (§2, место для пода)
   │
   └─ kubelet ──► CRI ──► runc ──► файлы cgroup контейнера

                     всё вместе ───► QoS-класс, oom_score_adj (§2, кого убить первым)
```

Схема 1. Путь чисел из манифеста: scheduler читает requests, kubelet и runc записывают значения в cgroup контейнера.

## 1. Какую задачу решают requests и limits

Два числа решают две разные задачи: куда поставить под и как не дать ему съесть чужое. Ниже разобрано, кто какое число читает и в каких единицах оно записано.

### Два числа для двух потребителей

**Request** (запрос) — сколько ресурса под просит: по нему scheduler выбирает узел, а ядро делит процессор между подами при споре. **Limit** (лимит) — потолок, который держит ядро: процессор сверх лимита замедляют, а процесс, который вышел за лимит памяти, убивают.

```yaml
resources:
  requests:            # сколько нужно поду; по этим числам планирует scheduler
    cpu: 250m          # 250 милликоров = 0,25 ядра
    memory: 256Mi      # мебибайты (2^20 байт)
  limits:              # потолок, который обеспечивает ядро
    cpu: "1"
    memory: 512Mi
```

Фрагмент манифеста контейнера: requests и limits задаются для каждого контейнера отдельно, под получает их сумму.

Таблица сводит роли двух чисел; подробности каждой строки разобраны в §2.

| Вопрос | Request | Limit |
|---|---|---|
| Планирование | scheduler суммирует | не учитывается |
| CPU | вес при споре за ядра | квота на каждые 100 мс |
| Память | в cgroup не пишется | жёсткий потолок |
| Превышение | можно взять больше, если есть свободное | CPU замедляют, память убивают |
| Не задан | считается как 0 | потолка нет |

### Единицы измерения

CPU измеряют в ядрах, память — в байтах, и у обеих величин есть суффиксы, которые легко перепутать.

- **Ядро** — `1` означает одно логическое ядро узла, а `0.5` и `500m` — одно и то же.
- **Милликор** (millicore) — одна тысячная ядра, суффикс `m`: `250m` равно четверти ядра.
- **Мебибайт** (mebibyte) — двоичная единица `Mi` = 2^20 байт; так же работают `Ki` и `Gi`.
- **Мегабайт** (megabyte) — десятичная единица `M` = 10^6 байт; так же работают `k` и `G`.

Разница заметна: `256Mi` — это 268435456 байт, а `256M` — 256000000, то есть на 4,6 % меньше. Для `1Gi` против `1G` разница составляет 7 %. Опечатка в одну букву молча меняет лимит, поэтому для памяти в манифестах используют только двоичные суффиксы.

### Что будет, если задана одна цифра

Если указан только limit, API-сервер подставляет request, равный limit. Поэтому лимит «на всякий случай» в 4Gi без request заставляет scheduler резервировать 4Gi на каждый под.

Если не указано ничего, request считается нулём, а потолка нет. Значения по умолчанию на уровне namespace подставляет LimitRange (05-2). Request больше limit API отклоняет сразу.

## 2. Как устроены requests и limits

Каждое число работает на своём уровне: request участвует в планировании и весе CPU, limit превращается в файл cgroup, а комбинация чисел определяет QoS-класс.

### Requests и планирование

Scheduler (01-1) ставит под на узел, если сумма requests уже размещённых подов плюс request нового не превышает allocatable (01-2 §4) — часть ресурсов узла, доступную подам.

```
allocatable = capacity − kube-reserved − system-reserved − порог eviction
```

Формула показывает, что от ёмкости узла вычитают резерв для системных служб и kubelet, а также порог вытеснения (05-5). Узлы стенда на kind резервов не имеют, поэтому allocatable равен capacity.

Реальную загрузку scheduler не смотрит. Узел, занятый на 5 %, может быть полным по requests, и тогда новый под остаётся в Pending. Обратная ошибка тоже случается: заниженные requests позволяют разместить на узле больше подов, чем он выдержит.

```
узел, allocatable памяти 16 ГиБ
├── под A  request 6 ГиБ   (потребляет 1 ГиБ)
├── под B  request 8 ГиБ   (потребляет 2 ГиБ)
└── свободно по requests: 2 ГиБ   ← под с request 4 ГиБ сюда не встанет,
                                     хотя реально свободно 13 ГиБ
```

Схема 2. Планирование идёт по requests: узел полон по бумагам при малом реальном потреблении.

Сообщение scheduler'а, когда места нет (запрос 20Gi на узлах по ~15,5Gi), читается по частям.

```
0/4 nodes are available: 1 node(s) had untolerated taint(s), 3 Insufficient memory.
no new claims to deallocate, preemption: 0/4 nodes are available: 4 Preemption is not helpful …
```

Control-plane отсеян taint'ом (05-3), у трёх worker'ов не хватает памяти, а вытеснение менее важных подов не поможет. Для пода с init-контейнерами и sidecar эффективный request считают по правилу из 02-1 §6.

**Limits при планировании не учитываются.** Под с request 64Mi и limit 40Gi запускается на узле с 15,5Gi. Сумма limits на узле может быть больше его памяти: это **overcommit** (превышение ёмкости), и `kubectl describe node` прямо пишет, что limits могут превышать 100 %.

### CPU: вес и квота

Процессор делят два независимых механизма ядра. На cgroup v2 (Ubuntu с 21.10, Manjaro, узлы kind; 01-2 §6) kubelet и runc записывают два файла в cgroup контейнера.

```
requests.cpu ─► cpu.weight ─► делит время между подами только при споре за ядра
limits.cpu ───► cpu.max ────► потолок всегда, даже если на узле свободны все ядра
```

Схема 3. Request влияет на вес, limit задаёт потолок; вес не ограничивает, пока ядра свободны.

**cpu.weight** (вес CPU) — число от 1 до 10000, по умолчанию 100; при нехватке ядер ядро делит время пропорционально весам. **cpu.max** (квота CPU) — пара «квота период» в микросекундах: за каждый период процессы контейнера вместе получают не больше квоты, а потом ждут следующего периода. Такое ожидание называют **throttling** (троттлинг, принудительная пауза). Период по умолчанию — 100 мс, поэтому лимит `500m` превращается в `50000 100000`.

Значения со стенда подтверждают это (Linux 6.18, containerd 2.3.1, лабораторная работа 1).

| Под | Ресурсы | Квота | Вес |
|---|---|---|---|
| Guaranteed | request = limit = 500m | 50000 100000 | 59 |
| Burstable | request 250m, лимита нет | max 100000 | 35 |
| BestEffort | ничего не задано | max 100000 | 1 |

Слово `max` вместо квоты значит «без ограничения». Вес строится в два шага: request переводится в «доли» (**cpu.shares**, привычные по cgroup v1: 1 ядро = 1024 доли), а потом доли — в вес v2. Формулу второго шага runc изменил, и от неё зависят числа в таблице.

```
shares = request в ядрах × 1024        500m → 512,  250m → 256,  без request → 2
старая формула: weight = 1 + (shares − 2) × 9999 / 262142     500m → 20,  250m → 10
новая формула:  weight = ceil(10^(L × (L + 125) / 612 − 7/34)), L = log2(shares)
                                                              500m → 59,  250m → 35
```

Старая формула давала одному ядру вес 39, хотя штатный вес cgroup v2 равен 100, а небольшие requests почти не различались: `100m` получало 4. Новая формула с runc 1.3.2 и crun 1.23 даёт одному ядру около 100, а `100m` — 17. Значения 59 и 35 на стенде говорят, что в узлах kind работает новая формула. На узле со старым runc те же манифесты дадут 20 и 10 (это расчёт по формуле, а не замер).

Отсюда практический вывод: число веса имеет смысл только в сравнении с соседями на одном узле. Сверять его с учебником или чужим кластером нет смысла. Новая формула отображает близкие requests в один вес (диапазон около `90m`–`109m` даёт 17), поэтому различать ими поды с разницей в несколько процентов не получится.

### Память: потолок и OOM

**memory.max** — файл cgroup с потолком памяти контейнера; он равен `limits.memory`. Когда контейнер приближается к потолку, ядро сначала пытается освободить память внутри cgroup: сбрасывает кэш файлов и выгружает то, что можно. Если не хватает и этого, срабатывает OOM killer (убийца процессов при нехватке памяти, 02-1 §4) этой cgroup.

Kubelet видит, что контейнер убит, и записывает в его состояние `reason: OOMKilled` с кодом 137. Код равен 128 плюс номер сигнала SIGKILL, то есть 9. Дальше kubelet перезапускает контейнер по `restartPolicy` с растущей паузой (02-1 §2).

Request памяти в cgroup не попадает: файл `memory.min` остаётся нулём, потому что функция Memory QoS по умолчанию выключена (§6). Request нужен scheduler'у и kubelet при вытеснении (05-5). У контейнера без limit потолка нет, и он может занять всю память узла.

**memory.oom.group** — переключатель cgroup: если он равен 1, при OOM ядро убивает все процессы контейнера, а не один самый «тяжёлый». Kubelet на cgroup v2 с версии 1.32 включает его для каждого контейнера (на стенде 1.36 — `oom.group=1` у всех подов). Раньше в контейнере с PID 1 (shell или супервизор) и воркерами OOM убивал одного воркера, контейнер жил «полуживым», а `OOMKilled` в статусе не появлялся. Старое поведение возвращает поле `singleProcessOOMKill: true` в конфиге kubelet, но нужно оно редко.

### Что входит в лимит памяти

В потолок `memory.max` входит не только куча приложения. Контейнеру засчитывают всё, что ядро выделило ради него. Это анонимная память процессов и **page cache** (кэш страниц, то есть файлы, которые контейнер читал и писал). Сюда же входит память ядра (стеки потоков, буферы сокетов) и tmpfs, включая `emptyDir` с `medium: Memory`.

Page cache ядро вытесняет перед OOM, поэтому использование «почти на лимите» у сервиса с активным диском ещё не беда. Метрика, по которой kubelet и `kubectl top` судят о памяти, — **working set** (рабочий набор): использование минус неактивный файловый кэш. Именно её сравнивают с лимитом, когда ищут риск OOM.

### QoS-классы

QoS-класс (01-2 §3) — метка пода, которую kubelet выводит из `resources` всех контейнеров и которая определяет, кого убьют первым при нехватке памяти на узле. Класс не задаётся полем: его считают сами, и его видно в `status.qosClass`.

- **Guaranteed** — у каждого контейнера (включая init) request равен limit и по CPU, и по памяти.
- **Burstable** — что-то задано, но условия Guaranteed не выполнены.
- **BestEffort** — не задано ничего.

Если заданы ресурсы уровня пода (05-2), класс определяют они, а не контейнеры. Класс влияет на три вещи: на значение **oom_score_adj**, на ветку cgroup и, косвенно, на порядок вытеснения kubelet (05-5).

**oom_score_adj** — поправка к «оценке виновности» процесса, которую ядро учитывает, когда память кончилась у всего узла: чем число больше, тем раньше убьют. Значения со стенда подтверждают формулу kubelet.

| Класс | oom_score_adj | Порядок убийства |
|---|---|---|
| Guaranteed | −997 | последним |
| Burstable | от 3 до 999 | в середине |
| BestEffort | 1000 | первым |

Для Burstable kubelet считает `1000 − 1000 × request / память узла` и ограничивает результат числами 3 и 999, а документация Kubernetes называет нижней границей 2. На стенде request 128Mi дал 992, а 64Mi — 996. Чем меньше request относительно потребления, тем раньше убьют.

```
/sys/fs/cgroup/kubepods.slice/
├── kubepods-pod<uid>.slice                  Guaranteed: прямо под kubepods
├── kubepods-burstable.slice/
│   └── kubepods-burstable-pod<uid>.slice    Burstable
└── kubepods-besteffort.slice/
    └── kubepods-besteffort-pod<uid>.slice   BestEffort
```

Схема 4. Ветка cgroup зависит от класса; внутри каждого пода лежат cgroup его контейнеров (на стенде с префиксом `kubelet-`, 01-2 §4).

Класс не равен защите от OOM своего контейнера. Лимит памяти срабатывает по cgroup независимо от класса и от свободной памяти узла, а класс работает только при нехватке памяти всего узла (§5).

## 3. Как управлять ресурсами

Управление сводится к трём решениям: какие числа поставить, как настроить рантайм под эти числа и где остальное. Подбор чисел по данным — основа, а детали живут в соседних частях.

### Выбор значений

Для памяти request равен limit, для CPU request обязателен, а limit ставят по осознанной причине. Память несжимаема: её нельзя «притормозить», поэтому поду нужна твёрдая граница, и равенство request и limit даёт предсказуемое место на узле. CPU сжимаем, и квота замедляет процессы (§5), так что limit по CPU нужен реже.

Класс при такой политике получается Burstable, и это нормально. По памяти под защищён: не выходит за свой request, а значит, не первый кандидат на вытеснение. Guaranteed нужен в основном для выделенных ядер (§6) и для критичных подов.

Вторая вещь — брать числа из измерений. Request CPU ставят около 95-го процентиля потребления плюс запас, request и limit памяти — около пика working set плюс запас. Измеряют через `kubectl top` и метрики cgroup (§4); рекомендации по этим числам даёт VPA (05-4).

Причины ставить limit CPU все связаны с изоляцией: жёсткая мультиарендность, предсказуемость для бенчмарков, лицензирование по ядрам, CPU Manager (§6). Защиту от «шумного соседа» даёт вес, то есть request, а не квота.

### Рантайм под лимит

Рантайм приложения не знает про квоту и размеряет пулы потоков по ядрам узла. Команда `nproc` в контейнере с лимитом `500m` показывает 12 — все ядра хоста стенда, потому что `nproc` читает маску процессора, а не cgroup. Приложение, которое создаёт поток на ядро, получает 12 потоков на квоту в полядра и троттлится ещё сильнее.

- **Go** — до версии 1.25 `GOMAXPROCS` равнялся числу ядер хоста (помогала библиотека `automaxprocs`); с 1.25 рантайм учитывает CPU-лимит cgroup (но не request), если `GOMAXPROCS` не задан вручную.
- **JVM** — учитывает cgroup начиная с 10-й версии; число задают явно флагом `-XX:ActiveProcessorCount`.
- **Python** — `os.cpu_count()` возвращает ядра хоста; число воркеров gunicorn или uvicorn задают явно.

Память требует той же дисциплины. Куча JVM по умолчанию занимает четверть лимита, и её поднимают флагом `-XX:MaxRAMPercentage` до 70–75 %, оставляя место потокам и нативной памяти. В Go мягкий потолок для сборщика мусора задаёт `GOMEMLIMIT`, в Node.js — `--max-old-space-size`. Иначе процесс упирается в `memory.max`, и убивает его ядро, а не сборщик мусора.

### Что настраивают на уровне пода и namespace

Остальное управление вынесено в 05-2. Там разобраны изменение ресурсов работающего пода без перезапуска (in-place resize), ресурсы уровня пода и подкачка (swap). Там же значения по умолчанию LimitRange, квоты ResourceQuota и ephemeral storage. Здесь важно одно ограничение: при изменении ресурсов QoS-класс пода измениться не может.

## 4. Как увидеть состояние ресурсов

Состояние видно на трёх уровнях: как scheduler видит узел, что реально потребляют поды и что показывают файлы ядра. Отдельно разберём троттлинг и давление.

### Сколько занято по requests

Команда `kubectl describe node <узел>` печатает раздел `Allocated resources`: сумму requests и limits всех подов узла в ядрах, байтах и процентах от allocatable. Это именно то, что видит scheduler. Если процент requests близок к 100, новый под не встанет на узел при любом реальном потреблении, а сумма limits выше 100 % означает overcommit.

### Реальное потребление

Команда `kubectl top pod` или `kubectl top node` показывает CPU и память подов, собранные metrics-server (стенд 00-1). Это среднее за окно около 15 секунд, и по нему не видны ни пики памяти, ни троттлинг внутри 100-миллисекундного периода. Память в `top` — это working set (§2).

### Файлы cgroup контейнера

Точные числа читают прямо из cgroup: внутри контейнера путь `/sys/fs/cgroup/` относится к его собственной группе. Для разбора ресурсов нужны семь файлов.

- `cpu.max` — квота и период.
- `cpu.weight` — вес, полученный из request.
- `cpu.stat` — счётчики использования и троттлинга.
- `memory.max` — потолок памяти.
- `memory.current` — текущее потребление, включая кэш.
- `memory.events` — счётчики событий памяти, среди них `oom_kill`.
- `memory.oom.group` — режим убийства всей группы.

Узлы kind и обычные узлы различаются только префиксом пути к cgroup пода. На обычном узле это `/sys/fs/cgroup/kubepods.slice/…` (схема 4), а на узле kind перед ним стоят `docker-…scope` и имена с префиксом `kubelet-`.

### Троттлинг

Троттлинг читают из `cpu.stat`: `nr_periods` — сколько периодов контейнер был активен, `nr_throttled` — в скольких из них упёрся в квоту, `throttled_usec` — сколько микросекунд простоял. В Prometheus тот же учёт даёт cAdvisor: доля `container_cpu_cfs_throttled_periods_total` от `container_cpu_cfs_periods_total`.

Есть ловушка с уровнем учёта. Если лимит задан у всех контейнеров, kubelet ставит квоту и на cgroup пода, и на каждый контейнер. На стенде основной учёт троттлинга оказался на уровне пода, а счётчик контейнера почти не вырос.

```
cgroup пода        cpu.max 20000 100000   nr_periods 27   nr_throttled 19   ← основной учёт
 ├─ контейнер app  cpu.max 20000 100000   nr_periods 22   nr_throttled 2    ← почти пусто
 └─ контейнер pause  cpu.max max          nr_periods 0                      ← без лимита
```

Схема 5. Одна и та же квота в двух местах: если метрика контейнера «почти ноль», проверьте cgroup пода (лабораторная работа 3, шаг 3). Цифры сняты на Linux 6.18; на другом ядре распределение учёта может отличаться.

### Давление PSI

**PSI** (Pressure Stall Information, информация о давлении) — счётчики ядра, которые показывают, какую долю времени задачи ждали ресурс: процессор, память или диск. Для каждой cgroup ядро ведёт файлы `cpu.pressure`, `memory.pressure` и `io.pressure`. Нужны cgroup v2 и ядро 4.20 или новее с `CONFIG_PSI=y`; если PSI собран, но выключен, его включают параметром загрузки `psi=1`.

Строка в файле имеет вид `some avg10=<доля> avg60=<доля> avg300=<доля> total=<мкс>`. Слово `some` значит, что ждала хотя бы одна задача, а вторая строка `full` — что ждали все задачи группы. В `cpu.pressure` у cgroup строка `full` есть с ядра 5.13. Числа `avg` — средняя доля времени ожидания за 10, 60 и 300 секунд в процентах, а `total` — накопленное время ожидания в микросекундах.

Функция kubelet KubeletPSI прошла путь от alpha в 1.33 и beta в 1.34 до GA в 1.36. Kubelet отдаёт эти данные в Summary API и метриками `container_pressure_*` на `/metrics/cadvisor`, например `container_pressure_cpu_waiting_seconds_total`, а сами файлы доступны всегда. Рост `memory.pressure` показывает нехватку памяти раньше, чем OOM убьёт процесс, а `cpu.pressure` — ожидание ядер при споре. Это отдельный сигнал от квоты: для троттлинга основным остаётся `cpu.stat`. Использование PSI в мониторинге разобрано в 11-4.

## 5. Что ломается и как найти причину

Четыре типичные поломки дают разные симптомы: убитый контейнер, медленный сервис, зависший Pending и убитый под при пустой памяти узла. Для каждой есть порядок поиска.

### OOMKilled и код 137

Контейнер перезапускается, в `lastState` стоит `reason: OOMKilled` и `exitCode: 137`: процесс вышел за `memory.max`. Порядок поиска такой.

1. `kubectl describe pod` → `Last State: Terminated, Reason: OOMKilled` или поле `lastState` в `-o yaml`.
2. Сравнить `kubectl top pod` (working set) с лимитом памяти.
3. Прочитать журнал ядра узла: `dmesg` или `journalctl -k`, строка `Memory cgroup out of memory`.
4. Проверить рантайм: размер кучи JVM, `GOMEMLIMIT`, число воркеров (§3).

События Kubernetes OOM не создают: в `kubectl get events` видно только `BackOff restarting failed container`. Логи тоже не помогают: процесс, убитый SIGKILL, ничего не успевает записать, а `logs --previous` между перезапусками иногда возвращает ошибку. Если повтор причины не даёт, а статус сменился на `CrashLoopBackOff`, это та же причина (02-1 §2). Решение — поднять лимит до реального пика или найти утечку, но не снимать лимит памяти.

Код 137 без `OOMKilled` означает другое: процесс не успел завершиться за grace period или его убила liveness-проба (02-1 §4).

### Две разные нехватки памяти

OOM внутри контейнера и OOM узла — разные события. Первый срабатывает по cgroup, когда контейнер вышел за свой `memory.max`, даже если на узле свободны гигабайты. Класс пода и `oom_score_adj` на него не влияют.

Второй случается, когда память кончилась у всего узла. Сначала kubelet пытается выселить поды по давлению на память (05-5). Если он не успел, глобальный OOM killer ядра убивает процессы по `oom_score_adj`: сначала BestEffort, затем Burstable с малым request, Guaranteed последними. Журнал ядра различает эти случаи: для контейнера строка начинается с `Memory cgroup out of memory`, а для узла — с `Out of memory`.

### Задержки растут, а загрузка CPU низкая

Это троттлинг: квота кончилась в середине 100-миллисекундного периода, и контейнер стоит до следующего. Квота общая на все потоки, поэтому они исчерпывают её быстро. Возьмём лимит в 1 CPU и четыре потока, которые проснулись одновременно. Они тратят 100 мс квоты за 25 мс, а следующие 75 мс стоят, даже если на узле простаивают десять ядер.

```
период 100 мс:   0          25                       100
лимит 1 CPU      ├──────────┤░░░░░░░░░░░░░░░░░░░░░░░░┤
4 потока         │ работают │ стоят: квота кончилась │ → следующий период
```

Схема 6. Квота тратится по всем потокам вместе: четыре потока выбирают её за четверть периода и ждут остальное.

Среднее потребление при этом низкое: за минуту набирается 20–25 %, а хвост задержек (p99) растёт. Замер на стенде: «запрос» — около 100 мс чистого CPU (цикл на Python), под без лимита и под с лимитом.

| Опыт | Без CPU-лимита, мс | С CPU-лимитом, мс |
|---|---|---|
| 1 запрос, лимит 200m | 93–100 | 414–512 |
| 4 запроса одновременно, лимит 500m | 97–102 | 798–1100 |

Порядок цифр совпадает с расчётом: 100 мс CPU при квоте 20 мс на период занимают пять периодов, то есть около 420 мс. Четыре запроса по 100 мс при квоте 50 мс занимают восемь периодов, то есть около 750 мс. Метрики контейнера могут при этом молчать (§4), поэтому смотрят `cpu.stat` пода.

Решение зависит от условий. Обычно снимают CPU-лимит и оставляют request. Если лимит нужен, его поднимают выше пиков, а число воркеров считают по лимиту, а не по ядрам узла. Один и тот же сервис с лимитом ведёт себя по-разному на узле с 4 и с 32 ядрами, если число потоков определяет рантайм.

### Pending при низкой загрузке узлов

Статус `Pending` с событием `Insufficient cpu` или `Insufficient memory` при загрузке узлов 10 % значит, что узлы полны по requests, а не по потреблению. Смотрят `Allocated resources` в `describe node` (§4), находят поды с завышенными requests и снижают их по измерениям. Добавлять узлы из-за завышенных requests дорого и не помогает.

## 6. Пределы и значения по умолчанию

Ниже собраны числа этой части и две возможности, которые на стенде 1.36 выключены или не нужны: Memory QoS и выделенные ядра. Значения взяты со стенда или из документации Kubernetes 1.36.

### Числа и умолчания

- Период квоты CPU — 100 мс; квота записывается в микросекундах, лимит `500m` даёт `50000 100000`.
- Вес CPU — от 1 до 10000; у контейнера без request доли равны 2, а вес 1.
- `oom_score_adj` — −997 у Guaranteed, от 3 до 999 у Burstable, 1000 у BestEffort.
- Код выхода при OOM — 137; события OOM Kubernetes не создаёт.
- `memory.min` — 0, request памяти в cgroup не попадает.
- `memory.oom.group` — 1 у всех контейнеров на cgroup v2.
- Окно `kubectl top` — около 15 секунд (разрешение metrics-server по умолчанию).

### Memory QoS

**Memory QoS** — функция kubelet, которая записывает память пода в файлы cgroup v2. Из request получается `memory.min` — память, которую ядро не отбирает. Между request и limit встаёт `memory.high` — порог, после которого ядро притормаживает выделение вместо убийства. Он равен `request + memoryThrottlingFactor × (limit − request)`, а множитель в 1.36 по умолчанию равен 0,9.

В 1.36 она остаётся alpha и выключена по умолчанию, поэтому на стенде `memory.min` равен нулю. В 1.37 гейт становится beta и включён, но без настройки файлы не меняются. Множитель там по умолчанию снят, а `memory.min` и `memory.low` пишет только политика `memoryReservationPolicy: TieredReservation`. Для функции нужно ядро 5.9 или новее (01-2 §6). Её цель — сделать поведение при нехватке памяти менее резким: ядро сначала замедляет контейнер у порога, а убивает только если замедление не помогло.

### Выделенные ядра и NUMA

По умолчанию поды делят все ядра узла, и вес только распределяет время. Политика **CPU Manager** `static` закрепляет за подами Guaranteed с целым числом ядер (request = limit, например `2`) выделенные ядра. Остальные поды делят оставшиеся. Это нужно для задач, чувствительных к переключению контекста и кэшу процессора.

К 1.36 в GA вышли три опции политики. Опция `full-pcpus-only` (с 1.33) выдаёт только целые физические ядра. Опция `strict-cpu-reservation` (с 1.35) не пускает обычные поды на резервные ядра. Опция `prefer-align-cpus-by-uncorecache` (с 1.36) размещает под в пределах одного блока кэша L3.

**Memory Manager** (GA в 1.32) с политикой `Static` привязывает память Guaranteed-подов к тем же NUMA-узлам. Обе политики настраиваются в KubeletConfiguration узла и несовместимы с изменением ресурсов на месте (05-2).

### Лабораторная работа 1. QoS-классы, requests и их cgroup

**Цель.** Создать поды трёх QoS-классов, прочитать их файлы cgroup и убедиться, что scheduler планирует по requests, а не по limits.

**Что понадобится.**

- Стенд 00-1 и namespace `lab-05-1` из подготовки.
- Образ `python:3.12-slim`.
- Доступ `docker exec` к узлам kind.
- Около 20 минут.

**Схема опыта.**

```
Pod guaranteed (req = lim)   ─┐
Pod burstable  (req, без CPU) ├─► kubectl exec: cpu.max, cpu.weight, memory.*, oom_score_adj
Pod besteffort (ничего)      ─┘
kubectl describe node         ─► Allocated resources
Pod big (request 20Gi), Pod greedy (limit 40Gi) ─► что делает scheduler
```

Схема 7. Три пода трёх классов дают три набора файлов cgroup; два пода с крайними числами показывают, что планирует scheduler.

#### Шаг 1. Создать три пода

Команда создаёт три пода: Guaranteed (request равен limit), Burstable (request есть, CPU-лимита нет) и BestEffort (без ресурсов), и ждёт их готовности.

```bash
kubectl apply -f - <<'EOF'
apiVersion: v1
kind: Pod
metadata: {name: guaranteed}
spec:
  containers:
  - name: app
    image: python:3.12-slim
    command: ["sleep", "infinity"]
    resources:
      requests: {cpu: 500m, memory: 256Mi}
      limits:   {cpu: 500m, memory: 256Mi}
---
apiVersion: v1
kind: Pod
metadata: {name: burstable}
spec:
  containers:
  - name: app
    image: python:3.12-slim
    command: ["sleep", "infinity"]
    resources:
      requests: {cpu: 250m, memory: 128Mi}
      limits:   {memory: 256Mi}
---
apiVersion: v1
kind: Pod
metadata: {name: besteffort}
spec:
  containers:
  - name: app
    image: python:3.12-slim
    command: ["sleep", "infinity"]
EOF
kubectl wait --for=condition=Ready pod --all --timeout=90s
```

| Часть команды | Значение |
|---|---|
| `requests: {cpu: 500m, memory: 256Mi}` | запрос в полядра и 256 МиБ |
| `limits: {memory: 256Mi}` | только потолок памяти, CPU-лимита нет |
| `command: ["sleep", "infinity"]` | контейнер работает, ничего не делая |
| `wait --for=condition=Ready pod --all` | ждать готовности всех подов namespace |
| `--timeout=90s` | не ждать дольше 90 секунд (образ тянется при первом запуске) |

Результат:

```
pod/guaranteed created
pod/burstable created
pod/besteffort created
pod/guaranteed condition met
pod/burstable condition met
pod/besteffort condition met
```

Разбор: `condition met` у каждого пода значит, что условие `Ready` получено, и можно читать файлы cgroup.

#### Шаг 2. Прочитать класс и файлы cgroup

Цикл печатает для каждого пода QoS-класс из статуса и значения его cgroup: квоту, вес, потолок и request памяти. Затем он выводит режим OOM, поправку `oom_score_adj` и число ядер.

```bash
R='echo cpu.max=$(cat /sys/fs/cgroup/cpu.max)'
R+=' cpu.weight=$(cat /sys/fs/cgroup/cpu.weight)'
R+=' memory.max=$(cat /sys/fs/cgroup/memory.max)'
R+=' memory.min=$(cat /sys/fs/cgroup/memory.min)'
R+='; echo oom.group=$(cat /sys/fs/cgroup/memory.oom.group)'
R+=' oom_score_adj=$(cat /proc/1/oom_score_adj) nproc=$(nproc)'
for p in guaranteed burstable besteffort; do
  echo "== $p qos=$(kubectl get pod $p -o jsonpath='{.status.qosClass}')"
  kubectl exec $p -- sh -c "$R"
done
```

| Часть команды | Значение |
|---|---|
| `R='…'`, `R+='…'` | собрать команду для контейнера из частей |
| `$(cat /sys/fs/cgroup/cpu.max)` | прочитать файл cgroup контейнера |
| `/proc/1/oom_score_adj` | поправка процесса с PID 1 |
| `$(nproc)` | число ядер, которое видит контейнер |
| `jsonpath='{.status.qosClass}'` | класс, который вычислил kubelet |

Результат:

```
== guaranteed qos=Guaranteed
cpu.max=50000 100000 cpu.weight=59 memory.max=268435456 memory.min=0
oom.group=1 oom_score_adj=-997 nproc=12
== burstable qos=Burstable
cpu.max=max 100000 cpu.weight=35 memory.max=268435456 memory.min=0
oom.group=1 oom_score_adj=992 nproc=12
== besteffort qos=BestEffort
cpu.max=max 100000 cpu.weight=1 memory.max=max memory.min=0
oom.group=1 oom_score_adj=1000 nproc=12
```

Разбор:

1. `cpu.max=50000 100000` — CPU-лимит есть только у guaranteed: 50 мс на каждые 100 мс. Остальные поды без квоты (`max`).
2. `cpu.weight` 59, 35 и 1 — веса от requests 500m, 250m и ничего. Это значения новой формулы runc (§2). Со старым runc ожидаются 20, 10 и 1 (расчёт, не замер).
3. `memory.max=268435456` — потолок 256Mi у guaranteed и burstable; у BestEffort потолка нет.
4. `memory.min=0` у всех: request памяти в cgroup не попал (§2).
5. `oom.group=1` у всех трёх — OOM убьёт контейнер целиком.
6. `oom_score_adj`: −997, 992, 1000. Для burstable проверьте расчёт: 1000 − 1000 × 128Mi / 15933Mi ≈ 992.
7. `nproc=12` у всех, лимит CPU на него не влияет.

Версию runc в узле показывает команда `docker exec lab-worker runc --version`: образ узла kind сам собирает runc и кладёт его в `/usr/local/sbin/runc`. Значения 59 и 35 соответствуют runc 1.3.2 или новее.

#### Шаг 3. Увидеть, сколько занято по requests

Команда печатает раздел `Allocated resources` узла, на котором работает burstable. Это то, что видит scheduler.

```bash
kubectl describe node $(kubectl get pod burstable -o jsonpath='{.spec.nodeName}') \
  | sed -n '/Allocated resources/,/Events/p'
```

| Часть команды | Значение |
|---|---|
| `kubectl get pod burstable -o jsonpath=…` | имя узла, на котором работает под |
| `describe node` | подробное описание узла |
| `sed -n '/Allocated resources/,/Events/p'` | оставить только раздел от заголовка до `Events` |

Результат (на этом узле оказались burstable и системные поды):

```
  Resource           Requests    Limits
  cpu                350m (2%)   100m (0%)
  memory             178Mi (1%)  306Mi (1%)
```

Разбор:

1. Requests CPU 350m — сумма requests подов узла, среди них 250m у burstable.
2. Limits CPU 100m меньше requests: в сумму limits входят только поды, у которых лимит CPU задан.
3. Проценты считаются от allocatable. На kind он равен capacity (12 ядер и 16315248Ki), в реальном кластере allocatable меньше.

#### Шаг 4. Планирование идёт по requests

Команда создаёт два пода. Первому нужно 20Gi памяти по request, больше, чем есть на любом узле. Второй просит 64Mi, а лимит у него 40Gi.

```bash
kubectl apply -f - <<'EOF'
apiVersion: v1
kind: Pod
metadata: {name: big}
spec:
  containers:
  - name: app
    image: python:3.12-slim
    command: ["sleep", "infinity"]
    resources:
      requests: {memory: 20Gi}
---
apiVersion: v1
kind: Pod
metadata: {name: greedy}
spec:
  containers:
  - name: app
    image: python:3.12-slim
    command: ["sleep", "infinity"]
    resources:
      requests: {memory: 64Mi}
      limits:   {memory: 40Gi}
EOF
sleep 5
kubectl get pod big greedy
kubectl get events --field-selector involvedObject.name=big,reason=FailedScheduling \
  -o jsonpath='{.items[0].message}{"\n"}'
```

| Часть команды | Значение |
|---|---|
| `apply -f -` | создать оба пода из манифеста на стандартном вводе |
| `requests.memory: 20Gi` | запрос больше памяти любого узла |
| `limits.memory: 40Gi` | лимит больше памяти любого узла |
| `--field-selector reason=FailedScheduling` | события, где scheduler не нашёл узел |
| `.items[0].message` | текст первого такого события |

Результат:

```
pod/big created
pod/greedy created
NAME     READY   STATUS    RESTARTS   AGE
big      0/1     Pending   0          5s
greedy   1/1     Running   0          5s
0/4 nodes are available: 1 node(s) had untolerated taint(s), 3 Insufficient memory.
no new claims to deallocate, preemption: 0/4 nodes are available: 4 Preemption is not …
```

Разбор:

1. `big` в Pending: request 20Gi не помещается ни на один из трёх worker'ов.
2. `1 node(s) had untolerated taint(s)` — control-plane отсеян taint'ом.
3. `3 Insufficient memory` — у трёх worker'ов не хватает памяти для request.
4. `greedy` в Running: лимит 40Gi больше памяти узла, но scheduler смотрит на request 64Mi и ставит под. Это overcommit.

**Итог.**

| Что узнали | Где видно |
|---|---|
| Класс пода вычисляет kubelet из requests и limits | `qosClass` |
| Request CPU превращается в вес, limit — в квоту | `cpu.weight`, `cpu.max` |
| Request памяти в cgroup не попадает | `memory.min=0` |
| `oom_score_adj` растёт от Guaranteed к BestEffort | −997, 992, 1000 |
| Scheduler считает requests и не смотрит на limits | `Pending` у big, `Running` у greedy |

**Уборка.** Команда удаляет все поды работы; namespace остаётся для следующих работ.

```bash
kubectl delete pod guaranteed burstable besteffort big greedy --now
```

**Вопросы для самопроверки.**

1. Почему у guaranteed `cpu.weight=59`, а у burstable с request 250m — 35?
2. Какой класс получит под, если у одного контейнера request равен limit, а у второго задан только request?
3. Почему под `greedy` запустился, хотя его limit больше памяти узла?

<details>
<summary>Ответы</summary>

1. Вес растёт вместе с request (500m и 250m дают 512 и 256 долей) и считается по формуле runc. Абсолютные числа зависят от версии runc, в сравнении у одного узла важен порядок.
2. Burstable: класс Guaranteed требует равенства request и limit у каждого контейнера по CPU и по памяти.
3. Scheduler суммирует requests и не учитывает limits. Сумма limits на узле может превышать память (overcommit).

</details>

### Лабораторная работа 2. OOMKilled

**Цель.** Вызвать убийство контейнера по лимиту памяти и доказать причину по статусу и журналу ядра.

**Что понадобится.**

- Стенд 00-1 и namespace `lab-05-1` из подготовки.
- Образ `python:3.12-slim`.
- Доступ `docker exec` к узлам kind.
- Около 15 минут.

**Схема опыта.**

```
Pod oom: limit 128Mi, процесс выделяет 200 MiB
   │
   ├─► ядро: Memory cgroup out of memory ─► SIGKILL, код 137
   ├─► kubelet: lastState = OOMKilled ─► перезапуск ─► BackOff
   └─► где смотреть: kubectl lastState  и  dmesg узла (не events)
```

Схема 8. Ядро убивает процесс, kubelet записывает причину в `lastState`, а события показывают только перезапуски.

#### Шаг 1. Создать под, который просит больше лимита

Команда создаёт под с лимитом 128Mi, процесс которого занимает 200 MiB, ждёт сорок пять секунд и читает статус.

```bash

apiVersion: v1
kind: Pod

spec:
  containers:
  - name: app
    image: python:3.12-slim

    - python
    - -c
    - |
      import time
      print('allocating 200 MiB', flush=True)
      b = bytearray(200*1024*1024)
      time.sleep(3600)
    resources:
      requests: {memory: 64Mi}
      limits:   {memory: 128Mi}
EOF
sleep 45
kubectl get pod oom
kubectl get pod oom -o jsonpath='{.status.containerStatuses[0].lastState}{"\n"}'
```

| Часть команды | Значение |
|---|---|
| `bytearray(200*1024*1024)` | выделить и заполнить нулями 200 MiB |
| `limits: {memory: 128Mi}` | потолок ниже, чем просит процесс |
| `sleep 45` | дать контейнеру несколько раз упасть и перезапуститься |

**Итог.**

|---|---|

```

**Вопросы для самопроверки.**

1. Почему в `get events` нет события об OOM?
2. Чем строка `Memory cgroup out of memory` отличается от `Out of memory`?
3. Что покажет `oom_score_adj` в журнале, если у пода request 128Mi вместо 64Mi?

<details>
<summary>Ответы</summary>

1. Kubernetes не получает событие от ядра: kubelet лишь видит, что контейнер завершён, и записывает причину в статус контейнера. Событие `BackOff` относится к перезапускам.
2. Первая строка значит, что процесс убит из-за лимита cgroup, вторая — из-за нехватки памяти всего узла (§5).
3. 992: формула `1000 − 1000 × request / память узла` для 128Mi дала это значение на шаге 2 работы 1.

</details>

### Лабораторная работа 3. Троттлинг CPU

**Цель.** Измерить, во сколько раз CPU-лимит замедляет код, и найти троттлинг в `cpu.stat` контейнера и пода.

**Что понадобится.**

- Стенд 00-1 и namespace `lab-05-1` из подготовки.
- Образ `python:3.12-slim`.
- Каталог `~/lab/k8s/05-1/` для скрипта нагрузки.
- kubectl 1.32 или новее: шаг 4 использует подресурс `resize` (05-2).
- Около 25 минут.

**Схема опыта.**

```
Pod cpu-free     (request 200m, лимита CPU нет)  ─┐
Pod cpu-limited  (request = limit = 200m)         ├─► work.py: ~100 мс CPU на «запрос»

Схема 9. Два пода с одним кодом: разница во времени ответа и в счётчиках показывает цену квоты.

#### Шаг 1. Создать поды и тестовую нагрузку

#### Шаг 3. Посмотреть cgroup пода на узле

#### Шаг 4. Поднять лимит на месте и запустить четыре запроса сразу
