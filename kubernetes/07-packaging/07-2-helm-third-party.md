## 1. Какую задачу решает чужой чарт

Чужой чарт экономит недели работы: базы, брокеры, мониторинг и операторы уже описаны в нём объектами Kubernetes. Но вместе с чартом вы получаете чужие решения и зависимость от чужих серверов, и вторую часть часто замечают поздно.

### Готовое решение вместо своих манифестов

Свой чарт пишут для своего приложения (07-1), а всё остальное ставят чужими. В чарте PostgreSQL уже есть StatefulSet, Service, проверки готовности, настройки безопасности и параметры хранилища. Вы не пишете сотни строк YAML, а передаёте несколько значений.

Цена этого удобства в том, что часть решений принята за вас. Чарт решает, какой образ запускать, какой пароль задать, сохранять ли диск при удалении и какие дополнительные объекты создать. Эти решения лежат в шаблонах и значениях по умолчанию, поэтому читать их нужно до установки.

### Цена зависимости

От чужого чарта зависят сразу три вещи, и каждая может исчезнуть. Первая — сам чарт: автор может сменить структуру значений, забросить проект или удалить версию из репозитория. Вторая — реестр образов, на которые ссылается чарт: образ может переехать, стать платным или перестать обновляться. Третья — тег образа: если он плавающий, как `latest`, завтра под запустит другую версию программы.

```
ваш релиз ─► чарт (репозиторий или OCI-реестр) ─► образ (реестр образов) ─► версия программы
              может исчезнуть или измениться       может переехать          может измениться
```

Схема 2. Три внешние зависимости чужого чарта: у каждой свой владелец и свои причины измениться без вашего ведома.

Защита одна: закрепить всё, что можно, и держать копию. Версию чарта задают флагом `--version`, а образ — точным тегом или дайджестом. Нужные образы зеркалируют в свой реестр: на стенде эту роль играет `localhost:5001`, а политика разрешённых реестров описана в 06-4.

### Случай Bitnami

Каталог Bitnami годами был стандартным ответом на вопрос «чем поставить PostgreSQL, Redis или RabbitMQ в кластер». Его чарты и образы в 2025 году изменились, и это хороший пример зависимости, которую не закрепили. Рецепт «helm install из bitnamicharts как есть» теперь надо считать анти-рецептом.

Хронология простая. С 28 августа по 29 сентября 2025 года Broadcom, владелец Bitnami, перенёс версионированные образы в репозиторий `docker.io/bitnamilegacy`: он остался без обновлений и патчей безопасности. Бесплатным остался только тег `latest`, и его предназначение — разработка. Закреплённые версии образов стали платной услугой Bitnami Secure Images. Чарты при этом остались в `oci://registry-1.docker.io/bitnamicharts` и по умолчанию ссылались на прежние адреса образов.

Последствий три. Установка старой версии чарта заканчивается статусом пода `ImagePullBackOff`, потому что образа с нужным тегом по прежнему адресу больше нет. Новая версия чарта ссылается на `bitnami/postgresql:latest` и сама предупреждает при установке: `WARNING: Rolling tag detected (bitnami/postgresql:latest), please note that it is strongly recommended to avoid using rolling tags in a production environment`. А перенос на `bitnamilegacy` лечит симптом и оставляет вас на образе без патчей.

Урок шире Bitnami, поэтому запомните его как правило. Версия чарта и реестр образов — две разные зависимости, и обе нужно контролировать. Плавающий тег делает установку невоспроизводимой. Бесплатный публичный реестр не даёт обещаний, которые вы можете положить в основу прода.

### Как выбирать чарт

Перед установкой чужой чарт проверяют по короткому списку.

1. Кто ведёт чарт: вендор программы, крупный проект или один человек.
2. Когда был последний выпуск и как часто они выходят.
3. Из какого реестра берутся образы и можно ли их заменить значениями.
4. Закреплены ли теги и можно ли задать дайджест.
5. Есть ли в README раздел об обновлениях и несовместимых изменениях.
6. Какие объекты чарт создаёт сам: Secret, NetworkPolicy, PodDisruptionBudget, ServiceAccount.

Для лабораторных этой части выбран чарт `postgres` из репозитория groundhog2k (версия 1.6.8, приложение PostgreSQL 18.6). Он запускает официальный образ `docker.io/postgres` (Docker Official Image), а не собственную сборку, поэтому тег совпадает с версией PostgreSQL, а образ обновляется вместе с самой базой. Чарт не генерирует пароли и по умолчанию запускает процесс от uid 999 с read-only корневой файловой системой и без лишних capabilities. Из-за этого проще увидеть, как пароль и данные связаны между собой.

У выбора есть честное ограничение: это проект сообщества, а не вендора, и репликации с резервными копиями в нём нет. Для production-базы используют оператор (CloudNativePG, 09-1), а чарт здесь служит учебным примером чужого чарта.

## 2. Как устроен чужой чарт и его поставка

Чужой чарт устроен так же, как свой (07-1), но вы видите его снаружи: через репозиторий, файл значений и номера версий. Разберём, откуда чарт приходит и что читать.

### Репозиторий и OCI-реестр

Чарт приходит из репозитория по HTTP или из OCI-реестра (07-1). **Репозиторий** (chart repository) — это сервер, который отдаёт файл `index.yaml` со списком всех версий и ссылками на архивы `.tgz`. Его подключают командой `helm repo add`, и после этого чарт называют `имя-репозитория/чарт`. OCI-чарт не подключают заранее: адрес `oci://…` указывают в каждой команде.

```
репозиторий (HTTP)                             OCI-реестр
helm repo add groundhog2k https://…            без подключения
helm install db groundhog2k/postgres           helm install db oci://host/path/postgres
        │                                              │
index.yaml ─► список версий ─► postgres-1.6.8.tgz      тег = версия чарта
```

Схема 3. Два способа получить чарт: у репозитория есть список версий в `index.yaml`, у OCI-реестра версия равна тегу.

### Что внутри: values как интерфейс

Для пользователя чужого чарта значения (values) служат интерфейсом: шаблоны вы не меняете, а передаёте параметры. Поэтому файл значений по умолчанию читают как документацию. Его даёт команда `helm show values`, а описание каждого ключа лежит в README чарта (`helm show readme`). У `groundhog2k/postgres` важны четыре группы ключей.

- **image** — реестр (`docker.io`), репозиторий (`postgres`), тег (пустой: тогда берётся `appVersion`) и политика загрузки.
- **settings** — суперпользователь и его пароль: значение прямо в values (тогда чарт сам создаёт Secret с именем релиза) или ссылка на существующий Secret.
- **storage** — размер PVC, класс хранилища, режимы доступа и судьба PVC при удалении.
- **resources** — запросы и лимиты; по умолчанию пусто.

### Версии: чарта, приложения и образа

У чужого релиза три номера, и путать их опасно. Номер `version` в `Chart.yaml` — версия чарта, `appVersion` — версия программы, а тег образа — то, что реально запускается. По умолчанию тег берётся из `appVersion`, поэтому обновление чарта может молча обновить программу. В журнале выпусков chart groundhog2k так и вышло: выпуск 1.5.0 принёс PostgreSQL 17, а минорный выпуск 1.6.0 — PostgreSQL 18. Номер чарта не предупреждает о смене мажорной версии базы, это нужно читать в README и в журнале изменений.

### Субчарты и зонтичные чарты

Один чарт может подключать другие как зависимости. **Субчарт** (subchart) — чарт-зависимость, который лежит в каталоге `charts/` родителя; **зонтичный чарт** (umbrella chart) — родитель, который собирает несколько субчартов в один релиз. Зависимости описаны в `Chart.yaml`.

```yaml
dependencies:
- name: postgres
  version: 1.6.8
  repository: https://groundhog2k.github.io/helm-charts/
  condition: postgres.enabled
```

Фрагмент Chart.yaml родителя: имя, точная версия и источник субчарта, а `condition` позволяет выключить его значением. Команда `helm dependency update` скачивает архивы в `charts/` и записывает точные версии в `Chart.lock`. Значения субчарта задают под его именем (`postgres.settings.existingSecret`), а общие для всех — в ключе `global`. Для стендов зонтичный чарт удобен, для продакшена опасен: база обновляется и удаляется вместе с приложением (§5).

## 3. Как управлять чужим чартом

Чужим чартом управляют так же, как своим, но с тремя дополнительными правилами: values ведут по окружениям, секреты хранят вне values и образы закрепляют. Для проверки перед обновлением нужен плагин helm-diff, его карточка идёт ниже.

### Карточка инструмента: helm-diff

**Назначение.** **helm-diff** — плагин Helm (plugin), который показывает разницу между работающим релизом и тем, что получится после `helm upgrade`. Он ничего не меняет в кластере и подходит для проверки в CI и для ручной проверки перед выкаткой.

**Как работает.** Плагин рендерит чарт с вашими значениями, как это делает upgrade, и сравнивает результат с манифестом последней ревизии релиза. Живое состояние объектов он по умолчанию не читает.

```
 чарт + новые values ──► рендер ──────────────┐
                                              ├──► diff ──► вывод (+ добавлено, - убрано)
 Secret sh.helm.release.v1.… ─► манифест ─────┘
 (последняя ревизия)           с флагом --three-way-merge: ещё и живые объекты
```

Схема 4. Что сравнивает helm-diff: новый рендер с записью последней ревизии; ручные правки кластера он видит только с флагом `--three-way-merge`.

**Откуда берёт данные.** Чарт — из каталога, репозитория или `oci://`, как у `helm upgrade`. Манифест текущего релиза — из Secret ревизии в namespace релиза, поэтому права нужны те же, что у `helm get manifest`. Кластер и namespace — из kubeconfig.

**Основные команды.**

```bash
helm diff upgrade db groundhog2k/postgres --version 1.6.8 -n ns \
  -f values/common.yaml -f values/staging.yaml   # что изменит upgrade с этими values
helm diff upgrade db … --context 3               # показать 3 строки вокруг изменений
helm diff revision db 1 2 -n ns                  # сравнить две ревизии релиза
helm diff rollback db 1 -n ns                    # что изменит откат на ревизию 1
helm plugin list                                 # установленные плагины и версии
```

**Команды для скриптов:**

- `--detailed-exitcode` возвращает код 2, если есть изменения: на нём строят проверку в CI.
- `-q` (`--suppress-secrets`) убирает из вывода изменения Secret целиком, а не только маскирует значения.
- `--version` задаёт точную версию чарта, чтобы сравнение не зависело от «последней».
- `--three-way-merge` добавляет сравнение с живыми объектами, то есть ловит ручные правки.

**Частые ошибки:**

- Установка падает на проверке подписи: Helm 4 по умолчанию проверяет происхождение плагина (provenance, подпись `.prov`), поэтому нужен импортированный ключ автора и архив плагина по прямой ссылке, а не адрес git-репозитория.
- Проверка не находит ключ: по умолчанию Helm ищет связку `~/.gnupg/pubring.gpg`, а GnuPG 2.1 и новее хранит ключи в `pubring.kbx`, поэтому ключ выгружают в файл и передают флагом `--keyring`.
- Сверяют не тот ключ: страница выпуска на GitHub показывает ключ B5690EEEBB952194, но им подписан коммит выпуска, а архив и файл `.prov` подписаны ключом автора EA17A2A206AFF8CD.
- Значения Secret попадают в лог CI: по умолчанию helm-diff маскирует их, но флаг `--show-secrets` печатает их открытым текстом.
- Плагин «не видит» ручную правку: без `--three-way-merge` он сравнивает только рендер и запись ревизии.

**Установка.** В Ubuntu и в Manjaro плагин ставится одинаково: он попадает в каталог пользователя, права root не нужны. Для проверки подписи нужны `gpg` и ключ автора; версию закрепляют в адресе архива (лабораторная работа 3). README плагина версии 3.15.15 требует Helm не ниже 3.18; на стенде стоит Helm 4.2.2.

### Values по окружениям

Одна и та же база в staging и prod отличается размером диска, запросами ресурсов и числом реплик, а всё остальное совпадает. Поэтому значения делят на общий файл и файлы окружений, а Helm складывает их по правилу «побеждает последний» (07-1).

```
values/
  common.yaml      одинаковое везде: версия образа, ссылка на Secret
  staging.yaml     1 ГиБ диска, малые запросы ресурсов
  prod.yaml        больше диска, запросы по замерам
helm upgrade --install db <чарт> --version 1.6.8 -f values/common.yaml -f values/prod.yaml
```

Схема 5. Структура values: общее лежит в одном файле, а окружение переопределяет только своё.

Правил четыре. Переопределяйте только нужное: копия всех значений чарта прячет ваши изменения и ломается при его обновлении. Версию чарта храните в коде деплоя: флагом `--version` или архивом в репозитории. В CI передавайте полный набор `-f`, а не `--reuse-values`, потому что флаг не подхватывает новые значения по умолчанию из обновлённого чарта (07-1). В файлах значений не должно быть секретов, только ссылки на них.

### Секреты через существующий Secret

Пароль в `--set` или в values-файле плохо по трём причинам. Он попадает в историю командной строки и в Git. Он хранится в Secret ревизии релиза, а значит виден каждому, кто читает Secret namespace (07-1, раздел 2). И он живёт вместе с релизом, хотя данные базы живут отдельно (§5).

Для чартов принят шаблон **existingSecret** — параметр, в котором вы указываете имя уже созданного Secret, а чарт только читает из него ключи. В `groundhog2k/postgres` это `settings.existingSecret`. Сам Secret создаёт внешний процесс: оператор секретов, SOPS или администратор (модуль 08). Тогда `helm uninstall` не трогает пароль, и пароль всегда совпадает с тем, что записан в базу.

### Закрепление образа

Образ закрепляют на двух уровнях. Первый уровень — точный тег программы (`17.6`), заданный в values и не зависящий от `appVersion` чарта. Второй — дайджест (02-2): чарт собирает ссылку на образ из реестра, репозитория и тега, а Kubernetes принимает тег вида `18.6@sha256:<дайджест>`, поэтому дайджест можно подставить в `image.tag`.

Дайджест не меняется, даже если кто-то перезапишет тег в реестре, и защищает от подмены и от плавающего `latest`. Обновляют его осознанно, а образы зеркалируют в свой реестр.

## 4. Как увидеть состояние чужого релиза

Чужой чарт видят с трёх сторон: что в нём написано до установки, откуда в манифесте берётся нужное поле и что изменится при обновлении. Все три способа работают до того, как вы что-то применили.

### Разведка до установки

Команды `helm show` читают чарт без установки. Команда `helm show chart` печатает `Chart.yaml`, `helm show values` — значения по умолчанию, `helm show readme` — документацию. Команда `helm pull` скачивает архив `.tgz` для изучения и для хранения в репозитории; с флагом `--untar` архив сразу распаковывается, и шаблоны можно читать как исходный код.

```
helm show chart  ─► версии чарта и приложения       helm show values ─► параметры по умолчанию
helm show readme ─► описание параметров             helm pull --untar ─► шаблоны для чтения
```

Схема 6. Четыре способа осмотреть чарт до установки; ни один не обращается к кластеру.

В значениях по умолчанию ищут ответы на вопросы из §1. Какой реестр и тег у образа, откуда берётся пароль, что будет с PVC, есть ли запросы ресурсов, какие объекты создаёт чарт сам.

### Источник поля

Если в манифесте есть поле, которого вы не ожидали, его путь идёт с конца. Команда `helm template` печатает манифесты, и каждый объект начинается строкой `# Source: <чарт>/templates/<файл>`. По этой строке находят шаблон. Флаг `--show-only templates/<файл>` оставляет один шаблон, а фильтр `grep` ищет в нём поле.

```
поле в кластере ◄─ helm get manifest ◄─ шаблон (# Source:) ◄─ ключ в values ◄─ helm show values
     kubectl get       что ушло          helm template        где задать
```

Схема 7. Цепочка от поля до его источника: идите справа налево, чтобы изменить поле, и слева направо, чтобы понять откуда оно взялось.

Если рендер падает, добавьте `--debug`: Helm выведет итоговый YAML даже с ошибкой, и по номеру строки видно, какая вставка сломала шаблон. Что именно вы передали, показывает `helm get values <релиз>` (только ваши значения, блок USER-SUPPLIED VALUES), а `helm get values <релиз> --all` добавляет значения чарта по умолчанию.

### Сравнение до обновления

Перед каждым upgrade смотрят разницу. Плагин helm-diff делает это с учётом релиза (карточка выше). Без плагина подходит связка `helm template … | kubectl diff -f -`: она сравнивает рендер с живыми объектами и ловит ручные правки, но не знает про релиз. Код возврата `kubectl diff` равен 1, если различия есть, и 0, если их нет.

Главная ловушка этого сравнения — стандартный вывод Helm 4. Команда `helm template oci://…` печатает в stdout строки `Pulled: registry-1.docker.io/…` и `Digest: sha256:…` перед манифестами, и `kubectl diff -f -` падает на них с ошибкой `Object 'Kind' is missing`. Для OCI-чарта сначала выполняют `helm pull` в файл (заодно фиксируются точная версия и дайджест чарта), а затем `helm template ./архив.tgz`. Чарты из HTTP-репозитория, как в лабораторных, этих строк не печатают.

## 5. Что ломается и как найти причину

В чужих чартах ломается чаще всего четыре вещи: образ, пароль, данные при смене версии программы и структура при смене версии чарта.

### Образ не скачивается

Признак — статус пода `ErrImagePull`, затем `ImagePullBackOff`. В `kubectl describe pod` есть событие `Failed to pull image … not found` или `manifest unknown`. Причина в чужом реестре: тег удалён или переехал (случай Bitnami, §1). Найти адрес образа помогает цепочка из §4: `helm get manifest` покажет строку `image:`, а `helm show values` — ключ, который её задаёт. Лечение — заменить реестр и тег в values, а в долгосрочной перспективе — зеркалировать образы в свой реестр и закрепить дайджест.

### Пароль и данные расходятся

PostgreSQL записывает пароль суперпользователя в данные один раз, при инициализации пустого каталога. Дальше значение переменной `POSTGRES_PASSWORD` игнорируется, и пароль знает только база. Отсюда три поломки.

- **Пароль не задан.** Образ отказывается инициализировать базу, под падает, а в логе строка `Database is uninitialized and superuser password is not specified`.
- **Пароль сгенерирован.** Чарты вроде Bitnami создают случайный пароль при каждой установке. После `helm uninstall` Secret исчезает, а PVC StatefulSet остаётся (02-3, 04-2). Новая установка кладёт в Secret новый пароль, а база на диске хранит старый.
- **Пароль изменён в values.** Новое значение попадает в Secret чарта и в переменную пода, но не в базу.

Во втором и третьем случае под остаётся `Running`, потому что проба `pg_isready` проверяет, что сервер принимает подключения, а пароль не проверяет. Приложения при этом не могут подключиться: в логах `password authentication failed`. Лечение — вернуть старый пароль или сменить его командой `ALTER ROLE` внутри базы. Профилактика — `existingSecret` с постоянным паролем (§3).

### Мажорная версия приложения

Смена мажорной версии программы — не обновление чарта, а миграция данных. PostgreSQL 18 отказывается открыть каталог данных, созданный PostgreSQL 17: под падает в `CrashLoopBackOff`, а в логе `database files are incompatible with server`. Так как StatefulSet с одной репликой сначала останавливает старый под, а потом создаёт новый, база недоступна, пока вы не откатитесь. Одного `helm rollback` мало: контроллер ждёт готовности сломанного пода и сам его не заменит, поэтому под удаляют вручную (forced rollback, 02-3 §5). Данные при этом не повреждаются, потому что сервер отказывается стартовать до записи на диск.

Правильный порядок выглядит так.

1. Сделать резервную копию и проверить восстановление (04-3).
2. Создать рядом новый релиз на новой версии с пустым диском.
3. Перенести данные дампом (`pg_dumpall`) или утилитой `pg_upgrade`.
4. Проверить приложение на новой базе и переключить трафик.
5. Старый релиз с диском держать, пока не убедитесь, что откат не нужен.

### Мажорная версия чарта

Чарт мажорной версии может изменить имена ключей values, имена объектов и селекторы. Поля `selector` у StatefulSet и Deployment и `volumeClaimTemplates` у StatefulSet нельзя менять после создания: upgrade упадёт с ошибкой `Forbidden: updates to statefulset spec for fields other than … are forbidden`. Поэтому сначала читают раздел об обновлениях в README и журнал изменений. Затем рендерят старую и новую версии чарта с одними values, сравнивают два манифеста и только потом применяют.

Особенно смотрят на `selector`, `volumeClaimTemplates` и метки внутри них: метка с номером версии чарта в шаблоне диска тоже меняет неизменяемое поле. В `groundhog2k/postgres` шаблон диска берёт метки только из `storage.labels`, поэтому смена версии чарта его не трогает. У зонтичных чартов опасность другая: у приложения и базы общий жизненный цикл, поэтому откат, обновление или удаление приложения трогают базу.

## 6. Пределы и значения по умолчанию

Значения по умолчанию задаёт автор чарта, поэтому их число отличается у каждого чарта. Ниже — значения `groundhog2k/postgres` 1.6.8 и ограничения самого подхода.

### Значения чарта

- **Образ.** Реестр `docker.io`, репозиторий `postgres`, тег пустой (берётся `appVersion`, здесь `18.6`), политика загрузки `IfNotPresent`.
- **Пароль.** Не задан: без `settings.superuserPassword` или `settings.existingSecret` под не стартует. Имя суперпользователя по умолчанию `postgres`.
- **Тип и диск.** StatefulSet (режим Deployment включает ключ `useDeployment`), режим доступа ReadWriteOnce, размер задаёт `storage.requestedSize`; без него том будет `emptyDir` и данные пропадут вместе с подом.
- **Каталог данных.** Том монтируется в `/var/lib/postgresql/data`, а `PGDATA` равен `/var/lib/postgresql/data/pg` (ключи `settings.dataDir` и `settings.pgDir`). Образ PostgreSQL 18 сменил свой `PGDATA` на `/var/lib/postgresql/18/docker`, но чарт задаёт переменную явно, поэтому для 17 и 18 путь одинаков.
- **Пробы.** Все три запускают `pg_isready -h localhost`; startup даёт до 30 попыток с периодом 10 с, liveness и readiness — 3 неудачи по 10 с.
- **Судьба PVC.** `persistentVolumeClaimRetentionPolicy` пуст, поэтому действует поведение Kubernetes по умолчанию: PVC сохраняется при удалении и при уменьшении числа реплик (02-3).
- **Запросы ресурсов.** Пусто: под получает класс QoS BestEffort (05-1).
- **Безопасность.** Процесс идёт от uid и gid 999, корневая файловая система только для чтения, повышение привилегий запрещено, все capabilities сброшены.
- **Порт.** Service типа ClusterIP, порт 5432.

### Ограничения подхода

У подхода есть пределы, и они не зависят от выбранного чарта.

- **Размер релиза.** Запись ревизии лежит в Secret, а Secret ограничен примерно 1 МиБ; огромные чарты с большими values не устанавливаются.
- **История.** `--history-max` равен 10; более старые ревизии удаляются (07-1).
- **Тайм-аут.** `--timeout` по умолчанию 5m0s; в лабораторных он короче, чтобы поломка проявилась быстро.
- **Сравнение.** helm-diff по умолчанию сверяет рендер с записью ревизии, а не с живыми объектами.
- **Файловые данные.** Helm не знает о содержимом PVC: он ни мигрирует, ни проверяет данные при смене версии программы.

### Права и секреты

Чтение значений релиза равно праву читать Secret в namespace, поэтому `helm get values` показывает пароли, переданные через `--set`, а helm-diff — с флагом `--show-secrets`. Пароль в Secret ревизии не шифруется Helm, он защищён только правами RBAC (06-1) и шифрованием etcd (04-1). Отсюда правило: секрет живёт вне релиза, а в values лежит только ссылка на него.

## Лабораторные работы

Четыре работы идут на стенде 00-1 в namespace `lab-07-2`, файлы лежат в `~/lab/k8s/07-2/`. Чарт для работ — `groundhog2k/postgres` версии 1.6.8 (§1). Имена объектов и сообщения в выводе ожидаемые, поэтому сверяйте их с тем, что покажет ваш стенд.

Подготовку выполняют один раз. Первая команда только проверяет контекст: она должна вывести `kind-lab`; если нет, переключитесь на контекст стенда самостоятельно перед продолжением.

```bash
kubectl config current-context
kubectl create ns lab-07-2
mkdir -p ~/lab/k8s/07-2/values
k() { kubectl -n lab-07-2 "$@"; }
q() { k exec "$1-0" -- sh -c \
  'PGPASSWORD="${2:-$POSTGRES_PASSWORD}" psql -h "$0" -U postgres -tAc "$1"' "$1" "$2" "$3"; }
```

Первая команда показывает текущий контекст, вторая создаёт namespace работ. Третья готовит каталог для файлов.

Функция `k` сокращает запись `kubectl -n lab-07-2`. Функция `q` выполняет SQL в поде StatefulSet: первый аргумент — имя Service (под называется так же с суффиксом `-0`), второй — запрос, третий — пароль (необязательный). Без третьего аргумента пароль берётся из переменной пода `POSTGRES_PASSWORD`, поэтому на хосте он не появляется. Подключение идёт к Service, а не к `localhost`: официальный образ пускает по loopback без пароля, и такая проверка ничего бы не доказала. Обе функции снимает уборка работы 4, а если вы закрыли терминал, объявите их заново.

Эту работу вы выполняете сами, результаты в ней — ожидаемые.

**Риски.** Работа меняет кластер стенда и две папки хоста: настройки репозиториев Helm и его кэш.

#### Шаг 5. Переустановить с другим паролем

Удаляем релиз, оставляя диск, ставим тот же чарт с паролем `second-pass` и проверяем оба пароля.

| Часть команды | Значение |
|---|---|
| `helm uninstall db` | удалить релиз; PVC остаётся |
| `--set …value=second-pass` | новое значение пароля |
| `q … second-pass` | подключиться с паролем из нового релиза |
| `q … first-pass` | подключиться со старым паролем |

3. Старый пароль `first-pass` работает и возвращает `42`: база помнит пароль, с которым её инициализировали, а новое значение в values ни на что не влияет.

Первая команда удаляет релиз, вторая — диск с данными, третья — сохранённые значения по умолчанию. Проверьте, что `k get pvc` не показывает ресурсов.

**Вопросы для самопроверки.**

1. Почему под в шаге 5 был `Running`, хотя пароль не подходил?

<details><summary>Ответ</summary>
Проба готовности запускает `pg_isready`: она проверяет, что сервер принимает подключения, и не проверяет пароль. Статус пода не говорит, смогут ли приложения подключиться.
</details>

2. Где в кластере виден пароль, переданный через `--set`?

<details><summary>Ответ</summary>
В Secret ревизии релиза `sh.helm.release.v1.db.vN`, а значит в выводе `helm get values`, и в Secret `db-postgres`, который создаёт чарт. Право читать Secret в namespace равно праву видеть пароль.
</details>

3. Почему после `helm uninstall` данные остались?

<details><summary>Ответ</summary>
PVC создаётся шаблоном volumeClaimTemplates StatefulSet, и Kubernetes по умолчанию не удаляет его вместе с StatefulSet (02-3, 04-2). Чарт не меняет это поведение.
</details>

4. Чем отличается поведение чарта Bitnami, который генерирует пароль, от этого чарта?

<details><summary>Ответ</summary>
Генерирующий чарт при каждой установке создаёт новый пароль, и расхождение с диском возникает само. Этот чарт требует пароль от вас, и расхождение возникает, только когда вы его меняете. Лечение одно: постоянный Secret и `existingSecret` (лабораторная работа 2).
</details>

### Лабораторная работа 2. Правильная установка: values по окружениям

### Лабораторная работа 3. Источник поля и diff перед upgrade

Эту работу вы выполняете сами, результаты в ней — ожидаемые.

**Риски.** Работа ставит плагин Helm и импортирует ключ GPG на хост; кластер меняется только upgrade в конце.

- **Что меняется:** в `~/.local/share/helm/plugins` (путь зависит от настроек Helm) появляется плагин diff, в связке ключей GPG — ключ автора, в кластере — ревизия релиза `db`.
- **Надолго ли:** плагин и ключ остаются до уборки работы 4.
- **Безопасность:** плагин — исполняемый код, поэтому версия закреплена, а архив проверяется подписью; отпечаток ключа сверяют с README проекта до установки, иначе проверка не имеет смысла.

- **Откат:** `helm plugin uninstall diff` и удаление ключа в уборке работы 4; `helm rollback` для релиза.

**Цель.** Найти шаблон, который порождает поле, поставить плагин helm-diff закреплённой версии, посмотреть разницу до upgrade и применить обновление без потери данных.

```
…
exit=2
-            memory: 512Mi
+            memory: 768Mi
```

Разбор вывода:

1. Заголовок называет объект, который изменится: StatefulSet `db-postgres`.
2. Различие одно, лимит памяти. Любое другое различие означало бы побочный эффект ваших правок.
3. Код возврата 2 при `--detailed-exitcode` можно использовать как условие в CI.
4. Вторая команда показывает то же самое, но сравнивает с живыми объектами; для неё нужен доступ к кластеру, а Helm про релиз она не знает.

#### Шаг 5. Применить upgrade и проверить данные

Записываем в базу строку, которая должна пережить обновление, применяем upgrade и проверяем лимит, историю и данные.

```bash
q db-postgres "create table keep(x int); insert into keep values (7)"
helm upgrade db groundhog2k/postgres --version 1.6.8 -n lab-07-2 \
  -f $V/common.yaml -f $V/staging-768.yaml --wait --timeout 3m
helm history db -n lab-07-2
k get pod db-postgres-0 -o jsonpath='limit={.spec.containers[0].resources.limits.memory}{"\n"}'
q db-postgres "select x from keep"
```

| Часть команды | Значение |
|---|---|
| `create table keep …` | таблица, которая должна пережить upgrade |
| `helm upgrade db … --wait` | обновить релиз и дождаться готовности |
| `helm history db` | все ревизии релиза |
| `jsonpath='limit={…}'` | лимит памяти нового пода |

Результат (ожидаемый, сокращён):

```
INSERT 0 1
REVISION   UPDATED   STATUS       CHART           APP VERSION   DESCRIPTION
1          …         superseded   postgres-1.6.8  18.6          Install complete
2          …         deployed     postgres-1.6.8  18.6          Upgrade complete
limit=768Mi
```

Разбор вывода:

1. Ревизия 2 имеет статус `deployed`, а ревизия 1 стала `superseded` (07-1).
2. В колонке `APP VERSION` стоит `18.6` — это `appVersion` чарта, а не версия образа: образ закреплён значением `17.6`. Эта колонка вводит в заблуждение, и по ней нельзя судить о версии работающей базы.

**Итог.**

| Что узнали | Где видно |
|---|---|
| `# Source:` и `--show-only` ведут от поля к шаблону | шаг 1 |
| Поле видно в values, манифесте и поде | шаг 2 |
| Плагин ставят закреплённой версией с проверкой подписи | шаг 3 |
| Diff показывает изменение до применения | шаг 4 |
| Upgrade не трогает данные на PVC | шаг 5 |

**Уборка.** Релиз, плагин и файлы нужны работе 4, поэтому их удаляет уборка работы 4. Если вы останавливаетесь здесь, выполните её сейчас.

**Вопросы для самопроверки.**

1. Чем helm-diff отличается от `helm template | kubectl diff`?

<details><summary>Ответ</summary>
Плагин сравнивает новый рендер с записью последней ревизии релиза. Связка с `kubectl diff` сравнивает рендер с живыми объектами и не знает о релизе, но видит ручные правки.
</details>

2. Для чего нужен `--detailed-exitcode`?

<details><summary>Ответ</summary>
Он возвращает код 2, если изменения есть, и 0, если нет. По нему CI решает, нужна ли выкатка или ручное подтверждение.
</details>

3. Почему в колонке APP VERSION истории стоит 18.6, а работает PostgreSQL 17.6?

<details><summary>Ответ</summary>
Колонка берёт `appVersion` из `Chart.yaml`, а не тег образа. Тег закреплён в values и может отличаться от неё.
</details>

4. Зачем при установке плагина закреплять версию и проверять подпись?

<details><summary>Ответ</summary>
Плагин — исполняемый код с доступом к вашему kubeconfig. Закреплённая версия и проверка подписи не дают подменить его при очередной установке.
</details>

### Лабораторная работа 4. Мажорная версия приложения и данные

Эту работу вы выполняете сами, результаты в ней — ожидаемые.

**Риски.** Работа специально ломает базу в своём namespace и в конце удаляет всё, что создали работы 1–4, включая плагин и ключ на хосте.

- **Что меняется:** в `lab-07-2` релиз `db` сломается и будет откачен, появится релиз `db18` с PVC; на хосте — файл дампа в `~/lab/k8s/07-2`.
- **Надолго ли:** до уборки в конце работы.
- **Безопасность:** пароль не выводится: дамп снимается внутри пода через переменную окружения; файл дампа содержит учебные данные.
- **Влияние на систему:** база релиза `db` недоступна несколько минут; другие проекты не затрагиваются, образ `postgres:18.6` скачивается из `docker.io`.
- **Откат:** `helm rollback` и удаление сломанного пода, затем блок «Уборка».

**Цель.** Увидеть, что diff не показывает несовместимость данных, воспроизвести падение при смене мажорной версии PostgreSQL, откатиться и выполнить правильную миграцию через дамп в новый релиз.

**Что понадобится.**

- Стенд, релиз `db` с таблицей `keep` из работы 3, плагин helm-diff.
- Образ `postgres:18.6` (скачается при первом запуске).
- Около 40 минут.

**Схема опыта.** Сначала мажорная версия меняется на месте и ломается, потом данные переносятся в соседний релиз на новой версии.

```
db  (17.6, PVC-1) ──► upgrade до 18.6 ──► CrashLoopBackOff: каталог данных от версии 17
        │ rollback + delete pod
        ▼
db  (17.6, PVC-1) ──pg_dumpall──► dump.sql ──psql──► db18 (18.6, PVC-2)  ← проверяем данные
```

Схема показывает два пути: смена версии на месте ломается, перенос в новый релиз работает.

#### Шаг 1. Сравнить версии чарта и увидеть diff образа

Сначала сравниваем рендер двух версий чарта с одними значениями, как перед обновлением чарта. Затем смотрим diff смены версии образа.

```bash
echo 'image: {tag: "18.6"}' > $V/major-18.yaml
diff <($R -f $V/common.yaml -f $V/staging.yaml) \
     <(helm template db groundhog2k/postgres --version 1.5.0 -n lab-07-2 \
       -f $V/common.yaml -f $V/staging.yaml) | grep -E '^[<>]'
helm diff upgrade db groundhog2k/postgres --version 1.6.8 -n lab-07-2 \
  -f $V/common.yaml -f $V/staging-768.yaml -f $V/major-18.yaml | grep -E '^[-+] '
```

| Часть команды | Значение |
|---|---|
| `echo 'image: {tag: "18.6"}' > major-18.yaml` | файл с новой версией образа |
| `diff <($R …) <(helm template … 1.5.0 …)` | сравнить рендер чарта 1.6.8 и 1.5.0 |
| `grep -E '^[<>]'` | оставить только строки различий |
| `-f staging-768.yaml -f major-18.yaml` | значения как в работе 3 плюс новая версия |

Результат (ожидаемый, сокращён):

```
<     helm.sh/chart: postgres-1.6.8
>     helm.sh/chart: postgres-1.5.0
<     app.kubernetes.io/version: "18.6"
>     app.kubernetes.io/version: "17.0"
…
<         checksum/scripts: …
>         checksum/scripts: …
…
<                 - pg_isready -h localhost -U ${POSTGRES_USER:-postgres}
>                 - pg_isready -h localhost
…
<     - apiVersion: v1
<       kind: PersistentVolumeClaim
<       metadata:
>     - metadata:
-           image: "docker.io/postgres:17.6"
+           image: "docker.io/postgres:18.6"
-           image: "docker.io/postgres:17.6"
+           image: "docker.io/postgres:18.6"
```

Разбор вывода:

1. Первый diff показывает, что отличается между версиями чарта при одинаковых values: метки версии, контрольная сумма ConfigMap со скриптами, команда проб и запись шаблона диска. Метки `helm.sh/chart` в шаблоне диска нет, а `selector` не изменился, поэтому неизменяемые поля смена чарта не задевает (§5).
2. Строка `checksum/scripts` в шаблоне пода меняется вместе с меткой чарта, поэтому любое обновление чарта перезапускает под базы.
3. Второй diff показывает одну замену в двух местах: образ init-контейнера и основного контейнера меняется с 17.6 на 18.6.
4. Ни один diff не говорит, откроет ли PostgreSQL 18 каталог данных версии 17: Helm видит манифесты, но не содержимое диска.

#### Шаг 2. Выполнить мажорный upgrade на месте

Применяем смену версии с коротким ожиданием. Ожидаем отказ.

```bash
helm upgrade db groundhog2k/postgres --version 1.6.8 -n lab-07-2 \
  -f $V/common.yaml -f $V/staging-768.yaml -f $V/major-18.yaml --wait --timeout 90s
k get pods
k logs db-postgres-0 --tail 4
helm history db -n lab-07-2 | tail -2
```

| Часть команды | Значение |
|---|---|
| `-f major-18.yaml` | образ 18.6 вместо 17.6 |
| `--wait --timeout 90s` | ждать готовности не больше 90 секунд |
| `logs db-postgres-0 --tail 4` | последние четыре строки лога |
| `history db \| tail -2` | две последние ревизии |

Результат (ожидаемый, сокращён):

```
Error: UPGRADE FAILED: …
NAME            READY   STATUS             RESTARTS   AGE
db-postgres-0   0/1     CrashLoopBackOff   …          …
FATAL:  database files are incompatible with server
DETAIL:  The data directory was initialized by PostgreSQL version 17, which is not compatible …
2   …   deployed   …   Upgrade complete
3   …   failed     …   Upgrade "db" failed: …
```

Разбор вывода:

1. Upgrade завершился ошибкой по тайм-ауту: ревизия 3 получила статус `failed`, а ревизия 2 осталась `deployed`, потому что Helm помечает прежнюю ревизию `superseded` только после успеха.
2. Под в `CrashLoopBackOff`: единственная реплика была остановлена, а новая не стартует, поэтому база недоступна.
3. Сообщение сервера прямо называет причину: каталог данных создан версией 17. Данные целы, потому что сервер отказывается стартовать до записи.
4. Для автоматического возврата служит `--rollback-on-failure` (07-1), но и он вернёт только шаблон: сломанный под StatefulSet придётся удалить вручную (шаг 3).

#### Шаг 3. Откатиться на ревизию 2

Возвращаем рабочую ревизию, удаляем сломанный под и проверяем, что данные не пострадали. Откат запускаем без `--wait`: контроллер StatefulSet не заменит под, который так и не стал готовым (02-3 §5), и ожидание закончилось бы тайм-аутом.

```bash
helm rollback db 2 -n lab-07-2
k delete pod db-postgres-0
k wait --for=condition=Ready pod/db-postgres-0 --timeout=3m
q db-postgres "select x from keep"
```

| Часть команды | Значение |
|---|---|
| `helm rollback db 2` | вернуть манифест ревизии 2 (новая ревизия 4) |
| `delete pod db-postgres-0` | убрать под, запущенный со сломанной ревизией |
| `wait --for=condition=Ready … --timeout=3m` | ждать готовности нового пода не больше 3 минут |
| `q db-postgres "select x from keep"` | проверить данные |

Результат (ожидаемый):

```
Rollback was a success! Happy Helming!
pod "db-postgres-0" deleted
pod/db-postgres-0 condition met
7
```

Разбор вывода:

1. Откат создал новую ревизию 4 с манифестом ревизии 2 (07-1), но сам под не тронул.
2. После удаления контроллер создал под заново из шаблона версии 17.6, и под стал готовым.
3. Строка `7` подтверждает, что данные целы. Откат вернул объекты, а данных он не касался, потому что и поломка до них не добралась; если бы новая версия успела изменить диск, откат образа не помог бы.

#### Шаг 4. Перенести данные дампом в новый релиз

Снимаем дамп внутри пода, поднимаем рядом релиз `db18` на версии 18.6 с чистым диском и загружаем дамп.

```bash
k exec db-postgres-0 -- sh -c \
  'PGPASSWORD="$POSTGRES_PASSWORD" pg_dumpall -h db-postgres -U postgres' \
  > ~/lab/k8s/07-2/dump.sql
wc -l < ~/lab/k8s/07-2/dump.sql
helm install db18 groundhog2k/postgres --version 1.6.8 -n lab-07-2 \
  -f $V/common.yaml -f $V/staging.yaml -f $V/major-18.yaml --wait --timeout 4m
k exec -i db18-postgres-0 -- sh -c \
  'PGPASSWORD="$POSTGRES_PASSWORD" psql -h db18-postgres -U postgres -q' \
  < ~/lab/k8s/07-2/dump.sql
```

| Часть команды | Значение |
|---|---|
| `pg_dumpall` | выгрузить все базы и роли в SQL |
| `> dump.sql` | сохранить вывод в файл на хосте |
| `helm install db18 …` | новый релиз со своим StatefulSet и PVC |
| `-f major-18.yaml` | образ 18.6 побеждает `17.6` из common, потому что файл правее |
| `exec -i … psql < dump.sql` | подать дамп на вход psql |

Результат (ожидаемый, сокращён):

```
<число строк>
STATUS: deployed
ERROR:  role "postgres" already exists
```

Разбор вывода:

1. Число строк дампа зависит от данных и версии, но не равно нулю: в файле лежит SQL всех баз.
2. Релиз `db18` поднялся на 18.6 на новом чистом диске, а `db` с данными не тронут.
3. Ошибка `role "postgres" already exists` ожидаема: дамп пытается создать роль, которая уже есть в новой базе. Остальные команды выполняются.
4. Оба релиза используют один Secret `pg-auth`, поэтому пароль у них совпадает.

**Вопросы для самопроверки.**

1. Почему diff не предупредил о смене версии PostgreSQL?

<details><summary>Ответ</summary>
Helm и helm-diff сравнивают манифесты, а совместимость данных зависит от содержимого диска. Мажорная версия базы — это миграция данных, а не изменение объектов.
</details>

2. Почему при падении нового пода база осталась недоступной?

<details><summary>Ответ</summary>
У StatefulSet одна реплика: он останавливает старый под перед созданием нового. Пока новый не стал готовым, работающего пода нет.
</details>

3. Что делает `helm rollback` с данными?

<details><summary>Ответ</summary>
Ничего: он возвращает манифест выбранной ревизии, а сломанный под StatefulSet приходится удалить вручную. Откат безопасен, только пока новая версия не изменила диск.
</details>

4. Почему миграцию делают в новый релиз, а не в старый?

<details><summary>Ответ</summary>
Старый релиз с диском остаётся рабочим путём возврата. Новый получает чистый диск и проверяется до переключения трафика.
</details>
