## 1. Какую задачу решает etcd

Все объекты Kubernetes лежат в одном хранилище, поэтому состояние кластера живёт ровно столько, сколько живёт etcd. Разберём, чем оно рискует и что остаётся на плечах оператора.

### Состояние кластера в одном месте

Потеря etcd означает потерю кластера: поды на узлах продолжат работать, но никто не знает, какие Deployment, Service и Secret должны существовать. Поэтому у etcd три требования: не терять записанное, переживать отказ узла и отвечать быстро. Первое решает диск, второе — репликация, третье — быстрый диск и сеть.

### Репликация и кворум

Один экземпляр etcd не переживает потерю своего узла. Поэтому в рабочем кластере etcd запускают как несколько **членов** (member) — процессов, каждый из которых хранит полную копию данных. Алгоритм Raft (01-1 §2) выбирает среди них одного лидера и подтверждает запись, только когда её приняло большинство. Это большинство — кворум.

Цена надёжности в том, что запись ждёт сети и диска нескольких узлов. Поэтому время записи в etcd складывается из задержки диска и задержки сети между членами, и оба числа надо знать (§4).

### Что остаётся оператору

Kubernetes не следит за etcd сам. Оператор отвечает за четыре вещи:

- **Размер базы** — не пустить её к квоте (§3, §5).
- **Диск** — дать etcd быстрый носитель (§2, §4).
- **Бэкап** — делать снимки и проверять восстановление (§3).
- **Состав** — заменять потерянных членов до потери кворума (§3).

В managed-кластерах (10-3) за эти четыре пункта отвечает провайдер. На своём кластере, который собран kubeadm, они ваши.

## 2. Как устроен etcd

Внутри etcd четыре слоя: Raft согласует порядок записей, журнал и база хранят их на диске, а MVCC (многоверсионность) оставляет старые значения. Разберём слои от сети к диску.

### Члены, лидер и выборы

**Лидер** (leader) — член, который принимает все записи и рассылает их остальным. Остальные члены — **последователи** (follower). Лидер каждые 100 мс шлёт последователям короткое сообщение — **heartbeat** (сигнал «я жив»). Если последователь не слышит лидера дольше **election timeout** (таймаута выборов, по умолчанию 1000 мс), он объявляет себя кандидатом и просит голоса.

**Срок** (term) — номер эпохи выборов; он растёт на единицу при каждых выборах. Кандидат становится лидером, если получил голоса большинства. Таймауты у членов слегка случайны, чтобы они не выдвигались одновременно.

```
   срок 7:  лидер A ──heartbeat 100 мс──► B, C
   A пропал:  B не слышит A дольше 1000 мс
   срок 8:  B ─► «голосуйте за меня» ─► C отвечает «да»  ─►  B лидер (2 из 3)
```

Схема 2. Выборы: у B и C есть кворум из двух, поэтому кластер продолжает работать без A уже через секунду-другую.

Частые выборы вредны, потому что на время выборов запись стоит. Они начинаются, когда лидер не успевает отправить heartbeat: из-за медленного диска, перегруженного узла или потерь в сети (§5).

### Кворум и число членов

Нужное для записи большинство считают как половина членов (округление вниз) плюс один. Сколько членов можно потерять без остановки записи, показывает таблица.

| Членов | Кворум | Можно потерять | Комментарий |
|---|---|---|---|
| 1 | 1 | 0 | только для опытов |
| 2 | 2 | 0 | хуже одного: два узла, оба нужны |
| 3 | 2 | 1 | минимум для рабочего кластера |
| 4 | 3 | 1 | не лучше трёх, а записей больше |
| 5 | 3 | 2 | рекомендация документации Kubernetes |
| 7 | 4 | 3 | верхний разумный предел |

Нечётное число выбирают потому, что чётное не добавляет надёжности: четыре члена переживают тот же один отказ, что и три, а каждая запись должна дойти уже до трёх. Документация etcd советует не больше семи членов, а Kubernetes — пять для рабочих кластеров. Каждый новый член замедляет запись, потому что лидеру нужно ждать больше подтверждений.

Кворум нужен ещё и для чтений: etcd по умолчанию отвечает на чтение, только убедившись, что лидер всё ещё лидер. Поэтому без кворума кластер не читает свежие данные, а не только не пишет. Часть чтений API-сервер отдаёт из своего кэша (01-1 §6), но свежие и записывающие запросы не проходят.

### Путь записи и диск

Запись проходит пять шагов, и два из них упираются в диск. Лидер добавляет запись в **WAL** (write-ahead log, журнал упреждающей записи) и вызывает **fsync** — системный вызов, который заставляет ядро физически записать данные на диск. Затем лидер отправляет запись последователям, и каждый делает то же самое. Когда подтвердило большинство, запись считается принятой и применяется к базе.

```
 клиент ─► лидер: 1. запись в WAL + fsync        (метрика wal_fsync_duration)
             │    2. отправка последователям (каждый: WAL + fsync)
             │    3. подтвердило большинство → запись принята
             ▼    4. применение к backend (в памяти, пачкой)
         backend (bbolt, файл db): 5. раз в ~100 мс пачка пишется на диск + fsync
                                      (метрика backend_commit_duration)
```

Схема 3. Две точки доступа к диску: журнал WAL при каждой записи и фоновая запись базы пачками.

**Backend** (бэкенд) — основная база etcd, файл `member/snap/db` в каталоге данных. Она построена на встроенном хранилище bbolt, которое хранит данные в страницах по 4 КиБ и читает файл через отображение в память. **Каталог данных** (data-dir) — каталог, где лежат WAL и backend; на узле kubeadm это `/var/lib/etcd`.

Журнал пишется при каждой записи, поэтому задержка fsync диска напрямую становится задержкой Kubernetes API. Поэтому etcd просят SSD, а лучше отдельный диск: соседний тяжёлый ввод-вывод делает fsync долгим. Документация etcd называет ориентир: для нагруженных кластеров нужно около 500 последовательных IOPS, для небольших хватает 50.

Параметр `--snapshot-count` часто путают со снимком для бэкапа. Это число принятых записей, после которого etcd сохраняет состояние Raft и сокращает журнал в памяти; в версии 3.6 по умолчанию 10000, раньше было 100000. К бэкапу он отношения не имеет.

### Ревизии и компакция

**MVCC** (multi-version concurrency control, многоверсионное хранение) значит, что etcd при изменении ключа не затирает старое значение, а пишет новое под новой ревизией. Ревизии (01-1 §2) общие для всего кластера, и каждый ключ хранит свою историю. Поэтому читатель может спросить значение ключа «как было на ревизии N», а watch (01-1 §2) может продолжить с нужной ревизии.

```
 ключ /registry/configmaps/lab/big:   рев. 100    рев. 140    рев. 190    ...
 значение:                            v1 (400 КБ) v2 (400 КБ) v3 (400 КБ)
                         живое значение — только v3, остальное — история
```

Схема 4. Один ключ с тремя ревизиями: все три копии лежат в базе, пока их не удалит компакция.

История растёт без остановки, поэтому её регулярно удаляют. **Компакция** (compaction) — удаление всех старых ревизий до заданной, при котором остаётся только последнее значение каждого ключа. После неё запрос ревизии старше точки компакции вернёт ошибку `mvcc: required revision has been compacted`, а watch с такой ревизии получит 410 (01-1 §5).

Компакция освобождает страницы внутри файла, но сам файл не уменьшается. **Дефрагментация** (defragmentation) — перестройка файла базы, которая выбрасывает свободные страницы и возвращает место системе. Пока она идёт, член не читает и не пишет, поэтому дефрагментируют по одному члену.

```
 после записей:      [данные|история|данные|история|история|данные]   размер = 32 МиБ
 после компакции:    [данные|свободно|данные|свободно|свободно|данные] размер = 32 МиБ
 после дефрагментации: [данные|данные|данные]                          размер = 4 МиБ
```

Схема 5. Компакция освобождает страницы внутри файла, а размер файла сжимает только дефрагментация. Квота (§3) считает размер файла, а не живые данные.

### Lease и события

**Lease etcd** — объект с временем жизни (TTL), к которому привязывают ключи; когда срок истекает, etcd сам удаляет все привязанные ключи. Не путайте его с объектами Lease в Kubernetes (01-1 §2): те лежат в etcd как обычные ключи и продлеваются клиентами.

API-сервер использует lease etcd для событий. Он привязывает каждое событие к lease с TTL, равным `--event-ttl` (1 ч), и поэтому старые события исчезают без участия контроллеров. Событий в кластере очень много: на пустом стенде они составляют больше половины ключей (01-1 §6). Каждое новое событие и каждое продление Lease узла записываются как новая ревизия.

Из этого следует главный источник нагрузки на etcd: частые мелкие записи. Это события, heartbeat узлов (01-2), статусы подов и продление лидерских аренд. В большом кластере события выносят в отдельный экземпляр etcd, чтобы их поток не мешал основным объектам; флаг API-сервера для этого — `--etcd-servers-overrides`.

## 3. Как управлять etcd

Управление состоит из пяти действий: сжимать историю, ограничивать размер базы, снимать копии, восстанавливаться из них и менять состав. Команды etcdctl ниже подразумевают адрес и сертификаты из карточки в 01-1 §4.

### Компакция и дефрагментация

**Компакцию делает API-сервер**: каждые 5 минут он просит etcd удалить историю старше предыдущей отметки. Интервал задаёт флаг `--etcd-compaction-interval` (по умолчанию 5m0s). Собственную автокомпакцию etcd (флаги `--auto-compaction-*`) в кластерах kubeadm не включают, чтобы не сжимать дважды.

Вручную компакцию запускают, когда база подошла к квоте. Сначала узнают текущую ревизию, затем сжимают до неё.

```bash
REV=$(etcdctl endpoint status -w json | jq '.[0].Status.header.revision')
etcdctl compact $REV
```

Первая команда читает ревизию из заголовка ответа, вторая удаляет всю историю до неё. Вывод второй команды — `compacted revision` с номером. Команда необратима: ревизии старше номера недоступны сразу.

Дефрагментацию в etcd 3.6 запускают на одном адресе за раз.

```bash
etcdctl --endpoints=https://10.0.0.12:2379 defrag
```

Команда дефрагментирует тот член, чей адрес указан, и блокирует его чтения и записи на время работы (секунды при базе в сотни мегабайт). Порядок такой: сначала последователи, затем лидер, каждый — после того как предыдущий снова отвечает на `endpoint health`. Лидера узнают по колонке `IS LEADER` в `endpoint status --cluster` (§4). Флаг `--cluster` у `defrag` обходит всех членов сам, но порядок контролировать труднее. Документация Kubernetes советует делать дефрагментацию как можно реже и автоматизировать её отдельным инструментом (например, etcd-defrag в CronJob), а не вручную по расписанию.

Если etcd остановлен, базу можно дефрагментировать офлайн командой `etcdutl defrag --data-dir <каталог>` (она появилась вместо `etcdctl defrag --data-dir`, который в 3.6 удалён).

### Квота базы

**Квота** (quota) — предел размера файла backend, который задаёт флаг `--quota-backend-bytes`. По умолчанию он равен 2 ГиБ, рекомендуемый максимум — 8 ГиБ, и при большем значении etcd предупреждает при старте. Квоту поднимают только после того, как понятно, почему база растёт: чаще виновата история без компакции, а не нехватка места (§5).

В кластере kubeadm флаг добавляют строкой в манифест static pod, в `/etc/kubernetes/manifests/etcd.yaml`: kubelet увидит изменение и перезапустит etcd. В кластере с несколькими членами манифест правят по очереди на каждом узле. Лабораторная работа 3 показывает это на отдельном кластере.

### Снапшот: etcdctl и etcdutl

**Снапшот** (snapshot) — согласованная копия backend в одном файле. Его снимает `etcdctl snapshot save` с одного члена, адрес которого указан в `--endpoints`. Пока снимок идёт, кластер работает как обычно.

**etcdutl** — утилита для работы с файлами etcd без запущенного сервера. Начиная с 3.6 `snapshot status` и `snapshot restore` есть только в ней, а из etcdctl они удалены. Карточка etcdctl — в 01-1 §4; etcdutl ставится вместе с ним и на стенде есть в образе etcd.

```bash
etcdctl --endpoints=https://127.0.0.1:2379 snapshot save /backup/etcd-2026-10-19.db
etcdutl snapshot status /backup/etcd-2026-10-19.db -w table
```

Первая команда пишет снимок в файл, вторая читает его заголовок и печатает хеш, ревизию, число ключей и размер. Снимок без проверки статусом ничего не гарантирует, а настоящую гарантию даёт только пробное восстановление (лабораторная работа 2).

Правила снимков такие:

- **Частота.** Снимок отражает состояние на момент записи, всё после него пропадёт; поэтому интервал равен допустимой потере (RPO, 04-3 §1).
- **Место.** Файл сразу уносят с узла control plane, иначе потеря узла уничтожит и кластер, и копию.
- **Защита.** Снимок содержит все Secret открытым текстом, если не включено шифрование (04-1 §3). Файл хранят как пароль, а ключ из `EncryptionConfiguration` хранят отдельно, но так, чтобы он нашёлся при восстановлении: без него зашифрованные Secret из снимка не прочитать.
- **Проверка.** Раз в период восстанавливают снимок на отдельном кластере, как в работе 2.

Снапшот etcd и Velero защищают разные уровни (04-3 §6): снимок возвращает кластер целиком после потери control plane, а Velero — отдельные namespace на живом кластере. Нужны оба.

### Восстановление

Восстановление создаёт новую базу из снимка. Оно всегда идёт в **новый каталог данных**, а старый остаётся нетронутым, пока восстановление не подтверждено. На кластере kubeadm с одним членом процедура такая:

1. Проверьте снимок командой `etcdutl snapshot status`.
2. Остановите API-сервер и etcd, переложив их манифесты из `/etc/kubernetes/manifests` в другой каталог (01-1 §3).
3. Восстановите снимок командой `etcdutl snapshot restore … --data-dir <новый каталог>`.
4. В манифесте etcd замените `hostPath.path` тома `etcd-data` на новый каталог.
5. Верните манифест etcd, а затем манифест API-сервера.
6. Проверьте `endpoint health`, списки namespace и состояние подов.

API-сервер останавливают потому, что его кэш (01-1 §2) помнит ревизии из будущего относительно восстановленной базы. Если сервер продолжит работать, клиенты получат расхождения между кэшем и etcd.

В etcd 3.6 у `snapshot restore` есть два флага для этой беды: `--bump-revision` добавляет к ревизии снимка заданное число, а `--mark-compacted` помечает всё до новой ревизии как сжатое. Клиенты с устаревшими ревизиями тогда получают ошибку и перечитывают данные, а не молча принимают старое состояние.

При нескольких членах каждый восстанавливается из одного и того же снимка со своими `--name`, `--initial-cluster` и `--initial-advertise-peer-urls`, но с общим `--initial-cluster-token`. Восстановление создаёт новый логический кластер с новыми идентификаторами, поэтому старые члены присоединиться к нему не смогут. Если снимок скопирован не командой `snapshot save`, а файлом из каталога данных, добавляют `--skip-hash-check`: в таком файле нет хеша целостности.

### Состав членов

Замену члена делают до потери кворума, а не после. Сначала удаляют отказавший член (`etcdctl member remove <ID>`), затем добавляют новый как **learner** — член без права голоса (`member add --learner`). Learner догоняет данные и не влияет на кворум. Когда он синхронизирован, его повышают командой `member promote`. Так кластер не рискует кворумом, пока новый член скачивает базу.

## 4. Как увидеть состояние etcd

Состояние видно по четырём источникам: статус и список членов, размер базы, метрики и распределение ключей. Первые команды разобраны в лабораторной работе 1.

### Здоровье и члены

Команда `endpoint health` проверяет, что член принял тестовую запись, а `endpoint status -w table` показывает полезные поля.

- `VERSION` — версия etcd (3.6.x в Kubernetes 1.36).
- `DB SIZE` и `IN USE` — размер файла и живая часть в нём.
- `PERCENTAGE NOT IN USE` — доля места, которую вернёт дефрагментация.
- `IS LEADER` — лидер ли этот член.
- `RAFT TERM` — текущий срок; быстрый рост значит частые выборы.
- `ERRORS` — активные тревоги, например `memberID:… alarm:NOSPACE`.

Команда `member list -w table` показывает идентификаторы, имена, адреса и признак learner. С флагом `--cluster` `endpoint status` опрашивает всех членов, а не один адрес. Новые проверки состояния в 3.6 — `/livez` (процесс жив) и `/readyz` (член может обслуживать запросы), а старый `/health` тоже остаётся.

### Размер и тревоги

Размер базы показывают `DB SIZE` и метрика `etcd_mvcc_db_total_size_in_bytes`. Квота считается по размеру файла, поэтому тревожный сигнал — размер, близкий к квоте, даже при малой `IN USE`. Команда `etcdctl alarm list` печатает активные тревоги; пустой вывод значит, что тревог нет.

Предупреждение лучше получать заранее. Поэтому на рабочем кластере настраивают оповещение, когда размер превышает примерно 80 % квоты, и отдельное — когда `IN USE` растёт, а компакция не снижает её.

### Метрики диска и лидера

etcd отдаёт метрики Prometheus на порту клиента и, у kubeadm, на `http://127.0.0.1:2381/metrics`. Для эксплуатации важны несколько метрик:

- `etcd_disk_wal_fsync_duration_seconds` — время fsync журнала; 99-й процентиль должен быть меньше 10 мс.
- `etcd_disk_backend_commit_duration_seconds` — время записи пачки в backend; 99-й процентиль меньше 25 мс.
- `etcd_server_leader_changes_seen_total` — число смен лидера; рост за час говорит о неустойчивости.
- `etcd_server_has_leader` — равно 1, пока член видит лидера.
- `etcd_mvcc_db_total_size_in_bytes` и `etcd_mvcc_db_total_size_in_use_in_bytes` — размер файла и живая часть.

Процентили считаются из гистограмм запросом PromQL. Он берёт скорость роста корзин за 5 минут и вычисляет 99-й процентиль.

```
histogram_quantile(0.99, rate(etcd_disk_wal_fsync_duration_seconds_bucket[5m]))
```

Значение выше 0,01 с на нескольких интервалах подряд значит медленный диск. Порог 10 мс взят из FAQ etcd; на нем строятся и оповещения, и разговор с командой, которая отвечает за хранилище.

### Кто создаёт нагрузку

Размер базы растёт от числа и размера объектов, а скорость ревизий — от частоты записей. Чтобы найти виновника, смотрят число ключей по ресурсам: метрика API-сервера `apiserver_storage_objects` с меткой `resource` показывает, каких объектов больше всего. Два типичных виновника — события (их много, но они живут 1 ч) и большие объекты, которые часто обновляют: ConfigMap или CRD с крупным статусом (09-1).

Скорость записи видна по приросту ревизии: если заголовок ответа `endpoint status` растёт сотнями в минуту на пустом кластере, кто-то пишет слишком часто (лабораторная работа 1, шаг 4).

## 5. Что ломается и как найти причину

Четыре поломки встречаются чаще остальных: база упёрлась в квоту, пропал кворум, диск замедлился и восстановление не удалось. Для каждой дан порядок поиска.

### database space exceeded

Симптом: все записи в кластер падают с ошибкой `etcdserver: mvcc: database space exceeded`, а чтения работают. Причина: размер файла backend достиг квоты (2 ГиБ по умолчанию), и etcd поднял тревогу `NOSPACE`. Кластер перешёл в режим «только чтение»: он принимает чтения и удаления и отклоняет остальное.

Компоненты, которые не могут писать, начинают сыпаться. Scheduler и controller-manager не продлевают аренду лидера (01-1 §2), теряют её и перезапускаются. Kubelet не обновляет статусы, а новые поды не создаются.

Порядок выхода такой:

1. Подтвердите тревогу: `etcdctl alarm list` показывает `alarm:NOSPACE`.
2. Узнайте текущую ревизию из `endpoint status`.
3. Сожмите историю: `etcdctl compact <ревизия>`.
4. Дефрагментируйте каждый член (§3), чтобы файл уменьшился.
5. Снимите тревогу: `etcdctl alarm disarm`.
6. Проверьте запись и найдите причину роста.

Без шагов 4 и 5 ничего не изменится: компакция не уменьшает файл, а тревога сама не снимается. Причину ищут отдельно (§4): сбой компакции, крупные объекты с частыми обновлениями или буря событий. Поднимать квоту без причины опасно, потому что больший файл дольше дефрагментируется и медленнее открывается. Опыт — лабораторная работа 3.

### Потеря кворума

Симптом: в трёхчленном кластере отказали два члена, и оставшийся не может выбрать лидера. Запись и свежие чтения не проходят, API-сервер отвечает ошибками, а уже запущенные поды продолжают работать, потому что kubelet не нуждается в etcd для живых контейнеров.

Порядок: сначала восстановить связь с отказавшими членами, потому что их данные целы. Если они потеряны безвозвратно, остаётся восстановление из снимка на всех членах (§3). Принудительный запуск одного члена как нового кластера (`--force-new-cluster`) документация etcd называет крайней мерой: он вызывает панику, если старые члены ещё живы, и применять его можно только когда они точно не вернутся.

### Медленный диск

Симптом: Kubernetes API отвечает медленно, в логах etcd повторяются строки `took too long … to execute` и `failed to send out heartbeat on time`, растёт `etcd_server_leader_changes_seen_total`. Причина — fsync дольше нормы, и лидер не успевает отправлять heartbeat.

Поиск: сначала метрики fsync и backend commit (§4), затем нагрузка на диск узла (`iostat -x`). Исправление — отдельный SSD под каталог данных или переезд etcd с общего диска. Если сеть между членами медленная, heartbeat-интервал поднимают до значения, близкого к времени кругового пути, а таймаут выборов — минимум в пять раз больше интервала. Это лечит симптом, а не причину.

### Сбои восстановления

Типичные ошибки восстановления из снимка:

- **Старый каталог.** Забыли сменить `hostPath` в манифесте: etcd поднимается на старых данных, и кажется, что восстановление «не сработало».
- **Занятый каталог.** Восстановление в существующий каталог не выполняется: нужен новый путь.
- **Не те имя и адрес.** Если `--name` и `--initial-advertise-peer-urls` не совпали с манифестом, член получает неверные адреса в списке членов. Для одного члена кластер ещё работает, а при добавлении второго возникают сбои.
- **Работающий API-сервер.** Кэш расходится с базой (§3).
- **Файл без хеша.** Снимок из каталога данных восстанавливается только с `--skip-hash-check`.

Первое, что проверяют после восстановления, — `member list` и путь к данным в манифесте.

## 6. Пределы и значения по умолчанию

Ниже собраны числа этой части. Значения взяты из документации etcd 3.6 и Kubernetes 1.36.

### Размеры и квота

- Квота backend — 2 ГиБ по умолчанию, рекомендуемый максимум 8 ГиБ (`--quota-backend-bytes`).
- Запрос к etcd — не больше 1,5 МиБ; ConfigMap и Secret ограничены 1 МиБ.
- Память — около 8 ГиБ для типичного кластера, 16–64 ГиБ при тысячах watch и миллионах ключей.
- Диск — SSD; около 500 последовательных IOPS при нагрузке, 50 для небольшого кластера.

### Время и частота

- Heartbeat — 100 мс, election timeout — 1000 мс (по умолчанию etcd).
- Компакция API-сервера — каждые 5 минут (`--etcd-compaction-interval`).
- TTL событий — 1 час (`--event-ttl`).
- `--snapshot-count` — 10000 (в 3.5 было 100000).
- Пороги 99-го процентиля — fsync журнала 10 мс, commit backend 25 мс.

### Состав и версии

- Членов — 3 или 5, максимум 7, нечётное число.
- Kubernetes 1.36 с kubeadm ставит etcd 3.6.8, а 1.37 — 3.7.0.
- В 3.6 удалено хранилище v2 (`--enable-v2`, проверка `etcdutl check v2store`), память упала примерно вдвое, добавлены `/livez` и `/readyz`. Перед обновлением с 3.5 надо сначала дойти до 3.5.20 или новее.
- Версия 3.6.0 — первая с полноценным понижением (`etcdctl downgrade validate`, затем `downgrade enable`). Снимок перед ним обязателен.
- В 3.7 добавлен RangeStream, который 1.37 использует через флаг `EtcdRangeStream`, и удалены флаги `--experimental-*`.

<summary>Ответ</summary>

1. Кворум четырёх равен трём, поэтому потерять можно по-прежнему одного члена, как и в трёх. Зато каждая запись должна дойти до большего числа членов.

3. Частую смену лидера: он не успевает посылать heartbeat из-за медленного диска, перегрузки узла или потерь в сети.

**Схема опыта.**

```
1. кластер lab-10-2 + namespace lab-10-2 (маркер)
2. snapshot save ──► файл на узле и копия на хосте
3. потеря: удалить lab-10-2, создать lab-10-2-after (появился после снимка)
4. restore в /var/lib/etcd-restored, смена hostPath, перезапуск static pod
5. проверка: lab-10-2 вернулся, lab-10-2-after исчез
```

Схема 7. Процедура восстановления: пять шагов от создания метки до проверки.

#### Шаг 1. Создать кластер и метку

Команда создаёт кластер со своим kubeconfig, задаёт функции `k` и `ec` и создаёт namespace с ConfigMap-меткой.

```bash
mkdir -p ~/lab/k8s/10-2
kind create cluster --name lab-10-2 --image kindest/node:v1.36.1 \
  --kubeconfig ~/lab/k8s/10-2/kubeconfig --wait 120s
k() { kubectl --kubeconfig ~/lab/k8s/10-2/kubeconfig "$@"; }
ec() { k -n kube-system exec etcd-lab-10-2-control-plane -- etcdctl \
  --endpoints=https://127.0.0.1:2379 --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt --key=/etc/kubernetes/pki/etcd/server.key "$@"; }
k create namespace lab-10-2
k -n lab-10-2 create configmap marker --from-literal=text=before-snapshot
k get nodes
ec endpoint health
```

| Часть команды | Значение |
|---|---|
| `kind create cluster --name lab-10-2` | создать кластер с контейнером `lab-10-2-control-plane` |
| `--kubeconfig …/kubeconfig` | записать доступ в отдельный файл, не в `~/.kube/config` |
| `--wait 120s` | ждать готовности control plane до 120 секунд |
| `k()` | kubectl, привязанный к этому файлу |
| `ec()` | etcdctl в поде etcd нового кластера, сертификаты как в карточке 01-1 §4 |
| `create configmap marker` | запись, которая должна пережить восстановление |

Ожидаемый результат:

```
namespace/lab-10-2 created
configmap/marker created
NAME                     STATUS   ROLES           AGE   VERSION
lab-10-2-control-plane   Ready    control-plane   …     v1.36.1
https://127.0.0.1:2379 is healthy: successfully committed proposal: took = …ms
```

Разбор: кластер из одного узла готов, etcd здоров, а метка `before-snapshot` записана до снимка.

#### Шаг 2. Снять снапшот

Команда снимает снапшот в каталог данных узла, проверяет его и копирует на хост.

```bash
ec snapshot save /var/lib/etcd/snap-10-2.db
k -n kube-system exec etcd-lab-10-2-control-plane -- \
  etcdutl snapshot status /var/lib/etcd/snap-10-2.db -w table
docker cp lab-10-2-control-plane:/var/lib/etcd/snap-10-2.db ~/lab/k8s/10-2/snap-10-2.db
ls -l ~/lab/k8s/10-2/snap-10-2.db
```

| Часть команды | Значение |
|---|---|
| `snapshot save <путь>` | снять копию backend в файл на узле (внутри пода это `/var/lib/etcd`) |
| `etcdutl snapshot status -w table` | прочитать заголовок файла: хеш, ревизию, ключи, размер |
| `docker cp` | унести файл с узла на хост |
| `ls -l` | проверить, что копия на хосте не пуста |

Ожидаемый результат (перед строкой `Snapshot saved` etcdctl печатает служебные JSON-записи, здесь они опущены):

```
Snapshot saved at /var/lib/etcd/snap-10-2.db
| HASH | REVISION | TOTAL KEYS | TOTAL SIZE |
| …    | …        | … (сотни)  | … МБ       |
```

Разбор:

1. Файл создан на узле, а `docker cp` кладёт копию на хост: так делают всегда, ведь снимок на узле погибнет вместе с узлом.
2. `REVISION` — ревизия на момент снимка; всё, что запишут после неё, в снимке отсутствует.
3. `TOTAL KEYS` — число ключей во всём кластере, а не одного namespace (сравните с Velero в 04-3 §6).

#### Шаг 3. Потерять данные

Команда создаёт namespace после снимка и удаляет метку.

```bash
k create namespace lab-10-2-after
k delete namespace lab-10-2
k get namespace lab-10-2 lab-10-2-after
```

| Часть команды | Значение |
|---|---|
| `create namespace lab-10-2-after` | данные, созданные после снимка |
| `delete namespace lab-10-2` | потеря метки |
| `get namespace … …` | показать, что осталось |

Ожидаемый результат:

```
Error from server (NotFound): namespaces "lab-10-2" not found
NAME              STATUS   AGE
lab-10-2-after    Active   …
```

Разбор: метки нет, а `lab-10-2-after` существует. После восстановления должно быть наоборот, потому что в снимке есть только `lab-10-2`.

#### Шаг 4. Восстановить в новый каталог

Сначала одноразовый под из того же образа, что и etcd, восстанавливает снимок в каталог `/var/lib/etcd-restored` на узле. Он нужен потому, что на узле нет `etcdutl`. Адрес и образ берутся из кластера, чтобы имя и адрес члена совпали с манифестом.

```bash
IP=$(k get node lab-10-2-control-plane \
  -o jsonpath='{.status.addresses[?(@.type=="InternalIP")].address}')
IMG=$(k -n kube-system get pod etcd-lab-10-2-control-plane \
  -o jsonpath='{.spec.containers[0].image}')
k apply -f - <<EOF
apiVersion: v1
kind: Pod
metadata: {name: restore, namespace: lab-10-2-after}
spec:
  nodeName: lab-10-2-control-plane
  restartPolicy: Never
  containers:
  - name: etcdutl
    image: $IMG
    command:
    - etcdutl
    - snapshot
    - restore
    - /host/etcd/snap-10-2.db
    - --data-dir=/host/etcd-restored
    - --name=lab-10-2-control-plane
    - --initial-cluster=lab-10-2-control-plane=https://$IP:2380
    - --initial-advertise-peer-urls=https://$IP:2380
    volumeMounts: [{name: host, mountPath: /host}]
  volumes:
  - name: host
    hostPath: {path: /var/lib}
EOF
k -n lab-10-2-after wait --for=jsonpath='{.status.phase}'=Succeeded pod/restore --timeout=90s
docker exec lab-10-2-control-plane ls /var/lib/etcd-restored/member
```

| Часть команды | Значение |
|---|---|
| `IP=$(… InternalIP)` | адрес узла, он же адрес пиров etcd |
| `IMG=$(… .image)` | образ etcd из манифеста, он содержит `etcdutl` |
| `nodeName: lab-10-2-control-plane` | запустить под сразу на узле, минуя scheduler |
| `snapshot restore /host/etcd/snap-10-2.db` | восстановить из файла снимка |
| `--data-dir=/host/etcd-restored` | новый каталог (на узле `/var/lib/etcd-restored`) |
| `--name`, `--initial-cluster`, `--initial-advertise-peer-urls` | задать членство, как в манифесте |
| `hostPath: {path: /var/lib}` | показать поду каталог `/var/lib` узла как `/host` |
| `ls …/member` | проверить, что в каталоге появились данные |

Ожидаемый результат:

```
pod/restore created
pod/restore condition met
snap
wal
```

Разбор: под завершился успешно, и в `/var/lib/etcd-restored/member` лежат каталоги `snap` и `wal`. Старый каталог `/var/lib/etcd` не тронут.

Теперь переключаем etcd на новый каталог. Сначала останавливаем API-сервер и etcd: их манифесты уходят из каталога static pod.

```bash
N=lab-10-2-control-plane
docker exec $N sh -c 'mkdir -p /etc/kubernetes/off && \
  mv /etc/kubernetes/manifests/kube-apiserver.yaml /etc/kubernetes/manifests/etcd.yaml \
  /etc/kubernetes/off/'
docker exec $N sh -c 'sleep 20; crictl ps | grep -E "etcd|apiserver" || echo "stopped"'
docker exec $N sed -i 's|^\( *\)path: /var/lib/etcd$|\1path: /var/lib/etcd-restored|' \
  /etc/kubernetes/off/etcd.yaml
docker exec $N grep -n 'path: /var/lib/etcd' /etc/kubernetes/off/etcd.yaml
```

| Часть команды | Значение |
|---|---|
| `mv … /etc/kubernetes/off/` | убрать манифесты из каталога static pod; kubelet остановит поды |
| `crictl ps \| grep …` | убедиться, что контейнеры etcd и API-сервера исчезли |
| `sed -i 's\|…path: /var/lib/etcd$\|…'` | заменить в манифесте путь тома данных на новый каталог |
| `grep -n 'path: /var/lib/etcd'` | проверить замену |

Ожидаемый результат:

```
stopped
NN:      path: /var/lib/etcd-restored
```

Разбор: строка `stopped` значит, что контейнеров нет. Найденная строка с `path:` должна указывать на `etcd-restored`; значение `mountPath` (внутри пода) остаётся прежним `/var/lib/etcd`.

Теперь возвращаем манифесты: сначала etcd, потом API-сервер, и ждём ответа API.

```bash
docker exec $N mv /etc/kubernetes/off/etcd.yaml /etc/kubernetes/manifests/
sleep 10
docker exec $N mv /etc/kubernetes/off/kube-apiserver.yaml /etc/kubernetes/manifests/
until k get --raw /readyz >/dev/null 2>&1; do sleep 3; done
ec member list -w table
```

| Часть команды | Значение |
|---|---|
| `mv … /etc/kubernetes/manifests/` | kubelet запускает static pod заново |
| `until k get --raw /readyz` | ждать, пока API-сервер станет готов |
| `ec member list` | проверить адрес и имя члена после восстановления |

Ожидаемый результат: список членов показывает один член `lab-10-2-control-plane` со статусом `started` и адресом `https://<IP>:2380`.

Разбор: адрес пира совпадает с манифестом, потому что мы передали `--name` и `--initial-advertise-peer-urls` при восстановлении. Без них член получил бы имя `default` и адрес `localhost:2380`.

#### Шаг 5. Проверить результат

Команда проверяет, что вернулось состояние снимка.

```bash

```

| Часть команды | Значение |
|---|---|
| `get namespace lab-10-2 lab-10-2-after` | запросить оба namespace |
| `jsonpath='{.data.text}'` | прочитать значение метки |

Ожидаемый результат:

```

lab-10-2   Active   …

```

Разбор:

1. `lab-10-2` вернулся вместе с ConfigMap, а `before-snapshot` — значение на момент снимка.
2. `lab-10-2-after` исчез, потому что был создан после снимка: восстановление не накладывает изменения, а возвращает состояние.

2. Что случится с объектами, созданными после снимка?
3. Зачем перед заменой данных останавливают API-сервер?
4. Чем снапшот etcd отличается от бэкапа Velero?

<details>
<summary>Ответ</summary>

1. Старый каталог остаётся откатом: если восстановление не удалось, достаточно вернуть прежний `hostPath`. Удалять его можно, когда новый кластер проверен.
2. Они пропадут: восстановление возвращает состояние на момент снимка. Допустимая потеря равна интервалу между снимками.
3. Кэш API-сервера помнит ревизии новее восстановленной базы. Запущенный сервер выдал бы клиентам состояние, которого в базе нет.
4. Снимок возвращает кластер целиком на момент съёма и нужен после потери control plane. Velero возвращает выбранные объекты и тома на живом кластере (04-3 §6).

### Лабораторная работа 3. Размер, компакция, дефрагментация и квота

Эту работу вы выполняете сами, результаты в ней — ожидаемые.

**Риски.**

- **Что меняется:** в манифест etcd кластера `lab-10-2` добавляется квота 32 МиБ, затем база намеренно доводится до тревоги `NOSPACE`.
- **Надолго ли:** до конца работы; во время тревоги кластер `lab-10-2` не принимает записи, а scheduler и controller-manager могут перезапускаться.
- **Безопасность и влияние:** затронут только кластер `lab-10-2`; стенд и хост не меняются.
- **Откат:** тревогу снимают шагом 5, кластер удаляется в уборке.

**Цель.** Увидеть, как история ревизий раздувает базу, довести её до тревоги и выйти из неё компакцией, дефрагментацией и снятием тревоги.

**Что понадобится.**

- Кластер `lab-10-2` из работы 2 с функциями `k` и `ec`; если работа 2 пропущена, создайте их по шагу 1 работы 2.
- jq из 00-2.

**Схема опыта.**

```
квота 32 МиБ ── 70 обновлений ConfigMap по 400 КБ ──► база ≈ 32 МиБ, тревога NOSPACE
        compact ► IN USE падает, размер файла прежний
        defrag  ► размер файла падает
        alarm disarm ► запись снова работает
```

Схема 8. Четыре шага выхода из `database space exceeded`: размер файла уменьшает только дефрагментация.

#### Шаг 1. Базовый размер

Команда определяет функцию `st`, которая печатает ревизию, размер файла и живую часть.

```bash
st() { ec endpoint status -w json | jq -c '.[0].Status | {rev: .header.revision, db: .dbSize, inuse: .dbSizeInUse}'; }
st
```

| Часть команды | Значение |
|---|---|
| `endpoint status -w json` | статус в JSON |
| `.header.revision` | текущая ревизия |
| `.dbSize` | размер файла в байтах |
| `.dbSizeInUse` | живая часть файла в байтах |

Ожидаемый результат: объект с тремя числами; размер базы свежего кластера — единицы мегабайт.

```
{"rev":…,"db":…,"inuse":…}
```

Разбор: запомните `db` и `inuse` — шаги 4 и 5 сравнивают с ними.

#### Шаг 2. Уменьшить квоту до 32 МиБ

Команда добавляет флаг квоты в манифест etcd, и kubelet перезапускает под.

```bash
N=lab-10-2-control-plane
docker exec $N sed -i 's|^    - etcd$|    - etcd\n    - --quota-backend-bytes=33554432|' \
  /etc/kubernetes/manifests/etcd.yaml
docker exec $N grep -n quota /etc/kubernetes/manifests/etcd.yaml
until ec endpoint health >/dev/null 2>&1; do sleep 3; done
st
```

| Часть команды | Значение |
|---|---|
| `sed -i 's\|^    - etcd$\|…'` | вставить новую строку флага после имени команды |
| `--quota-backend-bytes=33554432` | квота 32 МиБ (32 × 1024 × 1024 байт) |
| `grep -n quota` | проверить, что строка появилась |
| `until ec endpoint health` | ждать, пока etcd перезапустится |

Ожидаемый результат:

```

{"rev":…,"db":…,"inuse":…}
```

Разбор: флаг в манифесте и работающий etcd подтверждают смену. Квота 32 МиБ мала нарочно, чтобы дойти до неё за минуту; рабочие значения — от 2 до 8 ГиБ (§6).

#### Шаг 3. Раздуть базу ревизиями

Команда создаёт ConfigMap в 400 КБ и обновляет его в цикле, пока etcd не откажет.

```bash
head -c 400000 /dev/zero | tr '\0' 'a' > ~/lab/k8s/10-2/payload.txt
k create namespace lab-10-2
k -n lab-10-2 create configmap big --from-file=payload=$HOME/lab/k8s/10-2/payload.txt
for i in $(seq 1 200); do
  k -n lab-10-2 patch configmap big --type merge -p "{\"data\":{\"n\":\"$i\"}}" >/dev/null || break
done
echo "остановились на i=$i"
```

| Часть команды | Значение |
|---|---|
| `head -c 400000 … tr` | файл из 400 000 букв `a` |
| `create configmap big` | объект размером около 400 КБ (предел ConfigMap — 1 МиБ) |
| `patch --type merge` | изменить поле `n`, а etcd запишет весь объект новой ревизией |
| `\|\| break` | остановить цикл при первой ошибке записи |

Ожидаемый результат: цикл останавливается после 60–70 итераций, kubectl перед этим печатает ошибку записи.

```
Error from server: … etcdserver: mvcc: database space exceeded
остановились на i=…
```

Разбор:

1. Каждое обновление добавляет в базу ещё одну копию в 400 КБ, поэтому около 70 обновлений заполняют 32 МиБ.
2. Живое значение одно, в нём 400 КБ. Остальное — история, которую ещё не удалила компакция.
3. Текст ошибки совпадает с тем, который пользователи видят в рабочих кластерах при квоте в 2 ГиБ.

#### Шаг 4. Увидеть тревогу и режим «только чтение»

Команда показывает тревогу, пробует записать новый объект, читает старый и печатает размеры.

```bash
ec alarm list
k -n lab-10-2 create configmap small --from-literal=a=b
k -n lab-10-2 get configmap big -o jsonpath='{.metadata.name}{"\n"}'
st
```

| Часть команды | Значение |
|---|---|
| `alarm list` | перечислить активные тревоги |
| `create configmap small` | попытка записи |
| `get configmap big` | чтение |
| `st` | размеры из шага 1 |

Ожидаемый результат:

```
memberID:… alarm:NOSPACE
Error from server: … etcdserver: mvcc: database space exceeded
big
{"rev":…,"db":≈33554432,"inuse":≈ db}
```

Разбор:

1. `alarm:NOSPACE` — etcd перевёл кластер в режим «только чтение».
2. Запись нового объекта отклонена, а чтение `big` работает.
3. `db` близок к квоте, а `inuse` почти равен `db`: история ещё не сжата, поэтому занятые страницы считаются живыми.

Проверьте и побочный эффект: компоненты, которым нужна запись, могли перезапуститься.

```bash
k -n kube-system get pods
```

В выводе у `kube-scheduler` и `kube-controller-manager` счётчик `RESTARTS` мог вырасти: они не смогли продлить аренду лидера и вышли (01-1 §2).

#### Шаг 5. Выйти из аварии

Команды сжимают историю, дефрагментируют член и снимают тревогу; `st` показывает размеры между действиями.

```bash
REV=$(ec endpoint status -w json | jq '.[0].Status.header.revision')
ec compact $REV
st
ec defrag
st
ec alarm disarm
ec alarm list
k -n lab-10-2 create configmap small --from-literal=a=b
```

| Часть команды | Значение |
|---|---|
| `REV=$(… .header.revision)` | текущая ревизия |
| `compact $REV` | удалить историю до этой ревизии |
| `defrag` | перестроить файл базы |
| `alarm disarm` | снять тревогу `NOSPACE` |
| `create configmap small` | проверить, что запись снова работает |

Ожидаемый результат:

```
compacted revision …
{"rev":…,"db":≈33554432,"inuse":≈0,4 МиБ + база}
Finished defragmenting etcd member[https://127.0.0.1:2379]. took …
{"rev":…,"db":≈4 МиБ,"inuse":≈ db}
memberID:… alarm:NOSPACE      (команда disarm печатает снятую тревогу)
configmap/small created
```

Разбор:

1. После `compact` значение `inuse` резко падает, а `db` остаётся прежним: страницы освобождены внутри файла, но файл не сжался.
2. После `defrag` падает и `db`: файл перестроен без свободных страниц.
3. `alarm disarm` снимает тревогу; пустой `alarm list` и успешное создание `small` подтверждают, что запись восстановилась.
4. Порядок важен: тревога без компакции вернётся сразу, потому что файл опять переполнен.

**Итог.**

| Что узнали | Где видно |
|---|---|
| Каждое обновление добавляет полную копию объекта | шаг 3, рост `db` |
| При квоте кластер доступен только на чтение | шаг 4 |
| Компакция освобождает страницы, но не уменьшает файл | шаг 5, `db` и `inuse` |
| Файл сжимает только дефрагментация | шаг 5 |
| Тревогу надо снять вручную | `alarm disarm` |

**Уборка.** Удаляем кластер, каталог работы и функции.

```bash
kind delete cluster --name lab-10-2 --kubeconfig ~/lab/k8s/10-2/kubeconfig
rm -rf ~/lab/k8s/10-2
unset -f k ec st
kind get clusters
docker ps -a --filter name=lab-10-2
```

Первая команда удаляет контейнер узла и запись в kubeconfig работы, вторая стирает каталог файлов, третья снимает функции. Две последние команды проверяют уборку: список кластеров не должен содержать `lab-10-2`, а список контейнеров должен быть пуст.

**Вопросы для самопроверки.**

1. Почему после компакции размер файла не изменился?
2. В каком порядке выходят из `database space exceeded` и почему?
3. Что вы сделаете, если база выросла из-за события-бури, а не из-за долгой истории?
4. Почему на рабочем кластере не поднимают квоту выше 8 ГиБ?

<details>
<summary>Ответ</summary>

1. Компакция только помечает страницы внутри файла свободными. Размер файла уменьшает дефрагментация.
2. Сначала компакция (освободить страницы), затем дефрагментация (сжать файл), затем `alarm disarm`. Если снять тревогу раньше, база снова упрётся в квоту и тревога вернётся.
3. Нужно найти источник событий (`apiserver_storage_objects`, §4), остановить его, затем сжать и дефрагментировать. Для постоянной нагрузки события выносят в отдельный etcd (§2).
4. Файл большего размера дольше дефрагментируется и открывается, а пока идёт дефрагментация, член не обслуживает запросы. Рекомендуемый максимум — 8 ГиБ.

</details>
