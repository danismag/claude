# 12-3. System design на Kubernetes

> Модуль 12 «Подготовка к собеседованию» · часть 3 из 4 · 🟡🔴 · ~2 ч · Нужно: доска или лист бумаги. Опирается на весь курс.
>
> **Формат собеседования:** 45–60 минут, расплывчатая постановка («спроектируйте платформу для команд»). Оценивают: уточнение требований, компромиссы, цифры, эксплуатацию (как это обновлять, мониторить, чинить), а не перечень модных инструментов.

## Задача 1. Платформа для 30 продуктовых команд 🔴

**Постановка.** Компания переводит 30 команд (~200 сервисов) на Kubernetes. Нужна платформа: команды деплоят сами, не мешают друг другу, платформа отвечает за надёжность и безопасность. Облако, managed Kubernetes.

### Как ответил бы сильный кандидат

**1. Уточнения.**
- Окружения: dev/stage/prod?
- Требования изоляции: PCI/персональные данные у части команд?
- Нагрузка: суммарно ~2 000 RPS, пик ×3.
- Свои БД или managed?
- Есть ли CI и Git-хостинг?
- Сколько людей в платформенной команде (допустим, 5)?

**2. Размер.**
- 200 сервисов × 3 реплики × (0,25 CPU, 512 MiB) ≈ 150 CPU и 300 GiB на prod;
- с запасом на узлы и системные поды — ~25 узлов по 8 CPU/32 GiB, в 3 зонах;
- dev/stage меньше: 1 реплика, spot-узлы.

**3. Кластеры.**
- **prod** отдельно от **non-prod** — минимальный blast radius и разные права;
- для регуляторных сервисов — отдельный кластер (если требует аудит).

Итого 2–3 кластера. Кластер на команду — избыточно для 5 человек платформы. Namespace на команду × окружение даёт достаточную изоляцию при правильных политиках.

**4. Мультитенантность (namespace на команду):**

| Механизм | Что даёт | Часть |
|---|---|---|
| ResourceQuota + LimitRange | бюджет команды, дефолтные requests, защита от «съесть кластер» | 05-1 |
| NetworkPolicy default-deny + разрешения | сеть между командами только явно, DNS разрешён | 03-5 |
| PSA `restricted` (enforce) | нет privileged, root, hostPath | 06-2 |
| Kyverno/ValidatingAdmissionPolicy | свой реестр, запрет `:latest`, обязательные метки владельца, probes, requests | 06-2, 09-2 |
| Доступ через SSO-группы | команда управляет своими ns, платформа — кластером | — |
| PriorityClass | платформенные компоненты не вытесняются | 05-2 |

**5. Поставка.**
- GitOps (Argo CD): репозиторий платформы (аддоны, политики, namespace команд через ApplicationSet по каталогу `teams/`) и репозитории команд;
- онбординг команды — merge request в `teams/<team>.yaml`, генерируются namespace, квоты и Application (08-2);
- единый Helm chart «сервис» с безопасными дефолтами (probes, PDB, spread, securityContext) — команды задают только values (07-1).

**6. Входящий трафик.**
- Gateway API: GatewayClass и Gateway — у платформы, HTTPRoute — у команд с ReferenceGrant;
- cert-manager для TLS (03-4);
- Envoy ≥ 3 реплики со spread по зонам (урок 11-3).

**7. Ключевые решения и компромиссы.**
- *Один prod-кластер или по зонам/регионам?* Один мультизональный — проще. Потеря региона закрывается вторым регионом позже, по требованиям RTO.
- *CPU limits?* Requests обязательны (политика), limits — по выбору команды, на CPU по умолчанию нет. Мониторинг троттлинга (05-1).
- *Секреты:* External Secrets Operator из облачного хранилища. Командам — ExternalSecret, но не сами значения (04-1).
- *Автомасштабирование:* HPA — на командах (chart), Cluster Autoscaler/Karpenter — на платформе; квоты ограничивают максимальный масштаб.

**8. Отказы.**
- Узел/зона: spread и PDB в chart'е по умолчанию; ёмкость N+1 зона (при 3 зонах — 50 % запаса для 2 оставшихся или осознанно меньше с приоритетами).
- Вебхук политик упал: `failurePolicy` и исключения для kube-system, ≥ 2 реплики (09-2).
- Argo CD недоступен: деплои стоят, работающее не страдает; самоуправляемый Argo CD — bootstrap-процедура в runbook.

**9. Эксплуатация.**
- **Обновления**: managed control plane — раз в квартал по одному минору (сначала non-prod), узлы — surge-пулами (10-2).
- **Наблюдаемость**: метрики (Prometheus + долгое хранение), логи, трассировки. SLO по сервисам. Дашборд и алерты на команду генерируются платформой.
- **Стоимость**: метки владельца → отчёт по командам (requests × цена), правило «requests ≈ p95 использования», VPA в режиме рекомендаций.
- **Поддержка**: документация golden path, шаблон сервиса, тренажёры 12-2 для онбординга дежурных.

**Чего избегать:**
- кластер на команду при маленькой платформенной команде;
- «всё разрешено, потом закрутим» — политики проще ввести с первого дня;
- ручной `kubectl apply` в prod.

## Задача 2. Zero-downtime поставка orders-api с БД и откатом 🔴

**Постановка.** orders-api (stateless, 6 реплик) + PostgreSQL. Нужно: релизы несколько раз в день без ошибок у клиентов, миграции схемы, откат за минуты. GitOps уже есть.

### Как ответил бы сильный кандидат

**1. Уточнения.**
- SLO ошибок (например, < 0,1 % 5xx за релиз);
- длительность миграций и размер таблиц;
- клиенты — браузер или другие сервисы с ретраями;
- нужен ли canary;
- БД — оператор в кластере (CNPG) или managed.

**2. Путь релиза.**

```
PR → CI: тесты, сборка образа (тег = git sha), скан, подпись → push в реестр
   → CI обновляет тег в repo окружения dev (или Image Updater) → Argo CD sync dev
   → автотесты dev → MR: тег в stage → sync → smoke + нагрузочный
   → MR: тег в prod → Argo Rollouts / Gateway canary 5 % → 25 % → 100 % по метрикам
```

**3. Нулевой простой на уровне подов** (02-5, 05-2):
- readiness, которая честно отражает готовность (без каскада на БД в liveness);
- `preStop` sleep 5–10 с + обработка SIGTERM + `terminationGracePeriodSeconds` с запасом — без гонки эндпоинтов (на стенде без этого были ошибки при каждом rollout);
- `maxUnavailable: 0`, `maxSurge: 25%` — ёмкость не падает;
- PDB `minAvailable: 5` (из 6), topology spread по зонам;
- HTTP keep-alive: клиенты переподключаются; для gRPC — L7-балансировка.

**4. Миграции БД — главный риск отката.** Схема expand/contract:

| Релиз | БД | Код |
|---|---|---|
| N | добавить колонку `new_col` (nullable, без блокировок) | пишет в обе, читает старую |
| N+1 | backfill батчами | читает новую |
| N+2 | (после стабилизации) удалить старую колонку | только новая |

- Каждый релиз совместим с предыдущей версией схемы — откат кода всегда безопасен.
- Миграция — отдельный Job как PreSync hook Argo CD (или из CI), идемпотентная, с `lock_timeout` (08-2).
- Опасные операции (`ALTER` с перезаписью таблицы, индекс без `CONCURRENTLY`) — запрещены линтером миграций.

**5. Canary и автоматический откат.**
- Argo Rollouts (или Flagger) с Gateway API: веса в HTTPRoute (03-4);
- AnalysisTemplate по Prometheus: доля 5xx и p99 canary против stable;
- провал анализа → автоматический abort → трафик на stable за секунды.

**6. Откат.**
- Быстрый: abort canary (секунды).
- После полного выката: `git revert` коммита с тегом → Argo CD sync → rolling update (~1–2 мин на 6 подов).
- Ручной `kubectl rollout undo` при включённом self-heal перезапишется — runbook запрещает его в prod (08-1).
- Откат миграций не делаем — их совместимость обеспечена expand/contract.

**7. Отказы.**
- Реестр недоступен во время релиза: новые поды в ImagePullBackOff, старые работают (`maxUnavailable: 0`). Зеркало/кэш реестра.
- Argo CD недоступен: релиз откладывается, ничего не ломается.
- Failover БД во время релиза: окно ошибок записи ~2,5 с (CNPG, 09-1) — ретраи в приложении и `connect_timeout` в клиенте (без него клиент висит вечно, 09-1).

**8. Метрики релиза**:
- доля 5xx и p99 до/во время/после;
- время выката;
- частота откатов;
- DORA-метрики (lead time, частота деплоев, change failure rate, MTTR).

## Задача 3. Кластер в двух зонах с DR 🔴

**Постановка.** On-prem: два ЦОД (зоны) в одном городе, задержка 1 мс. Kubernetes self-hosted. Требование: потеря одного ЦОД — сервис работает (RTO 15 мин, RPO 1 мин), плюс восстановление после логической катастрофы (удалили namespace, повредили данные).

### Как ответил бы сильный кандидат

**1. Уточнения.**
- Есть ли третья площадка (хотя бы маленькая)? Это определяет кворум.
- Какое хранилище: распределённое между ЦОД или локальные диски?
- Какие данные критичны: БД, очереди, файлы?
- Что значит «сервис работает»: полная ёмкость или деградация?

**2. Ключевая проблема — кворум.** etcd с 3 или 5 членами на двух площадках: одна площадка всегда держит большинство. Если пропадёт именно она — кворума нет, control plane встаёт (01-3). Варианты:

| Вариант | Плюсы | Минусы |
|---|---|---|
| **3-я площадка-арбитр** с одним членом etcd (2+2+1 или 1+1+1) | автоматическое переживание потери любой площадки | нужна третья площадка с низкой задержкой |
| Растянутый кластер 2+1 без арбитра | просто | потеря «большой» площадки = ручное восстановление control plane |
| **Два кластера** (по одному на ЦОД) + GitOps в оба + репликация данных | независимые отказы, проще обновлять по одному | данные и трафик переключать на уровне выше (DNS/GSLB), сложнее stateful |

Рекомендация:
- при наличии третьей площадки — растянутый кластер с арбитром;
- без неё — **два кластера active/active** для stateless и active/passive для БД;
- Kubernetes-манифесты одинаковы через GitOps (ApplicationSet по кластерам, 08-2).

**3. Stateless.**
- Topology spread по зонам (`topology.kubernetes.io/zone`), ёмкость каждой зоны ≥ 100 % пиковой нагрузки (или с приоритетами — деградация некритичного);
- Gateway в обеих зонах;
- внешний балансировщик/GSLB с health check.

**4. Данные.**
- PostgreSQL: оператор с синхронной репликой в другой зоне (RPO ≈ 0 для подтверждённых транзакций, цена — задержка записи +1 мс) и асинхронной — для чтения.
- Failover — оператором (секунды, 09-1). В схеме «два кластера» — реплика в другом кластере (replica cluster) и ручное/автоматическое повышение по runbook.
- Тома: локальные диски + репликация средствами БД предпочтительнее растянутого сетевого хранилища (split-brain у хранилища опаснее).

**5. Логическая катастрофа** (удалили namespace, плохая миграция) — репликация не спасает, она копирует ошибку:
- бэкапы БД с PITR (WAL-архив в объектное хранилище в другой площадке): RPO минуты, проверка восстановления по расписанию;
- состояние кластера — из GitOps (манифесты) плюс регулярные бэкапы состояния кластера по процедуре kubeadm/etcd (деталей в курсе нет: часть 10-1 не опубликована) и инструменты вроде Velero для ресурсов и томов;
- защита от удаления: права на удаление ns и CRD только у платформы, `Prune=false` для критичного, finalizer-защита (09-2).

**6. Учения.**
- Раз в квартал: выключить площадку (как `systemctl stop kubelet` в 11-3, но целиком), замерить фактический RTO;
- восстановить БД из бэкапа на отдельный стенд;
- проверить, что алерты сработали.
- RTO без учений — предположение.

**7. Цифры для ответа.**
- Потеря узла: эндпоинты убираются за ~50 с, эвикция — через 300 с, критичным подам уменьшить `tolerationSeconds` (11-3).
- При двух зонах после потери одной ёмкость падает на 50 % — запас 100 % или приоритеты.
- etcd: задержка между членами < 10 мс, иначе таймауты лидера. 1 мс — нормально.

## Мини-задачи (10–15 мин каждая)

| # | Задача | На что обратить внимание |
|---|---|---|
| 1 | Сервису нужна очередь задач с масштабированием от 0 | KEDA по длине очереди, Job vs Deployment, `terminationGracePeriodSeconds` под длительность задачи, идемпотентность (05-3) |
| 2 | Batch-обработка ночью, днём ресурсы для онлайна | CronJob, PriorityClass (онлайн выше), отдельный пул spot-узлов с taint, квоты (02-4, 05-2) |
| 3 | Нужно показать клиентам их реальный IP в логах | `externalTrafficPolicy: Local` и распределение подов Gateway или PROXY protocol на балансировщике (03-4) |
| 4 | Миграция с ingress-nginx на Gateway API | Параллельная работа, перенос аннотаций в типизированные поля, по одному хосту, DNS-переключение, откат (03-4) |
| 5 | Сократить счёт за кластер на 30 % | Requests по фактическому потреблению (VPA-рекомендации), консолидация (Karpenter), spot для stateless/batch, выключение non-prod ночью, лимиты на логи и метрики (05-3, 05-4) |
| 6 | Каждый деплой даёт 1–2 % ошибок | Гонка эндпоинтов: preStop, SIGTERM, readiness, keep-alive (02-5) |
| 7 | Секреты команд хранятся в Git в base64 | Ротация утёкших, External Secrets/SOPS, сканер секретов в CI, политика (04-1) |
| 8 | 500 микросервисов и gRPC — нагрузка неравномерна | L4 kube-proxy не балансирует запросы в одном HTTP/2-соединении — L7 (Gateway/mesh) или клиентская балансировка по headless Service (03-2) |

## Типичные ошибки на system design

- Сразу рисовать схему с 15 инструментами, не уточнив требования.
- Не назвать ни одной цифры (RPS, узлы, RTO).
- Забыть данные: «stateless красиво, а БД — потом».
- Не обсудить отказ зоны/площадки и кворум.
- Не сказать, как это обновлять и мониторить.
- «Kubernetes сам всё перезапустит» без понимания, через сколько и при каких условиях.
