## 3. Контрольная без подсказок (90 минут)

Правила:
- без курса и поиска, только стенд и `kubectl explain`/`--help`;
- ответы письменно, по 3–6 предложений;
- проверка — по частям, указанным в скобках после контрольной.

### Часть 1. Теория (30 мин)

1. Опишите по шагам, что происходит от `kubectl apply` Deployment до первого успешного ответа пода через Service.
2. Чем readiness отличается от liveness? Приведите пример, когда неправильная liveness усугубляет инцидент.
3. Под на недоступном узле: что и через сколько секунд происходит с ним, его эндпоинтом и репликами? Чем отличается поведение для StatefulSet?
4. Почему `requests` важнее `limits` для планирования? Что произойдёт с HPA по CPU без requests?
5. Объясните `ndots:5` и предложите два способа уменьшить лишние DNS-запросы.
6. Что произойдёт с кластером, если validating webhook с `failurePolicy: Fail` недоступен? Как от этого защититься?

### Часть 2. Практика на стенде (45 мин)

Попросите напарника выполнить три любых поломки из 12-2 (по одной каждого уровня), не говоря какие. Для каждой запишите:
- симптом;
- команды диагностики;
- причину;
- исправление;
- как предотвратить.

Норматив — 🟢 5 мин, 🟡 10 мин, 🔴 15 мин.

### Часть 3. Мини-design (15 мин)

«Сервис из 4 реплик должен пережить потерю любого узла без ошибок у клиентов и проходить drain без простоя.» Перечислите все настройки в манифестах и в кластере и объясните каждую одной фразой.

<details><summary>Ориентиры для самопроверки</summary>

1. Аутентификация → авторизация → mutating → валидация → validating → etcd. Затем Deployment → ReplicaSet → Pod → scheduler → kubelet (CRI, CNI, образ) → пробы → EndpointSlice → kube-proxy/Gateway (01-1).
2. Readiness — трафик, liveness — рестарт. Liveness с проверкой БД — массовые рестарты при падении БД (02-5).
3. ~50 с → NotReady/Unknown, taints, под `Ready=False`, эндпоинт убран. 300 с → эвикция, контроллер создаёт замену. StatefulSet ждёт возврата узла или ручного решения (11-3).
4. Scheduler суммирует requests против allocatable; HPA CPU считает процент от requests — без них `<unknown>` (05-1, 05-3).
5. Поиск по search-доменам для имён с < 5 точками; FQDN с точкой, `ndots: 2`, NodeLocal DNSCache (03-3, 11-2).
6. Все попадающие под правило запросы отклоняются; исключения ns, ≥ 2 реплики, PDB, таймаут, мониторинг, `Ignore` для некритичных (09-2).
7. Мини-design:
   - readiness;
   - preStop + обработка SIGTERM + grace period;
   - `maxUnavailable: 0`;
   - PDB `minAvailable: 3` или `maxUnavailable: 1`;
   - topology spread по узлам (и зонам);
   - requests;
   - ёмкость кластера N+1 узел;
   - ≥ 2 реплики Gateway со spread;
   - при необходимости уменьшенный `tolerationSeconds` (02-5, 05-2, 10-3, 11-3).
</details>
